# 서 있는 차의 '요청받지 않은 움직임' 규칙 — 정지 교착 해소 (설계 1판, 2026-11-12)

텔레옵 다리(#459) 설계 2절에 적은 교착의 후속이다. 총괄 결정(2026-11-12): 카운트 정지가 확인된 주기에는 '요청받지 않은 움직임'을 없음으로 두고(경계 0) 요청 방향만 검사한다. 첫 비영 명령이 나간 뒤나 카운트가 움직이기 시작하면 정상 경계로 돌아간다. 외력 위험은 다음 주기 측정이 잡는다. 다리와 코어 4d-1 이 같은 규칙을 쓴다. S6 바닥 텔레옵 전에 끝낸다.

## 1. 문제 (측정값)

다리는 엔코더 속도의 가능 방향을 구간 `signed ± e` 로 정한다. 오차 폭 `e` 에는 가속 여유 `a_w·(Δt/2 + 나이)` 가 들어 있다. 그래서 서 있거나 느릴 때(`|signed| < e`, 지금 약 0.022–0.055 m/s)는 늘 두 방향이다. 코어 4d-1 규칙(`MissionCore._direction_limits`, 다리 `direction_limits` 와 같은 결과)은 요청과 다른 가능 방향을 경계 속도로 검사하고, 허가가 모자라면 정지(hold)한다.

라이브 장애물 층 허가(`config/obstacle_layer_single_a2_team_spec.yaml`)로 재면, 뒤 간격이 1 cm 격자에서 6.5 cm 이하, 5 cm 격자에서 8–17 cm 이하일 때 앞 출발까지 막힌다. 대부분은 허가의 고정 여유(정지 margin 5 cm, envelope 1 cm, 칸 크기)다. 경계 속도의 몫은 0.4–0.9 cm 다. 그래서 경계가 0 이 아니면 아무리 작아도(예: 양자화 폭 0.0005 m/s) 같은 거리에서 막힌다. **경계가 정확히 0 일 때만** 코어 규칙이 요청받지 않은 움직임을 비운다(`if speed.bound_mps > 0.0`).

## 2. 결정 문구 그대로의 결과 — 덜컥거림

'정지 확인 주기에만 경계 0, 첫 비영 명령 뒤 정상 경계' 를 그대로 하면 이렇게 된다.

1. 정지 확인 주기에 출발이 허락되고 첫 비영 명령이 나간다.
2. 다음 주기에 정상 경계로 돌아간다. 막 출발한 저속(`< e`)에서는 구간이 다시 0 을 걸쳐 뒤가 가능 방향이 된다. 뒤가 막혀 있으면 정지(hold)한다.
3. 정지 → 0.2 s 카운트 정지 확인 → 1 로 돌아간다.

벽에 붙어 선 차는 앞으로 한 주기씩 덜컥거릴 뿐 나가지 못한다. 교착이 형태만 바뀐다.

## 3. 제안 규칙 — 방향은 측정으로, 크기는 여유로

경계(`bound`, 크기)와 가능 방향(`directions`)을 다른 근거로 정한다.

- **크기**(`bound`)는 그대로 가속 여유를 포함한다. 과속 감시(경계 > 0.2 → STOP)와 구동 방향 검사의 속도는 바뀌지 않는다.
- **정지 기준점**: 카운트 정지(`counts_still`: 0.2 s 동안 바퀴마다 2 카운트 이하)가 확인되고, 그동안 MCU 가 아무것도 출력하지 않은(작용 중인 비영 명령 없음) 주기다. 그 주기의 `SafetySpeed` 는 **경계 0, 방향은 요청 방향**(요청이 없으면 `(1,)` — 경계 0 이라 어느 쪽으로도 검사하지 않는다)이다. 총괄 결정의 '경계 0' 과 같다.
- **그 뒤 한 방향으로만 명령해 온 동안**(기준점 이후 낸 비영 명령의 부호가 모두 `d`): 가능 방향 `d` 는 늘 넣는다. 반대 방향 `−d` 는 **측정 자체가 그쪽을 가리킬 때만** 넣는다 — `signed < −(양자화 폭)`(`d = +1` 일 때). 가속 여유로는 넣지 않는다. 근거는 다음과 같다.
  - 서 있다가 한 방향으로만 구동하는 동안, 구동이 반대 방향 가속을 만들지 않는다.
  - 반대 방향 움직임은 외력(경사·밀림)뿐이다. 외력은 카운트를 움직이므로 다음 표본(10 ms)의 `signed` 에 나타나고, 그 순간 반대 방향이 다시 가능 방향이 되어 검사된다(총괄 결정의 '다음 주기 측정이 잡는다').
  - 그 사이(표본 하나 + 나이 ≤ 50 ms) 외력으로 생길 수 있는 반대 방향 이동은 `½·a·t²` 다. 같은 가속 상한 A1(0.88 m/s²)을 외력에도 적용하면 1.1 mm 이하이고, 허가의 고정 여유(5 cm) 안이다.
- **방향을 바꾸면**(기준점 이후 두 부호의 명령이 나감), 카운트가 움직였으면(기준점이 끊김), 또는 속도가 무효면 지금 규칙(`signed ± e`)으로 돌아간다. 다시 쓰려면 새 정지 기준점이 필요하다.

결과적으로 벽에 붙어 선 차는 앞으로 나갈 수 있다. 뒤로 미끄러지기 시작하면(측정에 나타나면) 바로 뒤를 검사해 정지한다. 앞으로 가다 운용자가 후진을 명령하면 지금 규칙으로 돌아간다(그때는 앞쪽 잔류 운동을 경계 속도로 검사한다 — 4d-1 이 막으려던 경우).

## 4. 어디를 바꾸는가 — '다리와 코어가 같은 규칙'

규칙은 `SafetySpeed` 를 **만드는 쪽**(가능 방향의 정의)에 있다. 코어 4d-1 의 `_direction_limits` 는 받은 `directions`·`bound` 를 그대로 쓰므로 코드는 바뀌지 않는다.

- 새 공유 모듈 `src/forklift_core/safety/standing.py`: 정지 기준점·명령 부호 이력을 들고, 엔코더 판독(`encoder_speed`)에서 최종 `SafetySpeed` 를 만드는 `StandingDirections`. 다리는 지금 이것을 쓰고, 4e-2 의 실차 `hooks.safety_speed` 공급자도 같은 것을 쓴다. 그래서 두 쪽이 같은 규칙이다.
- `safety/truth_access.py` `SafetySpeed` 계약 문서에 '경계 0 = 측정으로 확인된 정지' 와 '방향은 측정, 크기는 여유' 를 적는다.
- 코어: 코드 무변경. 시험만 더한다 — 경계 0 의 `SafetySpeed` 에서 요청받지 않은 움직임이 비고, 요청 방향만 검사되는 것(이미 그렇게 동작함)을 코어 시험으로 고정한다.
- 재생 게이트: 코어·러너·장애물 층 코드가 바뀌지 않으므로 대상이 아니다(총괄 2026-11-12 면제 수용).
- **시뮬과 실차의 차이**(총괄 조건): 시뮬의 공급자는 `SafetySpeed.exact`(참값)다. 참값이라 서 있으면 경계가 정확히 0 이고, 방향은 속도의 부호 하나다. 그래서 시뮬은 이 교착을 처음부터 겪지 않았다. 반면 실차는 이 규칙(`standing.py`) 아래에서도 측정 불확실성이 남는다. 저속 구간의 가능 방향, 방향 전환 뒤 잔류 운동을 경계 속도로 검사하는 것, 정지 기준점까지 0.2 s 기다리는 것이 그 예다. '서 있다가 출발'과 '저속 방향 전환'에서 시뮬은 실차보다 허용적이다. 시뮬 공급자도 `standing.py` 를 거치게 옮기는 일은 4e-2(또는 그 전의 별도 PR)에서 재생 게이트 29/29 와 함께 한다(4e-2 필수 항목, `docs/design/2026-11-11-p04a-kinematics-and-command.md`). 그때까지 시뮬은 이 구간의 실차 동작을 예측하지 못한다.

## 5. 시험

- 공유 모듈 단위: 정지 기준점에서 경계 0·요청 방향, 기준점 이후 같은 부호 명령 동안 반대 방향은 측정이 가리킬 때만, 방향 전환·카운트 움직임·무효에서 지금 규칙으로, 경계(크기)는 바뀌지 않음(과속 감시 그대로).
- 다리 주기(가짜 MCU):
  - 뒤 허가 0 인 벽 앞 정지 → 앞 출발이 덜컥거리지 않고 이어진다(여러 주기 연속 비영).
  - **정지 확인 직후 밀림 반례**: 출발 직후 바퀴가 뒤로 밀리면(카운트 감소) 다음 표본에서 뒤가 가능 방향이 되고 정지한다.
  - 앞으로 가다 후진 명령 → 지금 규칙(앞쪽 잔류 운동 검사).
- 코어: 경계 0 의 `SafetySpeed` 에서 `_direction_limits` 가 요청 방향만 검사(hold 없음).
- 종단(MCU 모형): 벽 앞 출발 연속.
