# `slam_release_replan_failed: invalid_start` 진단 (2026-10-31)

지시: 총괄(2026-10-31). riib 출구 접두 면제 배치(`docs/validation/2026-10-31-riib-exit-prefix-default-batch.md`)의 C4 미달과 규칙 6 settle 실패가 같은 유형이고 면제 없는 A 팔에도 나온다. 그래서 면제와 따로 원인·재현·고칠 범위를 낸다. return_home 추종 실패는 원인이 다르면 따로 적는다.

방법: 경계 기록에서 해당 `Planner` 요청을 꺼내 같은 스냅숏의 플래너로 다시 부른다. 필요하면 시작 자세나 인자를 바꾼다.
- 도구: ws1 `test_runs/riibotics/tss_diag/replan_probe.py`, `prefix_delta.py`
- 결과: `tss_diag/inv/`
- 기록: `rx_6e6d8e1c/rx_B_aisle_rack_s1`(스냅숏 `rx_6e6d8e1c`)

riib 장면 모드(P6, 격자 재계획 아님)에서는 해제 재계획이 `invalid_start` 일 때 여유 0 재시도(`grid_planning` 전용)가 없다. 그래서 바로 실패한다(`MissionCore.slam_release`).

## 1. settle — 하역 뒤 복귀 해제 재계획

- 사례:
  - `rx_B_aisle_rack_s1`(214.09 s, 해제 점프 0.0225 m)
  - 이전 배치 `epc6_A_aisle_rack_s3`(210.01 s, 0.0111 m)
  - 2026-10-27 의 return_home `invalid_start` 4 건도 같은 계열이다(`docs/plans/2026-10-27-return-start-withdraw-extension.md`).
- 원인: 복귀 출발점(하역 뒤 물러난 끝)이 계획 여유 안에 있다. 그래서 `plan_return_leg` 가 시작 검사에서 바로 거부한다(계획 시간 0 s).
- 재현: 기록된 `plan_return_leg` 요청을 그대로 부르면 `invalid_start` 가 0 s 만에 난다.
- 요청의 목적지는 이미 해제 뒤 프레임으로 옮겨져 있었고, `@slot` 소품은 없다. 실제 호출의 `moved_slot_props` 38 개가 기본 slot 목록과 같다(Codex 확인).
- F2′ 복귀 출발 물러남(`--return-start-backoff on`, PR #176, 상한 `RETURN_START_BACKOFF_CAP_M` 0.30 m)은 이미 머지돼 있지만 riib 런처에서는 꺼져 있다. 같은 요청에 이것을 켜면 0.08 m 물러난 뒤 계획이 성공한다(2.7 s). 상한을 0.15·0.30·0.50 m 로 바꿔도 같다.
- 고칠 범위: 코드 변경은 없다. riib 런처에서 F2′ 를 켜는 것을 다음 배치 후보로 등록한다(켬 이유·상한·회귀 조건, 출구 접두 면제와 따로 판정). 런처 기본값 변경이므로 총괄 결정 범위다.

## 2. 운반 전환 — 꺼내기 → 운반 해제 재계획

- 사례: `rxi_box15_aisle_rack_s1`(81.93 s, 해제 점프 0.0373 m·0.0175 rad, 해제 뒤 자세 (2.2297, −4.0296, 0.0387)). 경계 기록이 없어, 같은 장면·seed 의 `rx_B_aisle_rack_s1` 운반 해제 재계획 요청에 이 자세를 넣어 재현했다. 그 요청의 키워드 인자는 `geometry`·`travel_config` 뿐이라 점유 격자 입력이 없다. 같은 장면·seed 면 시나리오도 같다.
- 재현 충실성(Codex 확인): 복호화한 `scenario` 전체가 box15 s1 의 입력과 같다. geometry·config·소스 해시도 같고, `travel_config=None`, 점유·deadline 입력은 없다. 운반 해제는 원 scenario 를 쓰고, 접두 벽도 그 scenario 의 LiDAR 가시 소품에서 계산한다.
- 재현:
  - 원래 요청(B s1 자세 (2.2314, −4.0328, 0.0356))은 성공했다. 출구 접두는 0.35 m, 최소 여유 0.398 m 였다.
  - box15 s1 자세로는 `invalid_start` 가 났다. 출구 접두 기록은 `unmet:search_no_path`, 길이 0 이다.
- 무엇이 실패했는가(`pallet_mission._transport_search`):
  - 출구 접두 0.35 m 는 찾았고, 곧은 후진도 통과했다.
  - 접두 끝에서 시작한 탐색이 `no_path` 였다.
  - 그러자 칸 안의 원래 시작점에서 일반 탐색으로 넘어갔고, 그 시작점은 여유 안이라 `invalid_start` 가 났다.
  - 최종 상태와 실패 문구(`slam_release_replan_failed: invalid_start`)는 마지막 시도의 것만 남는다. 그래서 진짜 실패(접두 끝 탐색 실패)가 가려진다.
- 민감도:
  - 해제 뒤 자세 둘레 35 칸(y −4.040…−4.020 m 를 0.005 간격, 방위 0.020…0.050 rad 를 0.005 간격, x 2.2305)은 모두 성공했다(잡 13009).
  - x 를 고정한 y·방위 평면에서 실패 자세 ±1 mm·±0.001 rad 의 주변 8 표본도 모두 성공했다. 중심점만 실패했다(잡 13044). 3 차원 자세 공간에서 고립된 단일점이라는 증명은 아니다.
  - 이 탐색에는 시간 상한(deadline)이 없어 결정적이다.
  - 접두 0.35 m 끝에서의 탐색 사다리(Codex 재실행):
    - 0.2 m·10° 격자, primitive 0.25 m, 연결 간격 8·4·2·1: 각각 `no_path`(확장 353).
    - 0.1 m·5° 격자, primitive 0.25 m: `expansion_limit`(30 000). 확장 예산을 120 000 으로 늘려도 `expansion_limit` 다.
    - 0.1 m·5° 격자, primitive 0.10 m: `no_path`(5 359).
    - 사다리는 마지막 시도의 결과를 돌려주므로, 최종 `no_path` 만 보고 앞선 미완료 탐색을 배제할 수는 없다.
  - 결론: 여유 부족이 아니다. 접두 끝 자세에서 탐색 이산화·연결 시도·확장 예산에 민감하게 갈린 탐색 실패다. 접두 끝과 목표의 시작 검사는 모두 통과했다.
- 접두를 한 단계 늘린 시험(잡 13056, `exit_prefix_length_m` 에 더함):
  - +0.05 m(접두 0.40 m, 최소 여유 0.445 m): 성공, 42.9 s.
  - +0.10 m(0.45 m): 성공, 72.7 s.
  - +0: `invalid_start`.
- 고칠 범위(코드, 플래너만):
  - (a) 시도별 사유 기록: `_transport_search` 가 접두 끝 탐색의 상태와 일반 탐색 대체를 모두 남긴다. 해제 재계획의 실패 문구도 마지막 시도만이 아니라 시도별 사유를 싣는다(총괄 2026-10-31 지시).
  - (b) 견고화 후보: 접두가 있고 접두 끝 탐색이 `no_path`·`expansion_limit` 로 실패하면, 접두를 `step_m` 씩 늘려 `cap_m` 안에서 몇 번(예: 2 번) 더 접두 끝 탐색을 한 뒤 일반 탐색으로 넘어간다.
    - 늘린 접두도 곧은 후진 검사·여유 검사·끝점 검사를 같은 규칙으로 받는다.
    - 기존 deadline 과 시도별 기록을 지킨다.
  - (b) 는 플래너만 고쳐서는 안 된다. core 의 `exit_prefix_m()` 은 명시적 `hooks.exit_prefix` 가 있을 때 채택된 경로의 기록이 아니라 최소 접두 길이를 다시 계산한다(`src/forklift_core/mission/core.py` 1153 행 부근). 그러면 늘어난 후진 구간을 하역 직선 예외로 분류해 장애물 허가가 꺼질 수 있다.
    - Codex CPU 반례: 최소 0.40 m, 채택 0.45 m, 진행 0.425 m 에서 `permission_acting()` 이 (False, True) 였다. 채택 기록을 읽으면 (True, False) 다.
    - 명시적 접두와 자동 keepout 접두 모두 실제 채택 길이를 읽게 고쳐야 한다. 자동 경로에서는 그 길이가 출구 접두 면제 구간 길이에도 들어간다.
  - 원인 분리 대조(고치기 전): 원래 접두 끝에서 고운 격자의 확장 예산이나 연결 간격만 바꿔 본다. 탐색 쪽 원인이 그것이면 접두 연장 대신 사다리를 고치는 쪽이 맞을 수 있다.
  - (b) 는 출구 접두가 있는 모든 운반 계획(riib aisle·trailer)의 결과를 바꾼다. 그래서 등록·CPU 반례(이 자세)·Isaac 확인이 필요하다. 플래너는 재생에서 기록된 응답으로 대체되므로 runs29 게이트에는 닿지 않는다. core 의 `exit_prefix_m()` 변경은 재생 게이트를 탄다.
