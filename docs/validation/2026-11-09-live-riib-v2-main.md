P-2 의 고정 관측 지점 여섯 곳은 P-2 축 위, 중심 뒤 2.6–3.8 m(x −1.952…−0.752)의 넷과 x −1.352, y ±0.4 의 둘이다. 여섯 곳 모두 같은 줄에서 P-1 뒤에 있다. 관측 지점은 그 팔레트만 보고 만든다(`tools/riibotics_isaac_scenes.py` `observation_waypoints`, 다른 팔레트는 고려하지 않음).
- **(a) m2 의 시작과 관측**: m1 은 `approach` 에서 취소돼 `clear_out` 회복을 거쳐 `cancelled` 로 끝났고, P-1 은 제자리에 남았다(`session_rest_largest` P-1 1.45×10⁻⁷ m, 9.95×10⁻⁵ rad). m2(P-2)는 관측 시도 다섯 번(관측 지점 계획 상태 success;success;success;invalid_goal;success;success)에서 판단이 `unresolved_in_radius`·`uncertain_in_radius`·`no_candidate_in_radius` 사이를 오갔고, 한 번도 선택되지 않았다. 검출 오차가 기록된 시도 셋의 앞뒤 오차는 0.98·0.98·0.84 m(거리 2.116·2.483·1.889 m)이다. P-1–P-2 간격이 0.972 m 이므로 검출된 것은 P-1 의 앞면이고, 그 위치는 P-2 의 인식 영역(중심 (1.848, 0), 반경 0.354 m) 밖이다. 영역 판정은 그것을 P-2 로 받지 않았다. m2 관측 중 P-1 과의 최소 간격은 0.398 m(t 41 s)였다. 이것은 P-1 이 검출됐다는 근거이지, 모든 관측 지점에서 P-2 가 물리적으로 안 보였다는 증명은 아니다.
- **(b) 상태 계승**: 인식 상태는 임무마다 초기화된다(`far_recognition_runtime.start_mission` → `reset_for_mission`, 늦게 끝난 작업은 그것이 들어온 임무에 귀속). m2 의 시도는 leg 0, 빈 `selection_history` 로 시작했다. 세션 장애물 메모리는 설계상 유지된다(P-1 은 목록의 바닥 팔레트). 상태 누수의 징후는 없다.
- **(c) 다른 세션의 m2**: 다른 line_m 세션 10 개(A/B 8, boxed 1, C2 on 1)의 m2 는 모두 P-1 을 D-1 에 옮긴 뒤 시작했고, 한 번의 시도로 `done`, 검출 앞뒤 오차 0.00 이었다. 시작 위치(`mission_scenario.start_rear.x_m`)는 그쪽이 −2.960…−2.945, 생명주기 4 가 −1.162 다. 장면 상태(P-1 이 남았는지)도 다르므로 시작 위치만으로 설명하는 비교가 아니다.
- **분류: (ii), 총괄의 범위 결정에 근거.** 기록이 보여 주는 것은 '상태 누수 징후 없음, 남은 P-1 과 P-2 의 고정 관측 지점이 만든 인식 능력 한계와 일치'까지다. 기존 계약에서 이 상황을 지원 범위 밖으로 둔 근거는 없다(`session_plan_check` 의 순서대로 처리한 상태는 CPU 계획 포락선 검사의 범위일 뿐, 라이브 제출 계약이 아니다). 총괄의 범위 결정: '남아 있는 바닥 팔레트에 가린 대상을 집는 상황'은 이번 ④⑤ 판정의 지원 범위 밖으로 두고, 알려진 한계로 받아들인다. 코드 수정이 필요한지는 열어 둔다(백로그).
- **알려진 한계(백로그, 이번 ④⑤ 판정 경로에서는 고치지 않음)**: 관측 지점 생성이 다른 바닥 팔레트에 가리는 경우를 고려하지 않는다. `targets.check_submit` 는 목록 개정·상태·목적지 점유만 보고, 남은 바닥 팔레트 뒤에 가린 대상을 거부하지 않는다. 그 결과 그런 제출은 수락되고, 관측 후보를 다 쓴 뒤 이유를 남기고 실패한다(접촉 없음, 세션은 계속).
- **시나리오를 고친 이유**: line_m 에서 P-1 이 남으면 다른 대상(P-2·P-3)이 모두 같은 줄의 P-1 뒤에 있다. 그래서 그 장면에서는 '취소 뒤 다른 대상으로 넘어가는' 생명주기를 시험할 수 없다. P-1 을 다시 제출하는 시험은 대상 변경(다른 인식 영역, 다른 팔레트로의 상태 전환)을 빼먹는다. 고친 생명주기 4 는 random_m 에서 `cycle P-4:D-1,P-5:D-2 --stop-wait-at approach:5 --stop-wait-sim-s 5 --manual-recovery --end-session` 이다. P-4 참값은 (0.688, 1.198), P-5 는 (0.954, −1.462)다. P-5 의 관측 지점 여섯 곳은 y −1.575…−0.780 에서 P-5 를 바라보므로 시선은 모두 y ≤ −0.78 에 있다. 남은 P-4 는 EPAL 6 외곽(0.6 × 0.8 m, yaw 10°)의 가장 낮은 모서리가 y 0.752 라서 어느 시선에도 걸리지 않는다. random_m 은 이미 생명주기 2·3 의 장면이다. 연쇄는 등록과 같다: m1(P-4) `approach` 도달 → STOP ack → STOPPED → 재무장 ack → 취소 ack → m1 `cancelled`(필요하면 수동 회복) → m2(P-5) 수락·`done` → `session_end` ack → 종료 코드 0. 제출 전에 ws1(r1c 뒤)에서 CPU 계획 확인을 한다: P-4 를 참값 자리에 남긴 상태에서 P-5 의 관측·운반 계획이 있는지. `start_rear` 는 둘로 나눠 따로 적는다. 하나는 세션 시작점 (−2.093, 0, 0), 다른 하나는 본배치 random_m A/B 세션 m1 의 `approach` 진입 시 참값 뒷차축 자세다(취소·회복 뒤 시작점의 대리값). 실패하면 Isaac 실행 전에 등록을 다시 본다. CPU 결과는 계획이 있다는 근거일 뿐이고, 실제 관측·완료 여부는 확인 실행으로 판단한다. 확인 실행 등록은 별도 문서로 한다.
