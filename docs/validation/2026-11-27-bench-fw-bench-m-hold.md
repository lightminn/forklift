## 이미지 — 범용 벤치 이미지(진단 브랜치 `diag/fw-bench`, main 에 없음 — origin 에 브랜치와 태그로 보존)

시험마다 진단 이미지를 따로 만들던 방식을 버리고, 하나의 벤치 이미지를 만들었다(사용자 지시, 총괄 전달). 멈추는 쪽은 우회하지 않고, 나머지 차단 검사는 도구 인자로 실행 한 번만 끈다.

| 태그 | 제품 문자열 끝 | 내용 | 벤치 |
|---|---|---|---|
| `diag-fw-bench-1` (86394435) | `lim=lr1 bench2` | 아래 BENCH_SET 과 이동량 카운터 | 구움·M 3바퀴 |
| `diag-fw-bench-2` | `lim=lr1 bench3` | + BENCH_HOLD(M 위치 유지, PI, 최소 듀티 옵션) | 구움·hold 시험. **지금 보드에 남아 있음** |
| `diag-fw-bench-3` | `lim=lr1 bench4` | + hold 감쇠 항 `--hold-kd` | **빌드만 하고 굽지 않음(미시험)** |

- **BENCH_SET(0x06):** DISARMED 에서만 받는다. 부팅 때는 아무것도 꺼져 있지 않다.
  - 우회 비트는 두 개다: `steer_range`·`lift_range`. KTH 프레임이 무효면 여전히 멈춘다.
  - 축별 듀티·연속 시간 상한을 펌웨어 검증 한계(1.0, 약 2,147 s)까지 줄 수 있다.
  - 기본값과 다른 설정이 걸려 있으면 STATE 고장 비트 31 `BENCH_OVERRIDES` 로 보인다.
  - 도구는 벤치 이미지에서 실행할 때마다 ARM 전에 BENCH_SET 을 보낸다. 받았는지는 일련번호와 비트로 확인한다.
  - 과전류·드라이버 결함·STOP·DISARM·명령 만료·IWDG·사이클 초과에는 우회 비트가 없다.
- **KTH 이동량 카운터:** 펌웨어가 조향 KTH 를 1 kHz 로 이어 붙여 누적하고, STATE `kth_alt_crc_errors` 칸(32비트)으로 보낸다. 셀 수 없으면 고장 비트 30 `BENCH_KTH_LOST` 로 M 을 세운다. 이 비트는 손실 뒤 정상 걸음을 다시 센 다음 ARM 이 받아들여질 때 지워진다(다시 세기 전의 ARM 으로는 안 지워짐). 셀 수 없는 경우는 다음 셋이다.
  - 셀 수 있는 프레임이 3 ms 넘게 없음
  - ms 당 512 카운트(1/8 바퀴)를 넘는 걸음
  - 0x0000 프레임만 계속 옴. 단 diag-fw-bench-2/3 은 직전에 센 각이 원시 0 에서 ±512 안이면 0x0000 도 센다([아래](#남은-위험--원시-0-근처에서-miso-가-low-로-붙는-경우))
- **도구 인자:** `--bench-bypass`, `--bench-duty-max`, `--bench-time-max`, `--stop-kth-turns`, `--hold-target here|zero|±카운트`, `--hold-kp/-ki/-kd/-deadband/-sign/-min-duty`.
- **검증:** 호스트 시험과 Codex 를 거쳤다.
  - 이동량 카운터까지는 Codex 8회차에서 "새 P1/P2 없음"이었다.
  - hold 부분은 사용자 지시(속도 우선)로 Codex 1회만 받았다. 기능을 깨는 지적 하나만 반영하고 안전 관련 지적은 넣지 않았다. 남은 위험은 [아래](#남은-위험--원시-0-근처에서-miso-가-low-로-붙는-경우)에 있다.

## 드라이버 R/M/H 초기화 실패와 회복

diag-fw-bench-1 을 처음 구운 뒤 `driver_status` 가 L 0xC0, R·M·H 0x00 이었고 모드는 BOOT 에 머물렀다. 펌웨어는 L→R→M→H 순서로 초기화하고 앞 채널이 실패하면 L 부터 다시 하므로, 0x00 이 확실한 것은 R 뿐이다. M·H 는 조회되지 않아 0 인 것일 수 있다. 원인이 이미지인지 하드웨어인지 가렸다.

| 기록 | 리셋 | 부팅 | L/R/M/H | 모드 |
|---|---|---|---|---|
| 11-26 23:38 diag-kthraw-2 | SOFTWARE | b6002148 | C0 ×4 | DISARMED |
| 00:0x–01:06 diag-kthraw-2 네 기록(사본 있음, 마지막 `kthraw_motor_1127_010637`) | POWER | **4be9b37a 하나**(가동 65→4,017 s) | C0 ×4 | DISARMED |
| `fwbench_first_1127_022423` diag-fw-bench-1 | SOFTWARE | 9b9e8207 | C0/00/00/00 | BOOT |
| `fwbench_m10_1127_022820` · `fwbench_recheck_0101_090057`(POWER) | — | — | C0/00/00/00 | BOOT |
| `ab_kthraw_soft_1127_031149` diag-kthraw-2 로 되돌림 | SOFTWARE | eeff9ec2 | C0/00/00/00 | BOOT |
| `nomotor_kthraw_0101_090045` 모터 등 모두 뺌 | POWER | 83f029b7 | C0 ×4 | DISARMED |
| `rj1_kthraw_0101_090050` → `cn3_kthraw_0101_090041` → `cn5_kthraw_0101_090049` 하나씩 연결 | POWER | 매번 새 부팅 | C0 ×4 | DISARMED |

- **이미지 원인일 가능성은 낮다(추정):** diag-kthraw-2 로 되돌려도 같았고, 진단 브랜치 기준점과 main 사이에 드라이버 초기화·SPI 코드 변경도 없다.
- **문제가 생긴 시점:**
  - 사본이 있는 네 기록은 한 번 초기화된 같은 부팅이다. 펌웨어는 준비 뒤에도 채널마다 FAULT_SUMMARY 를 계속 읽고, 무효 응답이면 FAULT 로 간다. 그러니 R/M/H 는 적어도 마지막 사본(가동 4,017 s) 때까지 SPI 에 정상 응답하고 있었다. 같은 부팅의 01:21 기록(가동 약 4,879 s)은 Jetson 에만 있고 사본이 없다.
  - STDS U8 교체·CN5 모터 연결·종단 제거는 모두 이 부팅 **안에서** 했다. 그 하드웨어 상태로 드라이버를 다시 **초기화**한 것은 02:24 가 처음이었고, 기록된 첫 실패도 이때다.
- **회복:** 모터 등을 모두 빼고 전원을 다시 켜니 넷 다 정상이었다. RJ1·CN3·CN5 를 하나씩 붙이며 매번 전원을 다시 켜도 정상이었다.
  - **(사용자)** 핀헤더를 다시 납땜한 뒤 회복됐다. 접촉 불량으로 본다.

## 남은 위험 — 원시 0 근처에서 MISO 가 low 로 붙는 경우

`zero` 목표에서 원시 0 에 멈추면 0x0000 프레임을 세지 않아 '잃음'으로 M 이 서던 문제가 있었다. 그래서 diag-fw-bench-2/3 은 **직전에 센 각이 0 근처(±512 카운트)이면 0x0000 도 센다**.

그 결과 이런 위험이 남았다(Codex hold 검토 지적, 사용자 지시로 고치지 않음).
- 축이 0 근처에 있을 때 MISO 가 low 로 붙으면, 실제 축은 그대로인데 카운터는 가짜 이동(예: −256 카운트)을 읽는다.
- 이때 hold 가 듀티 상한까지 밀 수 있고, 3 ms 손실 정지도 걸리지 않는다.
- main 에 반영할 때 고칠 항목이다.
