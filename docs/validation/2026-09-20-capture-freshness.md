# 캡처 신선도 계약: 렌더 지연 대응

## ws1 실측과 기존 계약의 결함

2026-09-20 사용자가 제공한 Isaac 5.1 ws1 실측에서 seed 0은 첫 캡처의 첫 시도에
`perception_capture_failed:acquisition_outside_capture`로 종료했다. 진단은
`sensor_frame_id=0`, `acquisition_time_s=0.0`, 물리 시각 전후
`26.925001 / 26.933335 s`, 거절 1회였다. 진단 저장 경로는 동작했다.

별도 프로브에서 `rendering_frame`·`rendering_time`은 스텝 0~2에서 0이고
스텝 3부터 채워졌다. `World(physics_dt=1/120, rendering_dt=1/60)`에서
`world.step(render=True)`는 물리 시각을 1/60 s 진행시켰다. 스텝 6 이후
획득 시각은 물리 사후 시각보다 0.066667 s, 즉 4 렌더 프레임 뒤처졌다.

| 스텝 | 물리 전 (s) | 물리 후 (s) | 획득 (s) | 한 스텝 구간 안 |
|---|---:|---:|---:|---|
| 6 | 0.116667 | 0.133333 | 0.066667 | 아니오 |
| 23 | 0.400000 | 0.416667 | 0.350000 | 아니오 |

프로브 전체에서 `물리 전 ≤ 획득 ≤ 물리 후`는 **0/24**였다. 따라서 기존 한 스텝
구간 계약은 이 파이프라인에서 재시도로도 충족할 수 없다. 영상 저장이 꺼진 주행에서는
렌더하지 않으므로 캡처 때 한 번만 렌더하면 이전 관측 지점의 큐가 남는다.
사용자가 관측한 첫 캡처의 여러 준비 재시도와 이후 한 지점씩 밀리는 현상에 부합한다.
이 수치들은 사용자 제공 실측이며 이번 로컬 작업에서 Isaac을 재실행한 결과가 아니다.

후속 ws1 seed 0 비교에서 주행 중 렌더를 끄면 인식 오차가 **966 mm**, `--video`로
렌더하면 **5.15 mm**였다. 966 mm 검출을 직전 후보 자세로 변환하면 **3.34 mm**로
줄었다. `run_transport.py`의 주행 루프는 `--video`일 때만 렌더하므로, 렌더 없는
주행 뒤 카메라에는 직전 관측 지점 프레임이 남는다. 첫 수정의 하한
`capture_start ≤ acquisition_time`은 **69.025004 s로 두 시각이 같은 낡은 프레임**을
첫 시도에 거절 없이 승인했다. 반면 `--video`에서는 1회 거절 후 2번째 스텝에
승인했다. 이는 거절·재시도 기제는 작동하지만 시작 시각 하한만으로는 부족하다는
사용자 제공 실측이다.

## 수정한 계약

- `SensorCapture`를 관측 지점 간 유지하고 마지막 승인 센서 ID를 보존한다.
  ID는 `get_current_frame()`의 `rendering_frame`, 획득 시각은 `rendering_time`이다.
  물리 시각으로 센서 ID를 대체하지 않는다.
- 첫 렌더 스텝 직전 물리 시각을 `capture_start_time_s`로 한 번 고정한다.
  **캡처 시작 + L ≤ 획득 시각 ≤ 현재 물리 사후 시각**인 프레임을 요구한다.
  `SensorCapture(..., render_latency_s=0.066667)`의 키워드 파라미터가 L이다.
  기본값은 위 ws1 실측 4 렌더 프레임 지연에서 왔으며, `rendering_dt`나
  파이프라인 깊이가 바뀌면 재측정하여 조정한다. 음수·NaN·무한대는 거부한다.
  픽셀이 참조 시각보다 L 뒤처질 수 있다는 보수적 여유를 적용한다.
  단순히 시작 시각의 등호만 제거하지 않는다. 상한은 재시도마다 갱신되지만,
  **현재 물리 시각보다 미래인 잘못된 센서 시각**을 막으므로 유지한다.
- 지연 여유 하한 미달 또는 상한 초과(`acquisition_outside_capture`)와 워밍업의 ID 0 또는 시각 0
  (`sensor_frame_not_ready`)은 거절 횟수를 기록하고 다음 스텝으로 재시도한다.
  fabric-time 딕셔너리의 분자 0도 아직 준비되지 않은 ID다. 고정 워밍업 스텝 수는 없다.
  `max_attempts` 소진 시 마지막 사유와 진단을 붙여 실패한다.
- 직전 승인 ID의 재사용은 계속 거절·재시도한다. 실패한 호출은 마지막 승인 상태를
  덮어쓰지 않는다. RGB/depth 직접 getter 전후 메타데이터도 같아야 한다.
  누락·잘못된 메타데이터와 읽기 중 ID 변경은 즉시 실패한다.
- 캡처 시작 자세(`pose_before`)를 고정하고 **모든 렌더 스텝 후 자세**를 비교한다.
  위치 1 mm 또는 회전 0.001 rad 초과는 워밍업 중이라도 즉시 실패한다.
  따라서 여러 스텝에 걸친 누적 이동도 제한한다.
- 승인 프레임의 world 변환에는 승인 스텝 후의 `accepted_pose`를 사용한다.
  진단 `pose_reference="stationary_capture_end"`는 이 자세가 **정지 가정하의 대표 자세**임을
  나타낸다. 실제 지연된 획득 순간의 자세를 보간하거나 복원한 값은 아니다.
  단일 스레드에서 스텝을 진행하며 픽셀 읽기 중에는 물리 스텝을 진행하지 않는다.
  스텝 사이 왕복 운동이나 실제 획득 순간의 정확한 자세는 증명하지 않는다.

`CaptureDiagnostics`에는 센서 ID·획득 시각, 고정 시작 시각·자세, 마지막 스텝 직전/직후
물리 시각(`physics_time_before_s` / `physics_time_after_s`), 마지막 스텝 후 자세
(`pose_after`), 시도·거절 횟수를 기록한다. `render_steps`는 실제 호출한 렌더 스텝 수이고
승인 시에는 승인까지 밟은 수다. `acquisition_since_capture_start_s`는 **획득 − 캡처 시작**이다.
사후 물리 시각 − 획득 시각으로 파이프라인 지연도 계산할 수 있다.
실패 시 진단은 마지막으로 수집한 값이며 `accepted_pose`는 비어 있다.
원시 깊이 통계 `FrameDiagnostics`는 그대로 유지한다.

일반 `capture_scene_input`도 `CaptureState` 전달 시 호출 간 재사용을 검사한다.
ID가 없는 일반 경로는 RGB와 depth가 모두 바뀌어야 승인하는 보수적 배열 비교를 유지한다.
엄격한 Isaac 경로는 메타데이터 누락 시 이 비교로 자동 강등하지 않는다.

## CPU 검증과 남은 확인

첫 수정 당시 기존 시험의 기대값은 수정하지 않았다. 지연 큐를 가진 가짜 카메라 시험을 추가하여
2·4·7프레임 지연, 0 워밍업 재시도, 렌더 없는 이동 뒤 이전 지점 큐 배출,
시도 예산 소진, 직전 승인 ID 재사용, 누적 자세 변화와 진단을 검사한다.
구현 전 추가 시험에서 **7 failed, 69 passed**, 구현 후 어댑터 **76 passed**를 확인했다.

Isaac 실행은 요청대로 수행하지 않았다. ws1에서 수정 후 seed 0과 다음 관측 지점의
캡처 결과, 저장 영상의 위치 대응, 진단의 스텝 수·시각 차이를 확인해야 한다.
CPU 시험은 annotator와 센서 메타데이터의 실제 대응이나 렌더 신선도 실측을 대신하지 않는다.

첫 수정의 전체 검증은 conda base의 이 저장소 editable 설치에서 실행했다:

```text
python -m pytest tests --ignore=tests/simulation -q -p no:cacheprovider -W error
925 passed in 118.62s (0:01:58)
```

이 결과는 첫 수정 당시 기존 미커밋 변경도 포함된 작업 트리 기준이다. 당시 작업 밖의
변경은 수정하지 않았다. 수정한 Python 세 파일의 Ruff lint·format check와
`git diff --check`가 통과했다. 기존 어댑터 시험 함수·클래스 40개의 AST가
HEAD와 동일함을 확인했다. 커밋하지 않았다.

### 후속 수정: 실측 지연 여유 하한

구현 전 가짜 카메라에 60 Hz, 물리 대비 4프레임 지연을 재현했다. 캡처 시작과
획득 시각이 같은 4번째 스텝을 승인하는 결함을 `DID NOT RAISE CaptureFailure`로
확인했다. 추가 시험 포함 **8 failed, 77 passed**였다(기존 동작 반례 4건,
신규 파라미터 미구현 4건). 구현 후 어댑터는 **85 passed**다.

- 시작 시각과 같은 획득 및 지연 여유 안쪽 획득을 거절하고 예산 소진 시 실패한다.
- 기본 L=0.066667 s는 정확한 4/60 s보다 약 0.33 μs 크므로 이 가짜 카메라는
  8스텝까지 거절하고 9스텝에 승인한다. 승인 시 획득 − 시작은 5/60 s다.
  경계를 느슨하게 만드는 부동소수점 허용 오차는 추가하지 않았다.
- 별도의 이진수로 정확히 표현되는 시각 시험에서 사용자 지정 L과 하한 등호를 검증했다.
- 호출 간 직전 승인 ID는 시간 조건을 충족해도 계속 거절되며 실패 시 승인 상태를 보존한다.
- 여러 스텝 후에도 미래 획득 시각은 거절한다. 기존 자세 한계와 진단 필드는 유지했다.

기존 시험 함수 39개의 AST와 기대값은 작업 시작 시점과 동일하다. 기존
`DelayedSensorCamera`는 픽셀 획득 시각 자체를 큐에 저장하는 모델이므로, 그 헬퍼에만
`render_latency_s=0`을 명시했다. 이 시험의 `delay + 1` 기대값을 변경하지 않았고,
새 `MeasuredLagCamera` 시험은 기본 지연 여유를 적용한다. 이 구분은 가짜 카메라
계약이며 실제 Isaac의 픽셀·메타데이터 대응을 입증하지 않는다.

후속 전체 시험 결과(동일한 위 명령, 기준선 925개 + 신규 9개):

```text
934 passed in 110.29s (0:01:50)
```

수정한 Python 두 파일의 Ruff lint·format check와 `git diff --check`도 통과했다.
이번 수정 대상 세 파일 외의 기존 미커밋 파일은 작업 시작 시점과 SHA-256이 동일하다.
커밋하지 않았다. Isaac은 실행하지 않았으며 실제 효과는 ws1에서
렌더 없는 주행 후 seed 0과 다음 지점의 오차·승인 시각·스텝 수로 확인해야 한다.
