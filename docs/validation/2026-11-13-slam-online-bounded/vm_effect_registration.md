# VM 켬이 CPU SLAM 재생 비용에 주는 영향 — 등록 (결과 전 고정, 2026-11-13)

총괄 결정(사용자 승인 범위 안): 사용자가 오늘 밤 ws1 의 VM(`ws1-win-gpu1`, GPU1 을 vfio 로 가져감)을 계속 쓴다. 그래서 VM 이 켜진 채 같은 CPU 재생을 돌려, 지금 규칙(VM 이 켜진 창 = 미평가)을 CPU SLAM 재생에 계속 적용할지 정한다. 이 문서는 실행 전에 커밋한다.

## 실행

- 스냅숏 `s3e_4c4d08d9`, P1 `forklift/ros2-slam:jazzy-2.8.5-p1-a511d6e5`, `s3_equiv_submit.sh` 의 같은 입력·인자(S2 입력을 sim 1,500 s 에서 자름, 빠른 재생, 그래프 덤프, CPU 2, 직렬).
- 팔·순서: `r0_1` → `p0_1` → `r0_2` → `p0_2`(VM 켬). 결과 폴더 ws1 `test_runs/live/slam_online/s3vm_4c4d08d9/`.
- 제출 전 확인: squeue 0, 다른 사용자 잡 없음. VM 은 켜져 있는 것이 조건이다.
- VM 상태는 노트북 표본기(`vm_watch`, 30 s, `systemd-inhibit`)로 기록한다. 각 창이 VM 켬이었는지(qemu 실행 중)를 적는다. 창 안에 VM 이 꺼진 표본이 있으면 그 실행은 비교에서 빼고 적는다.

## 비교 대상 (VM 끔)

- 18842–18848(스냅숏·이미지·입력 같음, 19:45:00–19:53:59, VM 표본 clear)의 같은 팔: `r0_1`·`r0_2`(R0), `p0_1`·`p0_2`(P0).

## 지표

- 실행마다 `drive.jsonl` 의 keyframe 처리 시간(`slam_wall_s`, 처리된 keyframe 전부) 평균, p99(numpy `percentile`, 선형 보간), 최대.
- 팔의 값 = 두 반복 값의 산술 평균.

## 판정 (팔마다: R0, P0)

1. **평균:** (VM 켬 팔 평균 − VM 끔 팔 평균) / VM 끔 팔 평균 ≤ 5 %.
2. **p99:** VM 켬 팔 p99 − VM 끔 팔 p99 ≤ 2 × |VM 끔 두 반복의 p99 차이|.
3. **결과값:** VM 켬 각 실행의 응답이 같은 팔의 VM 끔 실행과 `tools/slam_equivalence.py` 로 동등(응답 자세 1e-6, scan 순서, 그래프 노드·edge 수, 매개변수, 각 실행의 검사·종료 코드). 결과값은 VM 과 무관해야 한다.
- 최대는 기록만 한다.
- **두 팔 모두 1·2·3 을 채우면 "CPU SLAM 재생은 VM 켬 허용"**, 하나라도 못 채우면 지금 규칙(VM 켜짐 = 미평가)을 유지한다. 결정은 총괄이 한다.
- 이 결론은 CPU SLAM 재생에만 적용한다. Isaac 실시간 측정에는 적용하지 않는다.
- 알려진 한계: 재생은 결정적이어서 VM 끔 두 반복의 p99 차이가 아주 작을 수 있고, 그러면 2 의 허용 폭도 작아진다. 등록한 대로 적용한다.
