## 2. `range_min_m = 0.8` 의 앞 구간은 near clip 때문에 관측 불가다

2차 실행에서 교정판 캡처가 **RGB 완전 검정·depth 전부 비유한**으로 나왔다. 원인은 **USD 카메라의
기본 near clip 1 m** 와 첫 교정판의 optical Z **0.72336 m** 의 충돌이다. 배경을 숨긴 상태에서 판까지
잘리면 프레임이 통째로 빈다.

**이것은 시험 장치만의 문제가 아니다.** 검출기의 워크스페이스 필터는 **카메라 기준 수평거리 0.8 m
부터** 점을 받는데(`pocket_detector.py:63`·`:315`), `run_transport.py` 는 clipping range 를 설정하지
않으므로 **실제 임무 카메라도 기본값을 쓴다.**

| 화면 열 | optical Z = 1 m 이 되는 수평거리 |
|---|---:|
| u = 320 (중앙) | **1.000 m** |
| u = 100 · 540 | **1.106 m** |

**→ 수평거리 0.8–1.0 m(가장자리 1.106 m)는 볼 수 없다.** `range_min_m` 의 앞 20 cm 이상이 죽은 구간이다.

⚠️ **증거가 앞에 있었다** — 정상 동작한 마커 캡처의 depth 범위가 **1.00–4.71 m** 였는데, 최솟값이
장면 기하가 아니라 near clip 그 자체였다.

⚠️ **4순위(근접 추적)에 직결된다.** 접근·삽입 중 팔레트가 near clip 안으로 들어가면 사라진다.
포크 끝은 후축 앞 1.29 m, 카메라는 base_link 앞 0.75 m 다. 삽입 구간에서 팔레트 전면까지의 거리가
1 m 아래로 내려가는지 따로 계산해야 한다.

현재 구현은 **판 전체가 near 에 잘릴 때만** near 를 낮춰 재캡처하고 원본 캡처를 보존한다.
⚠️ 그 경우 **임무 카메라와 다른 설정으로 측정한 것**이므로 캡처마다 기록된다.

## 3. 주점이 반 픽셀 어긋나 있었다 — 인식 파이프라인의 계통 결함

### 3.1 발견

3차 실행에서 ②a(렌더 기반 K 추정)와 ⑦a′(높이)가 FAIL 했다. K 적합 18건 전부가 같은 편향을 냈다:

| | 값 |
|---|---|
| `fx`·`fy` 상대오차 | 최대 **0.028 %** (허용 0.12 %) → 초점거리는 정상 |
| **`cx` 편향** | **−0.5514 px** (σ 0.0374) |
| **`cy` 편향** | **−0.5699 px** (σ 0.0201) |
| 추정 표준오차 | 0.0031–0.0069 px |

**표준오차가 편향의 1/130 이다.** 그리고 높이 오차가 거리에 비례했다:

| 거리 구간 | 편향 | 0.57 px 예측 |
|---|---:|---:|
| 0.8–0.9 m | 0.855 mm | 1.0 mm |
| 1.5–2.5 m | 2.232 mm | 2.4 mm |
| 2.5–3.5 m | 3.181 mm | 3.7 mm |
| 4.5–5.0 m | 4.617 mm | 5.8 mm |

### 3.2 정확한 값은 0.5 다 — depth 로 독립 확인

RGB 코너를 **쓰지 않고** 저장된 depth 만으로 역산한 결과(Codex 교차검증):

| 독립 계산 | 결과 |
|---|---|
| 수평 높이판 유효 depth 6,246개 → `cy` | **239.499941 px** (σ 0.0000685) |
| 기울어진 원거리 교정판 9캡처 → `cx` | **319.5017 px** |

그리고 저장 캡처 재계산:

| 역투영 주점 | 평균 높이 오차 | 거리별 게이트 |
|---|---:|---:|
| 320 / 240 | +2.9683 mm | **0/285** |
| **319.5 / 239.5** | **+0.000248 mm** | **285/285** |
| 319.45 / 239.43 (RGB 적합값) | −0.4153 mm | 174/285 (과보정) |

**→ RGB 적합의 추가 0.05 px 는 depth 에 옮기면 안 된다.**

### 3.3 원인과 수정

Isaac 의 `get_intrinsics_matrix()` 는 `cx = width × 0.5 = 320.0` 을 돌려주는데, 이는 **화소 중심이
반정수**라는 규약이다. 검출기는 `np.indices()` 로 만든 **정수 인덱스**에 그 값을 쓴다
(`pocket_detector._base_points`, `rgbd.py:72-73` 이 정수 인덱스를 요구한다). 두 규약이 반 픽셀 다르다.

수정은 **Isaac 입력 어댑터에서 규약을 변환**한다(`perception_adapter.IsaacIntrinsics`).
`raw_sdk` 와 `integer_index` 를 쌍으로 들고, 후자는 매번 전자에서 계산하는 property 라 **누적 보정이
구조적으로 불가능하다**(2회·4회 통과해도 319.5 유지를 직접 확인).

🚫 `_base_points` 에 +0.5 를 더하는 방식은 채택하지 않았다 — 수학적으로 같지만
(`u+0.5−320 = u−319.5`) 공통 검출기라 CPU 합성·실센서 입력까지 바뀌고, 역투영 함수의 정수 인덱스
계약을 위반한다. **둘을 동시에 적용하면 이중 보정이다.**

### 3.4 ⚠️ 같은 문제가 저장된 Gazebo v1 데이터에도 있다

Codex 가 확인했다 — s095 의 알려진 상자 측면에서 역산한 `cx` 중앙값 **319.495**, 바닥 높이 평균
오차가 `cy=240` 에서 **+1.107 mm**, `cy=239.5` 에서 **−0.032 mm**. `sim/gazebo/README.md:25` 에
반 픽셀 차이가 **이미 적혀 있었다.**

⚠️ **이번 변경은 Isaac 입력 경로에만 적용했다.** v1 로더는 주점 보존을 계약으로 갖고
(`scene_dataset.py:83`), 보정하면 과거 관측 재생이 바뀐다(s009 의 왼쪽 개구 폭 0.27 → 0.26 m).
`tests/integration/test_detector_v1_replay.py` 가 그대로 통과함을 확인했다. **v1 의 반 픽셀 문제는
별도 항목으로 남긴다.**

### 3.5 이 편향이 설명하지 **않는** 것

두 가지를 처음에 주장했다가 **직접 측정으로 철회했다.**

| 철회한 주장 | 반증 |
|---|---|
| 「인식 오차의 상당 부분이 이 편향이다」 | 성공 5건을 두 주점으로 재생: 평균 **2.58 → 2.53 mm**. 개별로는 개선(3.68→0.37)과 악화(3.98→7.39)가 섞인다. 추정 위치는 예측대로 4–5 mm 움직이지만 **기존 오차의 방향이 제각각**이다 |
| 「계열 D(`lower` 14 대 15)의 원인이다」 | seed 0·A 재생: `lower` 가 **14 → 12·13·14**. cx 만·cy 만·둘 다 어떻게 해도 **15 를 회복하지 못한다** |

**반 픽셀 결함과 하부 증거 결함은 공존한다.** 하나가 다른 하나를 설명하지 않는다.

## 4. OpenCV 의 OpenCL 백엔드가 Isaac 과 GPU 를 다퉈 프로세스를 죽인다

4차 실행이 교정판 156/162 에서 죽었다. py-spy 역추적:

```
checkerboard_corners (sim/isaac/camera_calibration.py:822)
OpenCL error CL_MEM_OBJECT_ALLOCATION_FAILURE (-4) during clEnqueueNDRangeKernel('warpAffine', 512x336)
terminate called after throwing an instance of 'cv::Exception'
  what(): ... in function 'deallocate_'
```

`findChessboardCornersSB(..., CALIB_CB_ACCURACY)` 가 내부 `warpAffine` 을 OpenCL 로 돌리고, Isaac 이
같은 GPU 를 쓰므로 할당이 실패한다. 예외가 **소멸자 경로에서** 던져져 C++ 이 잡지 못하고 `terminate()`
한다 — **파이썬 `try/except` 로는 막을 수 없다.**

비결정적이다: 3차는 전량 측정을 끝내고 **종료 단계**에서
`Annotator rgb is not attached to any render products` 로 죽었다.

수정: `cv2.ocl.setUseOpenCL(False)` 를 측정 전에 호출하고 **실제 상태를 기록에 남긴다**
(`have_opencl: true, use_opencl: false`). 종료 경로에서 annotator 를 안전하게 분리한다.
5차 실행이 `exit=0` 으로 완주했다.

| r=4.0 h=0 u=320 | 실패 **20** (표본 60) | 실패 **0** (표본 40) | 실패 **0** |

**초점거리를 그대로 두고 중심만 바꿔도 사라진다** — `fx·fy` 가 아니라 **주점**이 원인이다.
0.06 px 차이로 `v=290` 행의 생존이 뒤집힌다(연속 경계 288.015 → 287.955, 정수 행 289 → 288,
2 px 침식 후 291 → 290).

→ **②a 2/18 과 ⑦a′ 10/54 는 별개 두 결함이 아니라 한 뿌리다.**

⚠️ **그러나 ②a 를 통과시켜도 ⑦a′ 가 보장되지 않는다.** `r=4.0` 의 주점 오차(−0.0707, −0.0299)는
**②a 허용치 0.1 px 안**인데 20개가 실패했다. 그리고 `r3.0 h=144 u=100` 은 반정수로 바꿔도 1건이 남는다.
**편차를 줄이는 것과, 남은 작은 불확실성이 화소 선정의 불연속 때문에 완전성 실패로 증폭되는 것을
막는 것은 역할이 다르다.**

⚠️ **아직 규명되지 않은 것:** RGB 적합 주점의 0.03–0.14 px 편차가 **어디서 생기는가**

## 8. ⑦a′ 선정 ROI 여유 수정 — CPU 검증, ws1 재실행 전

기준 revision `1c00357` 위의 미커밋 수정이다. **§5의 기존 FAIL과 원시 산출물은 그대로 보존한다.**
새 프로토콜은 `G1-v11-3`이며(이후 판 확장까지 반영된 최종값. 8차 실행이 기록한 값과 일치한다), 새로운 출력 디렉터리에서만 재검증한다. 이번 작업에서는 Isaac을
실행하지 않았다. 아래 CPU 시험은 §5의 54판을 재생한 결과가 아니다.

### 8.1 여유 유도와 적용 범위

투영식 u = fx × X/Z + cx, v = fy × Y/Z + cy에서 초점거리를 고정하면 Δu = Δcx,
Δv = Δcy다. 따라서 §5.3–5.4의 관측 최대 주점 편차 **0.1442 px**는 경계를 각 축에서
최대 0.1442 px 이동시킨다. 정수 경계의 위상이 어디에 있느냐에 따라 이 작은 이동도 한 행/열을
바꾼다. 정사각 침식 커널의 각 축 여유는 **ceil(0.1442) = 1 px**로 정한다.
두 축 동시 편차도 같은 정사각 커널이 감싼다.

- 평가 semantic ROI: 기존 **2 px** 침식을 유지한다. 교정판 코너의 평가 침식도 그대로다.
- 선정 geometric ROI: **2 + 1 = 3 px** 침식한다. 깊이 캡처 전에 결정한다.
- 선정 K: 해당 거리의 독립 RGB 적합 **repeat 0**을 그대로 쓴다. 주점·초점거리를 교체하지 않는다.
- 선정 후에는 모든 선정점의 semantic/depth 유효성을 요구한다. 실패점 제거·대체 선정은 없다.

이 값은 **관측된 주점 편차에 근거한 선정 여유**다. 모든 미래 적합값, 초점거리 오차,
렌더러의 임의 경계 오차를 보증하는 새 한계값은 아니다. 실제 배열에서의 완전성은 새 실행으로
확인해야 한다. ②a 허용치 0.1 px와 나머지 수치 합격 조건은 변경하지 않았다.

### 8.2 표본 감소와 구간 소실 기록

각 판에서 동일한 적합 K·장착·표면·stride-grid로 **추가 여유 전(2 px)**과 **후(3 px)**를
계산한다. 이 비교에는 semantic mask나 depth를 사용하지 않는다.

| 기록 필드 | 의미 |
|---|---|
| `selection_groups[].baseline_geometric_count` / `geometric_count` | 구간별 여유 전/후 격자 후보 수 |
| `baseline_planned_count` / `planned_count` | 구간별 min(20, 후보 수), 여유 전/후 선정 수 |
| `required_count` | 새 규칙으로 사전 선정한 수; 모두 수집해야 함 |
| `selection_coverage.baseline_sample_count` / `sample_count` / `removed_sample_count` | 판별 여유 전/후 선정 수와 감소량; 반복 1회분 |
| `selection_coverage.lost_bins` | 여유 전에는 표본이 있었지만 후에는 비어 버린 `[거리, 화면 열, 화면 행]` 구간; 0부터 시작 |
| `coverage_status` | 구간 소실 시 `FAIL`; 처음부터 빈 구간은 `UNOBSERVED` |

소실 구간은 표본 유효성의 `missing_count`와 별도로 남긴다. **다른 구간의 수치가 PASS여도,
선정점 전부가 유효해도, 판 전체가 여유 때문에 비어도 coverage FAIL이다.** 판 판정과 최종
⑦a′에 전파하며, 다른 판이 같은 거리를 측정했다고 지우지 않는다.

독립적으로 화소 경계를 지정한 CPU 합성 시험의 실제 결과:

|---|---:|---|---|
| 아래를 보는 카메라, raw 사각형 u=410…426, v=230…237 | **14 → 5** (9 감소) | 없음 | coverage COMPLETE |

  ⚠️ 다만 현재 적합은 초점거리와 주점만 추정하므로 **회전·전단·위치별 검출 편향은 배제되지 않는다**(§9.8).

⚠️ **수렴이라면 감속해 319.5 에 점근해야 하는데, 이 선형 추세는 rep ≈ 4.3 에서 319.5 를 지나친다.**
3 점으로는 선형인지 느린 수렴인지 가릴 수 없다. **반복을 더 찍어 곡선을 보기 전에는
「워밍업하면 해결된다」고 단정하지 않는다.**

### 9.4c 잡음은 누적 모형과 맞고, 계통 성분은 맞지 않는다

스텝 k 의 영상이 **앞 4k 서브프레임의 평균**이라면(한 호출 = `rt_subframes = 4`),
연속 차분의 표준편차 비가 자료 없이 예측된다:

- `X₂ − X₁ = (T − S₄)/8` → 분산 `1/8`  (`T` = 5–8 번째, `S₄` = 1–4 번째)
- `X₃ − X₂ = U/12 − S₈/24` → 분산 `4/144 + 8/576 = 1/24`
- 예측 비 **`√(1/8) / √(1/24)` = 1.732**

| | 예측 | 실측 |
|---|---:|---:|
| 잡음 비 (v 축) | 1.732 | **1.756** |
| 잡음 비 (u 축) | 1.732 | 2.092 |

**v 축은 거의 정확히 맞는다.** 잡음 성분은 누적 평균으로 설명된다.

계통 성분 \|b_k\| = 0.0955 · 0.0726 · 0.0490 을 세 모형에 맞춘 결과:

| 모형 | 예측 | 잔차합 |
|---|---|---:|
| `A/k` | 0.0955 · 0.0478 · 0.0318 | 0.0420 |
| `A/√k` | 0.0955 · 0.0675 · 0.0551 | 0.0112 |
| **선형** | 0.0956 · 0.0724 · 0.0491 | **0.0005** |

**선형이 압도적으로 맞는다** — 기울기 −0.02325/스텝, 0 을 지나는 지점 **k = 5.11**.
평균화 수렴이면 `1/k` 나 `1/√k` 여야 하는데 둘 다 어긋난다.

⚠️ **따라서 「누적이 수렴 중이다」로 계통 성분을 설명할 수 없다.** 잡음과 계통은 다른 기전이다.
3 점 선형 적합이 완벽하다는 것만으로 선형을 확정할 수도 없다 — 느린 곡선의 앞부분일 수 있다.
**반복 수를 늘린 진단 실행이 이 둘을 가른다.** 그전에는 `rt_subframes` 나 반복 수를 올리지 않는다.

### 9.5 ⑦a′ 는 ②a 와 분리된 문제가 아니다 — rep=0 의 K 로 선정한다

높이판 결과는 세 반복이 **완전히 동일**하다 — 표본 1,881, 소실 구간 11,
PASS 38 / FAIL 11 / UNOBSERVED 5 가 rep 0·1·2 에서 같다.

⚠️ **이 동일성은 depth 가 안정하다는 증거가 아니다.** `height_grid_selection` 호출은
반복 루프 **바깥**에 있고(`verify_perception_camera.py:865` 대 `:876`), 선정 K 는
`selection_fit_reference = {"collection": "intrinsics_fits", "index": 0, "repeat": 0}` —
**rep=0 의 적합**, 즉 §9.2 에서 가장 편향이 큰 그 값이다. 표본·bin·소실 구간이 판마다 한 번만
계산되므로 세 반복이 같은 것은 **구조상 당연**하다.

`height_grid_statistics` 는 반복마다 depth 로 높이를 다시 복원하고 편향·p95 도 다시 계산한다
(`camera_calibration.py:1137`). 구조적으로 고정된 것은 **선정점·bin·선정 coverage** 뿐이다.
**따라서 상태 개수가 같다는 것만으로는 depth 안정성을 주장할 수 없다** — 그 증명은 §9.5b 에서
저장 배열로 따로 했다.

#### rep=0 의 K 로 선정하는 것은 출처 결함이다 — 그러나 소실 구간의 원인은 아니다

다음 주장을 **적었다가 재계산으로 철회했다**: 「②a 를 고치면 여유가 불필요해지고
소실 구간 11 개가 함께 사라진다.」 **양쪽 다 틀렸다.**

| 철회한 주장 | 반증 |
|---|---|
| 「rep=0 을 빼면 봉투가 0.0943 px 라 여유가 없어진다」 | 여유는 `ceil(bound)` 다(`camera_calibration.py:54`). **`ceil(0.1442) = ceil(0.0943) = 1`** — 여유는 그대로 1 px 다 |
| 「②a 를 고치면 소실 구간이 돌아온다」 | 판 위치를 고정하고 **K 만 rep0→rep1→rep2 로 바꿔 재계산**: `[2,1,2]` 가 84→0 · 83→0 · **82→0**, `[5,1,1]` 이 61→0 · 61→0 · **61→0**. 구간은 K 와 무관하게 행 334·290 에 있다 |

남는 사실은 이것이다: **선정 K 를 `gate_2a` 와 무관하게 rep=0 에서 채택한다**
(`verify_perception_camera.py:804`). 검증되지 않은 적합을 선정 입력으로 쓰는 **출처 결함**이고,
그 K 는 선정뿐 아니라 **높이판의 물리적 배치**에도 쓰인다(`:833`) — K 후보를 비교할 때
판 위치까지 같이 바뀌지 않도록 갈라야 한다. 다만 이것은 소실 구간의 원인이 아니다.

**⑦a′ 와 ②a 는 결국 별개 문제다.** 다만 ②a 를 먼저 하는 순서는 유지한다 —
선정 K 의 출처를 고치려면 「판 교체 후 무엇이 안정 상태인가」를 먼저 알아야 하기 때문이다.

### 9.5b RGB 만 바뀐다 — depth·세그먼테이션은 비트 단위로 같다

저장 배열(`board_*_arrays*.npz`, 키 `depth_m`·`segmentation`)을 54 판 × 3 반복 전수 비교했다:

| 배열 | rep1 대 rep0 | rep2 대 rep0 |
|---|---|---|
| `segmentation` | **다른 화소 0 개** (54/54 완전 일치) | **0 개** (54/54) |
| `depth_m` | **최대차 0.0 m** | **최대차 0.0 m** |

이것이 두 가지를 정리한다:

- **코너 검출 입력이 바뀐다는 대안 기전이 배제된다.** `checkerboard_corners`
  (`camera_calibration.py:864-878`)는 `gray[~mask] = 255` 로 마스크 밖을 칠하고
  **마스크 경계상자 ±4 px 로 잘라서** SB 에 넣는다. 마스크가 1 px 만 달라져도 crop 원점
  `(x0, y0)` 과 흰색 영역이 바뀌어 검출 입력 자체가 달라지는데, **마스크가 완전히 같다.**
- **depth 는 실제로 반복에 무관하다.** §9.5 에서 상태 개수로는 주장할 수 없다고 했던 것을
  배열 비교로 직접 증명했다.

**기하·depth·세그먼테이션·crop 이 전부 동일한데 RGB 화소만 바뀐다.**

### 9.5c 원인 후보 — 기본 AA 가 DLSS 다

`verify_perception_camera.py:1017` 은 `SimulationApp({"headless": True,
"renderer": "RaytracedLighting"})` 로 시작하며 **AA 를 지정하지 않는다.**
`sim/isaac/` 전체에 `anti_aliasing`·DLSS 언급이 없다. ws1 설치본의 기본값:

**→ 측정은 DLSS 를 거친 RGB 로 하고 있었다.** DLSS 는 시간 누적과 서브픽셀 지터를 쓰는
**색 영상 전용** 처리다. 지금까지의 실측이 전부 이것과 맞는다:

| 실측 | DLSS 와의 정합 |
|---|---|
| 스텝마다 영상이 바뀐다 (§9.4) | 시간 누적 |

| 판 저작마다 초기화 (§9.4b) | 기하 변경 시 이력 무효화 |
| `fx` 는 안정, **주점만 평행이동** (§9.2) | 서브픽셀 지터 |

⚠️ **이것은 정합이지 증명이 아니다.** AA 를 끈 대조군에서 현상이 사라지는 것을 봐야 한다.

🚫 **→ §10 에서 이 가설은 반증됐다.** AA 를 완전히 꺼도 현상이 그대로다.

#### 범위 — 검출기에는 미치지 않는다

`run_transport.py:1294` 도 AA 를 지정하지 않아 **임무도 같은 기본값**이다.
다만 `pocket_detector.py` 는 `.rgb` 를 전혀 참조하지 않는 **depth 전용**이고,
`perception_adapter.py` 의 RGB 사용은 준비 상태 점검뿐이다.
**따라서 이 결함의 범위는 G1 의 RGB 코너 측정에 한정된다** — 검출 성적을 다시 무효화하지 않는다.

⚠️ 따라서 고칠 지점은 판의 크기 일반이 아니라 **양 끝 거리 구간이 격자행 한 줄뿐이라는 것**이다.
판을 늘린다면 **거리 구간 경계를 넘어서까지** 늘려 그 구간이 여러 줄을 갖게 해야 한다.
지금 판은 경계 근처에서 끝난다.

그 결론으로 떨어지게 되어 있고, ②a 가 FAIL 이라 걸린 것이다.
**②a 가 통과하면 세 마커 전부 `bright_centroid_outside_marker_bbox = true` 이므로
`global_brightness_method_discrepancy` 로 뒤집힌다** — ⑥ 에 별도 작업이 필요한 것이 아니다.
다만 게이트 자체는 설계상 `USER_JUDGMENT_REQUIRED` 로 남는다.

⚠️ **이 비교가 증명하지 않는 것**(적대적 검토에서 지적받아 표현을 낮췄다):

- **bloom 은 증명되지 않는다.** 밝은 화소가 마커 밖에 있다는 것까지가 측정된 사실이고,
  그것이 bloom 인지 다른 발광 반사인지는 가르지 않았다.
- **마커 한 위치의 일치가 카메라 전체의 0.1 px 정확도를 입증하지 않는다.**
  화면 한 지점의 결과다.
- **구의 실루엣 중심과 구 중심의 투영은 같은 측정량이 아니다.**
  기록도 `sphere_silhouette_is_not_projected_centre: true` 로 이를 명시한다.

따라서 **「밝기 방식에 결함이 관측됐다」와 「작은 교정 불일치는 미해결이다」는 동시에 성립한다.**

### 9.8 이 절이 확정하지 않는 것

- **표류의 기전은 미확정이다.** DLSS 가 유력 후보지만(§9.5c) **정합일 뿐 증명이 아니다.**
  AA 를 끈 대조군이 필요하고, 사라져도 내부 어느 단계인지는 특정되지 않는다.
- **세 점으로 함수 모양을 확정할 수 없다.** 선형 적합이 완벽해도(§9.4c) 관측 구간이 둘뿐이다.
  「누적 수렴이면 반드시 319.5 에 단조 점근한다」에는 **극한값이 319.5 라는 전제**와
  **단조 필터라는 전제**가 빠져 있다 — 편향된 극한, 일시적 초과, 주기적 지터의 일부 구간도
  현재 세 점과 양립한다. `rep ≈ 5.1` 교차점은 선형 외삽값일 뿐이다.
- **잡음과 계통이 같은 기전인지 다른지도 미확정이다.** `mean(|Δuv|)` 는 **연속 관측의 차이**이지
  각 관측의 잡음 표준편차가 아니다 — 시간 상관이 강해져도 차이는 줄어든다.
  §9.4c 의 1.732 정합은 그 한계 안에서 읽어야 한다.
- **「순수한 영상 평행이동」도 강한 결론이다.** 현재 K 적합(`camera_calibration.py:241`)은
  축별 초점거리와 주점만 추정하므로, `fx` 가 안정해도 작은 회전·전단·위치별 검출 편향은 남을 수 있다.
  판별 평균 이동을 뺀 잔차가 화면 위치에 따라 달라지는지 따로 봐야 한다.
- **고치는 방법도 미확정이다.** 반복·`rt_subframes` 를 늘리는 것은 곡선 모양을 먼저 봐야
  근거가 생긴다. 통과할 때까지 늘리는 것은 원인 규명이 아니다.
- **진단 실행 결과를 정식 G1 성적으로 집계하지 않는다.** `finish_result()`
  (`verify_perception_camera.py:929`)는 적합 18 · 보드 162 를 요구한다.
- **G1 은 통과하지 않았다.** `status: FAIL`, `g2_allowed: false`. G2 이후는 계속 중단이다.

### 9.9 작업 순서

1. **②a 진단** — 표류의 기전을 가른다. 반복을 늘리고 `rt_subframes` 와 교차하며 **AA 대조군**을 넣는다.
   이것이 선정 K 의 출처 문제(§9.5)와 ⑥ 판정 문자열(§9.7)을 함께 정리한다.
2. **⑦a′** — ②a 와 **별개 문제로 확정됐다**(§9.5). 소실 구간은 K 와 무관하다.
   판의 시선 방향 깊이를 거리 구간 경계 너머로 늘리는 배치 변경이 후보다(§9.6).
3. **⑥** — 1 이 끝나면 진단 **문자열**이 자동으로 바뀐다. 사용자 판단은 그대로 남는다.

## 12. ②a 계통 편향의 원인 — 검출기가 아니라 렌더다

7·8차의 `cy` 계통 편향(평균 −0.059 / −0.066 px)을 조사했다. Isaac 실행 없이,
진단 실행이 저장한 **원본 RGB** 와 CPU 합성 영상만 썼다.

### 12.1 검출 경로는 무죄다

정답 코너를 아는 **CPU 합성 체커보드**를 **수정하지 않은 `checkerboard_corners`** 에 넣은 결과:

| 합성 조건 | `du` | `dv` |
|---|---:|---:|
| 이상적 커버리지 (실제 G1 위상) | −0.0002 | +0.0009 |
| + 블러 · 언샤프 · 톤곡선 · 실측 잡음 | ≤ 0.0024 | ≤ 0.0018 |
| + 비등방 블러 (0.9u/0.5v, 0.5u/0.9v) | ≤ 0.0021 | ≤ 0.0012 |

서브픽셀 위상 스윕에서 최대 편향 **0.019 px**, 축 비대칭 없음.
**양성 대조**: 알려진 평행이동 (0,−0.067)·(0,−0.2)·(0.5,0.5) 주입 → **0.003 px 이내로 복원**.

검출 경로 각 요소의 기여(실제 영상 99장):

| 요소 | 생산 코드 대비 |
|---|---|
| **`gray[~mask] = 255` 제거/0/128** | **정확히 0.00000** (코너 비트 단위 동일) |
| crop 제거 · 여백 0/2/8/16 · 원점 ±1 px | ≤ 0.0005 |
| `flags = 0` · `ACCURACY\|EXHAUSTIVE` | ≤ 0.0015 |
| 그레이 변환 방식 | ≤ 0.0005 |

**전 요소 합이 0.002 px 미만인데 편향은 0.053–0.067 px 다.**
⚠️ 단, whitening 이 무해한 것은 **이 판들의 mask 가 흰 테두리 바깥에 있기 때문**이고,
패턴에 딱 붙는 mask 에 대한 증명은 아니다.

### 12.2 검출기를 쓰지 않아도 같은 값이 나온다

화소값만으로 흑백 경계의 서브픽셀 위치를 재고 극성별로 분해했다.
**반대칭 성분 = 평행이동**이며 평탄부 레벨 오차·조도 기울기·점별 톤 비선형성이 상쇄된다.

| | 흰색 팽창 (대칭) u / v | **평행이동 (반대칭) u / v** |
|---|---|---|
| `drift_A` (DLSS 켬, 99장) | +0.383 / +0.379 | **−0.0093 / −0.0668** |
| `drift_C` (AA 끔, 99장) | +0.389 / +0.389 | **−0.0111 / −0.0796** |

**팽창은 등방인데 평행이동만 v 축에 쏠린다.**

### 12.3 축 비대칭의 정체 — 기울인 판에는 편향이 없다

모든 판은 사각형이 정확히 **16.000 px**, 중심이 raw 화소 경계에 떨어지도록 저작된다.
즉 **모든 체커 경계가 두 축 모두에서 화소 격자에 완벽히 정렬된 축퇴 상태**다.
이 상태에서 렌더의 영상형성이 **v 방향으로만 홀수(반대칭) 모멘트**를 갖는다.

`checkerboard_layout` 은 `centre_uv[0] == cx` 인 판을 r = 5.0 에서 **10° 기울인다.**
그 판들만 수평 경계가 화소 격자에 놓이지 않는다. 8차 실행 실측(**직접 재현함**):

| | `du` | `dv` |
|---|---:|---:|
| **기울인 판** (r=5.0, u=320), n=9 | +0.0217 | **+0.0112** |
| 나머지, n=153 | +0.0057 | **−0.0609** |

**기울이면 편향이 사라진다** — 경계가 길이를 따라 모든 v 위상을 훑어 평균되기 때문이다.
7차에서도 같다(기울임 `dv` +0.0078 대 나머지 −0.048 ~ −0.069). 거리·화면열 교란은 두 실행 모두에서 배제된다.

### 12.4 순수 평행이동도 아니다 — 극성 의존

코너의 체커 극성(흰 사분면 NW–SE 대 NE–SW)에 따라 잔차가 갈린다:

| | `du` | `dv` |
|---|---:|---:|
| 실제 8차, 극성 A (n=5,022) | −0.0047 | **−0.0854** |
| 실제 8차, 극성 B (n=5,184) | +0.0176 | **−0.0293** |
| **합성 대조 (전 변형)** | — | **차이 ≤ 0.002** |

**순수 평행이동은 두 극성을 다르게 만들 수 없다**(합성으로 증명). 따라서 렌더의 실효 점확산은
밀린 것이 아니라 **비뚤어져(skew) 있고**, 흰색 0.38 px 팽창과 겹쳐 안장점의 순 변위가 된다.

### 12.5 8차가 떨어지고 7차가 통과한 진짜 이유 — 주기 4 변조

🚫 **「두 실행은 같은 분포이고 최대값이 허용치 양쪽에 떨어졌을 뿐」이라고 적었던 것을 철회한다.**
8차에만 **판 저작 카운터 mod 4 에 잠긴 변조**가 있다(**직접 재현함**):

| 저작 순서 mod 4 | 0 | 1 | 2 | 3 |
|---|---:|---:|---:|---:|
| **8차 `dv`** | **−0.156** | −0.008 | −0.012 | −0.048 |
| 7차 `dv` | −0.064 | −0.045 | −0.048 | −0.057 |

거리마다 판이 9 개이고 **9 ≡ 1 (mod 4)** 이라 위상이 거리마다 돈다.
`d ≡ 0 (mod 4)` 인 **r = 0.8 과 r = 4.0** 이 최악 위상에 3 판씩 받고, 실제로 그 둘이 가장 나쁘다
(r=4.0 −0.0864, r=0.8 −0.0778). **게이트를 깬 적합이 `r=4.0 rep0` 다.**

### 12.6 규명하지 못한 것

- **렌더 파이프라인의 어느 단계인지 특정하지 못했다.** 서브픽셀 지터·표본 패턴·재구성 필터
  설정이 **기록에 없다**(진단이 남긴 carb 키는 AA/DLSS 계열뿐).
- **Halton(2,3) 지터 모형은 계산해 반증했다** — N=4 에서 −0.094/−0.111, N=16 에서 −0.029/−0.037 을
  예측하는데, §10.5b 의 실측(4→16 에서 평균 이동 불변)이 이를 부정한다.
- **주기 4 를 렌더러 프레임 카운터에 연결하지 못했다**(mod 2–24 전수 검정, F ≤ 3.5, 조건 A·C 불일치).
- **주기 4 변조는 7차엔 없고 8차엔 있다 — 각 1 회 관측이다.**
- 외곽 실루엣 측정은 블룸 후광 때문에 결론을 내지 못했다.

### 12.7 이 결과가 함의하는 것

재현되는 v 축 DC 편향 **−0.054 ~ −0.061 px** 가 **0.1 px 예산의 약 60 %** 를 산포 이전에 소모한다.

⚠️ **다만 이 편향은 검출 경로로 전파되지 않는다.** `pocket_detector` 는 `.rgb` 를 전혀 읽지 않는
**depth 전용**이고(§9.5c), depth 역산은 `cy = 239.499941`(σ 0.0000685)다.
**②a 가 재는 것과 인식이 쓰는 것이 다른 경로다.**

## 13. 철회 — 판 레이아웃 축퇴 해소 제안

§12.3 의 기울임 대조를 근거로 **판을 기울이거나 위상을 분산해 축퇴를 해소**하자고 제안했다가,
적대적 검토와 **직접 재계산으로 철회했다.**

### 13.1 결정적 반증 — 기울이면 편향이 게이트 ④ 로 옮겨간다

현재 판은 **정면 평행**이다(광학 좌표에서 `Z` 가 판 전체에 일정). 따라서 `dZ/du = 0` 이고,
게이트 ④(depth 정확도)는 RGB 코너 오차에 **구조적으로 무감각**하다. 기울이면 결합된다:

| | max \|depth bias\| | max depth centered p95 |
|---|---:|---:|
| **8차** 비기울임 153 판 | 2.500e−07 m | 4.089e−07 m |
| **8차** 기울인 9 판 | **1.362e−04 m** (**545×**) | **4.079e−04 m** (**997×**) |
| **7차** 비기울임 | 2.504e−07 m | 4.385e−07 m |
| **7차** 기울인 | **1.386e−04 m** (**553×**) | **5.092e−04 m** (**1161×**) |

(허용치 1e−3 / 2e−3 m. 두 실행 모두에서 재현된다 — **직접 재계산함**.)

**제안의 순효과는 편향을 「생산이 쓰지 않는 게이트(②a, RGB)」에서
「생산의 depth 역투영을 흉내 내는 게이트(④·⑦b)」로 옮기는 것이었다.** 방향이 정반대다.
현 배치의 정면 평행성은 설계 미숙이 아니라 **설계 자산**이다.

### 13.2 무너진 나머지 근거

| 내가 든 근거 | 반증 |
|---|---|
| 「⑦a′ 선례와 같은 범주」 | ⑦a′ 는 측정 사각형 **바깥**에 여유를 붙여 **측정값이 하나도 안 바뀐다.** 레이아웃 변경은 **모든 측정값이 바뀐다**(모집단 평균 0.07 px 이동). **정당성을 빌려온 것이 맞다** |
| 「측정된 대조」 (n=9) | 판 **배치 3 개** × 반복 3 회다. 같은 저작의 반복은 독립이 아니다(§9.4b). 저작 단위로 묶으면 **약 2.3σ** |
| 「기전은 위상 평균화」 | 판 단위 `dv` 의 **실행 간 상관이 r = +0.23** 뿐이고, 극성 분리(−0.085 대 −0.029)는 두 극성이 **정확히 같은 위상**(16 px 정수 간격)이라 위상만으로 못 만든다. §12.4 에 사실로 적어놓고 제안과 연결하지 않았다 |
| 「실제 교정은 자세를 바꾼다」 | 여기서는 자세가 USD 로 정확히 알려져 있고 적합은 알려진 `X/Z`·`Y/Z` 에 대한 선형회귀라 **식별 축퇴가 없다.** 있는 것은 **표본 위상 집중**이지 파라미터 축퇴가 아니다 |

### 13.3 「그 배치가 실패를 냈다」도 부정확하다

36 개 적합 합산 평균 −0.0626, sd 0.0232 → 적합 하나가 0.1 안에 들 확률 0.946,
**18 개 전부 = 0.37**. **현 구성은 3 번에 1 번 통과한다.** 7차의 18/18 은 고쳐진 것이 아니라 운이다.

그리고 **8차를 떨어뜨린 것은 DC 편향이 아니라 mod 4 변조**다(§12.5).
mod 0 군을 빼면 평균이 −0.061 → **−0.024** 다. **기울인 배치에서는 이 변조가 보이지 않는다** —
카메라가 고쳐진 것인지 계기가 둔해진 것인지 구분할 수 없게 된다.
계획서가 「원인을 안 뒤의 질문」이라고 못박아 둔 순서를 뒤집는 것이다.

### 13.4 이 계기가 실제로 잡아 온 것

판 단위 `dv` 의 표준편차가 기울이면 0.0924 → 0.0104(8차)로 **6–9 배 둔감**해진다.
그 감도로 잡은 것: **mod 4 변조**, **저작 직후 첫 캡처의 −0.12 px 과도상태**(§10.3),
**기본 AA 가 DLSS 라는 사실**(§9.5c). ADR 0004 로 동적·부정 장면이 Isaac 한 곳에 몰린 상황에서
0.05–0.15 px 급 렌더 변화 감지기를 잃는 것은 실제 비용이다.

⚠️ **DC 성분 K 오차**(§3.1 의 반 픽셀 규약 결함 같은 부류)에 대한 감도는 **줄지 않는다.**
위상 평균은 DC 를 지우지 못한다. 잃는 것은 부수적 감도다.

### 13.5 채택한 방향

- **레이아웃을 바꾸지 않는다.** 현 배치가 판정 기준선이다.
- **(D) 기울임·위상 변형을 별도 진단 컬렉션으로 병행 기록한다** — 워밍업 캡처와 같은 패턴.
  먼저 답할 질문은 「통과하는가」가 아니라 **「주입한 K 오차를 두 배치가 똑같이 검출하는가」**다.
- **(A) ②a 의 역할 재분류는 사용자 결정으로 올린다** — 생산은 depth 전용이고(§9.5c),
  생산 K 는 FOV 유도 상수이며, §3.2 가 「RGB 적합의 추가 0.05 px 는 depth 로 옮기면 안 된다」고
  이미 판정했다. 「렌더 RGB 로 추정한 K 가 0.1 px 안에 들 것」이 **G2 차단 조건이어야 하는가**는
  계획서가 「완화는 사용자 결정 사항」으로 적어둔 항목이다.

### 13.6 검토가 남긴 미확인 항목

- **depth 역산 `cy = 239.499941`(σ 6.85e−5)을 재현하는 스크립트가 저장소에 없다.**
  그 σ 는 주어진 focal·장착·높이·depth 모형 아래의 값이지 카메라의 절대 정확도가 아니다.
- **Isaac 의 `distance_to_image_plane` 이 RGB 와 같은 투영행렬에서 나오는지** 확인 불가.
  확실한 한계 하나: **depth 경로가 일관돼도 RGB 경로만 어긋나는 결함은 통과시킨다.**
- **생산의 `camera.get_depth()` 와 G1 의 replicator annotator 가 같은 경로인지** 증명하는 시험이 없다.

### 14.2 판별력이 있는 수치는 **마스킹**이다

`cx`·`cy` 에 알려진 오차 δ 를 주입한 뒤, 적합이 **주입 전보다 명목값에 더 가까워진** 비율:

  ⚠️ **통과 확률 추정치는 신뢰하지 마라** — §13.3 은 약 1/3, 교차검증의 독립 추정은 약 0.55 인데,
  **둘 다 적합의 독립성을 가정하고 그 가정이 성립하지 않는다**(앵커마다 9 개 판을 공유한다.
  `layout_power` 의 `independence_caveat` 가 이를 명시한다). 확실한 것은 **draw 라는 것**뿐이다.
- **게이트는 자기 허용치 크기의 오차를 못 잡는다**(§14) — δ=0.05 주입 시 마스킹 100 %.
- **⑦a′ 도 마찬가지다** — H1 의 테두리 구간은 이번에 **안 나왔을 뿐**이고,
  `cy` 가 0.1442 px 움직이면 나타난다(§9.6). 기준 표본 1 개짜리 구간이 게이트 전체를 떨어뜨릴 수 있다.

### 17.2 확인된 것

**7 건 수정이 실제 렌더 환경에서 회귀를 내지 않았다.** 판정 규모가 유지되고,
⑦a′ 가 불리언에서 사유 목록으로 바뀌었어도 빈 목록 = PASS 로 정상 동작한다.

⚠️ **새 판별 실패 경로는 여전히 미실행이다** — 이번 실행에서 발동할 조건이 없었다.
두 `except` 분기와 `stage.RemovePrim` 은 CPU·AST 시험에만 의존하고,
**`RemovePrim` 은 저장소 어느 시험도 언급하지 않는다.**

⚠️ **⑦a′ 의 PASS 는 파생이지 독립 증거가 아니다.** 8차의 ⑦a′ 는 사유가 `selection_fit_unvalidated`
**하나뿐**이었고 그것은 ②a 실패의 결과다(8차도 소실 구간 0·기하 실패 0 이었다).
따라서 **②a 가 실패하면 ⑦a′ 는 통과할 수 없고**, 9차의 ⑦a′ PASS 는
「이번에 ②a 가 통과했다」 이상을 말하지 않는다.

### 17.2b `protocol_sha256` 이 산문 때문에 바뀌었다

8차 `31243ba9…` → 9차 `55875569…`. **표본 정책은 하나도 안 바뀌었다.**
결함 수정 7 번이 `height_selection_margin()` 안의 `derivation` **문자열**을 고쳤고,
그 문자열이 `protocol()` 에 직렬화되기 때문이다.
**해시만 비교하는 독자는 정책이 바뀌었다고 잘못 읽는다.**

### 17.3 남은 결정 (사용자)

수치가 통과했다고 두 결정이 사라지지 않는다. **오히려 지금이 정할 시점이다** —
다음 실행에서 다시 떨어질 수 있는 상태로 G2 를 여는 것이기 때문이다.

1. **②a 를 G2 차단 조건으로 유지할 것인가** — 통과 확률 1/3 인 게이트를 관문으로 두는 것의 타당성.
   논거는 §16 에 양쪽 다 적었다.
2. **coverage 에 최소 표본 하한을 둘 것인가**(H1) — `MIN_PLANE_SAMPLES = 6` 이 판 평면에는 이미
   적용되는데 coverage 구간에는 하한이 없다. 같은 파일 안에서 두 규칙이 「무엇이 측정인가」에
   대해 다르게 말한다. **이것도 게이트 의미 변경이라 사용자 결정이다.**

## 18. 사용자 결정 둘을 반영했다 (2026-09-21)

`20260922T0000Z_g1_decisions`. §16 에 사용자 결정으로 올려 둔 두 항목이 결정됐다.

### 18.1 결정 A — ②a 를 차단 조건에서 진단으로 내린다

`gates["2a"]` 는 **측정되고 기록되는 값 그대로 남고**, `numerical_pass` 기여에서만 빠진다
(`7b` 와 같은 방식). 근거가 `result.json` 자체에 남는다:

```json
"diagnostic_only_gates": {
  "7b": "recorded only; never an input to the numerical aggregate",
  "2a": "user decision 2026-09-21: measured and recorded as before, excluded from the numerical aggregate only. …"
}
```

근거: 생산 검출기는 **depth 전용**이고 `.rgb` 를 전혀 참조하지 않는다(직접 확인),
생산 K 는 FOV 유도 상수이며, **게이트가 자기 허용치에서 검출력이 없다**(§14, δ=0.05 px 마스킹 ~90 %).

🚫 **연쇄 강등은 하지 않았다.** ⑦a′ 의 `selection_fit_unvalidated` 는 실제 실패 사유로 남는다 —
②a 라는 게이트 전반이 아니라 **⑦a′ 의 측정 입력으로 쓰인 그 적합**에 대한 것이기 때문이다.

### 18.2 ⚠️ 그래서 ②a 는 여전히 간접적으로 막을 수 있다 — 조건이 정확히 밝혀졌다

⑦a′ 는 전역 게이트가 아니라 **각 판의 두 참조에 복사된 `gate_2a`** 를 읽는다
(`SELECTION_FIT_REPEAT = 0`). 10차 데이터를 변이해 **재생으로 실증했다**:

| 변이 | ②a | ⑦a′ | `numerical_status` | `status` |
|---|---|---|---|---|
| 무변경 | PASS | PASS | PASS | REVIEW_REQUIRED |
| **②a FAIL @ 선정 앵커 반복 0** | FAIL | **FAIL** | **FAIL** | **FAIL** |
| **②a FAIL @ 비선정 반복 1** | **FAIL** | PASS | **PASS** | REVIEW_REQUIRED |
| **②a FAIL @ 비선정 반복 2** | **FAIL** | PASS | **PASS** | REVIEW_REQUIRED |

**②a 가 FAIL 인데 `numerical: PASS` 가 나온다 — 강등이 실제로 작동한다.**
동시에 **선정 앵커에서 떨어지면 여전히 막힌다.** 8차가 그 경우였다.

→ 강등을 완전하게 하려면 `selection_fit_unvalidated` 도 내려야 한다. **지시에 없어 손대지 않았다.**

### 18.3 결정 B — coverage 에 최소 기준 표본 하한을 둔다

`MIN_COVERAGE_BASELINE_SAMPLES = 6` — `MIN_PLANE_SAMPLES` 와 현재 같은 값이지만
**별도 상수**로 두어 나중에 갈라질 수 있게 했다. 프로토콜에 사전 선언된다
(`minimum_coverage_baseline_samples: 6`).

- 기준 표본이 **하한 미만**인 구간이 여유에 비면 → **`BELOW_BASELINE_FLOOR`**,
  `baseline_geometric_count` 와 함께 **기록에 남고 실패시키지 않는다.** 삭제가 아니라 재분류다.
- 기준 표본이 **하한 이상**이면 → **그대로 FAIL**.

**하한이 기존 결과를 흔들지 않는 것을 전수 확인했다**: 7·8·9차에 저장된 bin 레코드
**43,740 개 전부**에 새 규칙을 다시 적용해 기록된 `coverage_status` 와 비교 → **0 건 변동**.
7차에서 잃었던 11 개 구간의 기준 표본은 최소 **12** 이므로 전부 그대로 실패한다.

⚠️ **하한이 겨냥한 경우는 실제 실행에서 한 번도 나온 적이 없다.**
§9.6 의 `[4,0,2]`(화소 3 개, 기준 표본 1)는 **명목 K 의 CPU 재현에서만** 나타났고
8·9·10차 실행에서는 0 건이다. 면제 경로는 CPU 시험으로만 검증됐다.

### 18.4 10차 실행 — 두 결정이 반영됐으나 발동하지 않았다

```
status: REVIEW_REQUIRED | numerical: PASS | g2_allowed: false
① PASS · ②a PASS · ②b PASS · ③ PASS · ④ PASS · ⑤ PASS
⑦a PASS · ⑦a′ PASS · ⑦b RECORD_ONLY · ⑥ USER_JUDGMENT_REQUIRED
cy 평균 −0.0390, 최대 |·| 0.0718 · 소실 구간 0
```

⚠️ **②a 가 통과하고 소실 구간도 0 이라, 바뀐 경로는 이번에 발동할 일이 없었다.**
효과는 §18.2 의 재생과 43,740 건 투영으로 확인했지, 이 실행이 확인한 것이 아니다.

⚠️ `protocol_sha256` 이 또 바뀌었다 — 이번에는 **실제 정책 변경**(하한 도입)이라 정당하다.
§17.2b 의 산문 변경과 구분해서 읽어야 한다.
