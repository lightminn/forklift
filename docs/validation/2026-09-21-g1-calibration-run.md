## 2. `range_min_m = 0.8` 의 앞 구간은 near clip 때문에 관측 불가다

2차 실행에서 교정판 캡처가 **RGB 완전 검정·depth 전부 비유한**으로 나왔다. 원인은 **USD 카메라의
기본 near clip 1 m** 와 첫 교정판의 optical Z **0.72336 m** 의 충돌이다. 배경을 숨긴 상태에서 판까지
잘리면 프레임이 통째로 빈다.

**이것은 시험 장치만의 문제가 아니다.** 검출기의 워크스페이스 필터는 **카메라 기준 수평거리 0.8 m
부터** 점을 받는데(`pocket_detector.py:63`·`:315`), `run_transport.py` 는 clipping range 를 설정하지
않으므로 **실제 임무 카메라도 기본값을 쓴다.**

| 화면 열 | optical Z = 1 m 이 되는 수평거리 |
|---|---:|
| u = 320 (중앙) | **1.000 m** |
| u = 100 · 540 | **1.106 m** |

**→ 수평거리 0.8–1.0 m(가장자리 1.106 m)는 볼 수 없다.** `range_min_m` 의 앞 20 cm 이상이 죽은 구간이다.

⚠️ **증거가 앞에 있었다** — 정상 동작한 마커 캡처의 depth 범위가 **1.00–4.71 m** 였는데, 최솟값이
장면 기하가 아니라 near clip 그 자체였다.

⚠️ **4순위(근접 추적)에 직결된다.** 접근·삽입 중 팔레트가 near clip 안으로 들어가면 사라진다.
포크 끝은 후축 앞 1.29 m, 카메라는 base_link 앞 0.75 m 다. 삽입 구간에서 팔레트 전면까지의 거리가
1 m 아래로 내려가는지 따로 계산해야 한다.

현재 구현은 **판 전체가 near 에 잘릴 때만** near 를 낮춰 재캡처하고 원본 캡처를 보존한다.
⚠️ 그 경우 **임무 카메라와 다른 설정으로 측정한 것**이므로 캡처마다 기록된다.

## 3. 주점이 반 픽셀 어긋나 있었다 — 인식 파이프라인의 계통 결함

### 3.1 발견

3차 실행에서 ②a(렌더 기반 K 추정)와 ⑦a′(높이)가 FAIL 했다. K 적합 18건 전부가 같은 편향을 냈다:

| | 값 |
|---|---|
| `fx`·`fy` 상대오차 | 최대 **0.028 %** (허용 0.12 %) → 초점거리는 정상 |
| **`cx` 편향** | **−0.5514 px** (σ 0.0374) |
| **`cy` 편향** | **−0.5699 px** (σ 0.0201) |
| 추정 표준오차 | 0.0031–0.0069 px |

**표준오차가 편향의 1/130 이다.** 그리고 높이 오차가 거리에 비례했다:

| 거리 구간 | 편향 | 0.57 px 예측 |
|---|---:|---:|
| 0.8–0.9 m | 0.855 mm | 1.0 mm |
| 1.5–2.5 m | 2.232 mm | 2.4 mm |
| 2.5–3.5 m | 3.181 mm | 3.7 mm |
| 4.5–5.0 m | 4.617 mm | 5.8 mm |

### 3.2 정확한 값은 0.5 다 — depth 로 독립 확인

RGB 코너를 **쓰지 않고** 저장된 depth 만으로 역산한 결과(Codex 교차검증):

| 독립 계산 | 결과 |
|---|---|
| 수평 높이판 유효 depth 6,246개 → `cy` | **239.499941 px** (σ 0.0000685) |
| 기울어진 원거리 교정판 9캡처 → `cx` | **319.5017 px** |

그리고 저장 캡처 재계산:

| 역투영 주점 | 평균 높이 오차 | 거리별 게이트 |
|---|---:|---:|
| 320 / 240 | +2.9683 mm | **0/285** |
| **319.5 / 239.5** | **+0.000248 mm** | **285/285** |
| 319.45 / 239.43 (RGB 적합값) | −0.4153 mm | 174/285 (과보정) |

**→ RGB 적합의 추가 0.05 px 는 depth 에 옮기면 안 된다.**

### 3.3 원인과 수정

Isaac 의 `get_intrinsics_matrix()` 는 `cx = width × 0.5 = 320.0` 을 돌려주는데, 이는 **화소 중심이
반정수**라는 규약이다. 검출기는 `np.indices()` 로 만든 **정수 인덱스**에 그 값을 쓴다
(`pocket_detector._base_points`, `rgbd.py:72-73` 이 정수 인덱스를 요구한다). 두 규약이 반 픽셀 다르다.

수정은 **Isaac 입력 어댑터에서 규약을 변환**한다(`perception_adapter.IsaacIntrinsics`).
`raw_sdk` 와 `integer_index` 를 쌍으로 들고, 후자는 매번 전자에서 계산하는 property 라 **누적 보정이
구조적으로 불가능하다**(2회·4회 통과해도 319.5 유지를 직접 확인).

🚫 `_base_points` 에 +0.5 를 더하는 방식은 채택하지 않았다 — 수학적으로 같지만
(`u+0.5−320 = u−319.5`) 공통 검출기라 CPU 합성·실센서 입력까지 바뀌고, 역투영 함수의 정수 인덱스
계약을 위반한다. **둘을 동시에 적용하면 이중 보정이다.**

### 3.4 ⚠️ 같은 문제가 저장된 Gazebo v1 데이터에도 있다

Codex 가 확인했다 — s095 의 알려진 상자 측면에서 역산한 `cx` 중앙값 **319.495**, 바닥 높이 평균
오차가 `cy=240` 에서 **+1.107 mm**, `cy=239.5` 에서 **−0.032 mm**. `sim/gazebo/README.md:25` 에
반 픽셀 차이가 **이미 적혀 있었다.**

⚠️ **이번 변경은 Isaac 입력 경로에만 적용했다.** v1 로더는 주점 보존을 계약으로 갖고
(`scene_dataset.py:83`), 보정하면 과거 관측 재생이 바뀐다(s009 의 왼쪽 개구 폭 0.27 → 0.26 m).
`tests/integration/test_detector_v1_replay.py` 가 그대로 통과함을 확인했다. **v1 의 반 픽셀 문제는
별도 항목으로 남긴다.**

### 3.5 이 편향이 설명하지 **않는** 것

두 가지를 처음에 주장했다가 **직접 측정으로 철회했다.**

| 철회한 주장 | 반증 |
|---|---|
| 「인식 오차의 상당 부분이 이 편향이다」 | 성공 5건을 두 주점으로 재생: 평균 **2.58 → 2.53 mm**. 개별로는 개선(3.68→0.37)과 악화(3.98→7.39)가 섞인다. 추정 위치는 예측대로 4–5 mm 움직이지만 **기존 오차의 방향이 제각각**이다 |
| 「계열 D(`lower` 14 대 15)의 원인이다」 | seed 0·A 재생: `lower` 가 **14 → 12·13·14**. cx 만·cy 만·둘 다 어떻게 해도 **15 를 회복하지 못한다** |

**반 픽셀 결함과 하부 증거 결함은 공존한다.** 하나가 다른 하나를 설명하지 않는다.

## 4. OpenCV 의 OpenCL 백엔드가 Isaac 과 GPU 를 다퉈 프로세스를 죽인다

4차 실행이 교정판 156/162 에서 죽었다. py-spy 역추적:

```
checkerboard_corners (sim/isaac/camera_calibration.py:822)
OpenCL error CL_MEM_OBJECT_ALLOCATION_FAILURE (-4) during clEnqueueNDRangeKernel('warpAffine', 512x336)
terminate called after throwing an instance of 'cv::Exception'
  what(): ... in function 'deallocate_'
```

`findChessboardCornersSB(..., CALIB_CB_ACCURACY)` 가 내부 `warpAffine` 을 OpenCL 로 돌리고, Isaac 이
같은 GPU 를 쓰므로 할당이 실패한다. 예외가 **소멸자 경로에서** 던져져 C++ 이 잡지 못하고 `terminate()`
한다 — **파이썬 `try/except` 로는 막을 수 없다.**

비결정적이다: 3차는 전량 측정을 끝내고 **종료 단계**에서
`Annotator rgb is not attached to any render products` 로 죽었다.

수정: `cv2.ocl.setUseOpenCL(False)` 를 측정 전에 호출하고 **실제 상태를 기록에 남긴다**
(`have_opencl: true, use_opencl: false`). 종료 경로에서 annotator 를 안전하게 분리한다.
5차 실행이 `exit=0` 으로 완주했다.

## 6. 이 기록이 말하는 것과 말하지 않는 것

- **말하는 것:** Isaac 입력의 주점 규약이 반 픽셀 어긋나 있었고 고쳤다. 고친 뒤 복원 높이의 편향이
  0.0002 mm 다. 실제 K·장착은 명목과 일치한다. `range_min_m` 의 앞 구간은 near clip 때문에
  관측 불가다. 같은 반 픽셀 문제가 저장된 Gazebo v1 에도 있다.
- **말하지 않는 것:**
  - **G1 은 통과하지 않았다.** ②a 2/18, ⑦a′ 10/54 가 남았고 `g2_allowed: false` 다.
  - **반 픽셀 수정이 인식 오차나 계열 D 를 개선한다는 증거는 없다**(§3.5).
  - ⑥(광학축 점검의 70 mm 불일치) 원인은 **미판정**이다.
  - ⑦b(점별 복원 오차)는 **기록 전용**이고 합격 조건이 아니다.
  - 보증 범위는 **검증한 판·배치와 사전에 정한 거리 × 화면 구간의 유효 표본**까지다.
    미검증 배치나 모든 점의 3차원 복원 오차는 보증하지 않는다.
  - **반 픽셀 수정이 검출 입력을 바꿨으므로 G2 의 5/9 와 정답 대조군 3/9 는 다시 무효다.**
    `primitive_length_m` 0.25 변경도 겹친다. 새 구성의 성적은 재실행으로만 확정된다.
