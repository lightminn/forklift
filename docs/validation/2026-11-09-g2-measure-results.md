## 4. 환경 멈춤 — GPU persistence mode 꺼짐 (M8 과 G5-2 의 재해석)

- **현상.**
  - 렌더 스텝의 world.step 이 벽시계 17.1 s 마다(중앙값, 대개 16.7–18.2 s) 0.5–1.3 s 걸렸다. 100 s 당 4–6 회였다.
  - 장면(hall·line_m)·배속(1.0·0.4)·계측 on/off 와 무관했다. 위상은 세션마다 달랐다.
- **드라이버 수준.**
  - 같은 순간 감시기의 `nvidia-smi -lms 200` 표본도 1.0–1.2 s 비었다. 드라이버 질의까지 막혔다는 뜻이다.
  - 주 스레드의 긴 호출 기록에는 겹치는 Python 호출이 없었다. GC 도 겹치지 않았다(gen2 는 세션당 1 회).
- **시작 시점(trace).**
  - r1c(16866, 08:27–11:40, 16 세션)에는 0 이다.
  - r1c2 에서 r1c_17(13:04–13:06)은 0 이다. r1c_18 에는 13:12:10.289 의 1.287 s 단발 하나가 있다. r1c_19 부터는 13:18:58.184 부터 주기적으로 멈췄다.
  - 두 스냅숏의 sim·src·deploy·config 는 같다(`run_transport.py` 해시 동일, 탐침만 다름). 우리 코드 변경이 원인이 아니다.
- **원인 대조(직접 관측).**
  - g2mf_01 실행 중 150 s 동안 프로세스 표에서 nvidia-smi 의 시작 시각과 소유자만 기록했다. 원기록은 ws1 `test_runs/live/rtb/g2mf_nvsmi_watch.jsonl` 이고, 대조 상대는 같은 세션의 `monitor/gpu.csv` 다.
  - 다른 사용자의 nvidia-smi 8 회(간격 17.1–17.6 s)마다 0.04–0.36 s 뒤 감시기 공백(1.05–1.38 s)이 시작했다. 8/8 일치했고, 그 창에서 그 호출 없이 생긴 공백은 0 이었다.
  - 같은 창의 우리 잡 안 nvidia-smi 78 회는 공백을 만들지 않았다. 잡 안에서는 cgroup 때문에 자기 GPU 만 보이고, 감시기가 그 GPU 를 계속 열어 둔다. 이 판단은 그 창의 잡 안 질의에 한한다. 잡 밖(로그인 셸)의 질의는 persistence 가 꺼져 있었다면 같은 멈춤을 만들 수 있다.
- **기전(총괄 확인, 이 문서의 자료로 재검증하지 않음).** 두 GPU 모두 persistence mode 가 꺼져 있었다. 잡 밖에서 모든 GPU 를 질의하면 놀던 GPU 1 이 그때마다 초기화·해제되고(커널 스레드 `irq/*-nvidia`·`nv_queue` 생성), 그동안 드라이버 전체가 막힌다.
- **해소.**
  - 총괄이 사용자 승인으로 persistence mode 를 켰다(재부팅하면 꺼진다; 확인 명령은 wiki `compute/ws1-isaac.md`). 켠 시각의 원기록은 총괄 쪽에 있다. 여기서는 감시 공백이 사라진 시각으로 잡는다.
  - g2mf_01 의 마지막 공백이 17:05:08 이다. F_02–F_05 에는 시작부 밖의 0.25 s 초과 world.step 이 0 이고, 최대가 0.044–0.064 s 다.
- **재해석.**
  - R1 결과의 "wall 팔이 긴 world.step(0.5–1.0 s) 뒤 명령 만료로 멈춤"은 r1c2 에서 쟀다. S-mark 의 1 s 픽셀 지연 p99 도 마찬가지다. 둘 다 이 환경 멈춤 아래의 값이다.
  - 픽셀 지연 p99 는 F 보충에서 환경 전 1.25–1.43 s, 후 0.58–0.59 s 다.
  - 이 문서 M8 의 긴 world.step 수도 같다.
  - 환경 멈춤 이전의 실행 중 멈춤은 r1c far 12 세션 중 1 회(r1c_05, 339 ms)와 G1 hall 8 실행 중 1 회(324 ms)뿐이다. F 켬 뒤 4 세션(AUTO 약 610 sim s)에는 0 이다.
