# ws1 live 세션 잡의 CPU 경합 조사 (2026-10-24)

질문(총괄): ws1 은 `task/cgroup` `ConstrainCores=yes`·`CR_CORE_MEMORY` 라 잡이 배정된 CPU 안에 갇힌다. live 세션 잡(`--cpus-per-task=4`, `--gres=shard:2`) 하나에 Isaac·SLAM·러너·학습 작업자가 같이 도는데, 다음 세 가지가 잡 안 CPU 굶주림과 관련이 있는가.
- 콘솔 연결 12.3 s 양방향 정지(CT-2 live, 잡 10499, 15:59:14–26 KST)
- 시작 직후 렌더 2.4–3.1 s
- Isaac 비결정성

## 결론

- **측정 구간에서 지속적인 CPU 부족은 보이지 않았다.**
  - 할당량 스로틀이 관측되지 않았다. 잡 cgroup 은 `cpu.max` = `max`·`throttled_usec` 0 이고, 조상(`ws1_slurmstepd.scope`·`system.slice`)도 `cpu.max` = `max` 다.
  - 잡은 CPU 4 개 가운데 약 1 개를 쓴다.
  - 배정된 CPU 는 73–79 % 가 논다.
- **순간 경합은 있다.** 잡 cgroup PSI `some` 이 약 18 % 이고, Isaac 스레드는 대기열에서 많이 기다린다.
  - 스레드 풀이 호스트 CPU 24 개 기준으로 잡혀 있다(`tbb.worker` 24–28 개, `carb.tasking` 약 24 개).
  - 이 풀이 논리 CPU 4 개(물리 코어 2 개)의 cpuset 에서 함께 깨어날 때 생긴다고 보는 것이 가장 잘 맞는다. 다만 스텝마다 동시에 깨어난다는 구체적 동작까지 확인하지는 않았다.
- **메인 스레드는 CPU 를 잘 받는다.**
  - 순수 계산 구간의 off-CPU 는 1–5 % 다.
  - off-CPU 비중이 큰 곳은 물리 스텝(`step.plain`) 약 20 % 다. 그중 스케줄러 경합분은 분리하지 않았다. 작업자·GPU·락 대기도 들어 있을 수 있다.
  - 그 off-CPU 차이(104.4 s)를 전부 없앤다고 가정하면 처리량은 약 2.5 % 늘고, 실시간 배율은 0.365 → 약 0.374 가 된다. 이것은 그 항목 하나만의 계산이고, 6 CPU 효과의 상한은 아니다.
- **12.3 s 정지:** 정지 동안 제어 틱은 1 s 넘는 틈 없이 계속 돌았다. 메인 루프가 CPU 를 못 받았다는 설명에는 강하게 반한다.
  - 원인은 확정하지 못했다. 후보는 터널·네트워크·브라우저 경로, 또는 서버의 연결별 송신 큐·`live-console` 스레드 정체다. 이 스레드는 Isaac 프로세스 안에서 자기 asyncio 루프를 돌리므로(`console/live/server.py` 모듈 설명·`threading.Thread(... name="live-console")`) GIL 을 메인 루프와 나눈다.
  - 같은 서버에 붙은 잡 내부 탐침(V3 실행들, 터널 없음)은 1.1 s 넘는 수신 틈을 본 적이 없다. 다만 다른 실행의 관측이라 그 사건의 대조군은 아니다.
- **시작 렌더:** 렌더 최장(2.5–3.2 s)과 1 s 넘는 틱 틈은 시작 직후에만 있고, 첫 픽셀 지연은 4.0–4.9 s 다. 초기화 지연으로 보이지만, 그 한 번이 CPU 계산 때문인지 작업자·GPU 동기화 때문인지는 이 자료로 가를 수 없다.
- **비결정성:** 벽시계로 비동기인 부분(SLAM 응답, 계획·학습 작업자)이 경합에 따라 다른 시뮬 시각에 들어오는 것이 설득력 있는 후보다. CPU 를 늘리면 시각은 바뀌지만 비동기성은 남는다.
  - CPU 작업자 수 자체를 비결정성 원인으로 채택할 근거는 없다. PhysX 문서는 조건을 붙여(같은 플랫폼·빌드, 같은 장면과 API 호출 순서, 일관된 시간 진행과 콜백 응답) 작업자 수와 무관하게 결정적이라고 적는다. 실행 전체의 결정성을 보장한다는 뜻은 아니다.

## 권고

1. **4 대 6 CPU A/B 는 지금 돌리지 않는다.**
   - 기대 효과가 작고 불확실하다.
   - 한 쌍에 CPU 10 개와 shard 4 개가 동시에 필요하다. 노드가 V3 배치로 차 있어(CPU 16/20, shard 8/8) 그 배치를 늦춘다.
2. **런처 기본값(`isaac_live.sbatch` `--cpus-per-task=4`)은 그대로 둔다.** 동시 실행 수도 바꾸지 않는다. 스레드 풀 크기와 작은 cpuset 의 조합이 경합 후보이고, CPU 를 늘렸을 때의 효과는 재지 않았다.
3. 12.3 s 정지가 다시 나면, 그 구간에서 메인 스레드와 `live-console` 스레드의 스케줄러 타임라인을 잰다(`perf sched timehist`, `sched_switch`·`sched_wakeup` 을 TID 로 거름).
   - 대부분 runnable 로 CPU 를 기다렸다면 그 스레드의 굶주림이다.
   - futex·poll 로 잠들어 있었다면 GIL·락·연결 쪽을 본다.
   - 평균 사용량이나 A/B 보다 직접적인 측정이다.
4. 스레드 풀을 cpuset 에 맞추는 것(`carb.tasking` 스레드 수, TBB)은 따로 검증할 실험으로 남긴다. 필요가 생기기 전에는 바꾸지 않는다.
5. 실차 Jetson AP 구성에서 같은 정지를 볼 때의 기준 시각과 부하는 [CT-2 콘솔 계획 5 절](../plans/2026-10-24-ct2-console-auto-item.md)에 있다.

## 측정

환경: ws1 = Ryzen 9 7900X, 논리 CPU 24(12 코어 × 2).
- Slurm `CPUEfctv=20`, `CoreSpecCount=2`. 표본 동안 CPU 8–11·20–23(논리 8 개 — specialized 4 + 미할당 4)은 99.6 % 놀았다.
- 표본 시점의 실행 잡은 V3 배치 `ct2v3` 4 개(10531·10532·10533·10535)로, 모두 우리 잡이고 읽기만 했다.
- 잡마다 cpuset 은 논리 CPU 4 개(물리 코어 2 개와 그 시블링)다.
- SLAM 브리지는 잡 cgroup 밖의 docker 컨테이너이고, `--cpuset-cpus "$CPU0"` 로 잡의 첫 CPU 에 고정된다. 잡 사용량에는 잡히지 않고, 6 CPU 로 늘려도 CPU 하나 고정은 그대로다.

표본 1(`cpu_sampler.py`, 360 s, 2 s 간격; 잡 cgroup `cpu.stat`·`cpu.pressure`, 프로세스별 스레드 `schedstat` 실행·대기 합):

- Isaac 대기의 대부분은 `tbb.worker`(합 2.0–2.7)와 `carb.tasking` 스레드들(각 약 0.14)이다.

- SLAM 컨테이너는 실행 0.02–0.12 CPU, 대기 비율 13–48 % 로 절대량이 작다.

- 러너 `perf` 타이머는 영역마다 벽시계 s·호출 수·최장·호출 스레드 CPU s 를 준다. 벽시계 − CPU 는 off-CPU 다(대기열 대기뿐 아니라 락·GIL·GPU 대기 포함).

## 교차검증

Codex(새 스레드)는 "굶주림 미확인 → A/B 보류·기본값 유지"를 지지했다. 아래 표현을 좁히라고 했고 모두 반영했다.
- '굶주림이 아니다' → 측정 구간에서 지속적 부족은 보이지 않았고, 순간 경합은 있다.
- '개선 상한 1–2 %' → `step.plain` 의 off-CPU 차이 104.4 s 만 없앤다고 가정한 계산이고 상한이 아니다.
- '원인은 네트워크' → 미확정이며, 서버의 연결별 송신 큐·스레드도 후보로 남는다.
- 시작 렌더의 성격 → 관측까지만 적는다.
- PhysX 멀티스레드 순서 → 작업자 수 자체를 원인으로 채택할 근거가 없다(문서의 조건 포함).
- 대기 합·PSI 의 뜻 → 처리량 손실이 아니다.

2 회차에서는 다음을 더 고쳤다.
- CPU 수의 영향을 배제한 문장 → 측정하지 않았다고 적음.
- '스로틀 없음' → 조상 cgroup 까지 확인해 적음.
- `step.plain` 의 경합분 → 분리하지 않았다고 적음.
- 영역 중첩·asyncio 스레드 구조 → 코드 근거를 붙임.
- 실시간 배율 → 실행마다 잰 중앙값 그대로 적음. 1 회차 질의에는 넷 다 0.365 로 뭉뚱그렸다.

Codex 가 다음 측정으로 고른 것은 권고 3 의 스케줄러 타임라인이다.
