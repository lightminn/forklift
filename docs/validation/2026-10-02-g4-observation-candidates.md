# G4-A — 덧붙인 관측 후보 (설계 기록)

계획: [G4 계획](../plans/2026-10-02-g4-observation-candidates.md). 도구: `tools/observation_candidate_design.py`, 커밋 전 작업 트리의
sha256 `2d618f45…`. 실행:

```
python -m tools.observation_candidate_design \
  --record artifacts/20261001_g2_rerun/perception/seed_0/result.json \
  --seeds 200:400 --workers 16 --json artifacts/20261002_g4_candidate_design/design_200_400.json
```

설정은 G2 재실행 seed 0 의 기록에서 재구성했다(`planner_config`·`geometry`·카탈로그 3 자산; 개발 9 seed 의 시나리오가 기록과 같음을
시험으로 고정). 설계 seed 200–399. G5 seed 1000–1029 와 100–129 는 도구가 거부한다. 대리 기준은 전면 보임 ≥ 1,500 화소이고,
통과하면 그 자리에서 정답 목표로 `plan_transport` 가 성공해야 "구함" 이다.

| 2 | (0.40, 1.20, 0.00) | 5 | 30 |

덧붙인 목록으로 171 / 200. 사전 고정한 탐욕 규칙으로 최대 3 개를 덧붙인 결과 29 seed 가 남았다 — 3 개 한도로 멈췄으므로, 이 격자로 그 29 개를 구할 수 없다는 뜻은 아니다(설계 JSON 의 `final_traces` 에 seed 별 경로가 있다).

## 개발 집합에서의 CPU 확인 (Isaac 아님)

- **seed 8:** 기존 5 개의 마지막(전면 0 화소, 가림) 뒤 첫 덧붙인 후보 (0.0, 2.1, −0.25) 에서 전면 5,646 화소, 접근 계획 성공. 관측 구간 누적
  15.95 m.
- **seed 1:** 대리 기준으로는 구해지지 않는다(기존 후보 4 에서 964 화소, 덧붙인 (0.4, 1.2) 은 8,090 화소지만 접근 계획 `expansion_limit`).
  seed 1 은 평면 예산 6 으로 후보 4 에서 이미 유효 검출되므로([G4-B](2026-10-02-plane-budget-six.md)) 덧붙인 후보에 가지 않을 것으로 본다 —
  G2′ 가 확인한다.
- seed 0·2·3·5·6 은 기존 후보에서 구해지고, seed 4·7 은 CPU 명목 접근 계획이 실패로 나오지만 G2 재실행 Isaac 에서는 완주했다 — CPU 접근
  계획은 보조 기준일 뿐이다(계획에 적은 한계).
