# ws1 Isaac 묶음 제출 검증 (2026-10-25)

계획: [docs/plans/2026-10-24-ws1-isaac-bundle.md](../plans/2026-10-24-ws1-isaac-bundle.md). 실행기 `tools/isaac_bundle.py`, 감싸개 `deploy/slurm/isaac_bundle.sbatch`. 원자료는 ws1 `test_runs/live/batch_eff/`(노드 표본 `gpu_node_*.jsonl`·`jobs_*.jsonl`·`docker_*.jsonl`, P2 `p2/`, P2b `p2b/`)와 `test_runs/riibotics/sbr4_bundle/`(P1)에 있다.

## 결론

- **노드 처리량이 늘었다. 기반 실패는 없다.**
  - 배치(P1, riib_scene 16 실행): 시간당 7.31 실행이다. 같은 장면의 단독 배치는 5.94 실행이라 **+23 %** 다.
  - live(P2): 묶음 4 세션이 단독과 같은 실시간 곡선으로 돌았다. GPU 한 장(shard 4)·CPU 8·24G 에 세션 4 개가 든다. 단독은 세션 하나가 shard 2·CPU 4·8G 를 잡는다.
  - 노드 전체로 보면 live 동시 세션이 4 에서 8 이 된다. 묶음 둘에 CPU 16·shard 8·48G 다. 노드 시뮬 처리량(Σ Δsim/Δwall)은 1.46 에서 약 2.9 로 늘어난다. 이것은 세션당 실측 배율(묶음 0.358–0.369)로 계산한 값이고, 8 세션을 동시에 돌려 재지는 않았다.
- **대가.**
  - 배치는 세션당 CPU 가 3.1 → 2.2 코어로 줄어 실행당 11–12 % 느리다(배치는 CPU 가 속도를 정한다).
  - live 는 Δsim/Δwall 이 단독 중앙 대비 −2 % 이고, 단독의 범위 0.358–0.367 안에 있다.
- **크기 상한.** riib 류(영상 기록)는 세션당 VRAM 이 4.15–4.47 GB 라 GPU 당 3 이 상한이다. live 세션은 3.9 GB 라 GPU 당 4 가 든다.

    - 즉 이 하락은 묶음의 CPU 경합이 아니라 콘솔 세션이 찾은 SLAM 그래프 크기 문제와 같은 현상으로 보인다. 근본 수정은 그 세션의 별건 계획이 맡는다.
    - `--pace-confirm`(기본 2): 느린 창이 평가 두 번 연속일 때만 물러난다(틱 정지는 바로).
    - 권장 하한은 단독 창 최소들 아래인 `--pace-floor 0.335` 로 낮췄다.
- **8 세션 동시 실측을 한 잡으로 할 수 없는 이유.** ws1 은 QOS 가 잡당 shard 를 4 로 막는다(`sacctmgr show qos` 의 maxtres `gres/shard=4`). 또 23.11 은 한 잡의 shard 를 한 GPU 에서만 준다(`MULTIPLE_SHARING_GRES_PJ` 꺼짐). 그래서 한 잡에 GPU 두 장 = 8 세션은 들어가지 않는다.
  - 동시 시작을 보장하는 후보는 이질 잡(`hetjob`, 구성요소마다 shard:4)이다. 실행기가 구성요소별로 `srun --het-group` 으로 세션을 띄워야 해서 별도 작업이다.
  - 그 전까지는 묶음 둘을 같은 목록(`--claim-dir`)으로 내고 대기열에서 둘이 함께 들어가는 때를 잰다.
- 미션 결과는 sw 세션 판정이다. 시작 74–84 s 에 `observe_replan_failed:invalid_start` 로 끝난 실행이 5 개였다(fix random_m s5·s7·s8, main·fix random_m s9). 이 seed 들은 단독으로 돈 적이 없어 묶음과의 관계를 가를 수 없다.
