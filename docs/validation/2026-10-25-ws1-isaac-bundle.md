# ws1 Isaac 묶음 제출 검증 (2026-10-25)

계획: [docs/plans/2026-10-24-ws1-isaac-bundle.md](../plans/2026-10-24-ws1-isaac-bundle.md). 실행기 `tools/isaac_bundle.py`, 감싸개 `deploy/slurm/isaac_bundle.sbatch`. 원자료는 ws1 `test_runs/live/batch_eff/`(노드 표본 `gpu_node_*.jsonl`·`jobs_*.jsonl`·`docker_*.jsonl`, P2 `p2/`, P2b `p2b/`)와 `test_runs/riibotics/sbr4_bundle/`(P1)에 있다.

## 결론

- **노드 처리량이 늘었다. 기반 실패는 없다.**
  - 배치(P1, riib_scene 16 실행): 시간당 7.31 실행이다. 같은 장면의 단독 배치는 5.94 실행이라 **+23 %** 다.
  - live(P2): 묶음 4 세션이 단독과 같은 실시간 곡선으로 돌았다. GPU 한 장(shard 4)·CPU 8·24G 에 세션 4 개가 든다. 단독은 세션 하나가 shard 2·CPU 4·8G 를 잡는다.
  - 노드 전체로 보면 live 동시 세션이 4 에서 8 이 된다. 노드 시뮬 처리량(Σ Δsim/Δwall)은 1.46 에서 약 2.86 으로 늘어난다. 이것은 세션당 실측 배율로 계산한 값이고, 8 세션을 동시에 돌려 재지는 않았다.
- **대가.**
  - 배치는 세션당 CPU 가 3.1 → 2.2 코어로 줄어 실행당 11–12 % 느리다(배치는 CPU 가 속도를 정한다).
  - live 는 Δsim/Δwall 이 단독 중앙 대비 −2 % 이고, 단독의 범위 0.358–0.367 안에 있다.
- **크기 상한.** riib 류(영상 기록)는 세션당 VRAM 이 4.15–4.47 GB 라 GPU 당 3 이 상한이다. live 세션은 3.9 GB 라 GPU 당 4 가 든다.

- **GPU 당 4 를 막은 것.** 세션 셋이 12.5 GB 를 쓴 상태에서 장치 여유(3.1–3.2 GB)가 3,950 MiB 보다 작았다. 그래서 실행기가 넷째 시작을 막았다(`gpu_full_waits` 1–2, `vram_waits` 4–5). riib 류의 실제 상한은 GPU 당 3 이다. 그런데 세션 셋(최대 4,465 MiB 씩)도 shard 셋의 몫(12,228 MiB)을 넘으므로, `sizes riib` 는 GPU 한 장(shard:4)·8 CPU·20G 를 낸다(재실행 10814 의 단일 세션도 4,464 MiB 로 shard 하나를 넘었다).
- **시간 한도.** 3 슬롯이면 8 실행이 세 번에 나눠 돈다. 그런데 `--time` 을 두 번 기준(2 h)으로 잡아, 마지막 실행 `sbr4_A_aisle_s6` 이 TERM(rc 143)으로 끝났다.
  - 그 실행은 93 분 동안 sim 236 s 에 머물렀다(sim/wall 0.04).
  - 마지막 40 분은 묶음에 혼자 남아 CPU 8 개를 쓸 수 있었으므로 CPU 경합 탓이 아니다. v-g2 는 A 팔에서 흔한 운반 정체로 본다.
  - 폴더는 `.timeout1` 로 옮겨 다시 돌렸다(10814). v-g2 의 판정은 이것과 무관하게 끝났다(D 3/7 대 A 0/7).
- **꼬리.** b1 은 89 분, b2 는 118 분에 끝났다. 그동안 b1 의 shard 가 먼저 놀았다. 실행 시간 합을 6 슬롯으로 나눈 이상적 소요는 1.42 h(11.3 실행/h)다. 그 대책으로 묶음 잡들이 한 목록을 공유하는 `--claim-dir` 를 넣었다(계획 2.1).
- **SLAM 브리지**(Slurm 밖): 컨테이너당 메모리 최대 0.18–0.74 GiB 다. 노드 메모리 검사의 브리지 몫을 760 MiB 로 잡았다.
