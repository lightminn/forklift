# ADR 0001: 개발·시뮬레이션·온보드 실행 플랫폼

- 상태: 채택 — **단 결정 2 중 접촉·관절 구동·제어의 동적 검증 부분만 [ADR 0004](0004-simulation-engine-and-insertion-depth.md)(2026-09-17)가 대체했다.** 같은 결정의 정적 센서·TF·`/clock` 기준선과 결정 1·3·4·5·6 은 유효하다.
- 결정일: 2026-09-10

## 맥락

노트북에서 반복 개발을 계속하면서 고성능 시뮬레이션은 원격 자원을 사용하고, 완성된 로봇은 네트워크 지연 없이 자체적으로 센서 처리와 제어를 수행해야 한다. 확정 센서는 D435i와 RPLIDAR이며, A2 세부형과 차체·구동 인터페이스는 아직 확인되지 않았다. DLS08 기반 모델은 상품 자료에서 만든 잠정 모델이므로 실제 차체 제약을 대신할 수 없다.

## 결정

1. 노트북 ROS 개발 기준은 **Ubuntu 24.04 컨테이너 + ROS 2 Jazzy**로 한다. 호스트의 임의 Python 환경에 ROS 패키지를 섞지 않는다.
2. **Gazebo Harmonic**으로 센서 메시지·TF·`/clock` 의 정적 기준선을 만든다. **← 이 부분은 유효하다.** 이미 만든 장면 생성기와 EPAL·v1 캡처는 [ADR 0004](0004-simulation-engine-and-insertion-depth.md) 가 읽기 전용으로 동결했다.
   ~~이어서 접촉, 관절 구동과 제어를 단계별로 검증한 뒤 결과 근거로 유지 여부를 판단한다.~~
   ⚠️ **취소선 부분만 [ADR 0004](0004-simulation-engine-and-insertion-depth.md) D1 이 대체했다 (2026-09-17).** 접촉·관절 구동·제어의 동적 검증은 Isaac Sim 이 맡는다. 그 검증은 이 ADR 이 **예정했을 뿐 구현되지 않았으므로, 폐기되는 것은 계획이지 코드가 아니다.**
3. 기존 **MuJoCo** 경로는 빠른 모델 로딩, 운동학, 무부하 안정화와 렌더 검사에 유지한다. Gazebo 통합 시험이나 실제 주행 증거를 대신하지 않는다.
4. 원격 자원은 시뮬레이션, 렌더링, 학습과 장시간 실험을 맡는다. 실제 로봇의 센서 처리·계획·제어 루프는 온보드 컴퓨터에서 실행한다. 노트북 또는 원격 서버와의 네트워크 연결을 실시간 폐루프 제어의 필수 조건으로 만들지 않는다.
5. 온보드 후보 기준은 **Jetson Orin Nano Super Developer Kit 8GB + JetPack 7.2.1의 Ubuntu 24.04 + ROS 2 Jazzy**다. D435i와 RPLIDAR의 ARM64 실물 검증을 통과하기 전에는 이 조합을 최종 배포 버전으로 동결하지 않는다.
6. 승인된 개발 컨테이너 구성은 진행할 수 있지만, 차체 수령 전에 차체 전용 ROS 패키지·구동기 계약·가상 기본 파라미터를 만들지 않는다.

ROS 2 Jazzy와 Gazebo Harmonic의 조합은 [Gazebo 공식 ROS 설치 안내](https://gazebosim.org/docs/harmonic/ros_installation/)를 기준으로 한다. Jetson 후보와 센서 검증 경계는 [하드웨어 정본](../hardware.md)에 둔다.

## 결과와 제약

- 노트북과 온보드 후보의 OS·ROS 계열을 맞춰 메시지·launch·설정 차이를 줄일 수 있다.
- 원격 계산 자원을 활용하면서도 로봇의 정지 경로와 기본 제어가 원격 연결에 의존하지 않도록 설계한다. 통신 단절 시 동작과 정지는 실제 제어기 구현 후 별도로 검증한다.
- x86_64 컨테이너 성공은 Jetson ARM64, 카메라 커널 경로, USB 대역폭 또는 실제 구동기 동작을 증명하지 않는다.
- Gazebo와 MuJoCo의 URDF/MJCF 모델은 형상·관절 정의를 공유할 수 있지만 접촉·마찰·구동·센서 결과의 동등성을 가정하지 않는다.
- 차체와 센서 장착을 측정하면 모델 파라미터, TF, 전원·열 설계와 실시간 성능 기준을 다시 결정하고 별도 검증 기록을 남긴다.
