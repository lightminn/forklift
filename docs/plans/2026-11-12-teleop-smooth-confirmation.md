# 매끄러운 텔레옵 확인 실행 — 등록 (2026-11-12, 결과 전 고정)

배경:
- [기존 기록 확인](../validation/2026-11-12-teleop-realtime.md): f 1.0(K)에서 TELEOP 배율 0.926, pacing ok 0.587, 직접 hold 출력 40–57 %.
- [설계](../design/2026-11-12-teleop-pacing.md).
- 사용자 요구는 "실시간으로 되는지"와 "매끄럽게 되길"이다. 끊김을 실제로 본 실행이나 그때의 배속은 알려지지 않았다.

총괄 결정(2026-11-12):
- 선언 배속을 낮춰 매끄러움을 얻는다. 조건은 `FACTOR=0.9` + `FORKLIFT_LIVE_CATCHUP_STEPS=6` 이다.
- pacing 판정(안전 게이트)·텔레옵 허가·코어는 바꾸지 않는다.
- 런처 기본(f 0.4, catch-up 0)도 바꾸지 않는다.
- 정확 키 캐시(`drive_permission` 밴드·own_lookup)는 별도 PR 이다. 이 실행은 캐시 없는 main 으로 돈다.

## 1. 근거 — 왜 f 0.9 + catch-up 6 인가

- **판정은 상대값이다.** `Pacer` 는 1 s 창 배율이 `0.9 × target_factor` 아래이거나 한 스텝 간격이 0.25 s(절대)를 넘으면 실패한다. 회복은 1 s 연속 유지다(`pacing.py`). 목표는 `--live-factor`(런처 `FACTOR`)로 세션 전체에 걸린다.
- **반사실 재생**(`factor_replay.py`, 결과는 이 문서 부록). 지연 B 배치(f 1.0, K) 12 세션의 스텝별 일 W 와 잠 overshoot ε 를 실제 `Pacer` 로 다시 돌렸다.
  - 실행기는 대기가 0 이어도 `sleep(0)` 을 부르므로 ε 를 매 스텝 넣는다(Codex P2-2).
  - f 1.0 K 재생은 측정값을 재현한다:

| | 재생 | 측정 |
|---|---|---|
| 배율 | 0.925 | 0.926 |
| ok | 0.589 | 0.587 |
| hold 출력 forward / reverse / left / right | 0.567 / 0.401 / 0.533 / 0.503 | 0.570 / 0.400 / 0.516 / 0.492 |

| 팔 | f | 재생 배율 | 문턱 | TELEOP ok(중앙, 세션 최저) | 직접 hold 출력 |
|---|---|---|---|---|---|
| K(catch-up 6) | 0.95 | 0.905 | 0.855 | 0.943, 0.856 | 0.62–1.0 |
| K | **0.9** | 0.877 | 0.81 | **1.0, 1.0** | 1.0 |
| K | 0.85 | 0.843 | 0.765 | 1.0, 1.0 | 1.0 |
| L(catch-up 0) | 0.5 | 0.460 | 0.45 | 0.731, 0.616 | 0.55–0.76 |
| L | 0.45 | 0.421 | 0.405 | 1.0, 1.0 | 1.0 |
| L | **0.4** | 0.380 | 0.36 | **1.0, 1.0** | 1.0 |

- **재생의 한계(Codex P2-1).** 기록에서는 pacing 거부 중 텔레옵 허가 계산을 생략했다(`teleop_drive.py` 219). 거부가 풀리면 그 계산이 더해지므로, 재생은 연속 출력 상태의 일을 과소평가한다. 그래서 재생은 f 0.9 를 지지하는 근거일 뿐 보장이 아니고, 이 실행으로 확인한다.
- **L 0.4 의 여유는 얇다**(0.380 대 0.36, 약 5.5 %). 결과에 창 최솟값과 문턱 아래 스텝 수를 함께 낸다(총괄).
- **나이 한도는 벽시계 판정이다**(Codex P2-3). 명령·영상 나이 한도는 설정값을 /f 로 늘려 벽시계로 검사한다(`run_transport.py` 3400, `arbiter.py` 568). catch-up 6 의 명령/영상 한도는 f 0.9 에서 278/500 ms, f 0.4(catch-up 0)에서 750/1250 ms 다. 같은 sim 이동량 노출을 지키려는 기존 설계이고, 벽시간 반응성이나 안전 여유가 늘어난다는 뜻은 아니다. 절대 stall 문턱 0.25 s 는 그대로다.

## 3. 판정 (결과 전 고정, `tools/teleop_realtime_report.py --factor F --verdict --slots <그 팔의 등록 이름 셋>`)

팔마다 따로 판정한다.

**자리(slot)와 재실행.**
- 팔마다 등록 세션 세 자리(`ts_lists.py` 이름)가 있다.
- 원래 세션이 CPU 겹침 규칙에 걸리면(다른 사용자 CPU 가 1 코어를 넘은 표본이 5 % 초과, 지연 1e (c)) 그 자리만 한 번 다시 돈다. 이름은 `<원래 이름>_re` 이고 `ts_submit.sh … -- <이름>` 으로 낸다.
- 원래가 유효하면 원래를 쓴다. 재실행도 걸리거나 재실행의 재실행이 있으면 그 자리는 미평가다.
- 팔이 통과하려면 **세 자리 모두** 판정 가능한 세션이 하나씩 있고, 그 세 세션이 아래 규칙을 모두 지켜야 한다(Codex 2라운드 P2-3).
- 판정 도구는 그 팔의 등록 이름 **서로 다른 셋**을 `--slots` 로 받는다. 셋이 아니거나, 다른 팔·원본 없는 재실행·모르는 이름이 섞이면 미평가다(3라운드 P2-1).
- 요약 통계는 판정에 고른 세션만으로 낸다(3라운드 P3).

**판정 가능 조건(하나라도 없으면 미평가, 미평가는 통과가 아니다; P2-2).**
- CPU 표본기 기록이 있어야 한다.
- live 로그가 `read_live_log` 를 통과해야 한다(잃은 줄·잘린 부분 없음).
- `tick_trace.npz`(pacing 창)가 있고, TELEOP 틱의 95 % 이상을 덮으며, 창 값이 하나 이상 있어야 한다(3라운드 P2-3).
- hold 일곱 종류가 모두 있어야 한다: loaded_forward·forward·reverse·left·right·lift_up·lift_down.
- 각 hold 의 [시작, 끝) 이 틱 기록으로 덮여야 한다. 시작 이전과 끝 이후에 틱이 있어야 한다는 뜻이다.
- result.json 에 안전 필드가 제 형식으로 있어야 한다: `forbidden_pocket_contacts`(목록), `obstacle_layer.unpermitted_entries`·`unpermitted_dir_entries`(정수), `scene_layout.obstacles`(비지 않은 목록), 외곽 형상. `scene_damaged` 만은 없거나 null 일 수 있다. 러너가 손상 때만 쓰기 때문이다(3라운드 P2-2).
- spool `slam.control`(완전성 검사 통과)이 있고, TELEOP 참값 행이 1 개 이상이어야 한다.

**규칙(판정 가능한 세션마다 모두).** hold 의 값은 probe 의 [start_mono, end_mono) 를 직전 틱 상태로 이어 붙여 적분한다(Codex 2라운드 P2-1: 안쪽 첫·끝 틱이 아니라 hold 경계).
1. **pacing 실패 0.** TELEOP 연속 틱에서 ok 다음에 not-ok 가 오는 일이 없어야 한다(1라운드 P2-4: 회복에 1 s 가 걸리므로 '끊김 ≤ 100 ms' 는 사실상 실패 0 이다).
2. **TELEOP 진입 not-ok ≤ 100 ms.** 각 TELEOP 구간의 첫 틱이 not-ok 이면, 첫 ok 틱까지의 시간이 100 ms 이하여야 한다(2라운드 P3: 규칙 1 은 앞 모드에서 이어진 not-ok 를 세지 않는다). ok 틱 없이 구간이 끝나면 길이와 상관없이 실패다(3라운드 P3).
3. **직접 구동 hold 출력 ≥ 0.95.** 종류별(loaded_forward·forward·reverse·left·right), 세션마다. 중재기 속도 목표가 0 이 아닌 시간 ÷ hold 시간이다.
4. **출력 끊김 ≤ 100 ms.** 직접 구동 hold 에서 첫 출력 뒤 출력이 0 인 가장 긴 구간이다.
5. **pacing not-ok 구간 ≤ 100 ms.** 모든 직접 hold(구동·승강)에서 가장 긴 연속 not-ok 구간이다.
6. **회전 첫 출력 ≤ 100 ms.** left·right 가운데 ok 로 시작한 hold 만 이 규칙으로 판정한다. not-ok 로 시작한 hold 는 규칙 2·5 가 판정한다.
7. **안전 비열화 0.**
   - `scene_damaged` 없음. 적재 운반(`loaded_forward`)의 적재 외곽 겹침은 러너가 이것으로 기록한다.
   - `forbidden_pocket_contacts` 0.
   - 러너 참값 평가기의 `unpermitted_entries`·`unpermitted_dir_entries` 0. 이 평가기는 AUTO 에서만 돈다(Codex 설계 3라운드 P2: 멈춘 미션에서는 돌지 않는다).
   - TELEOP 의 모든 제어 행에서, 참값 뒤 차축 자세(spool `slam.control` 4–6, 0 열은 로그 `tick_t` 와 같은 시계)의 hull 이 장면 장애물과 겹치는 틱 0. 적재 외곽 여유는 무적재 틱에도 계산한 보고값이라 판정에 쓰지 않는다.
   - 보호 판정 유지는 실행이 아니라 코드로 보인다. 이번 변경은 실행 설정(배속·catch-up)뿐이고, 게이트·허가 코드는 그대로다.

**함께 보고만 하는 것.**
- 팔별 AUTO 대조: 배율, ok, 미션 성공.
- TELEOP 배율, pacing 창 최솟값·p1·문턱 아래 스텝 수(L04 는 필수, 창은 step_end 로 재구성한 근사).
- 승강 변화량, 영상 hold 결과. 영상 hold 의 `permit:limit` 은 미진단이라 판정에서 뺀다.
- 참값 최소 여유(hull·적재 외곽).

**결과에 따른 처리(Codex 2라운드 P2-4: 검증한 점으로만 적는다).**
- K09 가 통과하면 결과 문서와 콘솔 텔레옵 도움말에 "검증한 설정: f 0.9 + catch-up 6 에서 텔레옵이 끊기지 않았다(line_m, 직접 조작 hold)"를 적는다.
  - 'f ≤ 0.9' 처럼 범위로 넓히지 않는다. 배속이 낮다고 단조롭게 좋아지지 않는다. 예를 들어 f 0.02 의 스텝 간격 417 ms 는 절대 stall 문턱 250 ms 를 넘는다.
- L04 가 통과하면 "콘솔 기본(f 0.4, catch-up 0)에서도 끊기지 않았다"를 같은 범위로 적는다.
- 통과하지 못한 팔은 실패 규칙과 원인 분류만 보고하고, 문구를 적지 않는다. 미평가인 팔도 문구를 적지 않는다.
- catch-up 6 의 런처 기본 승격은 이 결과를 근거로 나중에 따로 결정한다(총괄).

## 4. 주장의 범위

- 한 장면(line_m)·seed·짧은 hold 열의 예비 확인이다. 장시간 운용이나 다른 장면에서 "끊기지 않는다"는 일반화 근거가 아니다(Codex P2-4).
- 판정은 직접 조작 다섯 종류(loaded_forward·forward·reverse·left·right)와 승강에 한정한다. 영상 조작은 들지 않는다.
- 참값 겹침 검사는 이 장면 hold 들의 넓은 공간에서 한 것이다. 장애물 가까이의 텔레옵 안전을 시험하는 것은 아니다.
- 캐시 효과는 이 실행에 들지 않는다. 캐시가 머지된 뒤 다음 Isaac 배치에서 같은 f 로 대조해 보고만 한다.
- "캐시로 f 1.0 배율이 0.94–0.96 이 된다"는 앞선 추정은 거부 해제 뒤 늘어나는 허가 계산(P2-1)을 빠뜨린 것이라 철회한다.

## 5. 자체 검토

- Codex 1 라운드(배속 분석, 이 문서 전) 지적과 처리:
  - P1: 없음.
  - P2-1 스텝당 일 불변 가정: 재생을 근거로만 쓰고 실행으로 확인한다. 캐시 추정을 철회했다.
  - P2-2 ε 누락: 재생을 고쳐 측정값을 재현했다.
  - P2-3 나이 한도: 1 절에 적었다.
  - P2-4 끊김 기준·주장 범위: 규칙 1·3 과 4 절.
  - P2-5 0.4 와 1.0 의 분리: 팔을 둘로 나눴다.
  - P3: 표현을 고쳤다(창 시각은 step_end 근사, 감속 비율의 기준).
- Codex 2라운드(등록 문서, fb135eeb) 지적과 처리:
  - P1: 없음.
  - P2-1 hold 경계 적분: 도구가 [start, end) 를 직전 틱 상태로 적분한다. 덮이지 않는 hold 는 미평가다. 시험: `test_a_hold_is_judged_over_its_own_edges`.
  - P2-2 결측 통과: 판정 가능 조건을 두었다. 표본기·`read_live_log`·창·hold 일곱 종류·덮임·안전 기록이 없으면 미평가다.
  - P2-3 세 자리: 자리·재실행 규칙과 `--slots`(그 팔의 등록 이름, 다른 팔·원본 없는 재실행·모르는 이름은 미평가)를 두었다. 시험: `test_three_registered_slots_must_each_hold_one_judged_session`.
  - P2-4 문구 일반화: 검증한 설정으로만 적는다(3절).
  - P3 진입 not-ok: 규칙 2 를 추가했다. 안전 시각·hull 범위는 확인됐고, 적재 외곽 보고값의 성격을 적었다.
- Codex 3라운드(새 스레드, 3b5bb93a; 이전 스레드는 메모리 부족으로 중단):
  - P1: 없음.
  - P2-1 세 자리: 서로 다른 등록 이름 셋을 요구한다.
  - P2-2 안전 필드 결측: 형식 검사, 결측은 미평가.
  - P2-3 빈 창: TELEOP 덮임 95 % 와 창 값 존재를 요구한다.
  - P3: ok 없이 끝난 진입 구간은 실패로 하고, 요약은 고른 세션만으로 낸다.
  - 2라운드 P2-1·P2-4 는 해소로 확인됐다.
- Codex 4라운드(1·2 라운드 스레드에 3라운드 지적과 처리를 붙여 이어 감): **새 P1/P2 없음.** 반례(자리 셋, 원본 없는 재실행, 다른 팔, `_re_re`, 안전 필드 결측, 빈 창, 덮임 95 % 미만, ok 없는 진입)가 막히고, B01·B02 기록이 미평가 없이 판정됨(창 덮임 약 99.88 %)을 확인했다. 이로써 기준을 고정한다.
