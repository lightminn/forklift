# live 기본을 사전 지도 위치 추정으로 — 구현 계획 (S3, v3, 2026-10-26)

상위: [SLAM 그래프 크기 묶기](2026-10-25-slam-bounded-graph.md)(후보 A 확정, 6.2–6.3) · [상시 운용 세션의 SLAM](2026-10-20-slam-localization-session.md)(PR #62: 위치 추정 경로 L1–L7, 이미 main 에 있음) · [slam_link_failed](2026-10-25-slam-link-failed.md)(지금 기본값인 임시 완화)

사용자 결정(2026-10-26, 총괄 전달): A — 장면마다 미리 만든 지도에서 운행 중 위치만 추정 — 를 채택 후보로 확정했다. live 기본 전환은 이 계획이 수렴한 뒤 총괄에 요약 보고하고 그때 한다.

## 1. 목표

- 콘솔 live 세션이 장면의 조사 지도 묶음 위에서 위치 추정으로 돈다. sim 1 h 연속 운용에서 keyframe 처리 시간이 모두 1 s 미만이다(상위 계획의 목표).
- 묶음이 없는 장면은 지금처럼 mapping(임시 완화 설정)으로 돈다. 어느 쪽으로 도는지 화면·기록에 보인다.
- 정확도·임무 결과가 지금 기본값보다 나빠지지 않는다.

## 2. 이미 있는 것과 없는 것

있음(PR #62 S3·L3–L7, main):
- 런처 `MAP_BUNDLE`·`MAP_START_POSE`(`deploy/console/isaac_live.sbatch` 34–62), 감독자의 세션 단위 묶음 해시(`tools/live_supervisor.py` 25–28), 브리지의 묶음 적재·L4 시작 검사(`slam_map_mismatch`·`slam_map_not_loaded`·`slam_not_localized`), runner 의 묶음 대조(`run_transport.py` 3459–3480, ① 재계산에서 고친 행)와 조사 격자의 정적 층 적재, 결과 기록·화면의 `map_id`(`mission/results.py`, `console/web/js/ui.js`).
- 조사 에폭 런처(`deploy/console/slam_survey.sbatch`, SCENE_FILE·CYCLE 지원)와 묶음 작성기·검사(`tools/slam_survey_bundle.py`: finalize·received·nodes·world(V2′)·start·coverage·moving).

없음:
- 장면별 묶음과 그것을 고르는 등록부. 지금은 운용자가 `MAP_BUNDLE` 을 손으로 준다.
- seed 가 다른 세션의 묶음 재사용. `run_mismatches` 는 seed·`slam_noise_seed` 가 조사와 같아야 통과시킨다(`slam_map.py` 140–160). CT-2 시험은 seed 0–4 를 쓴다.
- CT-2 장면의 team-spec 조사 묶음(잡 11393·11394 진행 중).

## 3. 결정 (잠정)

- **D1 묶음 등록부.** `config/slam_map_bundles.yaml` 에 장면 파일(내용 해시)·오도메트리 모형별로 묶음 폴더, 전체 `map_id`, 출발 자세를 적는다.
  - 묶음 파일은 ws1 `artifacts/slam_bundles/<장면>_<모형>_<map_id 앞 12>/` 에 둔다. 저장소에는 등록부만 커밋한다(묶음은 큰 이진 파일).
  - 출발 자세는 `map ← base_link` 다(v2, Codex P3). 장면의 `start_rear` 를 그대로 쓰지 않는다.
    - 조사 묶음의 start 검사가 map ← world 가 항등임을 확인했으므로, 값은 조사 실행 첫 노드 시각의 참값 base 자세로 정한다. 이는 후축 자세에서 후축 오프셋(measured URDF −0.34 m)만큼 진행 방향으로 옮긴 값 (xᵣ + 0.34 cos ψ, yᵣ + 0.34 sin ψ, ψ) 과 같다.
    - 등록부 작성 도구가 묶음 manifest 와 조사 실행 기록에서 이 값을 계산한다. 손으로 옮겨 적지 않는다. yaw ≠ 0 인 시험을 둔다.
- **D2 런처 기본.** `isaac_live.sbatch` 가 `SCENE_FILE` 과 `ENCODER_MODEL` 로 등록부를 찾아, 있으면 `MAP_BUNDLE`·`MAP_START_POSE`·`EXPECTED_MAP_ID` 를 채운다.
  - 없으면 mapping 이다. `MAP_BUNDLE=none` 은 mapping 을 강제한다(대조 실험·조사 에폭용).
  - **등록부의 map_id 를 적재 검사까지 넘긴다(v2, Codex P2).** 지금 감독자는 `load_bundle(folder)` 로 폴더에서 읽은 id 를 세션의 기대 id 로 삼는다(`tools/live_supervisor.py` 272–280). 그래서 폴더가 다른 묶음(V2′ 불합격 묶음 포함)을 가리켜도 통과한다. 감독자는 `--expected-map-id` 를 받아 `load_bundle(folder, expected)` 로 대조하고, 다르면 첫 에폭 전에 끝낸다. 시험은 다른 id 의 폴더 거절, 같은 id 통과다.
  - 고른 결과(등록부 행, map_id, mapping 강제 여부)를 세션 기록(`supervisor.jsonl`)과 상태 메시지의 `slam.mode` 에 남긴다.
- **D3 seed 재사용(장면 파일 배치만).**
  - 지금의 대조(`slam_map.run_mismatches`)는 다음을 비교한다.
    - `seed`
    - `SHARED_ARGUMENTS`(`prism_colliders`·`slam_noise_seed`·`slam_noise_spec`)
    - `SHARED_INPUTS`(`base_scene`·`forklift_urdf`·`factory_layout`·`lidar`·`obstacle_layer` 의 파일 내용)
    - 기반 장면 폴더의 USD 해시(`scene_sha256`)

    여기에는 `scene_file` 이 없다(① 재계산에서 발견). 기반 장면이 같으므로 line_m 묶음을 random_m 실행에 써도 지금은 거절되지 않는다.
  - `--layout scene` 에서 seed 는 장면 기하를 바꾸지 않는다. `make_factory_scenario`·`make_scenario` 의 seed 는 다른 배치에서만 쓰이고, 장면 파일 배치는 파일의 visuals 를 그대로 놓는다. seed 는 잡음(`noise_seed`)에만 쓰인다(`run_transport.py` 2745–2818·3505·4083).
  - 바꾸는 것:
    - (a) `--layout scene` 실행에서만 `scene_file` 을 내용으로 필수 비교한다. 전역 `SHARED_INPUTS` 에 넣으면 양쪽 다 `scene_file` 이 없는 공장 홀 묶음이 전부 거절된다(v2, Codex P2: CPU 반례로 확인). 다른 필수 입력이 없을 때 거절하는 규칙은 완화하지 않는다.
    - (b) `--layout scene` 실행에 한해 `seed` 와 `slam_noise_seed` 의 일치를 요구하지 않는다. `slam_noise_spec`(잡음 모형)은 그대로 비교한다.
    - (c) 공장 홀 배치는 seed 가 소품 배치를 바꾸므로 지금처럼 비교한다.
  - 잡음 seed 가 다른 위치 추정은 S2 재생에서 이미 했다(지도 실행과 입력 실행의 잡음이 달랐다). Codex 도 `args.seed` 참조를 전수 확인해, 장면 파일 경로에서는 배치 생성 함수를 부르지 않고 팔레트·visuals·시작 자세를 파일에서 읽는다는 데 동의했다. auto 선택 순서는 잡음이 바꾼 추정 자세를 거쳐 간접적으로 달라질 수 있지만, 지도 대상 세계는 아니다.
  - 시험(장면 파일):
    - seed·잡음 seed 만 다른 실행은 통과한다.
    - 장면 파일 내용이 다르면 거절한다.
    - `scene_file` 해시가 없는 묶음은 거절한다.
  - 시험(공장 홀):
    - 같은 seed 는 통과한다(`scene_file` 없음).
    - 다른 seed 는 거절한다.
- **D4 위치 추정 설정.** 변형 J(`tools/slam_localization_params.py`, 버퍼·chain 3/3, 루프 켬, link 3.0 m, 루프 창 3.0 m·거리 2.0 m). S2 에서 J 두 번이 판정을 채웠다.
- **D5 묶음 수락 검사와 재조사(총괄 결정 2026-10-26).**
  - V2′(위치 최대 ≤ 0.10 m·방향 최대 ≤ 0.03 rad, 우리 잠정값, PR #62 계획 413 행)는 지도 묶음의 **수락 검사**다. 등록부에는 `slam_survey_bundle.py` 의 검사를 모두 통과한 묶음만 오른다.
  - 지도는 한 번 만들어 쓰는 산출물이다. 그래서 불합격이면 같은 설정으로 다시 조사한다(장면당 최대 3 회). 3 회 모두 불합격이면 원인과 숫자를 총괄에 올리고, 기준 조정은 총괄이 판단한다.
  - V2′ 는 대리 지표다. A 채택의 본 기준은 그 묶음 위의 실제 위치 추정 정확도다(4 장 3). 0.10 m 를 고칠 필요가 보이면 그 정확도를 근거로 올린다.
  - 조사 설정(S = 지금 survey 설정, M = 루프 탐색 완화값)은 장면마다 다르게 고르지 않고 하나로 정한다. 근거는 반복 조사의 V2′ 통과율과 keyframe 최대다. 조사 에폭도 live 미션이다.
- **D6 재조사 조건.** 장면 파일·URDF·LiDAR 설정·충돌체·오도메트리 모형이 바뀌면 묶음은 대조에서 거절되고(`slam_map_mismatch`, 감독자가 즉시 멈춤), 등록부를 새 조사로 바꿔야 한다. 이 절차를 운용 문서에 적는다.
- **D7 운용 중 위치 상실.** slam_toolbox 위치 추정에는 전역 재위치가 없다. 조사 덮개 밖으로 나가거나 크게 어긋나면 돌아오지 못할 수 있다. 이 계획은 막지 않고 잰다.
  - 4 장 3 의 순환은 고정 경로다. far recognition·recover·teleop 로 조사 경로를 벗어나는 경우는 잡지 못한다(v2, Codex P3).
  - 그래서 짧은 확인을 한 번 둔다. 수락된 묶음 위에서 teleop 으로 조사 경로 밖 통로(reference_path 에서 3 m 넘게 떨어진 곳)에 들어갔다가 돌아온다.
  - 기록할 것: 범위 밖 체류 시간·거리, 복귀 뒤 위치 오차, `slam_not_localized`·무응답 발생 여부.
  - 문제가 보이면 별도 계획으로 한다.
- **D8 지금 기본값 유지.** mapping 경로의 임시 완화 설정은 그대로 둔다(묶음 없는 장면용).

## 4. 단계

1. **조사(완료, 5 장):** line_m·random_m team-spec 조사 에폭과 반복. 설정은 S, 장면마다 수락된 묶음이 있다.
2. **구현(시험 먼저):**
   - D1 등록부와 그 작성 도구(출발 자세 계산)
   - D2 런처 선택(쉘 시험)과 감독자의 `--expected-map-id`
   - D3 대조 변경(시험은 D3 에 적은 다섯 가지)
   - 상태의 `slam.mode`
   - 1 시간 순서(아래)의 CPU 시험(직선 검사와 제출 수락)
   - 판정기(시험 먼저): sim 시각 창과 관측 길이, 응답·적용 자세의 위치·방향 중앙·최대, 적용 지연·보정 점프, 하역 결과, L/R 공통 구간 비교. 지금 `slam_v5_report.py` 의 출력만으로는 이것을 다 낼 수 없어 확장하거나 새로 만든다(v3, Codex P3).
3. **Isaac 확인(확인 전용, A 채택의 본 기준, v2).**
   - **1 시간 순서.** CT-2 의 이송 목록은 유한하다. 같은 쌍을 다시 내면 `already_there`, 찬 목적지는 `destination_occupied` 다. 장면 파일 세션은 처음 자리를 목적지로 등록하지 않는다(`sim/isaac/scene_file.py` 232–249). 그래서 같은 에폭 안에서 끝없이 이어지는 순서를 정한다.
     - 배달된 팔레트는 놓인 곳에서 바로 다시 제출할 수 있다(`targets.check_submit`: delivered 허용). fixed 대기열도 이를 받는다. auto 선택기는 delivered 를 빼므로 fixed 순서를 쓴다. Codex 는 합성 완료 사건으로 fixed 항목 240 개를 한 에폭에서 처리하는 것을 확인했다(`FINISHED_KEEP=50` 은 기록 보관 한도일 뿐이다).
     - **팔레트 하나를 목적지 셋에 돌린다(v3).** line_m 은 P-1:D-1, P-1:D-2, P-1:D-3, P-1:D-1, … 이고, random_m 은 P-4 로 같은 꼴이다. 나머지 팔레트는 처음 자리에 그대로 둔다.
       - v2 의 "팔레트 둘·빈 칸 하나" 순서는 line_m 에서 막힌다(Codex 2 회차 P2). 목적지가 한 줄(y −8.946 m, yaw 0; x 3.000·1.938·0.876 m)이라, P-2 가 D-2 에 있으면 D-1 의 P-1 을 다시 집는 정렬·삽입 직선이 P-2 와 부딪친다(팽창·여유 0 에서도 `straight_collision`).
       - 제출 수락만 보는 CPU 시험은 이를 놓친다.
     - 시험(CPU): 실제 장면 정의에서 순서의 매 상태마다 정렬·삽입·인출·하역 직선을 `pallet_mission` 의 직선 검사로 확인한다(그 상태의 다른 팔레트를 장애물로 넣는다). 매 제출도 `Targets.check_submit` 이 받아들이는지 본다. 걸리는 순서는 쓰지 않는다.
     - **관측 길이와 진행량(v3, Codex P3).**
       - L 의 실제 관측 길이(첫 응답부터 마지막 응답까지의 sim 시각)는 ≥ 3,600 s 여야 한다. 다리 수(24)는 목표가 아니라 최소다. 일찍 끝나면 순서를 이어 붙여 sim 1 h 를 채운다.
       - 고정된 sim 600 s 창 여섯 개 모두에서 다리 1 개 이상 완료, 처리 keyframe 50 개 이상이어야 한다. 시간축은 sim 시각이다. 기존 `slam_v5_report.py` 의 벽시계 창(`queued_mono`, 마지막 불완전 창 제외)은 그대로 쓰지 않는다.
       - 멈춰 선 1 h 는 비용 판정이 아니다.
   - **두 팔.** 수락 묶음 위의 위치 추정(L)과 지금 기본값 mapping(`MAP_BUNDLE=none`, R)을 같은 스냅숏·team-spec·장면·seed·순서·실행 환경으로 짝지어, 번갈아(같은 묶음 잡 안에서 섞어) 장면마다 두 seed 씩 돌린다(seed 는 조사의 0 과 다른 1·2).
     - slam_link 계획 6.3 표(reported, 500–600 s)는 오도메트리와 길이가 달라 참고 자료로만 쓴다(v2, Codex P2).
   - **판정(L 이 통과해야 한다):**
     - keyframe 모두 < 1 s, slam_link_failed·무응답 없음, 위 진행량 충족.
     - 정확도(`tools/slam_v5_report.py` 의 구분, v2 Codex P2): 응답 자세와 `slam.control` 의 적용 자세 각각의 위치 오차(중앙·최대)와 방향 오차(중앙·최대), 적용 지연·보정 점프, 미션별 하역 결과.
     - L 과 R 을 둘 다 관측한 공통 구간에서 L 의 값이 R 이하여야 한다. 공통 구간은 두 실행의 sim 시각 교집합으로 정한다. 공통 자료가 없으면 "비교 불가"로 적는다. R 이 먼저 실패하면 그 실패를 그대로 기록하고, 잘린 창을 정상 완료로 세지 않는다. L 의 나머지 구간은 절대 기준으로 판정한다. 절대 기준은 PR #62 V5 와 같은 적용 자세 위치 최대 ≤ 0.15 m·방향 최대 ≤ 0.05 rad 이고, 후반 30 분의 중앙값이 전반 30 분보다 커지지 않아야 한다.
     - 임무 완료 수는 공통 구간에서 L ≥ R.
   - **기록(판정 아님):**

## 5c. 진단과 기준 개정 (S3 를 본 뒤 개정, 2 차 확인 전에 고정 — 총괄 결정 (a), 2026-10-26)

이 절은 S3 결과(5b)를 본 뒤에 썼다. 개정한 기준의 근거는 S3 수치가 아니다. 아래에 각 근거의 출처를 적었다. S3 수치는 진단에만 썼다.

**진단 — 방향 FAIL 의 원인.**
- 보정 유지(hold, approach 의 수락 캡처부터 withdraw 까지)는 docking 중 보정 점프를 막으려고 받은 보정을 적용하지 않는 설계다. 놓기는 정지 상태에서 한다(`release_and_stand`, `pending_release` → `slam_release`).
  - 0.02 m·0.02 rad 는 놓기 점프의 상한이 아니다. 놓은 뒤 다음 다리를 다시 계획할지 가르는 분기값이다(Codex 개정 검토 P3).
- 유지 중 적용 자세의 오차는 두 가지의 합이다. 유지 시작 때 적용 보정이 가진 오차와, 그 뒤 오도메트리 증분의 오차다. 받은 보정과 적용 보정의 차이는 참값 오차가 아니다. 두 보정에 공통인 편향은 지워진다.
- 8 세션의 모든 유지 구간에서 `received_after` 와 `applied_after` 의 방향 차이를 쟀다(ws1 `test_runs/live/s3conf_874e44a4`, 스크립트 hold_gaps.py).
  - 이동 1 m 당 중앙값은 L 0.0055–0.0076, R 0.0058–0.0086 rad 다. 구간 최대도 L 0.024–0.041, R 0.017–0.040 rad 로 같은 범위다.
  - 이것은 "같은 기구(유지 중 오도메트리 드리프트)"와 맞지만, 위치 추정 결함이 없다는 증명은 아니다(Codex P2). 그래서 2 차 확인에서 놓기 점프와 유지 중 응답을 직접 비교한다(아래 1·7).
- line_m s1 의 방향 FAIL 은 R 이 579 s 만에 끝나 큰 유지 구간이 그 안에 들지 않은 것과 맞는다.
- 유지 정책은 고치지 않는다. 드리프트를 줄이는 것은 오도메트리(자이로 방향 등)의 일이다. 유지 정책을 바꾸면 docking 동작이 바뀌는데, 이는 S3 범위 밖이다.

**개정 기준(2 차 확인에 적용, 여기서 고정).**
1. **방향 비교를 상태별로 나눈다(적용 자세만).**
   - **tracking 행은 보수적으로 정한다.** 적용 자세 행(slam.control, 시각 t)은 다음 두 조건을 모두 채울 때만 tracking 이다. 나머지는 모두 holding 이다.
     - (a) result.json `slam_summary.holds` 의 세션 시간표에서, 각 `event == "hold"` 의 `time_s`(t_h)부터 그 뒤 첫 놓기 사건(`event` 가 `release` 로 시작, t_r)까지의 닫힌 구간 [t_h, t_r] 어디에도 들지 않는다. 놓기 틱의 행도 holding 이다. 끝나지 않은 유지는 세션 끝까지다.
     - (b) t 직전에 처리된 slam.records(`applied_tick_s` ≤ t)와 직후에 처리된 것(> t)의 `mode` 가 둘 다 `tracking` 이다.
   - 이렇게 정한 이유(Codex 개정 검토 1·2 회차 P2):
     - 놓기가 그 틱의 행을 고쳐 쓰는 경로(pending release)와 고쳐 쓰지 않는 경로(`release_before_stall_replan`: 새 보정이 다음 행부터)가 섞여 있다.
     - `start_clear_out` 처럼 시간표에 `hold` 사건을 남기지 않고 유지를 거는 경로도 있다. 그 유지는 (b) 가 기록의 mode 로 잡는다.
     - 경계의 행은 holding 쪽으로 보내 오래된 보정이 tracking 비교에 들어가지 않게 한다. 버려지는 tracking 행은 기록 간격(약 0.1 s) 정도뿐이다.
   - runner 의 기록은 바꾸지 않는다. 유지 사건 기록을 바꾸면 재생 게이트의 기록이 달라진다.
   - 적용 방향 L ≤ R(중앙·최대)은 tracking 행에만 건다. holding 행의 L 적용 방향은 V5 절대 한계 0.05 rad 이내여야 한다(R 은 기준선이라 판정 대상이 아니다).
   - **응답 방향 L ≤ R 은 유지 중 응답까지 포함한 모든 processed 응답에서 비교한다**(Codex P2). 유지 중 위치 추정이 나쁜 경우를 여기서 잡는다.
   - 위치는 지금처럼 전체 행으로 비교한다.
2. **표류 창과 허용 폭.**
   - 창은 첫 응답부터 0–30 분(A) 대 30–60 분(B)이다. 판정기 c7415c88 에서 고쳤다.
   - 허용: median(B) − median(A) ≤ (0.15 − median(A)) / 15.
   - 근거: V5 위치 한계 0.15 m 와 운용 8 h(30 분 창 16 개)다. 첫 창의 실제 수준에서 시작해 30 분마다 그만큼씩 늘면 8 h 끝에 V5 에 닿는다.
   - 앞 판(9 mm, 0 에서 출발)은 첫 창의 수준을 무시해 선형 증가를 놓쳤다(Codex P2 반례: 64 → 73 mm 는 8 h 에 196 mm). 이 식은 그 실행 자신의 A 를 쓰고 S3 수치를 쓰지 않는다. 예: A = 0.064 m 면 허용 5.7 mm 다.
   - 선형 가정은 검사 조건이 아니라 예산을 나누는 방식이다. 첫 1 시간의 최대 오차는 따로 V5 절대 기준으로 본다.
3. **하역 절대 기준(새로 판정, Codex P2 반영).**
   - 하역 판정에 이른 L 의 모든 시도가 대상이다. 완료(done)뿐 아니라 하역 판정에서 실패로 바뀐 미션도 넣는다. 사유 `MISSED`·`NOT_GROUNDED`·`FORK_INSIDE`(`forklift_core.mission.delivery`)이거나 `delivery_error_m` 이 기록된 미션이다.
   - 대상 시도는 모두 하역 오차 < 0.08 m(콘솔 U-case 한계)이고 하역 판정 실패가 없어야 한다.
   - done 미션의 `delivery_error_m` 이 없거나 유한하지 않으면 실패다.
   - 하역 최대의 L ≤ R 비교는 두지 않는다. 하역은 유지 중 near-field 추적이 정하기 때문이다.
4. **R 의 미션 실패 기록.** 판정기가 양쪽 `live_failures` 를 싣는다(c7415c88). 판정에는 쓰지 않고 함께 적는다.
5. 나머지는 그대로 둔다: keyframe < 1 s, SLAM 끊김 없음, 관측 ≥ 3,600 s·600 s 창 여섯, 공통 구간 위치(중앙·최대) L ≤ R, 완료 수 L ≥ R, R 이 먼저 끝나면 그 뒤 L 은 V5 절대 기준. 응답 방향은 위 1 처럼 모든 processed 응답으로 비교한다.
6. **R 이 일찍 끝날 때(총괄 추가).**
   - 쌍의 비교는 다음을 다 채울 때만 유효하다.
     - 공통 구간이 sim 600 s(판정기의 창 하나) 이상이다.
     - 그 안에서 R 이 미션 2 건 이상을 마쳤다. 고유 `mission_id` 의 `outcome == "done"` 이고 `ended_s` 가 공통 구간 안이어야 한다. 미션 한 건은 집기부터 하역까지의 한 주기다. 두 주기는 있어야 tracking 표본이 집기·운반·귀환을 다 지난다.
   - 그보다 짧은 쌍은 "비교 불가"로 센다(FAIL 이 아니다). 그 쌍의 L 은 절대 기준으로만 본다: V5 위치 0.15 m·방향 0.05 rad, 하역(위 3), keyframe < 1 s, 진행량.
   - 2 차 확인의 통과 조건:
     - (i) 네 쌍의 L 이 모두 절대 기준을 통과한다.
     - (ii) **장면마다 유효한 쌍이 하나 이상**이다(Codex P2: 두 쌍이 한 장면에 몰리면 다른 장면의 비교 근거가 없다).
     - (iii) 유효한 쌍은 모두 비교를 통과한다.
     - (iv) 아래 7 의 재진단 조건에 걸리지 않는다.
   - 재실행: 어느 장면에 유효한 쌍이 없으면 그 장면의 비교 불가 쌍의 R 만 같은 seed 로 한 번씩 더 돌린다(Isaac 은 비결정적이라 다시 돌리면 길이가 달라진다).
     - 재실행 R 이 유효한 쌍을 만들면 그 쌍의 비교에는 재실행 R 을 쓴다. 원래 R 의 기록(미션 실패 포함)은 함께 적는다.
     - 한 seed 는 한 쌍으로만 센다.
     - 7 의 R 유지 표본에는 원래 R 과 재실행 R 을 모두 넣는다.
     - 그래도 그 장면에 유효한 쌍이 없으면, 그 장면의 결론은 "절대 기준 충족"까지로 한정해 보고하고 총괄이 판단한다. 통과로 보고하지 않는다.
   - R 의 조기 실패는 mapping 의 운용 결과로 따로 기록한다. 제외된 구간에서 L 이 상대적으로 낫다는 증거로 쓰지는 않는다.
7. **유지 드리프트 비율(총괄 추가, 기록 + 재검토 조건).**
   - 유지 구간 하나의 값 = 그 구간 놓기의 방향 점프 |`jump_rad`|(시간표의 놓기 사건, wrap 처리된 값) ÷ 그 구간의 오도메트리 이동 거리(t_h–t_r 사이 slam.records 의 `odom_base` 증분 합, 0.1 m 미만이면 0.1 m).
   - 끝나지 않은 유지 구간은 넣지 않는다(놓기 점프가 없다).
   - 장면마다 L 두 실행의 구간 값을 모으고 R 의 구간 값(재실행 포함)을 모아 중앙값과 90 백분위수를 낸다. 실행별 중앙값의 중앙값이 아니라 구간 값을 모은 통계다.
   - 90 백분위수는 NumPy `percentile(..., 90, method="higher")`(보간 없이 위 순위값)로 계산한다. 보간(`linear`)은 꼬리 하나를 희석한다(Codex P3: L=[0.010×9, 0.049]·R=[0.010×10] 에서 linear 1.39 배, higher 4.9 배). 그래도 p90 이 10 개 중 극단값 하나를 반드시 잡지는 않는다. 그 한계는 남는다.
   - **재진단 조건(실질 게이트)**: 어느 장면에서든 L 의 중앙값 또는 90 백분위수가 R 의 1.5 배를 넘으면 유지 상태를 적용 방향 비교에서 뺀 근거가 깨진 것으로 본다. 그때는 위치 추정 모드의 결함으로 다시 진단하고 통과로 보고하지 않는다. 90 백분위수를 함께 보는 것은 중앙값이 꼬리를 놓치기 때문이다(Codex P2: 10 구간 중 하나만 4.9 배여도 중앙값 비는 1.0).
   - 자료 하한: 장면마다 R 의 끝난 유지 구간이 10 개 이상이어야 한다. 모자라면 "자료 부족"으로 적고 통과로 보고하지 않는다(총괄 판단). R 의 중앙값·90 백분위수가 0 이면 비교하지 않고 "자료 부족"으로 둔다.
   - 1.5 배는 독립적으로 검증된 변동 폭이 아니라 미리 정한 잠정 문턱이다. 같은 기구라면 같아야 할 두 통계에, 표본 수(R 은 일찍 끝나 유지 구간이 적다)와 장면별 동작 차이로 생길 흔들림을 넉넉히 둔 값이다. 초과하면 통과로 보고하지 않으므로 실질적인 게이트다.
   - 유지 중 드리프트 자체(오도메트리 방향, S3 에서 이동 1 m 당 0.006–0.009 rad)는 오도메트리 쪽 별도 계획의 입력으로 남긴다.

**2 차 확인.**
- seed 3·4 로 한다. 조사는 0, S3 는 1·2 를 썼다.
- 나머지 조건은 S3 와 같다(같은 장면·등록부 묶음·30 구간 순서·team-spec).

## 6. 남는 위험

- 조사 지도의 world 오차는 이번 CT-2 조사에서는 방향이 아니라 그래프 한 구간의 옆 밀림이었다(5 장). PR #62 S2 진단(오도메트리 방향이 지배)과 다르다. 재조사 불합격이 구조적이면(같은 곳에서 되풀이) 3 회 상한에 걸린다. 그때는 불합격 구간의 위치와 방향을 겹쳐 비교해 총괄에 올린다(agy ③ 7).
- 시뮬은 정적 세계다(P4). 실차 창고의 바뀌는 배치는 이 계획이 다루지 않는다. CT-2 에서 옮겨지는 빈 EPAL 6 은 높이 0.144 m 로 LiDAR 평면(1.05 m) 아래라 지도 대상이 아니다(Codex 확인). 높은 짐을 쌓거나 차체가 크게 기울면 이 결론을 넓힐 수 없다.
- 위치 추정의 `size()` 상한 함정(상위 계획 3 장)은 재생에서 해롭게 드러나지 않았지만 일반 보증은 아니다.
- 같은 장면·순서에서 seed 만 바꾼 확인은 궤적이 비슷하다. 다양한 운용 경로(auto 대기열·운용자 개입)에 대한 검증력은 제한적이다(agy ③ 8). D7 의 짧은 범위 밖 확인으로 일부만 보완한다.
- 에폭 안에서 SLAM 만 다시 맞추는 길은 없다(sim_reset = 새 에폭). 위치 추정이 깨지면 에폭을 다시 시작한다(agy ③ 10, 이 계획 밖).
