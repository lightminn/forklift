# WeAct H743 코어 보드 단독 확인 (2026-11-17)

작성일: 2026-11-16 · 상태: **준비, 실기 전** · 관련: [도착일 절차서](2026-11-12-arrival-day-procedure.md)(S0·4절), [보드 펌웨어 설계](../design/2026-11-12-weact-h743-board-firmware.md) 5·8·9절, [링크 계약 mcu-link/3](../interfaces/2026-10-22-mcu-link-contract.md)

사용자가 11-17 학교에서 코어 보드를 처음 연결해 본다(사용자 결정). 이번 확인은 **코어 보드 단독**이다. 메인보드·모터·VM 은 잇지 않고, `FW_MOTOR_OUTPUT` 은 0 그대로다. 확인하는 것은 세 가지다: DFU 로 굽기, USB 장치 열거, PC ↔ 보드 링크(mcu-link/3).

## 1. 굽는 이미지 — HIL 빌드

- **`FW_BUILD=hil` 을 쓴다**(출력 잠금).
- 이유: 보드 단독이면 DRV8244·KTH7801·엔코더가 없다. 그래서 정상·시운전 빌드는 드라이버 미준비·센서 무효 결함을 계속 띄운다. HIL 빌드는 공유 차량 모형이 입력을 채워 STATE 가 깨끗하다. 또 모터 쪽 주변장치(DRV·KTH SPI, LPTIM, ADC)를 하나도 켜지 않고 nSLEEP 을 low 로 둔다(보드 설계 9절).
- 링크·USB·IWDG·주기 경로는 정상 빌드와 같은 코드다.
- 이미지 정보:
  - 정체(USB 제품 문자열): `forklift-mcu hil locked 65f252a5c4b6`
  - main `65f252a5` 에서 빌드, Arm GNU 13.3.rel1
  - 크기 text 34,224 B
  - 해시: `data/h743_check/fw/SHA256SUMS`(1번 스크립트가 굽기 전에 대조한다)

## 2. 준비된 파일

메인 체크아웃의 `data/h743_check/` 에 있다(git 이 무시하는 폴더라 브랜치·워크트리와 무관하게 남는다). `tools/h743_check/stage.sh` 가 만든다. 실행기 잠금(실 안전 배선 설계 8.1) 머지 전에 만든 사본은 잠금·독 바이트열이 없으므로 **main 에서 다시 스테이징**한다. 새 `3_link_check.sh` 는 그런 사본이면 멈춘다.

| 파일 | 하는 일 |
|---|---|
| `1_flash.sh` | DFU 장치가 정확히 하나인지 확인 → 이미지 해시 대조 → 옵션 바이트 읽어 저장(쓰지 않음) → 굽기와 검증. 대량 지우기는 하지 않는다 |
| `2_enumerate.sh` | RESET 뒤 `/dev/forklift-mcu` 가 15 s 안에 생기는지, 읽기·쓰기 권한, USB 제품 문자열이 이미지 정체와 같은지 |
| `3_link_check.sh [초] [장치]` | 링크 확인 10 분(기본 600 s). 기록은 `data/h743_check/<날짜>_link.jsonl`, 마지막 줄에 판정 한 줄 |
| `fw/` | `fw_hil.elf`, `SHA256SUMS`, `BUILD.txt`(정체·빌드 정보) |
| `code/` | 3번이 쓰는 Python 코드의 사본(`tools/h743_link_check.py`, `src/forklift_core`) |

`tools/h743_link_check.py` 는 STATE 를 듣는 동시에 1 s 마다 `DISARM` 을 하나 보낸다. `DISARM` 은 언제나 받아들여지고(계약 3.1) `STATE.last_rx_seq` 에 그 seq 가 실린다. 그래서 보낸 때부터 그 seq 를 담은 첫 STATE 까지를 명령 → STATE 왕복으로 잰다. 그 밖의 명령은 보내지 않는다.

## 3. 손작업 순서

예상 손작업은 약 5 분이다(굽기 3 분, 열거 1 분). 3번의 10 분은 기다리기만 한다.

1. 노트북에서 이 세션이나 저장소 아래 아무 곳에서 실행한다. 경로는 `/home/light/school/2-2/embedded-design/forklift/data/h743_check/` 이다.
2. **DFU 진입**: WeAct 보드에 USB-C(데이터 케이블)를 노트북에 직접 꽂는다(허브 말고). **BOOT0 버튼을 누른 채 RESET 을 눌렀다 떼고**, 그다음 BOOT0 를 뗀다.
3. `! /home/light/school/2-2/embedded-design/forklift/data/h743_check/1_flash.sh` → `OK: flashed and verified` 를 확인한다.
4. **RESET 만 한 번 누른다**(BOOT0 는 누르지 않는다). 이제 이미지가 돈다.
5. `! /home/light/school/2-2/embedded-design/forklift/data/h743_check/2_enumerate.sh` → `OK: the board runs the staged image` 를 확인한다.
6. `! /home/light/school/2-2/embedded-design/forklift/data/h743_check/3_link_check.sh` → 10 분 동안 보드와 케이블을 건드리지 않는다. 마지막 줄 `PASS …` 또는 `FAIL … FAILED=<항목>` 을 총괄에 붙여 넣는다.

## 4. 판정 기준 (실행 전에 정함)

학교 수준이다: 링크가 끊기거나 밀리는지를 잡는 기준이고, 마이크로초를 따지지 않는다. 10 분 동안 모두 서야 `PASS` 다.

| 항목(`checks`) | 기준 | 이유 |
|---|---|---|
| `link_kept` | 장치가 끝까지 열려 있음 | USB 끊김 0 |
| `states_flowing` | STATE 수 ≥ 95 % × (초 × 100) | STATE 주기 10 ms |
| `no_frame_errors` | 호스트 쪽 CRC·COBS·길이·버전 오류 0 | v3 가 아닌 프레임도 여기에 잡힌다 |
| `no_seq_gaps` | STATE seq 끊김 0 | 오는 길에 잃은 STATE 0 |
| `mcu_period` | 인접 STATE 의 MCU 시각 차가 모두 9–11 ms, 평균 10 ± 0.05 ms | MCU 가 STATE 를 건너뛰면 20 ms 로 보인다 |
| `host_gap` | 호스트가 받은 간격 최대 ≤ 100 ms | 실행기는 이보다 오래된 STATE 를 낡은 것으로 본다(`state_max_age_s` 0.1) |
| `round_trip` | DISARM 잃음 0, 왕복 최대 ≤ 50 ms | STATE 한 주기(10 ms) + USB 왕복에 여유. DRIVE 유효 상한 150 ms 보다 충분히 작다 |
| `no_reset` | `boot_id` 가 한 번도 바뀌지 않음 | 워치독(또는 어떤) 리셋 0 |
| `mcu_rx_errors_zero` | STATE 의 `rx_errors` 변화 0 | MCU 쪽 받기 오류 0 |
| `no_cycle_overrun` | STATE 의 `cycle_overruns` 변화 0 | 1 kHz 주기 지연 0 |

평균·최대 수치(STATE 주기, 받은 간격, 왕복 p50/p95/최대)는 판정과 별도로 기록에 남는다.

## 5. 실패했을 때 볼 것

1. **DFU 장치가 안 보임**(`STOP: 0 DFU devices`): 데이터 케이블인지, 허브 없이 직접 꽂았는지 확인한다. BOOT0 를 누른 채 RESET 을 했는지 확인하고 2번부터 다시 한다. `lsusb | grep 0483` 을 본다.
2. **`/dev/forklift-mcu` 가 안 생김**: `lsusb` 에 `0483:df11` 이 남아 있으면 아직 ROM DFU 다. BOOT0 없이 RESET 만 다시 누른다. `0483:5740` 이 있는데 링크가 없으면 udev 규칙이 문제다(`udevadm control --reload` 와 `trigger` 는 sudo 로 사용자가 실행).
3. **3번이 `FAIL`**: `FAILED=` 뒤의 항목을 본다.
   - `link_kept` 이면 케이블이나 USB 포트를 바꿔 다시 한다.
   - `host_gap`·`round_trip` 만 실패면 노트북이 바빴는지 본다(다른 큰 프로그램을 끄고 다시).
   - `no_reset`·`mcu_period`·`no_cycle_overrun` 이면 보드 쪽 문제다. 기록 파일을 그대로 총괄에 넘긴다.

## 6. Jetson 에서 같은 확인

콘솔 세션이 Jetson 쪽을 준비한다(`tools/hwday/`). 굽기는 노트북에서만 한다(Jetson 에는 CubeProgrammer 가 없고, 필요하지도 않다). 보드를 Jetson 의 USB 에 옮겨 꽂은 뒤, Jetson 의 저장소 사본(이 문서가 들어간 main 이후)에서 다음을 실행한다.

```bash
cd ~/forklift && .venv/bin/python tools/h743_link_check.py --device /dev/forklift-mcu --seconds 600 \
  --out data/jetson_check/2026-11-17/h743_link.jsonl
```

- 걸리는 시간은 10 분, 판정 기준은 4절과 같다(`host_gap` 은 Jetson 의 수신 간격).
- 필요한 것:
  - `deploy/udev/99-forklift-mcu.rules` 설치. DFU 규칙은 필요 없다.
  - 사용자가 tty 그룹에 속해 있을 것. Ubuntu 에서는 `dialout` 이다(규칙은 `MODE="0660"` 만 주므로 그룹은 배포판 기본).
  - `pip install -e .` 로 깔린 `forklift_core`. 추가 패키지는 없다.

## 7. 이 확인이 하지 않는 것

메인보드·모터·센서 경로(드라이버 SPI, KTH, 엔코더, ADC)는 보지 않는다. 그것은 부품이 모두 도착한 뒤 도착일 절차서 S1–S5 의 몫이다. 옵션 바이트는 읽기만 하고 바꾸지 않는다.
