# 주변 RGB-D 4대 Vision SLAM 과 LiDAR SLAM 비교·융합 — 계획 v2

작성일: 2026-10-07 · 상위: [현황과 다음 단계](2026-09-17-project-status-and-next-steps.md) 5·6순위,
선행: [공장 홀·Isaac LiDAR SLAM](2026-09-26-factory-hall-and-isaac-slam.md)(오프라인 재생),
[온라인 SLAM 폐루프](2026-10-04-online-slam-closed-loop.md)(v3.8, slam_toolbox 로 주행)

## 요청과 사용자 결정

사용자(2026-10-07): 「지금 SLAM 은 LiDAR 기반일 텐데, 지게차 주변에 depth 카메라를 달아 Vision-based SLAM 시스템을 만들고 기존
시스템과 비교하고, fusion 했을 때 성능이 올라가는지, 올라간다면 얼마나 올라가는지 분석해서 보고서와 영상을 만들어 달라.」

같은 날 사용자가 고른 선택지:

| 질문 | 결정 |
|---|---|
| 카메라 배치 | **전후좌우 4대**(D435i 급). 전방 1대만 쓰는 비교도 함께 돌린다 |
| 비교 방식 | **온라인 폐루프 주행까지** — 각 방식의 추정 위치로 실제로 주행한다 |
| 평가 조건 | **기본 + 악조건**(재생 단계 센서 열화·고속 주행) |
| 보고서 | **저장소 기록 + 공유용 웹 페이지** |

**지금(2026-10-06):** 위치 추정은 2D LiDAR(A2M12 카탈로그 행, 1.05 m 장착) + 바퀴 오도메트리 + slam_toolbox 다. 조사 루프(116 m)
오프라인 재생에서 시작 정렬 ATE 평균 0.040 m(잡음 없음)·0.055 m(합성 잡음)([9/26 기록](../validation/2026-09-26-factory-hall-and-isaac-slam.md) §6), 온라인
폐루프 S1 seed 0 합성 잡음에서 제어 입력 raw RMSE 0.0755 m·최대 0.169 m([10/04 기록](../validation/2026-10-04-online-slam-closed-loop.md)). 카메라는 인식용
전방 1대뿐이고 Vision SLAM 은 없다.

**이 계획이 만드는 것 — 이름:** "**잠정 차체·합성 센서·이 공장 홀 조사 루프에 한정된, 주변 RGB-D Vision SLAM 과 LiDAR SLAM 의 합성 비교·융합 분석**".
실물 카메라 4대 구매·장착 결정이 아니고, 실물 센서 성능 주장이 아니다.

## 고정하는 전제

- **차체·장면:** `dls08_provisional` + `artifacts/base_scene_warehouse_forklift/scene.usda`, `south_hall_v2` 공장 배치, 조사 루프(14 지점 폐루프). 기존
  LiDAR SLAM 기록과 같은 조건이라 비교가 이어진다. 실측 차체(`dls08_measured`) 재검증은 범위 밖이다(현황 문서와 같음).
- **LiDAR:** `config/isaac_slam_lidar.yaml` 그대로(1,600 빔·10 Hz·0.2–12 m, 1.05 m, 순간 스캔). 잡음 σ 0.02 m.
- **바퀴 오도메트리:** 기존 가정 잡음(뒷바퀴 각속도 σ 0.2 rad/s, 조향 σ 0.005 rad).
- **카메라 4대(합성, `config/isaac_depth_rig.yaml`):** 640 × 480, fx = fy = 465.74 px(지금 인식 카메라와 같은 K — 수평 화각 69.0°, D435i RGB 의
  69° × 42°([Intel D435 계열 제품 소개](https://simplecore.intel.com/realsensehub/wp-content/uploads/sites/63/D435_Series_ProductBrief_010718.pdf))와 수평은 같고
  4:3 이라 수직 54.5° 로 더 넓다), RGB 와 정렬된 z-깊이(RealSense 의 depth-to-color 정렬에 해당). 깊이 유효 0.28–8.0 m(하한은 같은 자료의 최소 깊이
  약 28 cm, 상한 8 m 는 가정). 지붕(최고 1.01 m) 위 z = 1.03 m, 아래로 15° 기울여 바깥을 본다:

  | 이름 | base_link 위치 (m) | 방향 |
  |---|---|---|
  | front | (0.17, 0, 1.03) | 전방, 15° 아래 |
  | rear | (−0.42, 0, 1.03) | 후방(yaw 180°), 15° 아래 |
  | left | (−0.12, 0.32, 1.03) | 왼쪽(yaw +90°), 15° 아래 |
  | right | (−0.12, −0.32, 1.03) | 오른쪽(yaw −90°), 15° 아래 |

  URDF 충돌 상자로 보면 마스트 상단(x 0.48, z 0.67)은 전방 카메라에서 49° 아래, 포크 끝은 52° 아래라 아래쪽 화각 끝(15° + 27.3° = 42.3°)
  밖이다. 측면 카메라는 차체 최외곽(y 0.3125)보다 바깥이다. **차체가 화면에 들어오는지는 Isaac 에서 화소 광선 투사의 자기 적중으로 확인한다**(R0).
- **깊이 잡음(가정):** σ_z = 0.0036 · z²(m) 독립 가우시안, 그 뒤 1 mm 양자화와 유효 범위 밖 0(무효). 스테레오 오차식 σ_z = z²·σ_d/(f·b) 에 기선
  0.05 m·초점 447 px(848 폭, 87°)·부화소 σ_d 0.08 px 를 넣은 값이다 — 2 m 에서 14 mm(0.7 %)로 위 자료의 "2 m 에서 2 % 이하" 안이다. 공간 상관·
  모서리 날림·적외선 패턴은 없다. RGB 에는 렌더러 자체의 표본 잡음 외에 잡음을 넣지 않는다.
- **유리한 단순화(명시):** 카메라는 모션 블러·롤링 셔터·자동 노출이 없고 LiDAR 는 회전 왜곡이 없다. 둘 다 실물보다 유리하다. D435i 의 IMU 는
  쓰지 않는다.
- **센서 주기:** 스캔과 카메라 모두 10 Hz, 같은 물리 스텝(120 Hz 의 12 스텝마다)에서 찍는다. D435i 의 기본 15·30 fps 가 아니라 정확 동기를 위한
  시뮬레이션 선택이다.

## 설계

### D1 — 기록: 정지 렌더 캡처와 신선도 검사

`run_slam_drive.py --depth-rig config/isaac_depth_rig.yaml` 이 스캔과 같은 스텝마다 4대를 캡처한다. 렌더 파이프라인이 물리보다 뒤처지는 문제
([9/20 기록](../validation/2026-09-20-capture-freshness.md): 메타데이터가 2–4 렌더 프레임 뒤처짐)를 움직이는 카메라에서 피하려고, **물리를 멈춘 채
`world.render()` 를 N 번(기본 8 — `perception_camera.acquire_frozen_snapshot` 과 같은 수) 부른 뒤** RGB·깊이를 읽는다. 장면이 렌더 사이에 변하지 않으므로
화소는 그 물리 상태에 수렴한다. 매 캡처에서 물리 시각·자세가 렌더 동안 바뀌지 않았는지 확인한다.

**신선도 검사(정답, 평가용):** 20 캡처마다 카메라마다 화소 48 개(8 × 6 격자)에 PhysX 광선을 쏴 렌더 깊이와 비교한다. 지금 자세와 1·2·4 물리 스텝
전 자세에서 쏜 잔차를 모두 남기고, **지금 자세의 중앙 잔차가 가장 작아야** 한다(아니면 그 기록은 무효). 같은 광선의 자기 적중(`/World/Forklift`)
비율도 남긴다 — 0 이어야 한다.

저장: `rig/<카메라>/<번호>.jpg`(RGB, JPEG 품질 95 — 용량 때문, 온라인 실행은 원본을 보낸다), `rig/<카메라>/<번호>.png`(uint16 mm 깊이, 잡음 없음),
`rig_frames.json`(번호·물리 시각·스캔 번호·신선도 진단), `meta.json` 의 `depth_rig`(K 원본·정수 인덱스 정규화, base←optical, 잡음 가정).
`--chase-video` 는 로봇 뒤 위에서 따라가는 3인칭 카메라(30 fps)를 영상용으로 남긴다. 천장은 숨기지 않는다(카메라가 보는 장면을 바꾸지 않는다).

### D2 — 하나의 락스텝 브리지, 두 입력원

새 ROS 노드 `forklift_ros.rig_slam_bridge` 는 프레임(스캔·카메라 4장·odom→base) 하나를 받을 때마다:

1. `/clock`·`/tf`(odom→base_link)·`/odom` 을 그 시각으로, `/rig/rgbd_images`(rtabmap_msgs/RGBDImages, 선택한 카메라)와 `/scan` 을 발행한다.
2. 오도메트리 노드(rgbd_odometry 또는 icp_odometry)가 **그 시각의** 출력을 낼 때까지 기다린다.
3. 키프레임이면(`slam_link.KeyframeGate` 와 같은 규칙: 0.5 s 그리고 0.447 m 또는 0.5 rad) `/rig/key/*` 로 같은 데이터를 다시 발행하고, rtabmap 이
   **그 시각의** `info`·`mapGraph` 를 낼 때까지 기다린다. rtabmap 은 처리 주기·이동 문턱을 0 으로 두어 받은 키프레임을 모두 처리한다 — 무엇을 처리할지는
   브리지가 정한다(10/04 v3.3 의 교훈: SLAM 의 판정을 예측하지 않는다).
4. map←base(t) = map←odom_slam(마지막 키프레임) ∘ odom_slam←base(t, 오도메트리 노드) 를 내고, 실행기용 **map←wheel_odom = map←base(t) ∘ (wheel_odom←base(t))⁻¹**
   을 회신한다(기존 계약과 같은 형태). 기다린 출력이 시간 안에 안 오면 `failed`.

입력원은 둘이다: **온라인** = Isaac 실행기 소켓(`slam_link` 에 프레임 메시지 추가), **오프라인** = 기록 플레이어(`slam_log.npz`·`rig/` 를 읽어 같은
잡음 모델로 같은 순서를 재생). 오프라인도 락스텝이라 처리 속도와 무관하게 프레임을 버리지 않고 결정적이다(실행 후 확인: 프레임을 버리지 않는 것은 맞지만 비트 단위로 같지는 않고, 같은 재생의 ATE 차이가 0.01 cm 미만이다 — [기록 §8.3](../validation/2026-10-07-visual-slam-and-fusion.md). 온라인의 RGB 렌더는 실행마다 달라 카메라를 쓰는 폐루프는 재현되지 않는다). 영상 처리량 때문에 rosbag 은 만들지 않는다.

slam_toolbox(L-ST)는 **기존 코드 그대로** 쓴다 — 오프라인은 `forklift_ros.slam_replay` bag + `isaac_slam_replay.launch.py`, 온라인은
`isaac_slam_bridge` + `slam_bridge_container.sh`. 그래서 기준선이 지난 기록과 같은 코드다.

### D3 — 비교 구성 (RTAB-Map 0.23.13, `deploy/ros2_vslam/Dockerfile`)

> v2: 아래 표의 앞단 결합(특히 F 의 직렬 VO→ICP)은 v2 개정 #5 의 증분 융합으로 바뀌었다. 표의 센서 구성과 역할은 그대로다.

| 구성 | 센서 | 앞단(오도메트리) | 뒷단(rtabmap 정합) | 역할 |
|---|---|---|---|---|
| **L-ST** | LiDAR + 바퀴 | 바퀴 | slam_toolbox | **기존 시스템** |
| L-RT | LiDAR + 바퀴 | icp_odometry(바퀴 예측) | ICP | 같은 뒷단에서 센서만 바꾼 대조 |
| V1 | 전방 카메라 + 바퀴 | rgbd_odometry(바퀴 예측) | 시각 | 실물 1대 구성 |
| **V4** | 카메라 4대 + 바퀴 | rgbd_odometry(바퀴 예측, 4대) | 시각 | **Vision SLAM** |
| V4-noodom | 카메라 4대 | rgbd_odometry(예측 없음) | 시각 | 순수 시각(오프라인만) |
| **F** | 카메라 4대 + LiDAR + 바퀴 | rgbd_odometry(시각 + ICP, 바퀴 예측) | 시각 + ICP, 공간 근접 검출 | **융합** |

RTAB-Map 매개변수는 **개발 seed 0 에서만** 고르고 동결한 뒤 평가 seed 를 돌린다. 고른 값과 이유는 `ros2/src/forklift_bringup/config/rtabmap_*.yaml` 에
적는다. 동결 뒤에는 바꾸지 않는다(바꾸면 평가 seed 를 새로 뽑는다).

### D4 — 지표와 판정

- **오프라인:** 기존 `tools/evaluate_slam_replay.py` 와 같은 정의 — 프레임 시각마다 **그 시점의 온라인 추정**(루프 폐쇄 뒤 재최적화 궤적 아님)을 정답과
  비교한 시작 자세 정렬 ATE(주 지표)·최소자승 정렬 ATE·최대·최종 오차, 바퀴 오도메트리 단독 값 병기. 시각 오도메트리 소실 프레임 수, 프레임당 처리
  벽시계도 남긴다.
- **온라인:** 10/04 S1 과 같은 정의 — 제어에 실제로 쓴 추정과 정답의 **정렬 없는** raw RMSE·최대, 완주 여부, 정답 도착 오차, 실패 사유.
- **"융합이 얼마나 나은가":** 같은 기록(오프라인) 또는 같은 seed(온라인)의 **쌍별 비교**. 주 비교는 F 대 L-ST 와 F 대 V4 의 주 지표 비율
  (F/L-ST, F/V4)이며 seed 별 값·평균·나은 seed 수를 함께 적는다. seed 5 개라 통계적 유의성을 주장하지 않는다.
- **사전 등록:** 개발 seed 0(조정 가능), 평가 seed 1–5(동결 후 1 회). 평가 결과를 본 뒤 구성을 바꾸지 않는다.

### D5 — 악조건

기록은 그대로 두고 재생(오프라인)·전송(온라인) 단계에서 만든다. 모두 seed 로 재현된다.

| 이름 | 내용 | 의도 |
|---|---|---|
| lidar_blackout | 60–80 s·130–150 s·200–220 s 에 스캔 없음(드라이버가 내지 않음) | LiDAR 단일 고장 |
| lidar_short | 측정 거리 4 m 로 제한 | 넓은 공간에서 벽이 범위 밖인 경우 |
| camera_blackout | 같은 세 구간에 카메라 4대 영상 없음 | 조명 소실·가림 |
| wheel_slip | 바퀴 오도메트리 거리 +5 %(적재 미끄러짐 관찰값, 10/04 S2 v3.8c) | 오도메트리 계통 오차 |
| fast | **새 기록:** 조사 속도 1.0 m/s(바퀴 상한 8 rad/s = 1.08 m/s 안) | 고속 |

오프라인은 L-ST·V4·F 를 다섯 조건 모두, 나머지 구성은 기본 조건만 돌린다. 온라인 악조건은 오프라인에서 F 와 L-ST 의 차이가 가장 큰 조건 하나를
seed 1·2 에서 L-ST·F 로 돌린다.

### D6 — 온라인 폐루프

10/04 S1 과 같은 조사 루프 폐루프(`run_slam_drive.py --slam-feedback`)를 L-ST·V4·F 로 seed 1–5, 합성 잡음에서 돌린다. 실행기는 그대로
`SlamPoseTracker` 로 회신을 적용한다. 정답은 물리·평가·안전 검사(차체 외곽 겹침)에만 쓴다. 한 Slurm 작업에 Isaac 실행기와 컨테이너 하나(브리지 + SLAM),
`--network none`, 유닉스 소켓 — 10/04 와 같은 구성이다.

### D7 — 영상과 보고서

- 영상: 3인칭 추적 카메라, 카메라 4대 RGB(+깊이), 지도 위 정답·L-ST·V4·F 궤적, 시간축 오차 그래프를 한 화면(1920 × 1080)에. 기본 조건 한 seed 와
  악조건 한 구간을 담는다.
