# 복귀 cusp 재계획 계획 (2026-11-01, 2 판)

지시: 총괄(2026-10-31) 후보 1 — 진단 → 계획(검토 3 회) → 수정 → 게이트·비교 배치. 총괄 보탬: 곡률 여유(다)를 대조 후보로 넣고 오프라인 재호출로 잰다.
진단: `docs/validation/2026-10-31-return-cusp-diagnosis.md`.
정책(사용자 2026-10-24): 복구 로직·런처 기본값은 사용자 결정 없이 정하고 문서·보고로 남긴다.

2 판에서 바뀐 것(agy 1 차 7 지적, 오프라인 탐침, §7):
- 실패 자세에서 다시 계획이 되는지를 오프라인으로 쟀다(D1 근거). 4 자세 모두 보통 여유로 성공했다.
- 보류 뒤 정지 대기가 틱마다 어떻게 이어지는지, 단계 시간 한도가 어떻게 다시 시작되는지 적었다.
- 옵션 이름을 단계별로 나눴다: `--return-cusp-replans N`(기본 0 = 끔), `--transport-cusp-replans N`(기본 2).
- 비교 배치에서 aisle seed 를 0–15 로 늘렸다(실패가 aisle 에 몰림). 여유 0 경로 뒤의 `occupied` 정지 시간 초과를 따로 센다.
- (다) 측정 결과를 D3 에 적었다. 채택하지 않는다.

## 1. 무엇을 바꾸는가

- (가) 복귀 cusp 재계획: 복귀 단계 cusp 의 `endpoint_heading` 실패를, 운반 cusp 재계획처럼 서서 지금 자세에서 복귀 경로를 다시 계획해 이어 간다. 지금은 실행이 끝난다.
- (나) 운반 cusp 재계획 예산: 실행당 2 회를 3 회로 늘릴지 비교 배치의 별도 팔로 본다.
- (다) 복귀 계획 곡률 한계: 0.29 → 0.26 1/m 를 오프라인 재호출로 잰다. 이 계획에서 채택하지는 않는다. 측정 결과로 (가)만으로 충분한지 판단할 근거를 남긴다.

## 2. 근거 (진단 요약)

- riib 배치 2 의 cusp 방위 실패 6 건 = 복귀 4(복귀에는 cusp 재계획이 없음) + 운반 2(예산 2 회 소진 뒤).
- 운반 cusp 재계획: 33 회 모두 계획 성공, 그것을 쓴 23 실행 중 21 이 운반 단계를 넘겼다. 예산 2 회를 다 쓴 실행은 10 건(모두 aisle)이고, 그중 2 건이 세 번째 cusp 에서 실패했다.
- 계획된 복귀 경로 자세의 70 % 가 계획 곡률 한계 0.29 에, 추종 명령은 복귀 표본의 30 % 가 조향 한계 0.36 에 붙는다. 보정 여유가 0.07 1/m 다.

## 3. 설계

### D1 (가) 복귀 cusp 재계획

- 발동 조건(운반과 같음, 단계만 다름): 추종 상태 `failed`, 단계 `return_home`, 실패 `endpoint_heading`, `at_cusp`, `off_path` 아님, 이 복귀 다리의 재계획 횟수 < 2.
  - 보류(fix A′, 0.05–0.08 rad)가 `judged_out`·`window` 등으로 실패를 확정하면(`fail_pending`), 그 틱의 추종 결과가 곧 `failed` 가 된다. 지금은 같은 틱의 `command` 에서 `Tracking failed in return_home` 으로 끝난다(`MissionCore.command` 의 `require`).
  - 그래서 복귀 재계획 블록은 `MissionCore.follow` 에서 **보류 블록 뒤**에 둔다. 운반 재계획 블록은 보류 블록 앞에 있지만, 운반은 보류 단계가 아니라 문제가 없다. 이 위치면 보류가 실패를 확정한 틱에 바로 상태를 `braking` 으로 바꿔 끝나지 않게 한다.
  - 보류 규칙은 바꾸지 않는다.
  - 0.08 rad 이상이라 보류 없이 바로 실패한 경우도 같다(BF aisle s6).
  - 틱마다의 흐름(운반 cusp 재계획과 같은 방식):
    - 실패한 추종기는 그 뒤에도 매 틱 `failed` 를 돌려준다(래치). 보류 블록은 `cusp_pending` 이 풀렸으므로 다시 들어오지 않는다.
    - 재계획 블록은 매 틱 발동 조건을 다시 보고, 정지 틱 수(`ms.cusp_stop_ticks`)가 모자라면 그 틱의 결과를 `braking` 으로 바꾼다. 그래서 `command` 의 `require` 에 닿지 않는다. 명령은 실패한 추종기의 0 이다.
    - 정지 틱 수가 차면 계획한다. 보류 중에 이미 서 있었으면 정지 틱은 첫 틱부터 찬다.
    - 정지 틱 수는 운반과 같은 `ms.cusp_stop_ticks` 를 쓴다. 단계가 다르므로 겹치지 않고, 재계획 때 0 으로 돌린다.
- 정지 확인: 운반과 같은 `cusp_stop_needed`(12 틱) 동안 정지(SLAM 이면 `slam["stop_now"]`). 그동안 명령은 0(실패한 추종기가 이미 0 을 낸다).
- 계획: 장애물 재계획의 복귀 다리 재계획과 같은 호출을 쓴다(`hooks.plan_return_leg(grid_world(return_scenario), 지금 자세, return_to_pose, planner_config, geometry, travel_config, grid_kwargs("return", destination), turnaround, backoff)`). `invalid_start`·`no_path` 면 여유 0 으로 한 번 더 한다(같은 규칙).
  - `return_scenario` 는 SLAM 이면 `slam["return_scenario"]`(도킹으로 옮겨진 목적지), 없으면 운반 장면이다(장애물 재계획과 같은 선택).
- 성공: 경로·`state["paths"]["return_home"]`(`path_record`)·`paths.json`·표시·새 추종기를 설치하고, 장애물 진행 기록을 비우고, 단계 시작 시각을 바꾼다(운반 cusp 재계획과 같은 처리).
  - 단계 시작 시각(`ms.phase_started`)은 단계 추종 시간 한도(`tracking_limit`, 작업 시간 기준)의 기준점이다. 재계획 성공마다 복귀 단계의 시간 한도가 새 경로에 대해 다시 시작된다. 운반 cusp 재계획·장애물 재계획도 그렇게 한다.
  - 예산 2 회라 복귀 단계는 최대 세 번의 한도를 쓸 수 있다. 실행 전체 상한(`--max-sim-seconds`, riib 1500 s)은 그대로이고, 넘으면 `Mission exceeded simulation time budget` 으로 끝난다. 비교 배치에서 이 사유를 팔별로 센다.
- 실패: `return_cusp_replan_failed: <failed_plan_reason>` 로 실행을 끝낸다. 지금의 `Tracking failed in return_home` 과 구별된다.
- 기록: `state["return_cusp_replans"]` 에 항목마다 시각, 자세, 위치·방위 오차, 상태, 여유 0 재시도 여부, 계획 벽시계, `search_attempts`, 성공이면 새 경로 기록, 바뀐 경로 기록.
- 근거(오프라인 탐침, 2026-11-01, ws1 `tss_diag/probe.jsonl`, 잡 13617, 스냅숏 `r2_abe5e07b`): 실패 자세 4 개에서, 같은 장면의 기록된 `plan_return_leg` 요청에 출발점만 바꿔 다시 불렀다.

  - 셋은 첫 다리가 0.3–0.8 m 로 짧아 곧 다음 cusp 가 온다. 같은 곡률 한계로 다시 계획했기 때문이다. 짧은 cusp 에서 다시 어긋날 수 있고(agy 지적 4), 그때는 남은 예산 1 회로 한 번 더 계획한다. 예산이 그 고리를 끊는다.
- 예산: 복귀 다리마다 2 회. 운반의 `state["cusp_replans"]`(실행당 2 회)와 따로 센다. 다리가 바뀌는 다른 재계획(장애물·장면·해제)이 새 추종기를 설치해도 이 예산은 그 복귀 다리 전체에 대해 센다(실행당 복귀는 하나).
- 바꾸지 않는 것: `cusp_end_recovered`(짧은 다음 다리 판정)는 그대로 복귀 cusp 를 복구로 보지 않는다. 보류 판정의 결과는 그대로이고, 판정이 실패를 확정한 뒤에 재계획이 붙는다.
- 옵션: 러너 `--return-cusp-replans N`(복귀 다리당 횟수, 기본 0 = 끔). 기본 0 이라 기존 기록의 재생이 바뀌지 않는다. 배치 팔은 2 를 쓴다. riib 런처 기본값은 비교 배치 결과로 정한다.
- 위험(agy 지적 1): 랙에 붙은 cusp 자세에서는 여유 0 재시도 경로가 나올 수 있다. 그 경로는 출발 직후 장애물층 `occupied` 로 서서 시간 초과로 끝날 수 있다(BF aisle s0 와 같은 끝). 탐침에서는 나오지 않았다. 배치에서 여유 0 재시도 수와 그 뒤의 끝을 따로 센다.

### D2 (나) 운반 cusp 재계획 예산

- 러너 `--transport-cusp-replans N`(기본 2). 지금은 러너 지역 상수 `max_cusp_replans = 2` 이고 재생 설정의 `_bound` 로 덮어쓴다. 옵션은 그 상수의 값을 정할 뿐이고, 재생은 기록된 설정값을 쓰므로 기존 기록에는 영향이 없다. 비교 배치의 한 팔에서 3 을 쓴다.
- 이름에 단계를 넣는다(agy 지적 7). 복귀 예산은 D1 의 `--return-cusp-replans` 가 따로 정한다.
- 운반의 예산은 지금처럼 실행 전체 횟수다(riib 은 실행당 운반 다리 하나).

### D3 (다) 복귀 곡률 오프라인 재호출

- 입력: ws1 `r2_abe5e07b` 에 남은 경계 기록 19 건의 `Planner.plan_return_leg` 요청 전부. 표본이 적으면 gdrive 보관본에서 회귀 장면 기록 일부(line_2·random_1)를 되살려 더한다.
- 같은 요청을 곡률 한계 0.29(원래)와 0.26 으로 다시 부른다. 다른 설정은 그대로다.
- 보고: 장면별 성공 수, 실패 상태, 길이·후진 길이·기어 전환, 곡률 한계에 붙은 자세 비율, 계획 벽시계.
- 이 측정은 판정 항목이 아니다. 0.26 에서 실패가 늘지 않으면 다음 등록에서 (다)를 팔로 넣을지 총괄과 정한다.
- 측정 결과(2026-10-31, ws1 `tss_diag/curv`, 잡 13533, 스냅숏 `r2_abe5e07b`):

## 4. 시험 (구현 전 고정)

- 단위:
  - 복귀 cusp 실패 → 정지 대기 → `plan_return_leg` 호출(인자: 지금 자세, `return_scenario`, 목적지 grid, turnaround·backoff 인자) → 성공 설치·기록.
  - 여유 0 재시도(`invalid_start`·`no_path`).
  - 계획 실패 → `return_cusp_replan_failed:` 로 끝남, 기록 남음.
  - 예산 2 회 소진 → 지금처럼 `Tracking failed in return_home`.
  - 옵션 off → 지금과 같음(재계획 호출 없음).
  - 운반 cusp 재계획과 예산을 나눠 씀(운반 2 회를 써도 복귀 2 회가 남음).
  - 보류가 실패를 확정한 틱에 `Tracking failed` 로 끝나지 않고 `braking` 이 되며, 다음 틱부터 보류 블록이 다시 들어오지 않음.
  - 성공 뒤 `ms.phase_started` 가 바뀜(단계 시간 한도 재시작).
  - `--transport-cusp-replans` 가 운반 예산을 바꾸고 기본은 2. `--return-cusp-replans` 기본 0.
- 재생 게이트 runs29 29/29(옵션 기본 off).
- ws1 전체 시험.

## 5. 비교 배치 (등록은 이 계획 수렴 뒤 별도 문서)

- 팔: A = riib 기본(면제 켬), G = A + `--return-cusp-replans 2`, GN = G + `--transport-cusp-replans 3`.
- 장면: 대상 aisle_rack 0–15·trailer 0–4, 회귀 line_2·random_1 0–9 → 41 seed × 3 팔 = 123 실행.
  - aisle 을 0–15 로 늘린 것은 cusp 방위 실패 6 건이 모두 aisle 이기 때문이다(agy 지적 5). 배치 2 에서 aisle 8 seed 의 복귀 cusp 방위 실패는 B·BF 합 3 건이었다. 16 seed 면 팔당 기대 3 건 안팎이다.
  - 이 크기로 완주 수의 작은 차이를 가를 수는 없다. 그래서 판정의 중심은 "복귀 cusp 방위 실패 유형이 G 에서 사라지는가"와 "G 에서 새로 생긴 끝이 없는가"이고, 완주는 비열등(아래)으로 본다.
- 판정 초안:
  - G 대 A:
    - 복귀 cusp 방위 실패(`Tracking failed in return_home` 중 cusp 의 `endpoint_heading`): G 는 예산을 다 쓴 경우만 남아야 한다. 예산이 남았는데 이 실패로 끝난 G 실행이 있으면 구현 결함이다.
    - 완주: 유효 짝 합 G ≥ A − 1. 짝 부호 검정(두 방향 불일치 모두 셈, 단측 α 0.05)으로 G 쪽 악화가 유의하면 불합격.
    - 안전: 접촉·overlap 실패 0, 허가 없는 진입 합 G ≤ A, 면제 키 0.
    - 새 끝: G 에만 나온 실패 사유(`return_cusp_replan_failed`, 여유 0 재시도 뒤 `occupied` 시간 초과, `Mission exceeded simulation time budget` 등)는 실행 기록으로 원인을 대고, 재계획과 무관함을 보이지 못하면 불합격.
  - GN 대 G(G 통과와 무관하게 따로 판정; 순차로 묶지 않는다, agy 지적 5): 운반 cusp 방위 실패가 예산 3 회 소진 경우만 남음, 완주 유효 짝 합 GN ≥ G − 1, 같은 안전·새 끝 조건.
  - 런처 기본 켬은 G 통과일 때 `--return-cusp-replans 2`, GN 통과일 때 `--transport-cusp-replans 3` 을 각각 넣는다.
- 유효성·결측·디스크·재실행 규칙은 riib 배치 2 등록(§3–4)을 그대로 따른다.

## 6. 남는 것

- BF aisle s0 형(복귀 시작 때 경로에서 1 m, cusp 근처 0.23 m 벗어나 `occupied` 정지 시간 초과)은 다른 계열이라 이 계획 밖이다.

- (다) 곡률 여유는 D3 측정대로 채택하지 않는다. 다른 장면 측정은 남는다.
