## 1. 실행 경로

- **연속 이송은 콘솔 대기열로 돈다.** 배치 러너(`riib_scene.sbatch`)는 장면 하나에 임무 하나다. 여러 팔레트를 잇는 세션은 라이브 러너(`deploy/console/isaac_live.sbatch`)와 콘솔 대기열 탐침(`tools/live_console_probe.py --scenario queue`, `tools/mission_queue.py` = queue.js)으로 돈다. ws1 래퍼 `test_runs/live/ct1_queue.sbatch`(`SCENARIO=queue`, `CYCLE=`)를 그대로 쓴다.
- **장면:** 등록부(`config/slam_map_bundles.yaml`)에 있는 세션 장면 두 개 — `scenes_ct1_a770031/line_m_session.json`(sha256 83e27b4c…)·`random_m_session.json`(8b8fe554…). ws1 의 지도 묶음 `line_m_team_spec_quantized_0ff9e3bdff13`·`random_m_team_spec_quantized_0facac3eea66` 이 남아 있다. 라이브 기본대로 등록 지도에서 위치를 잡는다. 묶음 실행(`BUNDLE_TOKEN`)이라 알려진 출발(재위치 없음)이다.
- **사이클:** 세션마다 고정 순서 세 임무 — line_m `P-1:D-1,P-2:D-2,P-3:D-3`, random_m `P-4:D-1,P-5:D-2,P-3:D-3`. CT-1 PR ④(#119)·KEEPOUT 비교(2026-10-27)와 같은 순서라 과거 결과와 나란히 놓을 수 있다(합산하지는 않는다 — 코드와 기본값이 다르다). 대기열 정책은 실패하면 멈추므로, 앞 임무가 실패한 세션의 뒤 임무는 돌지 않는다. 그래서 노출은 단계별로 센다(4 장).
- **운영 기본(riib 런처 기본):** 라이브 런처는 riib 런처가 쌓아 온 기본값 가운데 일부만 넣는다(`ENCODER_MODEL`·`D7_HOLD`·근접 재관측). 빠진 것을 `MORE` 로 같은 값으로 넣는다.
  - `MORE` 에 넣는 정확한 값: `--exit-prefix-exempt on --low-clearance-guard on --restart-confirm-scans 3 --return-start-backoff boxed --near-end-stand on --return-cusp-replans 2` (각각 riib 의 EXIT_EXEMPT=on, LOW_CLEARANCE=on, RESTART_CONFIRM=3, RETURN_START=boxed #263, NEAR_END_STAND=on #273, RETURN_CUSP_REPLANS=2 #282). 앞 두 개도 값을 받는 인자다.
  - `--docking-degenerate-continue` 는 넣지 않는다(#310 의 허용 목록은 line_2_m 하나다. 세션 장면은 목록 밖이므로 riib 기본도 off 다).
  - KEEPOUT 0·NOISE const·START_BAND off·ESCAPE off 는 riib 기본과 같다(라이브 런처도 넣지 않는다). 근접 재관측의 `lower` 는 라이브 래퍼가 `waive_far_confirmed`, riib 가 `waive` 다 — 라이브 래퍼 값을 그대로 둔다(라이브 운영 경로의 값).
  - **이 조합(라이브 + 위 riib 기본)은 처음이다.** 각 기본은 riib 배치에서 검증됐고 라이브 세션에서는 처음 함께 돈다. 승격 검증 때와 다른 조건이 남는다 — 근접 재관측의 `lower` 가 라이브는 `waive_far_confirmed`(첫 근접 검출이 실패한 뒤 원거리 검출 조건을 만족해야 하단 증거를 면제)이고 riib 는 `waive`(처음부터 면제, 좁은 검색), SLAM 이 라이브는 등록 지도 위치 추정이고 riib 는 온라인 매핑이다. 그래서 결과는 **'라이브 + 여섯'의 새 조합**에 귀속하고, '승격된 기본에도 남은 실패'로 바로 읽지 않는다.
- **사전 점검(총괄 조건 2):** 제출 전에 여섯 인자가 라이브 경로에서 실제로 받아지고 켜지는지 세 단계로 본다.
  1. 스냅숏 러너 파서에 여섯 옵션이 있고 `--live` 와의 거부 규칙이 없는지(옵션 grep).
  2. 팔마다 `DRY_RUN=1` 로 래퍼·런처·러너 `--check-args` 를 통과시키고 실제 러너 인자 목록(`RUNNER_ARGS`)을 결과 폴더에 남긴다. D·D′·O6 은 여섯 인자와 값이 그대로 있는지, O0 은 여섯이 없이 라이브 런처 현재 기본 그대로인지 확인한다. `--deterministic` 은 D·D′ 에만 있어야 한다.
  3. 첫 회전의 첫 완료 세션 기록(실행 `result.json` 의 인자 기록)에서 여섯 값이 적용값으로 남았는지 확인한다.
  - 하나라도 라이브 러너가 거부하거나 무시하면(인자 기록에 없거나 다른 값) 그 인자는 빼고 이유를 결과 문서에 적는다. 확인 전에는 나머지 회전을 내지 않는다.

## 3. 실패 분류

- **단위:** 임무. 예정된 세 임무를 네 상태로 나눈다(Codex 1 회차 P2): **시작 확인**(탐침의 `ack`, 또는 그 임무 폴더·실행 기록이 있음) / **시작 여부 불명**(무응답 제출, `busy`·`stale` 거부 — 시작했을 수 있음) / **확정 거부** / **미제출**(대기열이 멈춰 내지 않음). 완료율의 분모는 시작 확인 임무이고, 불명 건수와 비율을 따로 적는다. `leg_failures_pairs._session` 의 '시작했을 수 있음' 경계 규칙은 판정 도구용이라 쓰지 않는다.
- **수집:** 집계 도구가 epoch·임무 ID·시작/종료 시각을 보존한다. 라이브의 제어·SLAM·표본·스캔 기록은 세션 spool(`run/spool/<이름>/*.jsonl|npz`)로 가므로(통상의 `slam_control.npy` 는 없다) 기전 확인은 spool 에서 읽고, epoch 마다 `spool/manifest.json` 의 `complete`·버린 항목·쓰기 오류를 함께 적는다. 기록이 불완전한 실패는 그 사실을 적는다. 임무 폴더(`missions/m*`)의 기록이 없거나 끊긴 임무는 그 epoch 의 실행 결과(`run/result.json` 의 `failure_reason`·단계)로 사유·단계를 채운다. 앞 임무와 끊긴 임무의 도킹 재시도가 모두 비어도 끊긴 임무를 잃지 않는다(`_session` 을 그대로 쓰면 잃는다 — Codex 재현).
- **결과:** `done` / 실패(사유 문자열) / 세션 중단(그 epoch 실행 기록의 사유) / 기록 없음. 세션 종료 사유는 그 시점에 진행 중이던 임무에만 붙이고, 이미 확정된 임무 결과를 덮어쓰지 않는다.
- **단계와 노출:** 전이 목록은 세션 소유라 임무 기록만으로는 단계를 못 센다. 그 epoch 의 전이 목록을 임무의 시작–종료 구간으로 잘라 임무별 단계 순서를 만든다. 접수된 임무는 첫 전이(observe) 전에 **준비(preparing)** 를 거치고 거기서 끝날 수 있으므로(`prepare:timeout`·`prepare:all_candidates_failed`·`prepare:reference:*`), 준비를 첫 단계로 둔다. 실패 단계는 사유 문자열이 말하면 그것(`Tracking failed in transport` → transport, `prepare:*` → preparing), 아니면 임무 기록의 마지막 단계, 근거가 없으면 '불명'이다. 운반·내림·빼기 단계의 실패는 하위 상태(하역 맞춤 전 / 맞춤 뒤 / D7 재접근)를 함께 적는다 — 같은 단계라도 고칠 곳이 다르다. 단계 노출 = 그 단계에 들어간 임무 수.
- **대기열 멈춤(Codex 1 회차 P2):** 세션마다 탐침 보고의 `queue.stop_reason`·`stops`·제출 거부 사유·멈춘 임무 순번을 따로 집계한다. 시작한 임무가 모두 성공했는데 상태 수신 끊김·권한 상실·제출 거부로 다음 임무를 못 낸 세션은 '대기열 차단'으로 분류하고 미제출 임무에 연결한다. 이것도 연속 이송의 차단 원인으로 후보 목록에 들어간다.
- **유형(문자열 규칙, 처음 표 — 새 문자열은 결과 문서에 추가 규칙으로 적는다):**

| 유형 | 문자열·조건 | 기전 확인에 볼 기록 |
|---|---|---|
| 준비 | `prepare:*` | 준비 계획 후보·거절 사유 |
| 인식 | `observe:*`, 근접 캡처 거절·`near_*`, 후보 없음 | 원거리 후보 수·확신, 근접 캡처 판정, oracle/학습 |
| 추종 | `Tracking failed in <단계>`, `Tracking timeout in <단계>` | 실패 순간 횡오차·요 오차·조향 포화(`slam_control`·제어 기록), 보정 나이와 마지막 보정의 크기, 경로 교체 이력 |
| 도킹·하역 | `transport_recovery_after_docking`, `Pallet missed`, 하역 맞춤 거부 뒤 실패 | 맞춤 라운드·상태(`delivery_docking`), D7 재접근 기록 |
| 계획·허가 | `scene_replan_*`, `permit_stop:*`, `invalid_start`, cusp | 거절 사유, 정지 위치와 가까운 점유, 재계획 횟수 |
| 적재 안전 | 차체 기울기·들기 기울기, 미끄럼, 금지 접촉 | 삽입 깊이·포크 위치, 미끄럼 판정 값, 접촉 기록 |
| SLAM 링크 | `slam_link_failed`, `slam_not_localized` | 브리지 기록·마지막 응답 스캔 ID |
| 대기열 | `queue.stop_reason`(상태 끊김·lease 상실·거부) | 탐침 보고·로그 |
| 기반 | 기동·래퍼·탐침 오류 | 래퍼·탐침 로그 |

- **문자열과 기전을 따로 적는다.** 같은 오류 문자열이 같은 기전이라는 뜻이 아니다. 각 실패에 위 표의 기록을 확인해 기전 꼬리표를 단다. 확인이 안 되면 '기전 미확인'으로 둔다. 후보의 근거는 기전 꼬리표가 붙은 실패를 쓰되, 미확인 실패를 빼면 관측하기 쉬운 기전이 위로 올라가므로, **미확인 실패가 각 유형에 들어갔을 때 순위가 바뀌는지**를 함께 적는다.
- **적재 운반 중 추종 실패(`Tracking failed in transport`·`Tracking timeout in transport`)는 따로 표시한다.** 질량 탐침 재검토 계기 (i)(#326) 판단에 쓰도록, 세션·임무·적재 상태·실패 순간의 회전 방향(좌·우, 전진·후진)·보정 나이를 함께 적는다. 이 조사로 계기 충족을 판정하지는 않는다 — 총괄의 판단 자료다.

- 후보마다: 근거(어느 유형·기전, 몇 건, 어느 단계·하위 상태, D·O6·O0 어디, **어느 장면·팔레트·목적지·순번**), **그 기전으로 종결된 관측 임무 수**(고쳤을 때 구제되는 수가 아니다 — 대기열이 첫 실패에서 멈추므로 고치면 같은 임무의 다음 차단점이나 뒤 임무의 새 실패가 드러날 수 있다; 예상 구제는 후속 비교로 확인할 가설), **차단 규모**(그 기전이 멈춘 세션 수·처음 막은 임무 순번·그 뒤 미제출 임무 수 — 앞단 차단을 고치면 뒤 임무도 돌 기회가 생긴다; 그 뒤 임무의 실제 회복은 미검증), 비용(코드·검증·Isaac 비교 규모), 기존 검증과 겹치는지(이미 기본인 변경의 남은 실패인지).
- 순위: 기전이 확인된 종결 건수와 차단 규모가 크고(D 기준), 단계 노출 대비 실패율이 높고, 비용이 작은 순. **D 기준 순위는 재현·디버깅 우선순위다**(oracle 마스크·픽셀 지연 0·작업자 기한 상한 조건). 결정 모드가 실패 유형의 비중·도달 경로를 바꿀 수 있으므로 같은 유형이 O 에서 나와도 운영 순위가 같다고 보지 않는다. **운영 개선 순위는 이 조사로 정하지 않고**, O6·O0 의 관측은 유형별로 따로 적는다(빈도로 비교하지 않고, O 에서 안 나왔다고 없다고 읽지 않는다). 장면은 고정 배치이고 뒤 임무의 장애물은 앞 임무가 놓은 팔레트에 따라 달라지므로, 순위는 장면·팔레트·목적지·순번에 묶어 적고 다른 배치·순서로 일반화하지 않는다.
- **선택지 ①의 순위:** 이 분기는 `--docking-degenerate-continue` 가 켜진 line_2_m 하역에만 있고, 세션 장면은 그 목록 밖이라(총괄 동의) 이 조사에서 노출이 0 일 것으로 본다. 노출이 0 이면 **'본 조사로는 순위 산정 불가 — 근거는 V3b 의 관측된 열화(off 가 성공한 3 seed)라는 외부 근거뿐'** 으로 적고, 목록에는 그 외부 근거와 비용으로 따로 놓는다.
