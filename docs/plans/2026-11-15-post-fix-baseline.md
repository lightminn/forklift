# 표시선 수정 뒤 Isaac 새 기준선 — 측정 계획 (2026-11-15, 4 판)

- 배정(총괄, 2026-11-15): 계획 경로 표시선 누출 수정(#512, 후속 #513) 뒤의 Isaac 기준 수치를 새로 잡는다. 수정 전·후 결과는 섞지 않기로 했으므로(총괄 결정, [수정 smoke](../validation/2026-11-14-path-display-fix-smoke.md)) 앞으로의 비교는 이 기준선에서 시작한다.
- 성격: **기술 기록이다. 합격·불합격 판정, 문턱, 승격 권고는 없다.** 런처·러너·기본값은 바꾸지 않는다.
- 수정 전 같은 조건의 기존 수치를 나란히 놓아, 기준선이 얼마나 바뀌었는지 함께 적는다. 다만 기존 수치와의 차이는 표시선 하나의 몫이 아니다(3 절).
- 결정 경계: 제출 여부·규모와 3.3 의 선택 팔은 총괄이 정한다. 결과를 본 뒤 무엇을 기준 수치로 쓸지도 총괄이 정한다.
- 3 판: 독립 검토 ①(원자료 대조), ②(Codex 적대적 검토 3 회, 수렴), ③(적히지 않은 전제)를 반영했다(9 절).
- **4 판 개정(결과 전, 총괄 결정 2026-11-15).** 계획(#524)과 두 묶음의 역할을 승인했다. 선택 팔 S 는 넣되 **40 실행으로 줄인다**: random_1 seed 0–29, line_2 seed 0–4, aisle_rack seed 0–4. 짝은 R 의 같은 장면·seed 40 개이고, R 의 나머지 30(random_1 30–59)은 S 짝 비교에 들지 않는다. 이유는 디스크와 시간이다(70 이면 `/home` 이 25 GB 아래로 내려간다). 순서는 0 단계 → R 74 → L 32 → S 40 이고, 단계 사이에 `/home` 여유 25 GB 이상을 확인한다. 모자라면 앞 단계 원본을 보관한 뒤 지우고 나서 진행한다. L 은 ws1 에 다른 잡 없이 단독으로 돌리고(총괄이 콘솔에 알림), 결정 모드 R·S 는 CPU 잡과 겹쳐도 된다. 3.3·5 절을 이 값으로 고쳤다.

## 1. 무엇을 기준선으로 두나

**두 묶음을 서로 다른 역할로 둔다.** 하나로 고르지 않는 이유는, 재현 가능한 짝 비교와 운영 조건의 수치가 한 모드에서 함께 나오지 않기 때문이다.

| 묶음 | 런처·모드 | 역할 | 답하는 질문 |
|---|---|---|---|
| R | riib 런처(`deploy/riibotics/riib_scene.sbatch`) + `--deterministic`, 임무 하나 | **결정 재현 기준.** 이 스냅숏의 참고 수치와, 같은 스냅숏에서 다시 돌려 원인을 볼 수 있는 실행 기록 | 같은 seed 에서 이 스냅숏이 어떻게 끝나나 |
| L-D | 라이브 런처(`deploy/console/isaac_live.sbatch`) + `--deterministic`, 고정 순서 세 임무 | 연속 이송의 결정 모드 참고 | 세 임무 연속에서 어디서 끝나나 |
| L-O | 라이브 런처 기본(학습 제안기), 같은 세 임무 | **운영 참고 통계** | 학습 인식이 도는 운영 조건의 비율·분포 |

- **R 을 결정 재현 기준으로 두는 이유.**
  - K1(#498·#514)·곡률 규칙(#509) 같은 최근 등록 비교는 모두 riib 결정 모드 짝 비교였다. 같은 seed 의 두 팔을 짝지어 보므로 결과가 달라진 짝을 하나씩 가릴 수 있다.
  - 결정 모드는 같은 스냅숏·seed 에서 다시 돌려 같은 궤적을 낸다. 그래서 이 기준선의 한 실행을 나중에 그대로 재현해 원인을 볼 수 있다.
  - 수정 전 비교 대상(곡률 비교 B0, 70 실행)이 같은 런처·같은 seed 목록·같은 입력 파일로 있다(3 절).
- **기준선을 다른 스냅숏의 B0 로 그대로 쓰지 않는다.** 등록 비교는 앞으로도 두 팔을 같은 스냅숏에서 함께 돌린다. 이 기준선은 (가) 수정 뒤 수치의 크기를 알려 주는 참고값, (나) 등록 비교의 B0 팔을 이 스냅숏에서 다시 돌렸을 때 같은지 볼 대조 기록, (다) 한 실행을 같은 스냅숏에서 재현해 원인을 보는 자료다. 나중 비교가 이 수치를 직접 쓰려면 스냅숏·적용값·입력 해시(2.1)가 같은지 먼저 확인하고, 다르면 쓰지 않는다. 결정 모드의 뜻도 스냅숏에 묶인다(실행 기록의 `deterministic` 블록과 그 `overrides` 를 결과 문서에 남긴다).
- **R 은 운영 성능의 수치가 아니다.** 결정 모드는 학습 제안기 대신 oracle 인스턴스 마스크를 쓰고, 설정된 픽셀 지연을 0 으로 둔다(`sim/isaac/run_transport.py` 의 `learned_replaced`, `docs/plans/2026-10-25-deterministic-sim-mode.md` D1b). 그래서 R·L-D 의 원거리 인식 수락률은 운영 중 학습 인식의 수락률이 아니다. 표시선이 가장 직접 닿았던 것은 인식 입력이었으므로(근접 depth 4/4 변화, [영향 조사](../validation/2026-11-14-path-display-impact.md) 1 절), 학습 인식이 도는 L-O 를 따로 둔다.
- **L-O 는 seed 마다 갈라진다.** 같은 설정을 다시 돌려도 결과가 같지 않으므로 짝 비교를 하지 않는다. 비율과 분포만 적는다.
- 라이브 결정 모드도 임무 수준에서 같은 결과를 내지 않았다(같은 seed 의 D·D′ 네 쌍 모두 첫 임무부터 종료 시각이 1.0–8.5 s 다름, [연속 이송 현황 조사](../validation/2026-11-06-ct-status-survey.md) 요약 6). 그래서 L-D 의 짝 비교는 결과·사유·단계까지만 하고, 시각·하역 오차는 분포로만 본다.

### 1.1 모집단과 빠진 장면

- R 은 최근 riib 등록 비교의 모집단(random_1·line_2·aisle_rack, 단일 임무)을 그대로 쓴다. 그래서 R 의 수치는 그 비교들을 이을 때만 쓴다. "표준 장면 전체 성능"으로 부르지 않는다.
- L 은 콘솔 운용 장면(등록부의 line_m·random_m)의 연속 이송이다.
- 넣지 않는 장면: 다른 riib 장면(trailer·conveyor·aisle_out 등), T11 시험체, hall(시작 재위치 검증 장면). 최근 등록 비교와 콘솔 운용 어느 쪽에도 쓰이지 않았고, 수정 전 같은 조건의 수치도 없다. 필요하면 따로 계획한다.
- 표본 한계:
  - R 70 실행 가운데 60 이 random_1 이고, line_2·aisle_rack 은 5 씩이다. 그래서 장면별 표를 먼저 두고, 장면을 합친 비율은 random_1 이 지배한다는 단서를 붙인다. line_2·aisle_rack 의 p90 은 5 개 가운데 최댓값에 가깝다.
  - L 은 장면당 8 세션이다. 한 세션의 세 임무는 순서가 고정되고 앞 임무의 끝 상태를 물려받으므로 독립 표본 24 개가 아니다. 비율은 세션 단위와 임무 단위를 함께 적는다.

## 2. 실행 조건

### 2.1 공통

- 스냅숏: 제출 직전의 main 커밋 하나를 고정해 모든 묶음이 같은 스냅숏을 쓴다. 이름은 제출 때 한 번만 정해 총괄에 보낸다.
- 입력 파일(①에서 확인): 수정 전 비교 대상과 같은 파일을 쓴다. `SCENE_DIR=test_runs/riibotics/scenes_p1c_81a007b1`, `BASE_SCENE=artifacts/20261013_fork_spacing/base_scene/scene.usda`, `FORKLIFT_URDF=artifacts/20261013_fork_spacing/dd_cfg/old/dls08_measured/forklift.urdf`, `ONNX=test_runs/s3/yolo_runs/yolo11s-seg_p15/weights/best.onnx`, `LEARNED_PY=venvs/learned/bin/python`(곡률 비교 B0 와 K1 재확인 실행 목록의 `env` 가 모두 이 값이다). 라이브는 현황 조사의 장면 묶음(`scenes_ct1_a770031`)과 등록부 지도를 쓴다.
- **입력 기록(지정 파일만으로는 닫히지 않는다).** 제출 전과 결과에 다음을 남긴다. 러너가 기록하는 소스 트리 해시와 기준 장면 해시는 실행 기록에서 읽고, 나머지는 따로 잰다.
  - 지정 파일의 sha256: 위 다섯과 장면 폴더 전체(파일마다), 라이브의 등록부 행이 가리키는 지도 묶음 파일, ws1 래퍼.
  - 실행 환경: Isaac 판, NVIDIA 드라이버 판(`nvidia-smi`), SLAM 브리지 이미지 ID(라이브 런처가 기록하는 값과 riib 쪽 값), 학습 작업자 venv 의 패키지 목록 해시.
  - 수정 전 비교 대상에 같은 값이 남아 있으면 대조표(3.1.1)에 넣고, 없으면 "기록 없음"으로 적는다.
- 표시 모드: 수정 뒤 기본(overlay). `FORKLIFT_PATH_DISPLAY_DIAGNOSTIC` 은 R·L 에 넣지 않는다(3.3 의 선택 팔만 예외).
- 런처 기본을 그대로 쓴다. `EXTRA_ARGS` 는 결정 모드 팔의 `--deterministic` 하나뿐이고, 기본을 바꾸는 환경변수(`NEAR_END_STAND`·`NEAR_OBSERVE_ARRIVAL`·`LAYER_BUDGET`·`RETURN_CUSP_REPLANS` 등)는 주지 않는다.
- **적용값 확인(제출 전 DRY_RUN 으로, 첫 완료 실행 뒤 다시).** argv 에 문자열이 있는지가 아니라 적용된 값을 본다. 런처는 일부 값을 다른 값에 따라 정하고(K1 은 적용된 C2 값이 on 일 때만 켜짐, line_2_m 만 `DOCKING_DEGENERATE_CONTINUE` on, aisle_rack 만 `KEEPOUT` 0.15), `EXTRA_ARGS` 가 덮을 수 있기 때문이다.
  - riib: 세 장면(random_1·line_2·aisle_rack) 각각 `DRY_RUN=1` 로 런처를 돌린다. 런처는 DRY_RUN 에서도 출력 폴더에 `riib_defaults.txt`(적용된 스위치와 그 출처)를 쓰고(`riib_scene.sbatch` 의 `printf ... > "$OUT/riib_defaults.txt"` 가 DRY_RUN 종료보다 앞), 러너 `--check-args` 로 실제 인자 목록을 찍는다. 이 둘에서 장면별로 다음 값을 표로 남기고, 첫 완료 실행의 `result.json` `arguments` 로 다시 맞춘다: `near_end_stand`, `near_observe_arrival`, `layer_latency_budget`, `return_cusp_replans`, `return_start_backoff`, `exit_prefix_exempt`, `low_clearance_guard`, `restart_confirm_scans`, `d7_reapproach_hold`, `docking_degenerate_continue`, `lidar_keepout_m`, `encoder_model`, `deterministic`, `path_display`.
  - 라이브: 두 팔 × 두 장면 각각 `DRY_RUN=1` 로 래퍼·런처를 돌려 `RIIB_DEFAULTS` 줄(적용된 C2·K1·복귀 출발 값)과 `RUNNER_ARGS`(러너 `--check-args`)를 남기고, 첫 완료 세션의 기록된 `arguments` 로 다시 맞춘다. 항목은 같은 것과 `far_capture_expected`, 지도 묶음, 출발 방식(`START_MODE`)을 남긴다.
  - 제출 전 DRY_RUN 의 값이 기대값과 다르면 제출하지 않고 총괄에 알린다. DRY_RUN 에 나오지 않는 항목이 있으면 그 항목을 표에 "DRY_RUN 미확인"으로 적고 첫 완료 실행에서 확인한다. 첫 완료 실행에서 다르면 묶음을 멈추고(`scancel`) 총괄에 알린다.
- 영상: R 은 `VIDEO=off`(평가 배치 규칙). 라이브 런처는 영상을 켜지 않는다.
- 결정성 확인에는 RGB 를 쓰지 않는다(RTX RGB 는 결정 모드에서도 프로세스마다 다름). `tools/deterministic_compare.py` 는 RGB 배열을 비교에서 이미 뺀다.

### 2.2 R — riib 결정 모드

- 장면·seed: random_1 seed 0–59, line_2 seed 0–4, aisle_rack seed 0–4 = 70 실행. 곡률 비교 B0(`lcrcmp_a2b91d2d`, 실행 목록 `docs/validation/assets/loaded-curvature-comparison/RUNS_cmp_a2b91d2d.jsonl`; K1 재확인 목록은 `docs/validation/assets/k1-recheck/RUNS_k1r_k1r_7744f285.jsonl`)와 같은 장면·seed 다. 런처가 `MARKERS=on` 이라 random_1·line_2 는 `_m` 사본, `RACK=on` 이라 aisle 는 rack 사본으로 돈다.
- 결정성 반복 4 실행: random_1 s0·s1, line_2 s0, aisle_rack s0 을 같은 스냅숏으로 한 번 더 돈다.
  - 비교: `tools/deterministic_compare.py <원본> <반복> --json`. 이 도구는 실행 폴더의 파일을 모아 비교한다. JSON 은 경로를 정규화해 구조로, `.npz`·`.npy` 는 배열로 비교하고, RGB 배열 멤버와 `.png`·`.mp4`·`.log`·`.txt`·USD 파일, `runtime_clock.json`, spool 의 manifest 는 뺀다. "같음"은 이 범위가 같다는 뜻이고, 그 밖의 파일까지 같다는 뜻은 아니다. 다르면 도구가 낸 처음 다른 항목을 적는다.
  - 두 실행이 모두 끝까지 기록된 짝만 비교한다. 한쪽이 인프라 실패면 그 짝은 "비교 못 함"으로 적고 다시 내지 않는다.
  - 반복은 집계에서 뺀다.
- 제출: `tools/isaac_bundle.py` riib 묶음 두 잡, 잡마다 3 슬롯, claim-dir 공유, `--retries 2`, `--run-est-min 15`(K1 재확인과 같음).

### 2.3 L — 라이브 연속 이송

- 장면: 등록부(`config/slam_map_bundles.yaml`)의 `line_m_session.json`·`random_m_session.json`, 등록 지도 위치 추정.
- 임무: 연속 이송 현황 조사와 같은 고정 순서 세 임무(line_m P-1:D-1 → P-2:D-2 → P-3:D-3, random_m P-4:D-1 → P-5:D-2 → P-3:D-3), 같은 ws1 래퍼(`test_runs/live/ct1_queue.sbatch`, `SCENARIO=queue`; 저장소 밖 파일이라 제출 전 내용과 sha256 을 결과 폴더에 남긴다), `MAX_EPOCHS=1`.
- **출발: 알려진 출발.** 라이브 런처는 묶음 실행(`BUNDLE_TOKEN`)에서 `START_RELOC` 를 끄고 알려진 출발로 둔다(런처 머리말). 운용자 세션의 기본(random_m 시작 재위치)과 다르다. 무인 배치에서는 B-P2d 유효 세션의 19 % 가 운용자 확인을 기다리며 끝났기 때문이다(forklift/CLAUDE.md). 현황 조사도 알려진 출발이었다. 콘솔 운용 기본과 다른 점으로 결과에 적는다.
- 팔:

| 팔 | 설정 | 장면 × seed | 세션 |
|---|---|---|---|
| L-D | 런처 기본 + `--deterministic` | line_m·random_m × seed 0–7 | 16 |
| L-O | 런처 기본(학습 제안기) | line_m·random_m × seed 0–7 | 16 |

- 배속: 라이브 묶음은 배속이 바닥(0.335)을 밑돌면 슬롯을 줄인다. 배속·틱 간격이 학습 인식·SLAM·결과에 끼어들 수 있으므로(같은 설정이라도 부하에 따라 다름), 세션마다 배속 기록(`pace.jsonl`)과 슬롯 변화, 틱 간격 요약을 결과에 함께 적는다. L-O 의 분포는 이 배속 조건의 표본이다.

### 3.2 차이를 어떻게 읽나

- 같은 seed 의 결과가 바뀐 짝(R ↔ 곡률 B0, L-D ↔ D)을 표로 모두 적는다. 바뀐 짝마다 앞선 실패 단계와 사유를 나란히 둔다.
- **차이는 "스냅숏 차이(표시선 수정 포함)"로 적고, 표시선 몫으로 돌리지 않는다.** 결과 문서에 두 스냅숏 사이 main 머지 목록과 3.1.1 의 적용값 차이를 붙인다.
- 이미 있는 근거의 범위: 표시 끔 진단(곡률 비교의 aisle_rack s0·s1 × 두 팔, 스냅숏 `pdoff_27daf0b0`)은 같은 수정 전 코드에서 표시 prim 이 있을 때와 없을 때를 비교했다. 근접 depth 가 4/4 바뀌고 원거리는 0/4 였다([영향 조사](../validation/2026-11-14-path-display-impact.md) 1 절). 4 실행이라 기준선 규모의 차이를 말하지 못한다.

### 3.3 선택 팔 S — 지금 코드 위의 누출 몫(총괄 결정: 40 실행으로 넣음)

- 내용: R 과 같은 스냅숏으로 random_1 seed 0–29·line_2 seed 0–4·aisle_rack seed 0–4 의 40 실행을 `FORKLIFT_PATH_DISPLAY_DIAGNOSTIC=stage`, `--path-display stage` 로 한 번 더 돈다(4 판 개정). 짝은 R 의 같은 40 실행이다. stage 는 표시선(`add_path_display`)과 목적지 고리(`add_destination`)를 수정 전처럼 장면 prim 으로 그려 인식 카메라에 보이게 하는 진단 모드다(`sim/isaac/run_transport.py` 의 `destination_ring`·`display_path`, `path_overlay.draws_stage`).
- 읽는 법: R 과 S 의 차이는 **같은 코드 위에서 표시 prim 이 인식 카메라에 보일 때와 안 보일 때의 차이**다. 지금 코드 위의 누출 몫이다. #512 이전 결과와 지금 결과의 차이 가운데 표시선 몫을 뜻하지 않는다(그 사이 다른 변경과의 상호작용은 나뉘지 않는다).
- 제출: 묶음 점검(`tools/isaac_bundle.py check`)이 진단 환경변수를 거부하므로 S 는 `deploy/slurm/isaac_array.sbatch` 로 낸다.
  - 실행 목록 `RUNS_pfb_stage_<스냅숏>.jsonl` 을 R 과 따로 만들고, 출력 루트도 따로(`test_runs/pfb/stage_<스냅숏>/`) 둔다.
  - 크기는 `tools/isaac_bundle.py sizes riib --array --runs 40 --run-min 15` 가 찍는 값(`--array=0-39%3 --gres=shard:2 --cpus-per-task=6 --mem=8192M --time=00:35:00`, task 하나 = 실행 하나)을 쓴다. array 런처가 요구하는 제출 전 점검과 결과 수집(`collect --expect 40`)을 그 런처의 사용법대로 한다. 세부 명령은 제출 전 보고에 적는다.
- 섞임 차단: R 집계는 R 출력 루트만 받는다. 표시 모드는 두 곳으로 확인한다.
  - R(overlay): `result.json` 의 `arguments.path_display` 가 `overlay` 이고, `path_display.jsonl` 머리줄의 `mode` 도 `overlay` 여야 한다. 기록값이 없으면 거부한다. stage 는 수정 전 기록처럼 이 값을 남기지 않으므로(`path_overlay.recorded_value`) 없음을 overlay 로 읽으면 안 된다.
  - S(stage): `arguments.path_display` 가 없고 머리줄 `mode` 가 `stage` 인 실행만 받는다. S 집계는 별도 명령으로만 한다.
  - 수정 전 비교 대상(머리줄 파일도 기록값도 없음)은 비교 대상 입력으로만 따로 받는다.
  - 시험에 overlay·stage·off·값 없음·파일 없음 사례를 넣는다.
  - overlay 의 합성·기록 실패는 실행을 멈추지 않고 `path_display.json` 의 통계에 남는다(#513). 합성은 영상 출력 사본에만 하므로 그 실패가 인식 입력을 바꾸지는 않는다. 그래서 집계에서 빼는 조건이 아니고, 실행마다 실패·경고 수를 결과에 적는다. `path_display.json` 이 없는 실행은 표에 따로 표시한다.
  - overlay 기록은 설정값이다. 인식 카메라에 표시 prim 이 없다는 것은 수정 smoke(S1: depth·인식 해시·궤적이 overlay 두 번과 off 에서 같음, overlay 색 픽셀 0)가 보인 범위로 기대고, 이 배치에서 다시 재지 않는다.
- S 의 결과는 진단 기록이고 기준선이 아니다.
- 비용: R 과 비슷한 GPU 시간과 디스크(5 절).
- 결정: 총괄이 40 실행으로 넣기로 했다(4 판 개정). 1 판의 권고는 70 이었다. 40 짝이라 random_1 30–59 의 누출 몫은 보지 않는다.

- `squeue` 에 측정 잡이 없는지(있으면 총괄에 묻는다), persistence 2/2, 팀원 잡이 있으면 dependency 로 그 뒤에 건다.
- `df -h /home`: 그 단계 예상 디스크 + 10 GB 보다 여유가 적으면 내지 않는다.
- 스냅숏 경로와 커밋, 실행 목록 sha256, 입력 파일 sha256 을 남긴다. 출력 루트가 비어 있는지 확인한다(이전 묶음과 겹치면 묶음이 실패한다).
- `tools/isaac_bundle.py check`(R·L), 기대 실행 수(R 74, L 32, S 40).

### 5.2 실행 중 감시와 끝난 뒤

- 입력 대조: 묶음이 끝나면 2.1 의 지정 파일·장면 폴더·지도 묶음·래퍼의 sha256 을 다시 재서 제출 전 값과 맞춘다. 실행 기록이 가리키는 경로(장면 파일, URDF, 기준 장면, 지도 묶음, ONNX)도 지정 경로와 같은지 실행마다 본다. 어긋난 실행은 집계에서 빼고 따로 적는다.
- 묶음 상태(`ended`·`ended_rc_nonzero`·`infra_failed_attempts`)와 디스크를 본다. 디스크가 25 GB 아래로 내려가면 다음 단계를 내지 않고 총괄에 알린다.
- 끝난 뒤 기대 수와 결과 수를 맞추고, 빠지거나 겹친 실행을 적는다. 시간 한도에 걸려 끝나지 못한 실행은 "미완"으로 따로 세고 다시 내지 않는다(R 은 `--retries 2` 가 인프라 실패만 다시 낸다).
- 묶음이 멈춤 감시(`stall_watch`)로 끊은 실행은 사유와 함께 적는다.
