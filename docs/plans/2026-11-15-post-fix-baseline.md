# 표시선 수정 뒤 Isaac 새 기준선 — 측정 계획 (2026-11-15, 1 판)

- 배정(총괄, 2026-11-15): 계획 경로 표시선 누출 수정(#512, 후속 #513) 뒤의 Isaac 기준 수치를 새로 잡는다. 수정 전·후 결과는 섞지 않기로 했으므로(총괄 결정, [수정 smoke](../validation/2026-11-14-path-display-fix-smoke.md)) 앞으로의 비교는 이 기준선에서 시작한다.
- 성격: **기술 기록이다. 합격·불합격 판정, 문턱, 승격 권고는 없다.** 런처·러너·기본값은 바꾸지 않는다.
- 수정 전 같은 조건의 기존 수치를 나란히 놓아, 기준선이 얼마나 바뀌었는지 함께 적는다. 다만 기존 수치와의 차이는 표시선 하나의 몫이 아니다(3 절).
- 결정 경계: 제출 여부·규모와 3.3 의 선택 팔은 총괄이 정한다. 결과를 본 뒤 무엇을 기준 수치로 쓸지도 총괄이 정한다.

## 1. 무엇을 기준선으로 두나

**두 묶음을 서로 다른 역할로 둔다.**

| 묶음 | 런처·모드 | 역할 |
|---|---|---|
| R (주) | riib 런처(`deploy/riibotics/riib_scene.sbatch`) + `--deterministic`, 임무 하나 | 앞으로 등록 비교의 기준 팔(B0)이 설 자리 |
| L | 라이브 런처(`deploy/console/isaac_live.sbatch`), 고정 순서 세 임무(연속 이송) | 운영 조건 참고. 결정 모드(L-D)와 운영 모드(L-O) 두 팔 |

- **R 을 주 기준선으로 두는 이유.**
  - K1(#498·#514)·곡률 규칙(#509) 같은 최근 등록 비교는 모두 riib 결정 모드 짝 비교였다. 같은 seed 의 두 팔을 짝지어 보므로 30–70 짝으로도 결과가 달라진 짝을 하나씩 가릴 수 있다.
  - 결정 모드는 같은 스냅숏·seed 에서 다시 돌려 같은 궤적을 낸다. 그래서 이 기준선의 한 실행을 나중에 그대로 재현해 원인을 볼 수 있다.
  - 수정 전 비교 대상(곡률 비교 B0, 70 실행)이 같은 런처·같은 seed 목록으로 있다(3 절).
- **결정 모드의 한계 — L-O 가 필요한 이유.** 결정 모드는 학습 제안기 대신 oracle 인스턴스 마스크를 쓰고, 설정된 픽셀 지연을 0 으로 둔다(`sim/isaac/run_transport.py` 의 `learned_replaced`, `docs/plans/2026-10-25-deterministic-sim-mode.md` D1b). 그래서 R·L-D 의 원거리 인식 수락률은 운영 중 학습 인식의 수락률이 아니다. 표시선이 가장 직접 닿았던 것은 인식 입력이었으므로(근접 depth 4/4 변화, [영향 조사](../validation/2026-11-14-path-display-impact.md) 1 절), 학습 인식이 도는 운영 모드 L-O 를 따로 둔다.
- **L-O 는 seed 마다 갈라진다.** 같은 설정을 다시 돌려도 결과가 같지 않으므로 짝 비교를 하지 않는다. 비율과 분포만 적는다.
- 라이브 결정 모드도 임무 수준에서 같은 결과를 내지 않았다(같은 seed 의 D·D′ 네 쌍 모두 첫 임무부터 종료 시각이 1.0–8.5 s 다름, [연속 이송 현황 조사](../validation/2026-11-06-ct-status-survey.md) 요약 6). 그래서 L-D 도 짝 비교는 결과·사유·단계까지만 하고, 시각·하역 오차는 분포로만 본다.

## 2. 실행 조건

### 2.1 공통

- 스냅숏: 제출 직전의 main 커밋 하나를 고정해 모든 묶음이 같은 스냅숏을 쓴다. 이름은 제출 때 한 번만 정해 총괄에 보낸다.
- 표시 모드: 수정 뒤 기본(overlay). `FORKLIFT_PATH_DISPLAY_DIAGNOSTIC` 은 R·L 에 넣지 않는다(3.3 의 선택 팔만 예외).
- 런처 기본을 그대로 쓰고, 적용된 값을 실행마다 남긴다(riib 는 `riib_defaults.txt`, 라이브는 `RUNNER_ARGS`·`RIIB_DEFAULTS` 줄). 제출 전 DRY_RUN 으로 인자 목록을 결과 폴더에 남기고, K1(`--near-observe-arrival 0.05,0.05`)·층 예산(`--layer-latency-budget`)·C2(`--near-end-stand on`)·`--return-cusp-replans 2`·`--return-start-backoff boxed` 가 들어 있는지 확인한다.
- 영상: R 은 `VIDEO=off`(평가 배치 규칙). 라이브 런처는 영상을 켜지 않는다.
- 결정성 확인에는 RGB 해시를 쓰지 않는다(RTX RGB 는 결정 모드에서도 프로세스마다 다름). depth 해시·인식 해시·궤적(SAMPLE)·결과 필드로 본다.

### 2.2 R — riib 결정 모드

- 장면·seed: random_1 seed 0–59, line_2 seed 0–4, aisle_rack seed 0–4 = 70 실행. 곡률 비교 B0(`lcrcmp_a2b91d2d`)와 같은 목록이다. 런처가 `MARKERS=on` 이라 random_1·line_2 는 `_m` 사본, `RACK=on` 이라 aisle 는 rack 사본으로 돈다. aisle_rack 의 `KEEPOUT` 0.15 와 line_2_m 의 `DOCKING_DEGENERATE_CONTINUE` 는 런처 기본이 정한다.
- 결정성 반복 4 실행: random_1 s0·s1, line_2 s0, aisle_rack s0 을 같은 스냅숏으로 한 번 더 돈다. 원본과 2.1 의 대체 지표가 같은지 본다. 반복은 집계에서 뺀다.
- 제출: `tools/isaac_bundle.py` riib 묶음 두 잡, 잡마다 3 슬롯, claim-dir 공유, `--retries 2`, `--run-est-min 15`(K1 재확인과 같음).

### 2.3 L — 라이브 연속 이송

- 장면: 등록부(`config/slam_map_bundles.yaml`)의 `line_m_session.json`·`random_m_session.json`, 등록 지도 위치 추정.
- 임무: 연속 이송 현황 조사와 같은 고정 순서 세 임무(line_m P-1:D-1 → P-2:D-2 → P-3:D-3, random_m P-4:D-1 → P-5:D-2 → P-3:D-3), 같은 ws1 래퍼(`test_runs/live/ct1_queue.sbatch`, `SCENARIO=queue`; 저장소 밖 파일이라 제출 전 내용을 결과 폴더에 복사해 둔다), `MAX_EPOCHS=1`.
- **출발: 알려진 출발.** 라이브 런처는 묶음 실행(`BUNDLE_TOKEN`)에서 `START_RELOC` 를 끄고 알려진 출발로 둔다(런처 머리말). 운용자 세션의 기본(random_m 시작 재위치)과 다르다. 무인 배치에서는 B-P2d 유효 세션의 19 % 가 운용자 확인을 기다리며 끝났기 때문이다(forklift/CLAUDE.md). 현황 조사도 알려진 출발이었다. 콘솔 운용 기본과 다른 점으로 결과에 적는다.
- 팔:

| 팔 | 설정 | 장면 × seed | 세션 |
|---|---|---|---|
| L-D | 런처 기본 + `--deterministic` | line_m·random_m × seed 0–7 | 16 |
| L-O | 런처 기본(학습 제안기) | line_m·random_m × seed 0–7 | 16 |

- 상한: 래퍼 시도 32, 기반 실패(Isaac 기동 실패·`startup_silent`·`startup_viewport`, 탐침 전 래퍼 종료) 재시도는 합계 4 회까지. 임무 실패·SLAM 링크 실패·대기열 멈춤은 다시 내지 않고 결과로 센다. 묶음 자동 재시도는 끈다(`--retries 0`). 현황 조사와 같은 규칙이다.
- 제출: live 묶음 두 잡, 잡마다 3 슬롯(shard 4), `BUNDLE_ARGS="--pace-floor 0.335 --pace-gap-p99-s 0.12"`. 세 임무 세션은 과거 최대 30.5 min 이었고(현황 조사 계획 2 절), 결정 모드는 더 걸릴 수 있다.

## 3. 수정 전 수치와 나란히 놓기

### 3.1 비교 대상

| 이번 | 비교 대상 | 스냅숏 | 같은 점 | 다른 점 |
|---|---|---|---|---|
| R | 곡률 비교 B0 | `lcrcmp_a2b91d2d`(수정 전) | 런처·결정 모드·VIDEO=off·70 seed 목록·K1 켬 | 표시선 수정과 그 뒤 main 변경 |
| R(40 seed 부분) | K1 비교 K1 팔 | `k1cmp_c7701296`(수정 전) | 같은 40 seed, K1 켬(인자로) | 스냅숏이 더 이름 |
| R(40 seed 부분) | K1 재확인 K1 팔 | `k1r_7744f285`(수정 뒤) | 수정 뒤, 같은 40 seed | #513 이후 main 변경 |
| L-D | 현황 조사 D | `cts_dfa9aaf2`(수정 전) | 장면·임무 순서·seed 0–7·결정 모드·`MAX_EPOCHS=1`·알려진 출발 | 그 뒤 승격된 K1·층 예산 등 런처 기본, 표시선 수정 |
| L-O | 현황 조사 O6 | `cts_dfa9aaf2` | 운영 모드 + 당시 여섯 | seed 0·1 의 4 세션뿐, 런처 기본 차이 |

- R 과 K1 재확인 K1 팔의 비교는 수정 뒤끼리의 스냅숏 이동을 보여 준다. 이 차이가 크면 수정 전 비교에서 보인 차이도 표시선 몫으로 읽기 어렵다.
- L-O 와 O6 은 4 세션뿐이라 유형만 나란히 놓는다.

### 3.2 차이를 어떻게 읽나

- 같은 seed 의 결과가 바뀐 짝(R ↔ 곡률 B0, L-D ↔ D)을 표로 모두 적는다. 바뀐 짝마다 앞선 실패 단계와 사유를 나란히 둔다.
- **차이는 "스냅숏 차이(표시선 수정 포함)"로 적고, 표시선 몫으로 돌리지 않는다.** 수정 전 스냅숏과 지금 main 사이에는 표시선 말고도 여러 변경이 있다. 결과 문서에 두 스냅숏 사이 main 머지 목록을 붙인다.
- 표시선 몫으로 좁혀 말할 수 있는 근거는 둘뿐이다. 하나는 이미 있는 표시 끔 진단(aisle_rack 두 짝)이고, 다른 하나는 3.3 의 선택 팔이다.

### 3.3 선택 팔 S — 같은 스냅숏에서 누출 재현(총괄 결정 필요)

- 내용: R 과 같은 스냅숏·같은 70 seed 를 `FORKLIFT_PATH_DISPLAY_DIAGNOSTIC=stage`, `--path-display stage` 로 한 번 더 돈다. stage 는 수정 전처럼 표시선을 장면 prim 으로 그리는 진단 모드다. 그러면 R 과 S 의 차이는 같은 코드에서 표시선만 다른 짝 비교가 된다.
- 제약: 묶음 점검이 진단 모드를 거부하므로 S 는 `deploy/slurm/isaac_array.sbatch` 로 낸다. near_tracking·s4 도구는 stage 기록을 거부하지만, 이 계획은 그 도구를 쓰지 않는다. S 의 결과는 진단 기록이고 기준선이 아니다.
- 비용: R 과 비슷한 GPU 시간(아래 5 절)과 디스크.
- 권고: 총괄의 질문("표시선이 기준선을 얼마나 바꿨나")에 기존 수치만으로는 스냅숏 차이가 섞인 답밖에 할 수 없다. 그 질문에 짝 단위로 답하려면 S 가 필요하다. 넣을지는 총괄이 정한다.

## 4. 지표

모두 서술값이다. 문턱은 두지 않는다.

| 지표 | R(실행 하나 = 임무 하나) | L(임무마다) |
|---|---|---|
| 완주 | `success` | 임무 결과 `done` |
| 원거리 인식 수락 | 첫 관측 시도에서 팔레트를 채택했는지, 관측 재계획 수 | 같음(기록이 있는 범위) |
| 근접 캡처 수락 | `near_capture` 상태(채택·거부·사유) | 같음 |
| 하역 오차 | 완주 실행의 `delivery_error_m` 중앙값·p90·최대 | `delivery_error` 같은 통계 |
| 운반 이탈 | 운반 단계 `tracking_failure`(cross_track·endpoint_heading)와 운반 cusp 재계획 수 | 같음 |
| 시간 | 완주 실행의 `simulated_time_s` 중앙값·p90 | 임무마다 `ended_s − started_s` |
| 안전 | 금지 접촉, `deterministic.broken` | 금지 접촉 |
| 실패 단계 | 끝난 단계와 사유 분류 | `stage`·`class` |

- 비율은 개수와 함께 적는다(예: 64/70). 장면을 합친 비율은 따로, 장면별 표를 먼저 둔다.
- R 의 원거리 인식은 oracle 마스크 기반이라는 단서를 표마다 붙인다.
- 집계 도구:
  - R: 새 도구 `docs/validation/2026-11-1x-post-fix-baseline/baseline_summary.py`(이름은 결과 문서 날짜를 따름). 배치 전에 머지한다. 필드 경로는 수정 전 기록(곡률 비교 B0)과 수정 뒤 기록(K1 재확인)에서 실제 값을 읽는 단위 시험으로 고정한다. 한쪽 기록에 없는 필드는 그 지표를 "비교 불가"로 적는다.
  - L: `tools/ct_survey.py` 를 스냅숏 판 그대로 쓴다. 현황 조사와의 비교는 그 조사의 `missions.csv` 열(결과·사유·단계·하역 오차·시각)로만 한다. 새 도구 판에만 있는 값은 이번 것만 적는다.
- 수정 전 원자료:
  - 곡률 비교 B0 70 실행의 `result.json` 은 gdrive 보관본에서 디스크 세션이 부분 복원한다(보관 위치는 디스크 세션 기록 `ws1-cleanup-20261114-f` 계열, 복원 전 확인).
  - K1 비교 K1 팔 40 은 `gdrive:ws1-cleanup-20261114-e/e_k1cmp.tar.zst`, K1 재확인 K1 팔 40 은 `ws1-cleanup-20261115-a/h_k1r`.
  - 현황 조사는 저장소의 `missions.csv`·`survey.json` 으로 충분하다.
  - 복원은 `result.json` 만 하고, 결과 문서가 머지되면 지운다.
