# 복귀 구간 전진 우선 — 출발 시 방향 전환 후보 비교 (`--return-turnaround`)

작성일: 2026-10-12 · 상위: [LiDAR 장애물 지도 계획](2026-10-04-lidar-obstacle-map.md) D7(Reeds–Shepp 목표 연결 · 발사 상한)

## 요청과 범위

사용자(2026-10-12, 리보틱스 중간 미팅 덱 3쪽): "3쪽 영상 복귀할때 후진으로 가는데 … 전진으로 이동하게 영상 다시 뽑아봐". 계획기가 전진을 선호한다는 전제가
이 장면에서는 성립하지 않는다는 분석을 보고한 뒤, 사용자가 "계획기 고쳐서 재촬영"을 골랐다(운반 · 접근 A–D 는 건드리지 않음).

**범위:** 무부하 복귀 구간에서 **트럭이 하역 · 물러나기 끝에서 출발할 때 설치하는 복귀 경로** — 격자 계획의 첫 실시간 복귀 계획(settle 단계의 SLAM
해제와 장애물 블록의 재투영 뒤에 돌고, 해제 재계획 경로를 대체한다)만. 해제가 아직 남아 있으면 적용하지 않는다. 복귀 중 장애물 · cusp
· stall 재계획, 운반 · 접근 · 관찰 · D7 도킹, `plan_transport` 의 임무 계획은 그대로다. 러너 플래그 `--return-turnaround` 로만 켜진다(진행 중인 D8 S4
판정 기준선을 바꾸지 않기 위해, D7 이 `--d7-planner` 로 들어온 것과 같은 방식).

## 원인 (ws1 CPU 재계획, 스냅숏 b66271f, seed 5 장면 · 진리 사각형, D7 travel config)

- 녹화 실행(ws1 `artifacts/20261011_meeting_video/seed_5_d7`)의 복귀는 22.81 m 전 구간 후진이다. 같은 시작 (−5.035, −19.663, −1.591) 에서 CPU 재계획이
  같은 경로를 **1 확장**으로 낸다: 뿌리 RS 발사(`root_shot` "taken"). 발사 상한은 길이 기준(직선 거리 19.85 m + 4 m)이라 22.8 m 후진 발사가 통과한다.
- `reverse_penalty` 1.6–10(가중 1.0/1.8)에서도 1 확장에 21.5 m 후진 + 0.93 m 전진 발사가 채택된다. 발사 상한을 0.5 m 로 넘기면 rp 1.3 은 2,000 확장
  뒤 같은 후진으로 fallback, rp 2.0 은 확장 200k · 인내 150k 에서 28 s · 41,536 확장에 후진 3.5 → 전진 22.75 → 후진 2.18 m 를 찾지만 러너의 20 s
  예산으로는 rp 1.6/2.0 · 가중 1.8/2.5 모두 timeout 이다.
- 휴리스틱(유클리드 · 목표 yaw 차 · 장애물 2D 거리)은 "집이 차 뒤에 있음"과 후진 비용을 모른다. rp 1.3 에서는 실제로도 후진이 싸다(전진 후보 후진 5.68 +
  전진 22.75 + 전환 2 → 32.1 대 후진 29.7). 즉 "전진 선호"(후진 × 1.3)는 길이가 비슷할 때의 우선일 뿐, 이 장면의 복귀에는 작동하지 않는다.

## 설계

`pallet_mission.plan_return_leg(..., forward_turnaround=True, turnaround_check=…)` → `_return_turnaround`:

1. 직접 계획(기존 `_search` 그대로)이 실패하면 그대로 돌려준다. 성공했고 후진 길이가 `RETURN_TURNAROUND_TRIGGER_M` = 3.0 m 이하이면 그대로 둔다.
2. 그보다 길면 후보의 호를 고정 순서로 검사한다(하위 탐색 순서는 아래 하한 순): 시작 자세에서 **최대 곡률 후진 호**, 좌(+1) · 우(−1) × 60 · 90 · 120 · 150 · 180°(합계 10개; 처음의 45–180° 15° 간격 20개는 CPU 회귀에서 60–150° 만 골랐고 이웃 각도 차이는 비용 약 1 안쪽, ws1 에서 최대 14 s 가 걸려 줄였다). 호는
   `_sample_arc` 로 같은 사각형 · 격자 · 탐색 여유(clearance)에 대해 연속 휩쓸림 검사를 받고, `turnaround_check` 가 있으면 통과해야 한다(러너: 주행 허가의
   현재 snapshot 에서 `ObstacleLayer.check_turnaround_arc` — ① 출발에 필요한 부분, 즉 허가 자신의 걸음(3 m)을 다른 경로와 똑같이 검증하고 ② 호 전체에
   알려진 점유 칸이 없을 것(UNKNOWN 은 지나치는 걸음, `unknown_passes`). 나머지는 모든 경로처럼 허가가 주행 중 검증한다. 격자는 센서에서
   `max_clear_m` 5 m 안, 그리고 FREE 생성의 마지막 거리 대역(`rho_bands_m`, 뒤차축에서 4 m) 안의 칸만 FREE 로 만들기 때문에 차체가 그보다 멀리
   쓸고 가는 90° 이상 호는 출발점에서 전체를 검증할 수 없다(cusp 위치 정체 7판의
   prefix 검사와 같은 두 부분). 계획 격자가 UNKNOWN 을 자유로 다루는 것을 이 검사가 보완한다. 호 전체 걸음을 위해 `DrivePermission.check_path` ·
   `ObstacleLayer.check_candidate` 에 이번 검사만의 `lookahead_m` 을 더했다). 호 끝에서
   Hybrid A* 1회(재시도 사다리 없음, 후보당 8,000 · 전체 60,000 확장; 장애물 휴리스틱 격자는 목표 · 격자가 같으므로 후보끼리 한 번 만들어 공유).
3. 직접 계획과 성공 후보를 **경로 전체 비용**으로 비교해 최소를 고른다(동률은 직접): 전진 길이 + `RETURN_TURNAROUND_REVERSE_WEIGHT`(3.0, 처음 2.0 — 아래 Isaac v6) × 후진 길이
   + 전환 1.0 m × 횟수 + steering 0.15 × |κ/κmax| × 길이 + steering 변화 0.15(출발 직진에서의 변화 포함) — travel config 의 항목으로 만든 경로 전체 비교용 목적함수이며,
   탐색은 해석 발사에 steering 항을 매기지 않으므로 탐색 비용 그 자체는 아니다. 가중은 측정값이 아니라 정책값(긴 무부하 복귀는
   전진 우선)이고, 탐색 자체는 travel config 의 1.3 을 그대로 쓴다. 결과는 "평가한 후보 중 최소"이지 가중 비용의 최적 경로가 아니다.
4. 시간은 안전장치만: 후보 단계(호 검사와 하위 탐색 모두)는 호출자의 deadline(절대 시각, 또는 호출 시작부터 센 `SearchBudget` — 직접 계획과 공유)과 직접 계획 뒤 18 s 중 먼저 오는
   시각에서 멈추고 남은 후보를 `skipped_time`, 그 뒤에 끝난 후보를 `late`(비교하지 않음)로 남긴다. 이 장치가 발동하지 않은 실행에서만 같은 입력 → 같은 결과다.
5. 경로는 호 표본 + 하위 경로(첫 자세 중복 제거)를 이은 하나의 `PlanResult`(sample 0 과 호 표본은 후진 · 호 곡률). `PlanResult.turnaround` 에 직접 계획 ·
   후보별 상태와 비용 항목 · 선택 · 확장 수 · 시간 중단을 기록하고, 러너는 `paths.json`(path_record)과 실시간 계획 이력(`live_plans[].turnaround`, 전체
   기록 — 뒤의 재계획이 `paths.json` 을 덮어써도 남는다)에 남긴다. 경로 길이는 호의 해석 길이 + 하위 경로 길이.
