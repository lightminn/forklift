# M-a 미션 실행부 분리 (계획 3판, 2026-10-15)

상태: 3판, 독립 검토 3회와 수렴 확인 완료 — 1판 검토(② Codex 적대 P2 9·P3 1, ③ 독립 P1 2·P2 8)를 2판에서, 2판 재검토(해결 14·일부 6·새 P2 3)를 3판에서 반영 · 설계: [운용 콘솔 설계](../design/2026-10-13-operator-console.md) 4.1–4.5·6절 · 계약: [console/1 초안](../interfaces/2026-10-13-operator-console-contract-draft.md) 1·5·6·9절

## 1. 목적, 범위, 완료의 뜻

`sim/isaac/run_transport.py` 의 미션 판단을 Isaac 없이 도는 `forklift_core/mission/` 으로 옮기고, 작업 지시·일시정지·정지·재개·취소를 받는 경계와 중재기(M-b)에 내보낼 미션 안전 상태를 둔다.

**M-a 의 완료 = 시뮬레이션용 미션 분리와 명령 경계.** 실차가 이 코어를 그대로 쓰려면 결정에 쓰이는 참값(2절)을 실측 피드백으로 바꿔야 하는데, 그것은 동작이 바뀌는 일이라 M-a 밖이다. 대신 M-a 는 참값 의존을 포트 하나(`SimTruth`)에 모아 목록으로 내고, **실차 준비 게이트**(M-a 뒤 별건: 항목마다 대체 피드백·판정 규칙·검증)를 정의해 둔다. 그 전까지 실차 구성에서 참값 포트를 요구하는 기능은 시작 전에 거부한다(조용한 대체 금지).

제외: 중재기(모드·세대·lease — M-b), 실시간 실행기(M-c), 계획기·추종기·인식 알고리즘 변경, 참값 제거, 물리·plant 변경.

**사용자 결정(2026-10-15): "M-a, b 부터 차례대로 진행".** 설계는 M-a 를 S4 확인 배치 뒤로 두었다. plant 승격 보류로 재측정·정식 S4 를 다시 돌려야 하므로, M-a 를 먼저 끝내고 새 소스로 잰다(측정 도구가 전체 소스 사전을 비교한다 — `run_transport.py:1436`, `tools/s4_drive_terms.py:398`).

## 2. 현황 (원본에서 셈, 2026-10-15)

- `run_transport.py` 8,915 줄, `run()` 1539–8780(AST), 그 안의 함수 정의 85 개. 주 루프 5734 행. 판단 코드는 루프 안 약 1,700–2,000 줄과 루프 앞 클로저 약 2,400 줄.
- 단계: `observe → approach → insert → lift → extract → transport → lower → withdraw → settle → return_home → home_settle → complete`, 조기 종료 `repeat_capture_done`·`repeat_target_not_reached`·`near_tracking_stopped`. 실행기는 시작 전에 시나리오로 계획을 세우고(3754) 첫 단계를 스스로 고른다(4132) — 작업 지시를 기다리지 않는다.
- **결정에 쓰이는 참값**(실차 준비 게이트 목록의 출발점): 허가 방향·검사 속도·재계획 조건의 차체 속도 `truth_speed`(7614 에서 계산, 7621·7647·7650·7732 — SLAM 을 켜도 쓴다), N9 침묵 중단(7785), SLAM 없을 때 cusp 정지(5007·6234), 승강·내리기 종료의 팔레트 z·승강 관절 `require`(7576–7586), `--planning-target` 의 참 목표(7166), 비상정지 탐침의 `truth_rear`(8382).
- **평가 순서**(이동 때 보존): 루프 시각 `t` 는 5735 에서 한 번만 정한다. 캡처는 안에서 물리를 여러 틱 진행시키고(`perception_adapter.py:400`) 그 뒤 `now_s`·`rear`·`rear_stamp` 만 바뀐다(6678–6704) — 같은 반복의 전이는 옛 `t` 를 쓴다(7499). 같은 틱 안에서 SLAM release 가 `rear` 를 바꾼 뒤(5951–5954) 격자 재투영·허가를 계산한다(7624–7650). 그 밖에 틱 중간 `rear` 덮어쓰기 5953·6066·6117·6160·6595·6703·7849.
- **비결정 후보**: 계획 예산의 `time.monotonic()`(`obstacle["deadline"]`, `pallet_mission.py` 123·177(마감을 넘기면 성공 경로도 timeout 으로 바꾼다)·1101·1243, `hybrid_astar.py` 596–604(마감에 닿아도 찾은 경로는 성공으로 낼 수 있다)), SLAM 브리지의 `/map` 콜백이 `latest_map.npz` 를 4 스레드 실행기에서 교체하고(`isaac_slam_bridge.py:127–167·318`) 계획이 호출 순간의 파일·mtime 을 읽는 것(3178–3208), 기록에 들어가는 `id()`(2292 경로 표시, `cusp_heading_hold.py:73` 등).
- **시계**: 장애물 진행 감시는 `since_s` 로 60 s(7820), `StopDetector` 는 유지 시간을 호출 횟수로 센다(`slam_pose.py:284–285`), 승강은 누적 목표를 관절 위치 목표로 보낸다(7564·8466) — 목표만 멈춰도 관절은 목표까지 계속 간다.
- **근접**: 접근–삽입–추출의 SLAM hold 는 포켓과 차체의 상대 프레임을 지키려는 것이고(4292), 근접 제어는 같은 hold episode 인지 검사하며(2707), 추적기는 관측 소실이 `reacquire_s` 를 넘으면 실패로 고정된다(`near_field_tracking.py:615`) — 실행기는 이를 종료 정지·임무 실패로 잇는다(2728·2928).

## 3. 결정

**D1 코어와 포트, 평가 순서.** `MissionCore` 는 한 제어 틱을 지금 코드와 같은 **순서의 하위 단계**로 돈다: 상태 읽기 → SLAM release → 추종·hold·재계획 → 도착 전이 → 승강·시간 전이 → 허가·장애물 대응 → 명령 조립. 각 하위 단계가 필요한 세계 값은 그 자리에서 포트로 받는다(허가를 틱 시작에 미리 받지 않는다 — release 뒤 좌표계에서 계산해야 하므로). 시각은 둘로 나눈다: `tick_t`(루프 시각, 한 틱 안에서 불변)와 포트가 돌려주는 관측 시각(캡처 뒤의 `now_s` 등). 포트는 지금 실행기 동작 그대로 구현한다.

**코어와 서비스의 소유 구분.** 물리 틱마다 갱신되는 상태 — SLAM 자세 추적기(`SlamPoseTracker`: 보정 수신·hold·release), 오도메트리·정지 감지, 장애물 층(격자·스캔), 근접 프레임 읽기 — 는 코어가 아니라 **서비스**가 가진다. 캡처처럼 코어 호출 안에서 물리가 도는 동안 이 상태가 바뀌어도 그것은 서비스 안의 변화이고, 코어는 서비스 메서드(`release`, `hold`, `limit` 등)를 포트로 불러 그 응답만 본다. 그래서 재생은 서비스 응답을 고정하면 된다. **코어는 벽시계를 읽지 않는다.** 계획 마감(`obstacle["deadline"] = time.monotonic() + 20`, 7861 등)은 시계 포트로 읽고, 그 값은 재생 기록에 들어간다(또는 마감 생성·검사를 계획 포트 안으로 묶는다 — M-a0.5 에서 둘 중 하나로 고정).

**D2 동등성 증거 — 재생이 기본, 폐루프 A/B 는 회귀.**
- **기본 증거 = 기록 재생.** M-a0 에서 이동 전 실행기에 **경계 기록기**를 넣는다: 틱마다 코어가 받을 입력과 모든 포트 호출의 요청·응답(읽은 지도 버전, 계획 결과, 캡처 결과, 허가 결과, 참값 포트 값)과 출력(구동 후보·적용 명령·승강 목표·단계·이벤트). 기록은 `id()` 대신 **논리 ID**(경로 번호, 추종기 일련번호)를 쓴다. 이동 뒤 코어를 같은 기록에 개방 루프로 돌려 틱별 출력과 포트 요청이 같은지 본다 — 계획 마감·지도 콜백 같은 비결정 요인은 기록된 응답으로 고정되고, 벽시계는 시계 포트 응답으로 고정되므로 재생은 결정적이다. 기록기는 포트 응답을 다시 읽지 않고 **당시 값을 복사**해 남기고, 예외와 호출자에게 보이는 변경(서비스 상태의 요약)도 기록한다. 기록기가 비동기 입력(지도 콜백 시점)을 전혀 흔들지 않는다고는 보장하지 못하므로, 재생 증거는 **계측된 기준 실행에 대한 것**이라고 적는다.
- **회귀 = 폐루프 A/B.** 같은 설정·seed 로 이동 전·후 소스를 돌려 정규화한 기록이 같은지 본다. 정규화 규칙을 M-a0 에서 고정한다: 출력·소켓·스냅숏 경로, 벽시계 필드(`*_wall_s`, `wall_time_s`, `slam_wall_s` 등 — 목록으로), JSON 키 순서 무관·값 비트 비교, NPZ 배열 비트 비교(NaN 같음), 소스 provenance 와 입력 파일 내용은 따로 검사. 같은 소스 두 번이 같지 않은 행(지도 콜백 경쟁, 계획 마감)은 그 행만 A/B 에서 빼고 재생으로 덮는다고 보고한다.
- **분기 통과 목록.** 묶음은 seed 개수가 아니라 **통과해야 할 이벤트·분기 목록**으로 완료를 정한다: 관찰 후보 전환·재관찰, 근접 보정 수락·거절, 관측 소실, 재캡처·재정렬, D7 재접근(4758–4792), cusp 재계획·heading hold, 정체 재계획, 장애물 정지·후퇴·탈출·재계획 실패, 인증 인출, 도킹, 복귀, 각 미션 거절 사유. 기록기가 분기 이름을 남기고, 묶음 전체에서 목록이 채워질 때까지 seed·주입을 늘린다. 조기 실패·마감 제외로 빠진 분기는 '미검증' 으로 남는다.

**D3 참값 = `SimTruth` 포트.** 2절 목록의 각 사용을 포트 메서드로 옮기고 이름을 붙인다. 실차 준비 게이트(별건)의 항목이 된다. 참값 불변식 위반(기울기·겹침·포크 접촉 등)은 평가 쪽에 남는다.

**D4 거절 = 명시적 종료.** `require` 로 나가던 미션 거절은 코어가 `MissionFailed(reason)` 으로 즉시 끝내고, 실행기가 같은 문자열의 예외로 바꾼다. 동등성에는 실패 사유 문자열뿐 아니라 **실패 시점과 그때까지의 부분 기록·부수 효과**(경로 파일, 기록 배열)가 같아야 한다는 것을 넣는다.

**D5 명령과 시간 계약(M-a0.5 에서 먼저 고정, 구현은 M-a3).**
- **명령**: `mission_submit(pallet_id, destination_id, targets_revision)` → `mission_id`, `mission_pause`·`mission_resume`·`mission_cancel(mission_id)`, 중재기가 주는 정지 종류 `none`·`controlled`·`preempt`(설계 4.2), 보류 `held`/복귀(TELEOP 진입·이탈, M-b 와 함께). 배치 실행기는 시작 때 시나리오 대상으로 `mission_submit` 을 스스로 넣는다 — 기본 경로를 지금과 같게 유지한다.
- **적용 단위**: 정지 종류는 물리 틱마다(`step_world` 경로) 출력에 걸린다 — 캡처처럼 코어 호출 안에서 물리가 도는 동안에도 `preempt` 는 바로 속도 0 이 된다. 미션 명령(pause·cancel)은 다음 제어 틱 시작에 반영한다. **배치 실행기의 포트는 동기라서 진행 중인 연산(캡처·계획·release+재계획)은 원자적으로 끝난다** — 반쯤 끝난 상태가 생기지 않고, 그 틱에 끝난 연산의 결과(경로 설치, 단계 전이 포함)는 유효하다. 일시정지는 그 다음 틱부터 전이·승강을 멈추고, 재개 절차의 경로 재검사가 그 결과를 다시 확인한다. 정지 요청부터 반영까지의 지연은 한 제어 틱 + 진행 중 연산 시간이며, 그동안 차량은 물리 틱마다 걸리는 정지 종류로 막힌다. 물리 틱 정지 override 는 `world.step()` 직전에 적용하고, 적용 명령·slew 상태·정지 감지용 명령 기록을 같은 값으로 맞춘다 — `none` 이면 지금 출력 경로를 그대로 통과한다(출력 조립을 물리 틱마다 다시 하지 않는다).
  - **비동기 포트(M-c 이후)의 늦은 결과**: 그때는 연산을 미션 세대(`mission_gen`, 정지 경계마다 증가)로 표시하고 세대가 바뀐 결과를 버린다. 이것이 성립하려면 포트를 부르기 전에 미션 상태를 바꾸지 않아야 한다(준비 → 포트 → 확정). 지금 코드에는 그렇지 않은 연산이 있다 — 예: `slam_release()` 는 계획 포트 전에 `pending_release=None` 으로 바꾸고 보정을 release 한다(4313). M-a0 에서 이런 연산을 전부 목록으로 만들고, 구조 변경(준비·확정 분리)은 동작이 바뀔 수 있으므로 M-c 착수 전 별건으로 한다.
- **승강 정지**: 일시정지·preempt 면 승강 목표를 **실측 승강 위치로 동기화**해 유지하고(목표 동결이 아니다), 재개 때 실측에서 다시 출발한다. Isaac 시험에 들기·내리기 중 일시정지를 넣는다.
- **타이머 분류**: M-a0 에서 실행기의 모든 시계·카운터를 목록으로 만들고 셋 중 하나로 분류한다 — 작업 시간(일시정지에 멈춤: 단계 한도·`phase_elapsed_s`, 장애물 진행 감시 60 s), 신선도(계속 흐름: 격자 FREE 증거 나이, 센서 침묵, SLAM 보정, 근접 관측 나이), 틱 수 기반(시간으로 바꿀지 결정: `StopDetector` 등 — 제어 주기가 바뀌면 의미가 달라진다). 배치 전체 예산 `max_sim_seconds` 는 그대로 두고, 일시정지 시험은 그만큼 예산을 늘려 돌린다(작업 예산과 시험 한도를 구분).
- **재개 정책은 단계별**(설계 4.3·4.5 를 실제 분기에 맞춤):

  | 하위 상태 | 재개 | 근거 |

  | 근접 구간 진입 뒤 ~ insert(포크가 포켓 안 포함), hold 중 | hold 를 유지한 채 정지 확인·근접 관측 유효성 확인; 추적기가 실패로 고정됐으면 재개 불가 → 축을 따라 똑바로 빼기만 허용 | hold episode 검사(2707), 추적기 실패 고정(615) |
  | lift·lower | 승강 목표를 실측에 맞춰 이어서; 4.5 s 단계 한도 시계는 멈췄던 만큼 연장 | 고정 시간 전이(7576·7579) |
  | extract(적재, 포크가 포켓에서 나오는 중) | 정지 확인 → 같은 후진 직선을 적재 footprint 로 재검사 → 이어서. 인증 경로가 아니다 | 적재 footprint 로 계획한 별도 후진 직선(`pallet_mission.py:1472`) |
  | transport, 자유 구간 | 빈 차체 자유 구간과 같은 절차, 적재 footprint | 4.5 표 |
  | transport, 도킹 중(`goal_frame="held"`) | hold 유지, 정지 확인 → 도킹 직선 이어서. release 가 필요하면 `carry_on_release()`(목표·인출 경로·목적지·`to_world` 를 함께 옮김)로만; 일반 재계획 금지 | 도킹 목표 hold 고정(4574), 일반 복구 거부(6128), `docking_retry.py:27` |
  | withdraw(포크가 포켓 안, 인증 인출) | 정지 확인 → 인증된 같은 축으로 이어서 | known_transition 인증은 withdraw 에만(4184) |
  | settle·home_settle | 정지 확인 → 남은 대기 시간 이어서(작업 시간) | 1 s 고정 대기(7588·7594) |

  표의 하위 상태는 단계 × 도킹 상태 × hold 소유 × 진행 중 연산의 조합이다. M-a0.5 에서 코드의 실제 분기를 전부 세어 표를 닫고(빠진 조합은 '재개 불가 → 정지 유지' 로), 계약 6절 사유와 맞춘다.
  - **일시정지 중 근접 보호는 계속 돈다.** 관측 전달·`status()`·보호 판정을 일시정지 동안에도 매 틱 수행한다(호출을 건너뛰면 실패 고정 여부 자체가 달라진다 — 소실 검사를 미루면 `failed` 가 아닌 채로 남는다). 일시정지 중 실패로 고정되면 재개는 빼기 복구만 허용한다.
  실패 사유 이름은 계약 6절 잠정안(`stop_confirmed`·`state_verified`·`frame_reexpressed`·`path_rechecked`)에 위 분기를 맞춰 M-a0.5 에서 확정하고 계약을 고친다.
- **작업 생명주기**: `idle` → (`mission_submit` 수락, `mission_id` 는 코어가 발급) `accepted` → `running` ⇄ `paused`·`held`·`resuming` → `done`·`failed`·`cancelled` → `idle`. 활성 임무는 하나이고, 활성 중 새 제출은 `reject(mission_active)`. 종료 뒤 실제 상태(적재·삽입·승강)는 남으므로, 새 임무는 **빈 차체·근접 구간 밖**에서만 받고 그 밖이면 복구(빼기·내리기)를 먼저 요구한다(`reject(recovery_required)`). 배치 실행기의 자동 제출은 이 생명주기의 첫 전이를 대신 누를 뿐이다.
- **취소**: 정지 확인 뒤 `cancelled` 로 끝난다. 적재·삽입 상태는 그대로 보고하고(포크가 포켓 안이면 빼기 복구만 허용), 배치 실행기에서는 `complete` 외 종료를 실패로 보던 종료부(8532)에 `cancelled` 를 별도 결과로 더한다.
- **근접 계약과 명령 일정**: `--mission-commands` 는 `POST_MEASUREMENT_ARGUMENTS` 에 `None` 으로 등록한다. 값이 있으면 근접 계약이 실행을 거부한다(`near_tracking.py:1170–1181`) — 근접 bounds 는 일시정지 없는 실행에서 잰 것이라 그 적용은 별도 결정이다. 그래서 근접 구간의 일시정지 시험은 **근접 추적 없이**(D5 off) 돌리거나, bounds 적용 조건 확장을 따로 계획한다(열린 질문).

**D6 미션 안전 상태 출력(M-b 입력).** 코어는 매 제어 틱 실제 상태를 낸다: 적재 여부(단계 추정이 아니라 판정 근거와 함께), 포크가 포켓 안인지, 승강 실측·목표, 근접 보호 상태(관측 유효·실패 고정), 현재 경로 번호·프레임(보정) 버전, 마지막 적용 명령. `held`·`failed`·`cancelled` 에서도 낸다. M-b 는 이것만 보고 주행·승강 허가를 따로 판정한다(설계 4.5) — 미션 내부를 들여다보지 않는다.

**D7 대상·목적지 목록(M-a4).** `targets`(ID·자세·상태)와 `destinations`, `targets_revision`. revision 은 자세·상태·보정 버전이 바뀔 때 오르고, 운반 중 대상은 `pose: null`(`carried`), 내려놓은 뒤 새 위치로 다시 등록한다(계약 5.1). 운반 중 자세 갱신으로 revision 이 폭증하지 않게 `carried` 동안은 자세를 싣지 않는다. ID 는 한 지도·세션 안에서 재사용하지 않는다.
