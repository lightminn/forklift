# 1e 다음 단계: 코어 추가 스레드 작업자, 부족하면 프로세스 작업자 (2026-11-10 계획, 결과 전 고정 대상)

실시간화 계획 5.28(`docs/plans/2026-10-17-realtime-sim.md`)의 1e 는 장애물층 스캔 갱신의 계산을 메인 스레드에서 떼어 내는 일이다. 1e-0 의 등록식 결과(`docs/validation/2026-11-10-g3-1e0-run.md` 재측정 2, 잡 17604)는 "스레드 작업자로는 순절감 0.0182 < 0.03707 → 프로세스 설계를 총괄에"였다. 이 문서가 그 설계다. 총괄 지시(2026-11-10)에 따라 "스레드 작업자 + 물리 코어 추가"(a)와 "프로세스 작업자 + 코어 추가"(b)를 같은 기준으로 비교하고, (a) 가 충분하면 (a) 를 고른다.

독립 검토 셋(자체 검토 절)의 결론으로 **두 단계**로 나눈다.
- 단계 1: (a) 를 잰다.
- 단계 2: (a) 가 부족할 때만 (b) 를 따로 설계·측정한다.

나누는 이유: (b) 는 그림자 기억의 소유를 바꾸는 큰 변경이다. 동기 재투영·스크래치 계획 복사가 그 상태를 쓰기 때문이다(7 절). (a) 가 충분하면 필요 없는 일이다. 선택 결과는 "둘 다 재고 (a) 우선"과 같다.

## 1. 출발점

- 1e-0(17604, 세션이 SMT 짝 코어 하나)의 관측:
  - 옮긴 몫(메인 층 갱신 일의 차) 0.0695 s/sim s.
  - 스레드에서 계산 벽시계가 2.35 배(스캔당 7.0 → 16.5 ms), 스캔별 CPU/벽시계 0.98 → 0.55.
  - 메인 다른 일 +0.0505. 순절감(k = 4) 0.0182, 직접 W 차 −0.0084(분해식과의 잔차 −0.0266).
- **1e-0 분석기의 k = 4 대기는 구조적으로 0 이다**(검토 ②·③, 코드 확인). k = 3 실행에서는 `LayerWorker.tick_start`(`sim/isaac/layer_worker.py` 91–104)가 scan + 3 의 시각을 적은 뒤 같은 호출에서 설치를 기다린다. 그래서 scan + 4 의 시각에는 그 대기와 설치가 이미 들어가 있고, 분석기의 k = 4 정시 대기(`g3_1e0_analyze.py` 280–283)는 늘 0 이 된다.
  - 17604 의 "k = 4 대기 0.00 ms"는 측정값이 아니다.
  - 그래도 결론("스레드 작업자로는 부족")은 그대로다. 실제 k = 4 대기는 0 이상이라 순절감이 더 작아질 뿐이다.
  - k = 2·3(실행한 k 이하)의 대기는 영향이 없다.
- **세션이 실제로 쓰는 CPU 는 물리 코어 하나다.** 묶음 실행기는 세션을 `session_cpus` 로 묶는다(`tools/isaac_bundle.py` 1581·1754, `taskset -c`).
  - 17604 의 `session_cpus` 는 [0, 12] 이고(`g3e0r2/bundle/summary.json`), ws1 의 `lscpu -e` 에서 CPU 0 과 12 는 같은 코어 0 이다. 브리지는 [1, 13](코어 1)이다.
  - 같은 코어를 Kit 메인 스레드, PhysX 작업 스레드, 원거리 인식 스레드, 계획 작업자 프로세스, 학습 제안기 프로세스, 1e-0 의 레이어 작업자가 나눠 쓴다.
  - 1e 판정 실행 6 세션의 세션 트리 평균 사용은 1.60 코어였다(Σcpu_s/Σwall_s, `docs/validation/2026-11-10-g3-1d-1e/g3el_bundle_results.jsonl`). 논리 CPU 둘 가운데 1.6 이다.
- 그래서 스레드의 CPU/벽시계 0.55 와 메인 다른 일 증가는 GIL 경합과 물리 코어 부족 모두와 맞는다. 1e-0 은 둘을 가르지 못했다. 이 계획은 원인을 가르는 실험이 아니라, **물리 코어 둘의 배치에서 어느 구조가 문턱을 넘는지**를 고르는 실험이다(검토 ② P2-10). 다만 스레드마다 실행 큐 대기를 기록해 원인의 정황을 보고한다(4 절).

## 2. 단계 1 의 팔과 배정

**배정(두 팔 공통).**
- 세션에 물리 코어 둘(A, B)을 준다. 논리 CPU 는 각 코어의 `thread_siblings_list` 로 정한다(ws1 은 코어당 둘; SMT 가 없는 곳은 하나). 브리지 코어는 지금처럼 따로다.
- 세션 프로세스 전체를 A·B 에 묶는다(`taskset`, 지금 묶음 실행기 방식의 확장).
- T 의 작업자 스레드는 시작할 때 B 에 자기를 고정한다(`os.sched_setaffinity(0, B)`). 리눅스에서 스레드 안의 호출은 그 스레드만 바꾸고, 그 뒤 그 스레드가 만드는 스레드가 물려받는다.
- 나머지(Kit·PhysX·인식·계획 작업자·학습 제안기·인코더)는 A·B 안에서 OS 가 배치한다. 그래서 B 는 작업자 전용이 아니다(한계).

**팔.**

| 팔 | 계산이 도는 곳 | 기준 |
|---|---|---|
| D `delay` | 메인 스레드(설치만 k 틱 늦춤, 작업자 없음) | 순절감의 기준 |
| T `thread` | 작업 스레드, B 에 고정 | — |

- 같은 배정의 D 를 기준으로 한다. 이것은 "물리 코어 둘에서 작업자를 둘 때의 추가 효과"를 잰다(검토 ②). 코어 추가 자체의 효과나, 지금의 코어 하나 운용 대비 총효과는 이 비교로 식별하지 않는다. 17604 와의 비교는 보고만 한다.
- 문턱 0.03707 은 W 의 운영 목표로 다시 채택된 값이다(계획 5.28). 여기서는 "물리 코어 둘의 D 위에서 T 가 0.03707 을 더 줄이는가"로 쓴다. D 가 코어 추가만으로 좋아져도 T 의 추가 절감이 작으면 T 는 탈락한다. 이 해석을 명시해 둔다(검토 ② P3-11).

## 3. 측정 등록(단계 1; 설계 승인 뒤 결과 전 고정; rv4 뒤에 냄)

- 장면: 1e-0 과 같다(line_m far K f 1.0 confirm, seed 0, 1b·1c·1d 켬, INSTR off).
- 배정: 2 절. 한 잡에 한 세션씩 순차(`--slots 1`). 묶음 실행기의 지금 구조는 잡 전체에서 CPU 를 한 번 나누고 모든 슬롯이 같은 `session_cpus` 를 쓰므로, 단일 슬롯 측정에서만 "세션당 코어 둘"이 그대로 성립한다(검토 ② P2-9).
- k: 실행 k = 3. 판정에 쓰는 k 는 실행한 k 이하(2, 3)만 기록에서 읽는다.
  - 두 짝 모두에서 T 의 k = 3 정시 대기 평균이 0.5 ms 이하면, 두 짝에서 공통으로 만족하는 가장 작은 k 를 쓴다. k = 2 가 골라져도 직접 W 와 다른 비용은 k = 3 설정에서 본 값이라, k = 2 는 후보 예측이다. 선택된 실제 k 는 1e-2 에서 확인한다.
  - 아니면 보충 짝(D T T D, k = 4 실행)을 내고 k = 4 로 판정한다. D 도 k 에 따라 설치 지연·정지 모형·사용 나이가 바뀌므로(`worker_config`) 같은 k 로 다시 잰다.
- 세션: D T T D(두 짝, 순서를 뒤집어 시간 흐름을 상쇄). 1e-0 의 세션당 약 4 분(17604: 3 세션 12 분)으로 약 20–25 분, 보충 짝이 생기면 그만큼 더한다.
- 무효:
  - 1e-0 과 같다(자기 GPU 감시 + CPU sampler). 다른 GPU 의 사용자 잡은 17604 의 총괄 결정처럼 한계로 기록한다(이 등록에서 미리 정함).
  - 환경·인프라 무효(겹침, 감시 실패, 기동 실패·재시도로 순서가 바뀜)만 그 짝(D·T 둘)을 한 번 다시 낸다. 다시 낸 짝도 무효면 총괄에 올린다.
  - 작업자 오류(`layer_worker_failed`·timeout), 미션 실패, 안전 사건은 재실행으로 지우지 않는다(검토 ② 2 차 P2). 환경 무효가 함께 확인되지 않으면 그 짝은 "T 불합격"으로 세고, 원인 확인을 총괄에 올린다. 분석기는 두 종류의 무효를 따로 낸다.
- 짝마다 계산(1e-0 등록식 그대로, 기준은 같은 짝의 D): net_T(k) = 옮긴 몫 − 정시 대기 × 스캔률 − 장벽 대기 − max(0, 메인 다른 일 증가). 직접 추정 W(D) − W(T)와 잔차를 함께 낸다.
- **결정 규칙(잠정 분기; 채택은 1e-1 구현과 1e-2 폐루프 판정, 검토 ② P2-4).**
  1. 두 짝 모두 net_T ≥ 0.03707 이고, 두 짝 모두 직접 W(D) − W(T) ≥ net_T 의 절반이면 → (a) 를 고른다(1e-1 로).
  2. 아니면 단계 2((b) 설계)로 가서 총괄에 올린다. 분해식만 통과하고 직접 W 가 따르지 않는 경우도 여기다(1e-0 의 잔차 −0.0266 이 그 반례였다).
- 보고만:
  - 스레드별 CPU 시간과 실행 큐 대기: 세션 트리의 스레드·자식 프로세스의 `/proc/<pid>/task/<tid>/stat`(utime+stime)와 `schedstat`(run_delay)를 10 s 마다 표본한다. 도중에 생기거나 사라진 스레드는 관측한 수명 구간만 세고, 표본 사이에 생겼다 사라진 수(누락)를 함께 보고한다.
  - 작업자 스레드는 스캔마다 계산 전후의 자기 `schedstat`·`sched_getcpu()` 를 적는다(검토 ③). CPU/벽시계가 1 보다 작은데 run_delay 가 크면 코어 경합, 작으면 잠김(GIL 등)의 정황이다. 원인별 몫은 주장하지 않는다.
  - 코어 추가 자체의 효과(총괄 요청): D(코어 둘)의 실현 AUTO 배율과 W 를 17604 의 `delay`(코어 하나, 배율 0.941, W 0.8739)와 견준다. 나중에 잡 크기를 정할 때 쓴다. 다른 잡·다른 시각이라 판정에 쓰지 않는다.
  - `evidence_stale` 틱 수와 미션 결과. k = 4 의 보정 추정(대기 + 설치 시간을 scan + 4 시각에서 뺀 값)도 보고만 한다.
- 분석기: 1e-0 분석기를 확장한다(배정 대조, 두 짝, 공통 k, 직접 W 조건, 스레드별 기록, k = 4 보정 보고). 결과 전에 커밋하고 Codex 리뷰를 받는다.

## 4. 단계 1 의 구현 범위(설계 승인 뒤, 시험 먼저)

1. 묶음 실행기: 단일 슬롯 잡에서 세션에 물리 코어 둘을 주는 옵션(`--session-cores 2`). 형제 CPU 는 `thread_siblings_list` 로 찾는다. 다중 슬롯의 슬롯별 배정은 범위 밖이다(6 절).
2. 러너: `--layer-worker-cpus`(T 의 작업자 스레드 고정). 실제 affinity(메인 프로세스의 모든 TID, 작업자, 자식 프로세스)와 스레드별 `stat`·`schedstat` 을 기록한다.
3. 작업자 스레드의 스캔별 `schedstat`·`sched_getcpu()` 기록.
4. 분석기·목록 생성기 확장(3 절).
5. 단위 시험(배정·고정·기록·분석기), off 경로 불변은 runs29 게이트 29/29, ws1 전체 pytest, Codex 수렴. 그 뒤 총괄 승인 하에 측정.

## 5. 단계 2 의 전제: (b) 프로세스 작업자에 필요한 것(단계 1 이 부족할 때만 따로 계획)

독립 검토가 찾은 것을 그대로 남긴다. 단계 2 의 계획은 이것들을 먼저 닫아야 한다.

- **그림자 기억의 소유(검토 ② P1, ③).**
  - 메인의 동기 `refresh`(SLAM 재투영 `core.py` 4995 부근, 단계 전이 등)도 `refresh_compute` → `shadow.apply` 로 기억을 바꾼다. 스크래치 계획(`run_transport.py` 5761 부근)은 층을 `deepcopy` 해서 따로 `refresh` 한다.
  - 기억을 작업자만 가지면 이 경로가 깨지고, 메인에도 두면 서로 다른 기억이 된다. 동기 계산을 어디서 할지와, 스크래치 복사용 상태를 어떻게 넘길지를 먼저 정해야 한다.
- **메인 격자의 prune(검토 ② P2-2).** 메인 격자는 `snapshot` 안에서만 prune 된다. 스캔 snapshot 을 작업자로 옮기면 메인 스캔 목록이 계획기 호출 사이에 계속 커지고 `_memory_hits` 가 그 전체를 돈다. 메인 prune 지점과 그 비용 계측이 필요하다.
- **affinity(검토 ② P2-5).** 자식 PID 에 나중에 적용하면 그 PID 의 메인 스레드만 바뀐다. 수치 라이브러리를 import 하기 전에 자식이 자기 마스크를 정하고, 모든 TID 를 검증해야 한다. 스레드가 있는 부모에서 `preexec_fn` 은 쓰지 않는다.
- **준비(검토 ② P2-6, ③).** 커널 모드는 `plan_worker` 의 `worker_env` 처럼 명시적으로 넘긴다(새 인터프리터의 기본은 `reference`). 예열은 일회용 격자·기억으로 모든 커널 분기를 돌린 뒤 버린다. 준비 응답에 실제 커널·스위치·초기 상태를 담는다.
- **수명(검토 ② P2-7, ③).** 상태가 있는 작업자는 재시작·재전송(`PlanWorker` 방식)을 할 수 없다. 준비 실패·EOF·전송 막힘·계산 상한·pending 중 종료 모두에서 실패 확정 → 제한 시간 안의 종료·kill·wait → 파이프 정리를 정의한다. 종료 통계는 응답마다 사본으로 받아 두어 종료 때 왕복하지 않는다.
- **전달 시각(검토 ② P2-8, ③).** 분석식의 `done_t` 는 부모가 설치할 수 있는 응답을 확보한 시각(부모 시계)이다. 역직렬화는 설치 안(`install_s`)에서 한다. `PlanWorker` I/O 루프의 최대 5 ms poll 같은 큐 지연을 따로 잰다. 스캔 메시지(`add_scans`)의 전달도 센다.
- **전달 비용 예상(로컬, 참고).** 1e-0 의 작업과 같은 크기의 사전(직렬화 90 KB)과 응답(창 240 × 240 칸의 raw·최종 스냅숏, 1.04 MB)을 파이프로 주고받았다(`2026-11-10-g3-1e-process-worker/ipc_bench.py`, 노트북 Core Ultra 5 125H, 단일 실행).
  - 메인 쪽 직렬화 + 보내기 0.086–0.092 ms, 응답 역직렬화 0.032–0.033 ms. 왕복 평균 1.15–1.20 ms, p99 2.0–2.5 ms.
  - 메인 쪽 비용을 스캔당 0.5 ms 로 넉넉히 잡으면 초당 10 스캔에서 0.005 s/sim s 다. 이 0.5 ms 는 예상값이다(I/O 스레드의 GIL 몫과 Kit 안 경합은 재지 않음).
  - 1e-0 의 옮긴 몫 0.0695 에서 문턱까지의 여유는 0.0325 다. 전달 비용 0.005 를 빼면 정시 대기·장벽 대기·메인 다른 일 증가가 함께 쓸 수 있는 몫이 약 0.027 이다.

## 6. 코어와 슬롯의 맞바꿈

live 세션 묶음의 지금 크기(`tools/isaac_bundle.py sizes live`)는 세션당 CPU 2(물리 코어 하나), 잡당 브리지 코어 하나(CPU 2), GPU 당 3 슬롯(VRAM 한계)이다. 노드는 VM 이 꺼져 있으면 CPU 20·GPU 2, 켜져 있으면 CPU 8·GPU 1 이다(`~/wiki/compute/ws1.md` 2026-11-07 기록).

| 세션당 물리 코어 | 잡 CPU 예약(슬롯 1 / 2 / 3) | CPU 20·GPU 2 의 동시 세션 상한 | CPU 8·GPU 1 의 동시 세션 상한 |
|---|---|---|---|
| 1(지금) | 4 / 6 / 8 | 6(3 슬롯 잡 둘, CPU 16) | 3(3 슬롯 잡 하나, CPU 8) |
| 2 | 6 / 10 / 14 | 4(2 슬롯 잡 둘 = 20, 또는 3 + 1 슬롯 = 20) | 1(1 슬롯 잡, CPU 6) |

- 이것은 예약 산술의 동시성 상한이고, 처리량은 아니다. 시간당 완료 수를 유지하려면 6 → 4 에서는 세션이 1.5 배, 3 → 1 에서는 3 배 빨라져야 한다. 비용 판단에는 완료당 CPU 시간과 세션 소요 시간을 함께 본다(검토 ② P3-12).
- 다중 슬롯에서 "세션당 코어 둘"을 실제 고정으로 만들려면 슬롯별 A/B 배정과 작업자 CPU 전달을 묶음 실행기에 따로 설계해야 한다. 지금 구조는 모든 슬롯이 하나의 CPU 풀을 나눠 쓴다.
- 운용 콘솔(`deploy/console/isaac_live.sbatch`, 한 세션)은 묶음 실행기를 거치지 않는다. 채택하면 그 런처의 CPU 예약(4 → 6)과 코어 배정을 따로 고친다.
- 그래서 채택하더라도 "작업자를 켜는 실행만 세션당 코어 둘"로 하고, 배치 기본값은 따로 정할 수 있다. 결정은 측정 뒤 총괄이 한다.

## 7. 한계

- 기존 기준선(1b·1c·1d 의 배율·절감, 1e 판정 실행, 1e-0)은 모두 세션이 SMT 짝 코어 하나에서 돈 조건의 값이다. 코어 둘 조건의 측정과 바로 섞지 않는다.
- B 는 작업자 전용이 아니다. D 에서도 T 에서도 메인 프로세스의 다른 스레드가 B 에 갈 수 있다. 같은 배정 안의 비교라 순절감에는 공정하지만, 결과는 "이 배치에서의 효과"다.
- 두 짝은 작은 표본이다. 결정 규칙이 "두 짝 모두"를 요구하는 것은 그 때문이다.
- 실차(Jetson Orin Nano, SMT 없음)로의 이전은 이 측정이 말하지 않는다. 코어 배정은 형제 목록으로 일반화해 두지만, 실차의 코어 예산은 따로 본다.
- 원거리 인식·학습 제안기·계획 작업자의 순간 경합은 스레드별 기록으로만 본다.
