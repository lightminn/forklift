# 1e 다음 단계: 코어 추가 스레드 작업자 대 프로세스 작업자 (2026-11-10 계획, 결과 전 고정 대상)

실시간화 계획 5.28(`docs/plans/2026-10-17-realtime-sim.md`)의 1e 는 장애물층 스캔 갱신의 계산을 메인 스레드에서 떼어 내는 일이다. 1e-0 의 등록 결과(`docs/validation/2026-11-10-g3-1e0-run.md` 재측정 2, 잡 17604)는 "스레드 작업자로는 순절감 0.0182 < 0.03707 → 프로세스 설계를 총괄에"였다. 이 문서는 그 설계다. 총괄 지시(2026-11-10)에 따라 "스레드 작업자 + 물리 코어 추가"를 비교 팔로 함께 둔다.

## 1. 출발점

- 1e-0(17604, 같은 SMT 짝 코어)의 관측:
  - 옮긴 몫(메인 층 갱신 일의 차) 0.0695 s/sim s.
  - 스레드에서 계산 벽시계가 2.35 배(0.070 → 0.164), 스캔별 CPU/벽시계 0.98 → 0.55.
  - 메인 다른 일 +0.0505. 순절감(k = 4) 0.0182, 직접 W 차 −0.0084.
- **세션이 실제로 쓰는 CPU 는 물리 코어 하나다.** 묶음 실행기는 세션을 `session_cpus` 로 묶는다(`tools/isaac_bundle.py` 1581·1754, `taskset -c`).
  - 17604 의 `session_cpus` 는 [0, 12] 이고, ws1 의 `lscpu -e` 에서 CPU 0 과 12 는 같은 코어 0 이다(SMT 짝). 브리지는 [1, 13](코어 1)이다.
  - 같은 코어 하나를 다음이 나눠 쓴다: Kit 메인 스레드, PhysX 작업 스레드, 원거리 인식 작업 스레드, 계획 작업자 프로세스(`plan_worker`, 세션의 affinity 를 물려받음), 학습 제안기 프로세스, 그리고 1e-0 의 레이어 작업자.
  - 앞선 측정에서 세션 프로세스 트리의 평균 사용은 1.6 코어였다(계획 5.28 "CPU" 줄; 논리 CPU 둘 중 1.6).
- 그래서 스레드 작업자의 CPU/벽시계 0.55 와 메인 다른 일 증가는 두 원인과 모두 맞는다.
  - 같은 프로세스의 GIL 경합: 프로세스로 떼면 없어진다.
  - 물리 코어 부족: 코어를 더 주면 없어진다. 프로세스로 떼어도 같은 코어면 남는다.
- 1e-0 은 두 원인을 가르지 못했다. 이 계획의 측정이 가른다.

## 2. 비교할 팔

모든 팔은 같은 CPU 배정(아래 3 절, 물리 코어 둘)에서 잰다. 순절감은 같은 배정의 `delay` 를 기준으로 낸다. 배정이 달라지면 기준도 달라지기 때문이다.

| 팔 | 계산이 도는 곳 | 메인과 나누는 것 |
|---|---|---|
| D `delay` | 메인 스레드(지금 동기와 같은 일, 설치만 k 틱 늦춤) | — (기준) |
| T `thread` | 같은 프로세스의 작업 스레드, 코어 B 에 고정 | GIL |
| P `process` | 별도 프로세스, 코어 B 에 고정 | 없음(전달 비용만) |

- 선택 규칙(측정 전 고정, 총괄 지시): T 가 충분하면 T 를 고른다. T 가 더 단순하기 때문이다(새 프로세스·전달·상태 복제 없음).

## 3. CPU 배정(두 팔 공통)

- 세션에 물리 코어 둘(A, B; 논리 CPU 넷)을 준다. 브리지 코어는 지금처럼 따로다.
- 고정:
  - 세션 프로세스 전체: `taskset` 으로 A·B 의 논리 CPU 넷(지금 묶음 실행기 방식의 확장).
  - 작업자(T 의 스레드, P 의 프로세스): 시작할 때 B 의 논리 CPU 둘에 자기를 고정한다(`os.sched_setaffinity(0, …)`). 리눅스에서 스레드 안의 호출은 그 스레드만 바꾼다. 프로세스는 Popen 직후 그 pid 에 적용한다.
  - 메인 프로세스의 나머지(Kit·PhysX·인식·계획 작업자·학습 제안기)는 A·B 안에서 OS 가 배치한다. D 도 같은 배정이고, D 에서는 B 를 쓰는 작업자가 없다.
- 결과에 실제 affinity(메인 프로세스, 작업자, 자식 프로세스)를 기록하고 분석기가 등록 값과 대조한다.

## 4. 프로세스 작업자(P)의 설계

**소유.**
- 작업자 프로세스는 계산에 필요한 상태의 복제본을 가진다: 자기 `ObstacleGrid`(같은 설정, 같은 스캔), 그림자 기억(`ShadowMemory`). 그림자 기억은 계산(`refresh_compute`)만 바꾸므로 작업자만 가진다.
- 메인은 지금처럼 자기 격자를 유지한다. 계획기 스냅숏(`_planner` 의 `grid.snapshot`)과 계획 기억의 hits(`_memory_hits`)가 메인에서 격자를 읽기 때문이다.
  - 두 격자는 같은 스캔을 같은 순서로 받는다. prune 은 각 snapshot 의 `now_s` 로 하므로 두 쪽의 스캔 목록이 시각마다 같지 않을 수 있다. 결과는 각자 쓰는 곳에서만 쓰인다.
- 메인이 그림자 기억을 읽는 곳은 종료 요약(`layer.shadow.stats`, `run_transport.py` 11034 부근)뿐이다. 종료 때 작업자에게서 받는다.

**메시지(`plan_worker` 와 같은 방식).**
- `python -m` 으로 띄운 자식 프로세스와, 물려준 파이프 둘로 통신한다(`src/forklift_core/planning/plan_worker.py` 의 선례, spawn 이 아님). I/O 데몬 스레드가 보내고 받는다.
- 메인 → 작업자:
  - 스캔마다 `add_scan` 의 `ObstacleScan`(빔 1,600 개, 거리·self_hit·limit 약 27 KB; 각도는 시작 때 한 번).
  - 갱신 작업마다 `refresh_prepare(detach=True)` 의 작업 사전. 자세, 경로(수백 자세), 외곽, 알려진 팔레트, 회랑·면제·출구 검증, 깊이 지원 값(창 크기 bool, 57.6 KB)이 들어간다. 1e-0 의 `delay`/`thread` 가 쓰는 같은 사전이다.
- 작업자 → 메인: `refresh_compute` 의 결과. raw·최종 스냅숏(창 240 × 240 칸: 상태 uint8 57.6 KB + free_stamp float64 460.8 KB, 둘이면 약 1.04 MB)과 출구 갱신, 작업자 쪽 타이머·CPU 시간.
- 설치(`refresh_install`: 계획 기억 clears, 스냅숏, 허가 `update`)는 지금처럼 메인에서 한다. 1e-0 의 D4 장벽·정시 설치·k 규칙도 그대로다.

**시작·준비.**
- 작업자는 설정·오차표·외곽을 받아 층의 계산 부분을 만든다. 합성 스캔으로 numba 커널을 데운 뒤 "준비" 를 보낸다. 런처는 준비 전에 AUTO 를 시작하지 않는다. 1e-0 의 첫 설치 상한(0.5 s)이 JIT 시간에 걸리지 않게 하려는 것이다.
- 실패·상한 초과는 1e-0 D6 과 같이 세션 실패로 처리한다(바퀴 정지, 층 사용 불가, 기록 보존).

**off 경로.** 작업자를 끄면(`off`) 지금 코드와 같다. 러너·장애물층을 건드리므로 runs29 재생 게이트 29/29 와 ws1 전체 pytest 를 거친다.

## 5. 전달 비용: 예상값과 측정

**예상(로컬 미세 측정, 2026-11-10; 노트북 Core Ultra 5 125H, 1 분 안의 단일 실행).**
- 1e-0 의 작업과 같은 크기의 사전(직렬화 90 KB)과 응답(1.04 MB)을 파이프로 주고받았다(`multiprocessing.connection`, pickle 프로토콜 5, 300 회 중 앞 20 회 제외).
- 메인 쪽 직렬화 + 보내기 평균 0.086 ms. 응답 역직렬화 0.033 ms. 응답 수신(파이프 읽기)은 I/O 스레드가 한다.
- 왕복 지연 평균 1.20 ms, p99 2.04 ms(작업자 쪽 복사 포함, 계산 제외).
- 메인 스레드가 쓰는 전달 비용(직렬화, 보내기, 역직렬화, I/O 스레드의 GIL 몫)을 스캔당 0.5 ms 로 넉넉히 잡으면, 초당 스캔 10 개에서 0.005 s/sim s 다.
- 지연: 왕복 1.2 ms + 계산(1e-0 `delay` 의 스캔당 계산 7.0 ms) ≈ 8.2 ms 로, k = 3 의 겹칠 수 있는 시간 p10 11.0 ms(계획 5.28 표) 안이다.

**문턱을 잠식하지 않는다는 근거.**
- 순절감 = 옮긴 몫 − 정시 대기 − 장벽 대기 − 메인 다른 일 증가(등록식). 옮긴 몫이 1e-0 과 같은 0.0695 라면, 문턱 0.03707 까지 모든 비용에 쓸 수 있는 여유는 0.0324 다.
- P 의 전달 비용은 메인 쪽 일이라 측정에서 "메인 층 갱신 일"과 "메인 다른 일"에 들어간다. 예상 0.005 는 여유의 약 15 % 다.
- 여유의 나머지(약 0.027)는 메인 다른 일 증가가 이보다 작아야 한다는 조건이다. 1e-0 의 +0.0505 가 코어 부족 때문이었다면 코어 B 에서 크게 준다. GIL 때문이었다면 P 에서만 준다. 이것이 측정이 가르는 것이다.
- 예상이 틀릴 위험: ws1 의 파이프 성능, Kit 프로세스 안의 GIL 경합 아래 I/O 스레드. 그래서 P 세션에서 다음을 스캔마다 기록하고 분석기가 따로 보고한다: 메인 쪽 직렬화+보내기, 역직렬화, 왕복, I/O 스레드의 GIL 대기 흔적(I/O 스레드 CPU/벽시계).

## 6. 측정 등록(설계 승인 뒤 결과 전 고정; rv4 뒤에 냄)

- 장면: 1e-0 과 같다(line_m far K f 1.0 confirm, seed 0, 1b·1c·1d 켬, INSTR off, k = 3 실행, k = 2·3·4 대기는 기록에서 읽음).
- 배정: 3 절의 물리 코어 둘(세션) + 브리지 코어. 한 잡에 한 세션씩 순차(`--slots 1`).
- 세션: D T P P T D(6 세션, 두 짝, 순서를 뒤집어 시간 흐름을 상쇄). 약 45–60 분.
- 겹침 무효: 1e-0 과 같다(자기 GPU 감시, CPU sampler). 다른 GPU 의 사용자 잡은 17604 와 같이 한계로 기록한다(총괄 결정 2026-11-10의 선례; 이 등록에서 미리 정함).
- 짝마다 계산: net_T(k), net_P(k). 1e-0 등록식 그대로이고, 기준은 같은 짝의 D 다. k 는 팔마다 "정시 대기 평균 ≤ 0.5 ms 인 가장 작은 k".
- **결정 규칙.**
  1. 두 짝 모두 net_T ≥ 0.03707 → (a) 스레드 + 코어 추가를 고른다.
  2. 아니고 두 짝 모두 net_P ≥ 0.03707 → (b) 프로세스 + 코어 추가.
  3. 아니면 총괄에 올린다(두 팔 모두 부족하거나 짝이 갈림).
- 보고만:
  - 세션 트리의 스레드·자식 프로세스별 CPU 시간(`/proc/<pid>/task/*/stat`, 시작·끝 차).
  - 코어 추가 자체의 효과: D(코어 둘) 대 17604 의 `delay`(코어 하나). 다른 잡·다른 시각이라 판정에는 쓰지 않는다.
  - `evidence_stale` 틱 수와 미션 결과.
- 분석기: 1e-0 분석기를 확장한다(P 의 전달 기록, 배정 대조, 6 세션 두 짝). 결과 전에 커밋하고 Codex 리뷰를 받는다.

## 7. 코어와 슬롯의 맞바꿈

live 세션 묶음의 지금 크기(`tools/isaac_bundle.py sizes live`): 세션당 CPU 2(물리 코어 하나) + 잡당 브리지 코어 하나(CPU 2), GPU 당 3 슬롯(VRAM 한계). 노드는 VM 이 꺼져 있으면 CPU 20·GPU 2, 켜져 있으면 CPU 8·GPU 1 이다(`~/wiki/compute/ws1.md` 2026-11-07 기록).

| 세션당 물리 코어 | 잡 CPU(슬롯 1 / 2 / 3) | 노드 CPU 20·GPU 2 의 동시 세션 | 노드 CPU 8·GPU 1 의 동시 세션 |
|---|---|---|---|
| 1(지금) | 4 / 6 / 8 | 6(3 슬롯 잡 둘, CPU 16) | 3(3 슬롯 잡 하나, CPU 8) |
| 2 | 6 / 10 / 14 | 4(2 슬롯 잡 둘 = CPU 20, 또는 3 + 1 슬롯 = 20) | 1(1 슬롯 잡, CPU 6) |

- 배치 처리량: 세션당 코어를 둘로 하면 VM 이 꺼진 노드에서 동시 세션이 6 → 4(−33 %), 켜진 노드에서 3 → 1 이다.
- 운용 콘솔(isaac_live, 한 세션)은 CPU 4 → 6 으로 노드 안에 들어간다.
- 그래서 채택하더라도 "작업자를 켜는 실행만 세션당 코어 둘"로 하고, 배치 기본값은 따로 정할 수 있다. 결정은 측정 뒤 총괄이 한다.

## 8. 한계

- 기존 기준선(1b·1c·1d 의 배율·절감, 1e 판정 실행, 1e-0)은 모두 세션이 SMT 짝 코어 하나에서 돈 조건의 값이다. 코어 둘 조건의 측정과 바로 섞지 않는다.
- 전달 비용 예상은 노트북 단일 실행이다. ws1 의 값은 P 세션의 기록으로 본다.
- 두 짝은 작은 표본이다. 결정 규칙이 "두 짝 모두"를 요구하는 것은 그 때문이다. 짝이 갈리면 총괄에 올린다.
- 코어 B 에 작업자만 고정하고 나머지는 OS 에 맡긴다. 그래서 D 에서도 B 가 메인 프로세스의 다른 스레드에 쓰일 수 있다. 같은 배정 안의 비교라 순절감에는 공정하지만, "B 를 작업자에게만 준" 조건은 아니다.
- 원거리 인식·학습 제안기·계획 작업자의 순간 경합은 이 측정의 보고 항목(스레드·자식별 CPU 시간)으로만 본다.

## 9. 구현 범위(설계 승인 뒤, 시험 먼저)

1. 묶음 실행기: 세션당 물리 코어 수 옵션(`--session-cores 2`)과 크기 계산(7 절 표).
2. 러너: `--layer-worker-cpus`(작업자 고정)와 affinity 기록. `--layer-worker process` 와 그 작업자 모듈(4 절).
3. 1e-0 분석기 확장과 목록 생성기(6 절).
4. 단위 시험(배정·고정·메시지·준비·실패·off 동일), runs29 게이트, ws1 전체 pytest, Codex 수렴. 그 뒤 총괄 승인 하에 측정.
