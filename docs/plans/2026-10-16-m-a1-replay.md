# M-a1 마지막 판정: 계측 기준 기록과 재생 (3판, 2026-10-16)

상위 계획: [M-a 미션 코어](2026-10-15-m-a-mission-core.md) 4절 M-a1 행, 5절 "M-a1 7 조각 설계"·"7.0 감사"·"7.1 재생 입력 상의". 사용자 결정(2026-10-16): 재생 판정까지 진행한다.

## 1. 판정 문구(개정)

M-a1 의 전체 동등성은 **"설정 입력을 보충해 계측한 이동 전 소스(`a8b4f66`)의 기준 기록을, 이동 뒤 코드가 처음부터 끝까지 같은 요청·출력·분기·종료로 재생한다"** 로 판정한다. 동결 기록 4 개(`ma1base_*`)는 지금처럼 접두·회귀 기준으로 남기고, "동결 기록 재생 완료" 라고 쓰지 않는다. 증거의 범위는 D2 와 같다 — 계측된 기준 실행에 대한 동등성이다(계측이 지도 콜백·마감 시점을 흔들지 않는다고 보장하지 못한다).

## 2. 구조

**실행기를 둘로 나눈다(이동 뒤 코드).** `run()` 은 지금 tick -1 전(약 1,530 줄, 3113 행까지)에 Isaac 호출과 순수 계산을 섞어 세계를 만든다. 이를 

- `setup(args) -> SetupResult` — Isaac 의존(장면·자산·관절·카메라·정착·서비스 생성)과 그 결과 값,
- `drive(setup, ports) -> result` — tick -1 의 초기 계획부터 끝까지, Isaac 을 import 하지 않는 CPU 실행부(`sim/isaac/transport_driver.py`),

로 나눈다. `drive` 가 Isaac 에 닿는 곳은 모두 포트(기록되는 프록시)나 어댑터(Sink: USD 프림·영상·오버레이)를 거친다. Isaac 실행에서는 `setup` 이 실제 객체를, 재생에서는 하네스가 스냅숏과 재생 포트를 넘긴다.

**적용 시점(Codex 7.1 P2-1, 2판 P2-1).** tick -1 은 초기 계획만 덮는다. 그 뒤 루프 전까지 실행기는 SLAM 링크·추종기·시계 원점(`initial_time = world.current_time`)·배송 기준 스캔(`robot.get_world_pose()` 와 광선 투사 `cast_scan`)을 만든다. 이 구간은 지금 기록되지 않는다. 계측은 이 구간을 **bootstrap tick(-2)** 으로 연다. 외부 입력마다 공급 방법을 정한다: `world.current_time`·`robot.get_world_pose()` 는 그 시점에 이미 있는 객체를 프록시로 감싸 기록, 광선 투사(`planar_lidar.cast_scan`, USD 장면에 대한 질의)는 기록 함수(`SimTruth.cast_scan`)로 감싼다, SLAM 사전·링크·추적기는 **생성되는 자리에서** 프록시·watch 를 연결한다(먼저 만든 `DictWatch` 가 `slam=None` 을 붙잡지 않게). tick 경계도 계약으로 고정한다: 틱 머리의 `t = world.current_time - initial_time` 은 `tick_begin` 뒤로 옮겨 기록하거나(계측본 두 소스에 같게) 시계 포트로 공급하고, 정상 완료의 `break`·조기 종료·예외 때 tick 을 닫는 위치(마지막 참값 검사가 어느 tick 에 들어가는지)를 정한다. 프록시가 호출을 통과시킨다는 성질만으로 새 기록 구간의 무해성이 증명되지는 않는다 — 3 절 무해성 확인을 이 구간에도 적용한다. 스냅숏은 **계획 전 입력**만 담고, 초기 계획·후보 변경·추종기 구성·`initial_time` 이후의 값은 재생이 다시 계산하거나 기록된 응답에서 얻는다 — 기준 실행의 `paths`·`trackers` 를 정답으로 주입하지 않는다.

## 3. 계측 패치

같은 계측을 두 소스에 넣는다: `a8b4f66`(기준 기록용, 별도 브랜치 `rec/a8b4f66-replay`)과 이동 뒤 코드(하네스 자기 검증용). 기록 전용이며 동작을 바꾸지 않는다.

1. **설정 스냅숏**: tick -1 직전에 2 절 표의 "다시 계산"·"Isaac 값"·"컨테이너 초기 상태" 를 버전 있는 값 DTO(`forklift_setup_snapshot/1`, JSON + 배열 파일)로 쓴다. pickle 은 쓰지 않는다. 읽은 지역 변수만 복사하고 추가 조회·step·상태 변경을 하지 않는다.
2. **프록시 설치 시점**: 2 절 "적용 시점" 대로 앞당긴다. 프록시는 호출을 그대로 통과시키므로 동작은 같다(M-a0 에서 루프 구간에 대해 확인한 성질).
3. **계획 메모리(Codex 7.1 P2-2)**: `Obstacles.memory` 가 돌려주는 `PlanningMemory` 를 `RecordingProxy("Memory")` 로 감싸 그 메서드 호출(`retract_endpoints` 등)과 응답을 기록한다. 비필드 상태(`_pending`)는 직렬화하지 않는다 — 그 상태에 기대는 결과는 이 호출 기록으로 공급된다.
4. **콜백 요청 기술자(2판 P2-2·P2-3)**: Planner 요청 안의 콜백은 타입 이름만 기록되므로, 콜백 내부의 설정(순항 속도 등)이 바뀌어도 요청이 같게 보인다(Codex 반례: S4b 콜백 입력 `[0.2, 0.29]` → `[0.3, 0.39]` 에도 요청·응답 동일). 그래서 콜백을 넘기는 **모든** Planner 호출(`redraw_docking` 의 S4b·1 단계 dry run, `plan_return_leg` 의 `turnaround_check`)에 대해, 호출 직전 콜백의 의미 있는 요청 기술자(순서 있는 `dry_configs`, 시작 자세, 검사 종류)를 Trace 항목(`Trace.callback_spec`)으로 남긴다 — 실행 여부와 무관하게. 1 단계 재작도는 실행된 콜백의 결과(궤적)를 별도 목록(`Trace.redraw_rollouts`)으로 복사한다(다시 rollout 하지 않는다). 콜백 0·1·2 회 실행, 콜백 전 예외, 첫 콜백 뒤 예외를 구분해 남긴다 — `redraw_rollouts` 는 **예외 때도 항상** 남긴다(실행된 만큼, 콜백 전 예외면 빈 목록; 예외 자체는 Planner 호출의 예외 기록). 이동 뒤 코드도 같은 `callback_spec` 을 남긴다(traced 포트는 궤적을 응답으로 내므로 `redraw_rollouts` 는 없다).
5. **Sink·기록 효과(2판 P2-4)**: 코어 쪽 Sink(`write_paths`, `save_npz`, `save_capture`, `record_capture_evaluation` 의 기록, `dump_tracking`, `echo`)의 호출 순서·논리 경로·payload 해시를 `Sink.*` 항목으로 남긴다. 디스크 쓰기는 재생에서 생략해도 효과는 비교한다.

**무해성 확인**: (a) 패치 diff 가 기록 경로 밖 문장을 바꾸지 않음(AST 대조), (b) 결정적 대역 포트로 원본/계측본을 같은 입력에 돌려 비기록 호출·결과가 같음, (c) Isaac 에서 계측본 기록 켬/끔 비교(M-a0 정규화 규칙, 다른 행은 원인 기록).

## 4. 재생 하네스(`tools/boundary_replay.py`)

- **복원 층**: `read_record` 위에 타입 복원(dataclass 이름 → 클래스 등록표, 튜플·키 복원), 예외 재발생(타입·속성), `request_after` 를 호출자 인자에 적용, `watched` 의 append/delete/값을 대상 사전에 적용(예외 때도).
- **재생 포트**: 호출마다 기록의 다음 항목과 `port`·`method`·요청을 대조(인코딩 동일; opaque 자리는 타입만; 벽시계 응답은 기록값을 그대로 돌려준다)하고 응답을 돌려준다. 건너뛰기 없음 — 순서가 어긋나면 그 자리에서 실패. 통째로 기록된 서비스(`Vehicle.step`, `Capture.capture`, `Frames.read_pocket_frame`)는 응답과 변경분만 복원한다.
- **콜백 기술자 대조**: 콜백을 넘기는 Planner 호출은 앞의 `Trace.callback_spec` 과 재생 쪽이 만든 기술자를 대조한다. 불투명 함수 자리의 타입 비교는 이 기술자가 검증되는 자리로만 한정한다.
- **이동 전/뒤 호환 어댑터**: 기준 기록의 `Trace.callback_spec` + `Planner.redraw_docking` + `Trace.redraw_rollouts` 묶음은 이동 뒤 코드의 `Trace.callback_spec` + `Planner.redraw_docking_traced` 에 대응한다(예외면 `Planner.redraw_docking` 예외 → `Trace.redraw_rollouts`(빈 목록 또는 부분 결과) 묶음 ↔ 예외를 내는 traced 호출: 어댑터가 Trace 를 소비·검증한 **뒤** 원래 Planner 예외를 재발생시키고, 그 전 효과를 보존). 요청(`start_rear`, 순서 있는 `dry_configs`, 나머지 Planner 인자)을 대조하고 응답 `(plans, record, 궤적들)` 을 Trace 에서 만든다. 이 대응 하나만 명시적으로 허용하고, 기준 기록 형식 전용 시험(성공·거절의 0·1·2 회 실행, 콜백 전·후 예외)을 둔다.
- **벽시계**: `drive` 모듈이 직접 부르는 시간 함수도 Clock 포트(기록되는 `time` 프록시)를 거친다 — 모듈 수준 `time` 을 하나로 묶고, 재생은 기록값을 돌려준다(agy 3).
- **판정(2판 P2-4)**: 틱마다 호출 순서·요청, `Sink.*` 항목(순서·경로·payload 해시), `tick_end` 출력, 분기 목록, 종료(성공·실패 사유·종료 틱 **과 그 틱 안의 호출 위치**)가 같고, 기록의 미소비 호출이 0. 마지막에 결과 기록(`result.json` 의 코어 쪽 키 — 비결정 기록 필드 목록은 따로 보고)을 비교한다. 주입 시험: 파일 생성 생략, payload 변조, 같은 틱 안 실패 위치 이동, 콜백 설정 변경이 각각 실패해야 한다.

**변경 모형(R1 구현, Codex 검토 반영).** 형식 2 기록은 호출마다 그 호출이 볼 수 있는 상태(인자, 감시 키 전부, 추가 전용 목록과 그 항목)를 호출 전후로 비교해, 재생이 정확히 되돌릴 수 있는 변경인지 판정한다 — 있던 객체는 제 경로에 그대로(내용은 바뀔 수 있음) 있거나 바뀌지 않은 채 상태를 떠나고, 바뀐 경로와 그 아래는 새 객체이며, 새 객체는 한 경로에서만 닿고 있던 객체를 담지 않는다; 추가 전용 목록은 같은 객체로 새 항목만 늘고 마지막 항목은 내용도 그대로; 사전 키는 문자열·정수·bool·None(과 그 튜플), 감시 키는 문자열; 값 인코딩이 없는 객체(집합 등 포함)·순환 구조는 상태 안에 두지 않는다. 로그(추가 전용 목록)는 **값 기록**이다 — 새 항목이 이미 기록된 항목과 안쪽 객체를 공유하는 것은 허용하고(`grid_kwargs` 의 캐시된 묶음, 재생은 항목마다 따로 만든다; 기록된 객체를 나중에 고치는 코드는 없다), 코어 상태(인자·감시 값)와 객체를 공유하는 것은 거부한다. 벗어나면 그 호출 기록에 `unsupported` 를 남기고 재생이 거부한다. **알려진 한계**: 추가 전용 목록의 마지막보다 앞선 항목을 서비스가 호출 안에서 고쳤다가 끝나기 전에 되돌리는 경우는 호출마다 보지 않는다(매 물리 틱 로그 전체를 다시 인코딩하는 비용). 고친 채 남으면 기록 끝의 최종 상태 비교(`final_state.json`)가 잡는다. 현재 코드에서 기록된 로그 항목을 고치는 곳은 `obstacle["plans"][-1]` 두 곳뿐이고, 하나는 같은 기록 호출(`grid_kwargs`)이 방금 추가한 항목, 하나는 재생에서도 다시 도는 실행기 코드(`correction_grid`)다(2026-10-16 grep).

## 6. 열린 문제

- 원본→원본 재생은 하지 않는다(`a8b4f66` 의 `run()` 분리는 기록 전용 범위를 넘는다). Codex 2판 검토: 엄격한 R6 가 원본 기록 전체를 통과하면 원본 분리를 필수로 둘 필요는 없다 — 원본 브랜치는 계측 전용으로 두고 원본 전용 복원·호환층 시험을 더한다. 대가: R6 실패가 기록 부족인지 이동 회귀인지 바로 갈리지 않을 수 있다 — 실패 때 원본 계측 기록의 그 지점을 감사해 가린다.
- `new_obstacles` 일정은 기록된 포트가 없다 — 재생은 같은 일정 파일로 Schedule 을 다시 돌린다. 일정의 입력(`driven`·`leg`)이 비트 단위로 같아야 하므로, 계측본은 매 틱 Schedule 의 입력과 내놓은 동작을 `Trace.schedule` 로 남기고 재생이 대조한다(agy 8). 4 구성에는 새 장애물이 없다 — 이 경로의 증거는 R5 의 추가 구성이다.
- 비트 단위 비교: 같은 머신(ws1)·같은 패키지에서 같은 계산을 다시 하는 재생이라 의도한 엄격함이다(agy 10). 패키지 버전은 스냅숏 출처에 남긴다.
- 반환 서비스 감사: 기존 4 기록에 없던 반환 객체(bootstrap 구간, dwell 의 `get_articulation_controller()` 등)를 R5 기록의 감사에서 확인한다.
- 남는 위험: 기록한 구성이 덮지 않는 조건의 회귀는 재생으로 드러나지 않는다(agy 9) — 조각별 동작 시험이 그 몫이다.
- D2 필수 분기 목록에서 4 구성이 덮지 못하는 분기의 목록과 그것을 내는 구성.
