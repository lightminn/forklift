# team-spec 오도메트리 나이 표를 미션 주행까지 덮게 다시 만든다 (6판)

브랜치 `feat/team-spec-age-table`(origin/main `689a020`, PR #105 포함). 사용자 결정(2026-10-22, 총괄 경유): 관절각(`team_spec_quantized`) 오도메트리 승격을 다시 판정한다.

순서는 다음과 같다.
1. 이 표를 보완한다(이 계획).
2. `on_s2` 근거리 SLAM 오차를 분해한다.
3. #105 위에서 24 회 비교를 다시 돌려 승격 조건 넷을 판정한다.

조건을 모두 채우면 기본값 변경은 사용자 결정으로 올린다.

## 1. 사실

- **지금 표.** `config/obstacle_odometry_age_team_spec.json`(sha256 `0bcf52a4…`, 커밋 72c55a0)은 S2 조사 주행 r6/r7 두 개만으로 만들었다. reported 기록의 바퀴 관절각을 `p0a_measure age --regenerate-encoder team_spec_quantized --draws 1` 로 다시 셌다.
  - r6/r7 의 후진 속도는 −0.26 m/s 까지다.
  - 미션의 −0.6 m/s 후진 선회, 옆면 다리, 적재 중 정지는 들어 있지 않다.
- **넘침**(`docs/validation/2026-10-22-joint-angle-odometry.md`):
  - team-spec 미션 12 회 모두, 장애물 층이 쓰는 나이(FREE 0.2 s, OCCUPIED 0.3 s) 안에서 이 표를 넘었다. FREE 최악 비율은 yaw 1.55, OCCUPIED 최악은 위치 1.91 이다.

## 2. 고칠 것

### T1. 표 입력과 만드는 방법

- **입력 기준:** ws1 에서 SLAM 로그(`slam_log.npz`·`meta.json`·`result.json`)가 남은 **모든 reported Isaac 미션 실행**과 S2 조사 주행 r6/r7 이다.
  - 대상 폴더는 `test_runs/bd_isaac/*/run`, `test_runs/riibotics/*/run` 이다.
  - 빼는 것은 셋이다. team-spec 으로 기록된 실행(재계수 대상이 아님, V1 이 여기서 나옴), 경계 기록(`record_boundary`), 바퀴 반지름이 다른 실행(0.125 m 가 아님)이다.
  - 2026-10-23 에 센 결과는 192 개다(bd_isaac 106, riibotics 86). team-spec 19 개가 빠졌다. 목록은 ws1 `bd_isaac/age_inputs_final.txt` 다.
  - 실행별 결과 194 개가 모두 병합됐다(스캔 시작 0 인 입력 없음). 결과는 1 절의 새 표다.
  - 1판의 "골라 뽑은 29 개" 는 고른 기준이 없었다(Codex P3). 전부 넣으면 그 질문이 없어진다.
  - 완료·실패·검사 켬·끔, 얕은 T11·T11 x0.6, 리보틱스 장면이 섞인다. 각 실행에 실제로 남은 주행 구간만 들어간다. 최댓값 표라 같은 장면이 여러 번 들어가도 값이 평균처럼 끌리지 않는다. 다만 실행 수를 독립 표본 수로 읽지 않는다.
- **방법:** 실행마다 `p0a_measure.py age --run <하나> --draws 1 --regenerate-encoder team_spec_quantized` 로 그 실행의 나이별 최댓값을 구한다(ws1 배열 잡 `bd_isaac/age_per.sbatch`). 그것을 `bd_isaac/age_merge.py` 로 합친다.
  - 합치는 방법은 `p0a` 의 `age_command` 와 같다. 실행 사이의 최댓값을 구한 뒤, 나이 축으로 누적 최댓값을 잡는다.
  - 병합은 입력이 하나라도 빠지거나, 스캔 시작이 0 이거나, 설정(나이·엔코더·반지름)이 다르거나, 값이 유한하지 않으면 거부한다.
  - 결과 파일마다 실행이 하나이고, 그 실행이 목록의 같은 줄과 같아야 한다. 목록에 중복이 없어야 한다.
  - 배열 잡은 `set -euo pipefail` 로 돌고, 시작할 때 그 줄의 옛 결과·기록을 지운다. 계산이 성공했을 때만 완료 기록을 쓴다. 병합은 완료 기록의 `exit` 0 과 결과 파일 해시가 지금 결과와 같은지도 확인한다(Codex 4차).
  - 배열 잡이 실행마다 계산 직전·직후의 입력 해시(meta.json 과 slam_log.npz, 라이브는 spool 전체; ws1 `bd_isaac/age_hash.py`)를 `<i>.inputs.json` 에 남긴다. 병합은 그 기록이 같은 줄·같은 스냅숏인지, 직전과 직후가 같은지, 지금 입력의 해시와 같은지를 확인하고 하나라도 어긋나면 거부한다. 그래야 provenance 의 원자료 해시가 결과가 센 자료다. 파일 시각(mtime)은 쓰지 않는다(시각을 보존한 교체를 못 잡는다, Codex 3차).
  - provenance 에는 입력별 계산 시점 해시와 결과 파일 해시를 남긴다.
  - 반례로 확인했다: 2 번 결과를 1 번 결과로 바꾸면 "result is not for live/s2_survey/r7" 로 거부한다. 5판 배열 잡(ws1 job 9144, 194/194 EXIT 0) 뒤 병합(`v4.json`)은 v3 와 바이트까지 같다(sha256 `b853b34a…`; 실행별 결과가 결정적이고 계산 시점 해시가 v3 의 입력 해시와 같다). 해시 대조 반례도 확인했다: 직전 기록만 바꾸면 "inputs changed during the count", 직전·직후를 함께 바꾸면 "inputs changed after the count", 다른 스냅숏 이름이면 "input record is not for …" 로 거부한다.
  - 4판 병합 결과(ws1 `bd_isaac/age_table_team_spec_v3.json`)의 표 값과 `runs` 는 2판 병합(`v2.json`)과 같다. 다른 것은 provenance 의 결과 파일 해시뿐이다. 저장소에는 v3 를 넣는다.
  - `team_spec_quantized` 는 INL 이 0 이라 draws 를 늘려도 같은 계수가 나온다.
- **이상값을 빼지 않는다.** `c_on_s1` 의 미끄럼은 실제 미션 사건이다. 빼면 장애물 정지 순간의 오차를 과소평가한다.
- **배율은 1.0 이고, 검증 전에 정한다.** 검증 실행을 보고 배율을 고르면 그 실행이 튜닝 자료가 된다.
  - 이 표는 Isaac 입력 실행에서 본 **경험적 포락선**이다. 앞으로의 실행이나 실차의 상한이 아니다(실차 마찰·백래시·지연은 따로 잰다).
  - V1 의 여유(후보 표 0.92, 새 표 0.58)나 0/12 가 일반적인 여유·신뢰수준을 뜻하지 않는다. 독립 동일분포를 가정해도 0/12 의 단측 95 % 상한은 22 % 다.
  - 검증(T3)에서 넘침이 나오면 표를 키우지 않고 멈춰 보고한다.
- **출처를 남긴다.** 표 파일의 `provenance` 에 남기는 것:
  - 입력마다 `meta.json`·`slam_log.npz` 의 SHA-256
  - 도구 스냅숏과 명령
  - 계획 경로

### T2. 적용

- `config/obstacle_odometry_age_team_spec.json` 을 같은 경로에서 바꾼다. 쓰는 설정(`obstacle_layer_single_team_spec.yaml`)과 러너의 대조(`age_table_problem`: 엔코더 모형·heading·반지름)는 그대로다.
  - 옛 표·새 표 모두 이 대조를 통과한다. 그러니 러너는 어느 표인지 구별하지 않는다.
- **실행이 읽은 표의 귀속:** 실행 기록은 설정 경로만 남기고, `source_sha256` 은 Python 소스만 해시한다(Codex P2). 그래서 귀속은 불변 스냅숏으로 한다.
  - 실행은 git archive 스냅숏 폴더에서 돈다. 그 폴더의 표 파일 SHA-256 을 실행·라이브 epoch 마다 검증 기록에 남긴다.
  - 단계 3 의 24 회는 실행별 (스냅숏, 표 SHA-256) 목록을 검증 문서에 넣는다.
  - V-G2·라이브처럼 다른 세션의 실행도 같은 방식으로 귀속하도록 알린다.
- 옛 표는 git(72c55a0, SHA-256 `0bcf52a4…`)에 있다.

### T3. 검증

- **V1(입력 밖 실행):** 지금 표로 돈 team-spec 미션 12 회(`jao_tq_{off,on}_s0–5`, 표 입력이 아님)를 새 표에 대고, 장애물 층이 쓰는 나이 범위에서 넘침을 센다(`age_use.py`). 0 이어야 한다.
  - 이 12 회는 옛 표로 만든 궤적이다. 그래서 V1 은 "새 표가 기존 궤적을 덮는가" 까지만 보인다.
  - **결과(새 표, 2026-10-23, ws1 `bd_isaac/age_v1v3-direct.log`, 4판 검사): 12/12 VALID(덮음 모두 1.000), 넘침 0/12.**
    - 최악 비율은 FREE 0.50(`jao_tq_off_s2`, return_home, 위치 11.8 mm 대 표 23.6 mm), OCCUPIED 0.58(`jao_tq_off_s0`, return_home, 14.9 대 25.7 mm)이다.
    - 후보 표로 미리 잰 값(ws1 `bd_isaac/age_v1-8915.log`)은 넘침 0/12, 최악 0.92(yaw)였다. 새 표는 짧은 나이 yaw 가 커져 비율을 정하는 축이 위치로 바뀌었다.
    - 이 여유도 V1 12 개에 한정된다. 일반적인 여유로 읽지 않는다.
- **V2(새 표의 폐루프):** 단계 3 의 24 회 중 team-spec 12 회가 새 표로 돈다. 그 원로그에서 넘침 0 이 승격 조건 4 다.
- **판정의 전제(Codex P2):** `age_use.py` 는 실행마다 다음 셋을 확인하고, 하나라도 어긋나면 `INVALID` 로 표시한다. INVALID 는 통과로 세지 않는다.
  - 다시 만든 오도메트리가 기록 `odom_base` 전부와 일치한다(`odom_drift_terms.reproduction`).
  - 검사한 창 수가 0 보다 크다. FREE·OCCUPIED 각각에 양의 나이까지 닿은 창이 있다(시작 틱 하나만 보는 창은 세지 않는다).
  - 다시 만든 오도메트리, truth, 표, 계산한 오차와 비율이 모두 유한하다.
  - 검사한 창이 움직이는 틱(뒤 축 truth 속도 > 0.02 m/s)의 90 % 이상을 덮는다.
  - 반례로 확인했다(2026-10-23, `jao_tq_off_s5` 복사본): truth 를 NaN 으로 바꾸면 `finite False`, 스캔을 마지막 틱 하나로 줄이면 양의 나이 창 0·덮음 0 으로 둘 다 INVALID 다. 원본은 VALID, 덮음 1.000 이다.
- **가용성도 함께 본다(agy; 기준은 Codex 2차 P3 로 V2 전에 정한다).** 넘침 0 은 오차를 과소평가하지 않는다는 것만 보인다.
  - 비교 대상은 같은 스냅숏·같은 seed·같은 검사 설정의 reported 실행이다. 이 비교는 오도메트리 **조합 전체**(엔코더 + 표)의 비교라, 차이를 나이 표 하나의 비용으로 귀속하지 않는다.
  - 보류 규칙은 넷이다. 하나라도 걸리면 승격 조건 넷을 채워도 "가용성 보류" 로 보고한다.
    - A1 사이클 시간: 두 쪽 모두 완주한 쌍에서 완료 시각 비(team-spec / reported)의 중앙값이 1.10 이하.
    - A1 의 완료 시각은 양쪽 `success` 가 참인 쌍의 `transitions` 중 `complete` 전이의 `time_s` 다.
    - A2 occupied/unknown 제한 판정 시간: `obstacle_layer.slowed_reasons` 에서 키(`단계:이유`)의 마지막 `:` 뒤가 `occupied` 또는 `unknown` 인 항목의 틱을 모두 더해 120 으로 나눈 초(물리·제어 dt 1/120 s). team-spec 12 회 합이 reported 합 × 1.5 + 5 s 이하. 이 카운터는 허가 판정이 명령에 실제로 적용됐는지 보기 전에 늘어나므로(`core.py` 의 `acting` 검사 앞), "실제로 깎인 시간" 이 아니라 "제한 판정 틱의 환산 시간" 이다.
    - A3 재계획 수: 기록 항목 수의 합이다. 대상은 `obstacle_layer.replans`(회피 `escape` 포함), `obstacle_layer.mission_replans`, 최상위 `cusp_replans`·`stall_replans`·`observe_replans` 이다. 다리마다 한 번씩 정해진 `obstacle_layer.live_plans` 는 세지 않는다. team-spec 합이 reported 합 × 1.5 + 2 이하.
    - A4 계획 실패: 사건 단위는 위 다섯 배열과 `obstacle_layer.live_plans` 의 기록 하나, 그리고 첫 계획(`planning_status`) 하나다. 실패는 기록에 `failed` 가 있으면 그 값이 참일 때, 없으면 `status` 가 `success` 가 아닐 때다(그래서 `status="escape", failed=false` 는 실패가 아니다). 첫 계획은 `planning_status` 가 있고 `success` 가 아닐 때 실패다. `planning_status` 가 없으면 계획을 부르기 전에 끝난 실행이다(지금까지 6 건 모두 `phase="scene"`, 전이·계획 기록·SLAM 로그 없음: 인식 worker 초기화 실패 2, 장면 생성 중 USD 오류 4). 이것은 `not_attempted` 로 따로 세고 A4 실패 수에 더하지 않는다. 실행 실패로는 승격 조건 2·3 에 그대로 남는다. 필드가 없는데 계획 전 종료라는 근거(`phase="scene"` 이고 전이 없음)도 없으면 그 실행의 A4 는 판정 보류다. 실패 종류의 키는 `배열이름:status` 다. 탐색 내부 시도(`planning_traces`, `observation_candidates`)는 세지 않는다. team-spec 실패 수가 reported 이하이고 reported 에 없는 키가 없다.
  - 보류가 나오면 표의 몫을 가르는 추가 비교(같은 스냅숏에서 team-spec + 옛 표)를 제안하고, 그 전에는 원인을 표에 돌리지 않는다.
  - 위의 허가 채터와 그때의 정지 거리는 표 넘침과 분리해 기록한다.
- 둘 중 하나라도 넘치면 표를 키우거나 배율을 고르지 않는다. 넘친 실행·나이·상황을 보고한다.
