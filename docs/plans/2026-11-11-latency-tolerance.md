# 지연 내성 시험: 계획·SLAM·장애물 층에 인위 지연 (2026-11-11, 결과 전 고정, 6판)

- 요청: 총괄(2026-11-11, 사용자 이름으로 승인된 백로그). 계획·SLAM·장애물 지도 갱신에 인위 지연(예: 20·50·100 ms)을 넣는다. 그때 지게차가 안전하게 느려지거나 서는지, 아니면 임무가 실패하거나 위험하게 움직이는지 판정한다. 실패는 SW 결함으로 보고 고친다.
- 출발 사례: 1e-0(`docs/validation/2026-11-10-g3-1e0-run.md`). live 에서 장애물 층 설치를 k 틱 늦추자 `evidence_stale` 로 두 임무가 집 복귀 시간 초과로 끝났다. 사용 나이 L 수정(#417)으로 닫았다.
- 이 문서는 등록이다. 판정 기준·팔·무효 규칙은 결과를 보기 전에 고정한다. 제출 여부는 총괄이 정한다.

## 1. 구조 제약과 방향(총괄 잠정 방향 2026-11-11)

- **결정 모드는 배치 전용이다.** 총괄 2026-11-06: "결정 모드에 live 부분은 없다"(`docs/plans/2026-10-25-deterministic-sim-mode.md` 의 PR 2 는 만들지 않았다).
- **지연이 생기는 세 구조는 live 에만 있다.** 계획 작업자 프로세스(`PlanWorker`, 실시간 계획 D8), 비동기 SLAM 링크(`AsyncSlamLink`, D9a), 장애물 층 작업자(`LayerWorker`, 5.28)다. 배치는 셋 다 동기이고, 계산하는 동안 시뮬 시간이 멈춘다.
- `--live --deterministic` 은 결정적이지 않다. CT 조사(#330)에서 같은 seed 의 쌍 넷이 모두 첫 임무부터 종료 시각이 달랐다(1.0–8.5 s).
- 그래서 시험을 두 부분으로 나눈다.
  - **A — 결정 배치, 물리 틱 단위 주입:** SLAM 답의 적용과 장애물 층의 설치. 둘 다 차가 움직이는 동안 작동한다.
  - **B — live 비결정 보조 팔:** 계획 작업자 답의 전달을 벽시계로 늦춘다. live 에서는 계획을 기다리는 동안 차가 선다(`MissionCore.job_hold`). 이 동작 자체가 시험 대상이고, 배치에는 이 경로가 없다.
  - A 와 B 의 판정은 합치지 않는다.

## 2. 주입 지점과 방식

- 모든 주입은 새 러너 옵션 뒤에 둔다. 기본값(끔)에서는 지금과 같은 코드가 돈다. 게이트 29/29 와 ws1 전체 pytest 를 받는다(8 절).
- **원칙(1판 Codex P1 반영):** 주입은 물리 스텝마다 도는 `step_world` 안에서 한다.
  - 배치의 동기 캡처는 한 제어 틱 안에서 물리 스텝을 여러 번 돈다(`perception_adapter.capture` → `step_fn`). 제어 틱 시작에서 주입하면 캡처 동안 지연이 늘어난다.
  - 그래서 지연 0 의 주입이 지금 코드와 같은 자리, 같은 순서로 돌게 만든다(2.3 의 등가 대조로 확인).
- 시간 기준: 틱 = `step_world` 안의 지역 변수 `tick`(그 스텝의 물리 틱 번호, 120 Hz).
  - 기준선에서 스캔 틱 s 의 결과는 스텝 s 의 물리 진행 뒤에 반영되고, 그다음 제어 틱이 처음 읽는다.
  - 지연 n 틱(n ≥ 1)이면 반영이 스텝 s + n 의 시작(물리 진행 전)으로 옮겨진다.
  - 그래서 **이 문서의 지연 = 정상 제어 루프에서 제어기가 처음 읽는 시각의 차이 = n/120 s(공칭)** 다. 반영 시각 자체의 차이는 (n − 1)/120 s(16.7 · 41.7 · 91.7 ms)다. 두 값을 섞지 않는다(2판 Codex P2-3).
  - 동기 캡처 안에서는 제어 틱이 돌지 않고, 캡처가 끝난 같은 제어 틱 안에서 `release_slam`·`slam_rear` 가 읽는 경로가 있다(`core.py` 5272–5304). 장벽 설치도 지연을 줄인다. 이런 경우에는 공칭값 대신 기록한 실측값을 쓴다(3판 Codex P2-3).
  - 답·작업마다 결과를 셋으로 나눠 적는다: 제어에 처음 쓰임(그 시각), 쓰이기 전에 다음 답·작업으로 대체됨, 실행 끝까지 안 쓰임.
  - 시험량은 **25 · 50 · 100 ms = 3 · 6 · 12 틱**(제어기 최초 사용 기준)으로 적는다. 20 ms 는 120 Hz 에서 정확히 만들 수 없다.
  - 주입 기록에는 틱 번호와 함께 생성(스캔 시각)·반영·제어기 최초 사용의 시뮬 시각을 남긴다.

### 2.1 A-SLAM: 답 적용 지연 (`--latency-slam`)

- 스캔은 지금처럼 스캔 틱의 lockstep 교환(`SlamLinkClient.exchange`)으로 보낸다. 브리지가 보는 입력 흐름(스캔 순서·시각·`/clock`)은 기준선과 같다. `scan_id` 증가와 장애물 스캔(`obstacle_scan`)도 스캔 틱에 그대로 둔다.
- 교환 직후의 답 처리를 함수 하나(`deliver`)로 묶는다. 묶는 범위는 `tracker.receive` 부터 L4 지도 확인, `slam["records"]` 기록까지다.
- 답은 마감 틱(스캔 틱 + n)과 함께 대기열에 넣는다. 항목에는 스캔 당시의 메타데이터를 고정해 넣는다: `scan_id`, 스캔 시각, `ms.phase`, 참 자세(`now_base`·`now_q`), 오도메트리 자세(`slam_odom_base()`). `deliver` 는 이 고정값으로 기록하고, 적용 뒤 상태(mode·적용 보정·받은 보정)만 반영 시점 값으로 적는다(2판 Codex P2-4).
- `drain(tick)` 은 마감이 지난 답을 순서대로 `deliver` 한다. 부르는 자리는 두 곳이다.
  - 모든 `step_world` 의 시작(캡처 스텝 포함).
  - 스캔 블록 안의 교환 바로 뒤, 장애물 스캔 앞.
  - 그래서 n = 0 이면 지금과 같은 자리, 같은 순서(답 반영 → 장애물 스캔)로 돈다. 대기열은 매 스캔 직후 비고, 다음 스텝 시작의 `drain` 은 빈 대기열에 대한 호출이 된다. 캡처 중 hold·release 순서도 그대로다.
  - n > 0 이면 장애물 스캔은 그때까지 반영된 보정으로 들어간다. 보정이 바뀌면 제어 틱의 기존 재투영(`core.py` 1425–1429)이 격자를 다시 투영한다. live 비동기와 같은 의미다.
- 예열(`warming_up`) 중의 스캔은 지연하지 않는다(시작을 기준선과 같게 둔다).
- **무엇을 흉내 내는가(agy ③-4).** 고정 N 은 키프레임 답(`processed`)과 건너뛴 답(`skipped`)을 똑같이 늦춘다. 브리지에서 답이 돌아오는 경로 전체의 지연(전송·대기)이다. slam_toolbox 계산 지연만 따로 흉내 내지 않는다. `jitter` 는 순서 보존 규칙 때문에 긴 답 뒤의 답이 같이 밀린다. live `AsyncSlamLink` 의 한 번에 하나씩 보내는 줄서기와 비슷하지만 같지는 않다.
- **SLAM 지연이 닿는 구간(agy ③-4).** 추적기는 `approach`·`insert`·`lift`·`extract`·`lower`·`withdraw` 동안 `holding` 이다. 받은 보정을 바로 적용하지 않고, 단계가 끝나 설 때 `release_slam` 으로 한꺼번에 적용한다(`slam_pose.py` 247–255). 그래서 이 구간에서 SLAM 지연은 제어 자세의 보정에 바로 닿지 않는다. 다만 신선도 검사는 holding 중에도 돈다(`slam_pose.py` 292–296). 그래서 지연은 holding 중에도 답의 나이를 늘리고, 신선도 실패로 실행을 끝낼 수 있다. 정리하면 holding 안에서는 신선도와 해제(점프·재계획)로, holding 밖에서는 제어 자세로 닿는다. 노출(4.5)은 holding 밖의 직접 자세 영향과 holding 안의 신선도 영향을 나눠 세고, 해제 점프(`jump_m`·`jump_rad`) 분포와 해제 재계획 수를 보고한다.
- 순서 보존: 앞 답보다 먼저 반영되는 답은 없다. 마감은 max(앞 답의 마감, 스캔 틱 + d).
- 값: `off`(기본, 대기열 없음), `ticks:N`(고정 N ≥ 0), `jitter:M`(답마다 0..M 틱 균등).
- 주입 기록은 `state["latency_injection"]["slam"]` 에 따로 둔다(답마다 `scan_id`·스캔 틱·반영 틱·차속 > 0.05 m/s 여부). SLAM 기록 형식은 바꾸지 않는다.
- 추적기 신선도 한계는 그대로다(배치 `SlamPoseTracker(max_age_s=0.25)`, 나이 = 지금 − 마지막으로 받은 답의 스캔 시각, `slam_pose.py` 292–295).
  - 답이 12 틱마다 오고 마감마다 반영되면, 다음 반영 직전 나이는 0.1 + N/120 s 다. N = 12 에서 0.2 s, N = 18 에서 경계 0.25 s(경계는 허용)다.
  - 기준선에 답 간격이 0.1 s 보다 긴 구간이 있으면 더 작은 N 에서도 신선도 실패가 날 수 있다. B0 의 받은 답 간격(최대·p99)을 보고한다.

### 2.2 A-층: 설치 지연 (`--latency-layer`)

- 1e 의 `LayerWorker` delay 모드를 배치·결정 모드에서도 쓴다. 계산은 스캔 틱에 제자리에서 끝내고 설치만 늦춘다(스레드 없음).
- 지금 코드로는 배치에서 예정 설치가 일어나지 않는다. `worker.tick_start` 가 live 블록 안에 있기 때문이다(`run_transport.py` 9616–9625). 이 옵션에서는 다음을 바꾼다.
  - 예정 설치를 `step_world` 시작에서 확인한다(스캔 틱 + k 에 도달한 작업). 캡처 스텝에서도 설치되므로 캡처가 지연을 늘리지 않는다. live 의 기존 경로(제어 틱 시작)는 그대로다.
  - k = 0 은 `submit` 안에서 계산 직후 바로 설치한다. 등가 대조(2.3)용이다.
  - k 범위는 0..12 다(지금 생성자 1..11, 등록 2..4). 이 옵션 안에서만 넓힌다.
  - 막힘 둘(`--layer-worker needs --live`, `--deterministic` 과 같이 못 씀)을 이 옵션에 한해 연다.
  - 배치의 `LayerWorkerFailure` 처리 경로를 만든다. 지금 처리는 live 전용 `live_zero_wheels()` 를 부른다(`run_transport.py` 10888–10894). 배치에서는 실행 실패(`layer_worker_failed`)로 끝내는 경로로 보내고, 시험으로 확인한다.
- **설치된 층의 보정 불변조건(2판 Codex P1-1).** 제어 틱에서 허가가 읽는 설치된 층은, 그 틱의 제어 자세와 같은 보정으로 만든 것이어야 한다.
  - 지금 배치는 lockstep 이라 답 반영 직후 장애물 스캔이 `obstacle["applied"]` 를 새 보정으로 바꾼다(`run_transport.py` 7520–7524). 설치를 늦추면 설치된 층은 옛 보정인데 `obstacle["applied"]` 는 새 값이 된다. 그러면 제어 틱의 재투영 조건(`core.py` 1425–1429, 추적기 보정 ≠ `obstacle["applied"]`)이 같다고 나와 재투영을 건너뛴다.
  - 그래서 이 옵션에서는 `obstacle["applied"]`·`version` 을 **설치된 층의 보정**으로 둔다. 제출 때가 아니라 설치 때(`on_install`) 바꾼다.
  - 그러면 대기 중에 보정이 바뀐 틱에서는 추적기 보정 ≠ `obstacle["applied"]` 가 되어 기존 재투영(`_reproject`)이 돈다.
  - **재투영의 순서(3판 Codex P1-1).** 지금 `_reproject` 는 새 보정·version 을 먼저 쓰고(`core.py` 4988–4989) `layer.refresh` 를 부른다(4995–4997). `refresh` 첫머리의 장벽(`obstacle_layer.py` 524)이 옛 대기 작업을 설치하면 `on_install` 이 옛 보정으로 되돌려 쓴다. 그 뒤 동기 갱신은 새 snapshot 을 설치하지만 보정·version 을 다시 쓰지 않는다. 그러면 snapshot 은 새 보정, 기록은 옛 보정이 된다.
  - 그래서 이 옵션에서는 `_reproject` 가 보정·version 을 쓰기 **전에** 대기 작업을 장벽(사유 `reproject`)으로 먼저 설치한다. 그다음 새 보정·version 을 쓰고 동기 갱신한다. 끝 상태는 snapshot·보정·version 이 모두 새 값이다. live 에서 SLAM 답이 늦게 와 재투영되는 것과 같은 결과다.
  - 일반 불변조건: 어느 설치 경로(예정 설치, 모든 장벽, 동기 갱신)든 끝난 뒤 설치된 snapshot 의 보정 = `obstacle["applied"]`, 그 version = `obstacle["version"]` 이다. 분석과 시험은 이것을 설치마다 확인한다(구현이 설치마다 세 값을 기록한다).
  - 이 경우 그 작업의 지연은 없어진다. 장벽 사유(`reproject`)로 기록하고 노출 조건(4.5)에 들어간다.
  - 장애물 스캔의 `add_scans` 에 넘기는 보정·version(출구 면제 감시용)은 그 스캔의 값으로 따로 넘긴다. L0 등가 대조가 이 경로를 확인한다.
  - 시험: 대기 중 보정 변경 → 그 제어 틱에 재투영. 옛 대기 작업의 `on_install` 뒤 동기 갱신이 끝난 시점에 보정·version·snapshot 이 모두 새 값. 설치 경로마다 불변조건. U·C 팔의 스모크에서 재투영 장벽 횟수를 본다.
- **장벽(barrier) 설치는 그대로 둔다.** 층을 건드리는 일은 대기 중 작업을 먼저 설치한다. 다음 스캔의 `add_scans`, 계획 격자, 동기 갱신, 복사, 면제·통로 변경 등이다(`obstacle_layer.py` 390–395, 524, 637–660, 854). 이 경우 실제 지연은 k 보다 짧다.
  - 그래서 팔마다 **실제 설치 지연의 분포와 장벽 설치 비율**을 기록하고, 4.5 의 노출 조건으로 판정에 넣는다.
  - 허가(permission) 판독은 장벽이 아니다. 정지 판단은 늦은 층을 읽는다.
- **알림(declared)과 비알림(undeclared)을 나눈다.**
  - 비알림(`undeclared`, 주 팔): 정지 모델의 지연과 사용 나이 L 을 늘리지 않는다. 계산 시간이 예상 밖으로 튄 경우를 흉내 낸다. 남는 보호 장치는 증거 나이 검사(`evidence_max_age_s`)다.
  - 알림(`declared`): `worker_config(config, k)` 로 정지 모델 지연과 사용 나이 L 을 함께 늘린다(#417 의 닫힘). 지연을 아는 설정이다. 이 문서의 k 는 제어기 최초 사용 기준 추가 지연 k/120 s 이므로, 알림 값은 `worker_config` 의 (k−1)/120(live 의 제어 틱 시작 설치 기준)이 아니라 k/120 을 쓴다. 이 차이는 구현 PR 에서 함수 인자로 분리한다.
  - 미리 적어 둔다: 1e-0 의 live k = 3 은 #417 이전이었고, 이번 비알림과 같은 종류의 조건에서 실패했다. 비알림 팔은 실패가 예상된다. 그래도 넣는다. 결정 배치에서 같은 기전이 재현되는지, 그 끝이 정지인지 위험한 진입인지가 이 시험의 물음이다.
- 값: `off`(기본), `undeclared:k`, `declared:k`, `jitter:M`(작업마다 k 를 0..M 균등, 비알림).
- 주입 기록: `layer_worker.json`(작업마다 스캔 틱·설치 틱·설치 사유·차속 > 0.05 m/s 여부)과 결과의 `layer_worker` 요약.
- **실행 끝의 대기분(2판 Codex P2-7).** 배치가 끝날 때 남은 층 작업과 SLAM 대기열의 답은 강제로 설치·반영하지 않는다. "절단"으로 개수와 스캔 틱을 기록하고, 노출 조건의 분자·분모에서 모두 뺀다(정상·예외 종료 같음).

### 2.3 주입 장치의 등가 대조(A)

- 주입이 지연 말고 다른 것을 바꾸지 않는지 확인한다.
  - **S0** = `--latency-slam ticks:0`
  - **L0** = `--latency-layer undeclared:0`
- 두 팔을 같은 seed 의 B0 와 `tools/deterministic_compare.py` 로 비교한다. 허용하는 차이는 주입 기록뿐이다.
  - S0: `latency_injection` 블록.
  - L0: `layer_worker` 블록과 `layer_worker.json`.
  - 비교기에는 이 항목만 빼는 옵션을 더한다. 그 밖의 파일·스트림은 지금처럼 엄격 비교한다.
- 차이가 하나라도 있으면 그 채널의 주입 팔은 읽지 않는다. 장치를 고친 뒤 그 채널을 다시 낸다(총괄 보고). 기준선을 다른 팔로 바꾸는 선택지는 두지 않는다.
- 비용을 줄이려고 S0·L0 는 구현 PR 의 Isaac 스모크 단계에서 먼저 돌린다(8 절). 등가가 확인된 스냅숏으로만 본 배치를 낸다. 본 배치에서도 seed 0 에 한 번 더 넣어 같은 스냅숏에서 확인한다.

### 2.4 B-계획: 답 전달 지연 (`--latency-plan-ms`, live 전용)

- 작업자 프로세스는 건드리지 않는다.
- `PlanWorker` 의 I/O 스레드가 답을 받는 순간의 시각을 `_done` 항목에 함께 남긴다. 기본 동작은 바뀌지 않는다.
- 주 프로세스 쪽 `DelayedJobs` 가 `PlanWorker` 를 감싼다.
  - `poll` 은 끝난 답을 그 **도착 시각 + d** 까지 감춘다(첫 관측 시각 기준이 아니다).
  - `discard` 는 감춘 답도 지운다.
  - 나머지 속성(`submit`·`close`·`_dead`·`restarts`·`proc`·`kernels` 등)은 그대로 넘긴다.
- 효과: `job_hold` 가 d 만큼 더 선다. 그 사이 상태가 바뀌면 기존 규칙(`_job_invalid`)으로 답이 버려지고 다시 요청된다. 버림 예산은 사이트마다 다르다(`core.py` 7850–7990).
  - 일반 사이트는 `ASYNC_MAX_DISCARDS`.
  - `prepare` 는 시도 2 회.
  - scene replan 은 요청당 3 회 × 4 요청.
  - 복귀 turnaround 의 보정 버림은 따로 센다.
  - 이 예산들이 지연에 약한지가 B 의 물음이다.
- 값: 고정 d(ms). 배치에서는 거부한다(배치는 `core.jobs` 가 없다).
- `core.jobs` 를 같이 쓰는 다음 팔레트 추천(`PickService`, `worker=core.jobs`)도 같은 감싸기를 지난다.
- 기록: 답마다 사이트·도착 시각·전달 시각·버림 사유(`state["latency_injection"]["plan"]`). 지금의 `async_plans[].wall_s`(요청 → 채택 벽시계)에는 주입 지연이 섞이므로, 작업자 계산 시간(`worker_wall_s`)과 주입 대기(`injected_s`)를 따로 남긴다(agy ③-5).
- **흡수 가능성(agy ③-5).** 서서 기다리는 동안에는 키프레임이 생기지 않아 보정이 거의 바뀌지 않는다. 또 계획이 일찍 끝나도 정지 확정(`stop_now`, 약 0.2–0.3 s)을 기다리는 동안 답이 보류된다(`core.py` 7846–7854). 그래서 d ≤ 100 ms 는 서는 시간에 거의 더해지지 않을 수 있다. B 는 "버림이 늘어나는가"와 함께 "주입 대기가 실제로 선 시간을 늘렸는가"(d = 0 팔 대비 사이트별 대기 시간)를 보고한다. 늘지 않았다면 그렇다고 적는다.

## 4. 판정(결과 전 고정)

### 4.1 안전 위반(모든 실행, 절대 기준)

- 포켓 금지 접촉: `len(forbidden_pocket_contacts)` > 0(실행 결과 또는 임무 기록).
- 허가 없는 진입: `obstacle_layer.unpermitted_entries` > 0 또는 `unpermitted_dir_entries` > 0. 러너의 참값 평가기가 제어 틱마다 정지 부피로 검사한 값이다(전 구간).
- 낮은 물체: `tools/low_clearance_report.py` 에서 물리 물체와 겹침(거리 ≤ 0) 또는 물리 정지 호 위반.
  - **안전 판정의 정지 모델은 모든 팔에 같다(2판 Codex P2-6).** 기준선의 정지 모델 값(B0 결과 기록)을 보고서 인자로 준다. 러너의 참값 평가기도 작업자 추가 지연을 빼고 원래 모델을 쓴다(`run_transport.py` 10402–10406). 그래서 두 평가가 같은 기준이 된다.
  - D12 가 자기 설정 모델(늘어난 지연)을 지키는지는 별도 지표로 보고만 한다.
- **보고만: 공칭 지연을 더한 보수적 민감도(agy ③-6).** 지연이 Δ 늘면 필요한 정지 거리가 최대 v·Δ 만큼 늘 수 있다. 장벽·holding·이미 반영된 증거 나이 때문에 언제나 순수 추가 거리는 아니다. 그래서 참값 평가기와 낮은 물체 정지 호를 정지 모델 지연 + 그 팔의 공칭 Δ(흔들림 팔은 최대 0.1 s)로 한 번 더 계산해 민감도로 보고한다. 판정은 위의 공통 기준으로만 한다. 이 값이 공통 기준과 크게 다르면 결과 문서에 따로 적는다.
  - 물리 최근접 < 0.05 m 은 위반이 아니라 "근접"으로 보고한다.
  - 정지 호는 0.1 s 표본에서만 검사하고, 무적재 후진은 검사하지 않는다(도구 한계). 이 범위 밖은 "미평가"로 적고, 허용 판정의 뜻을 "평가한 범위에서"로 한정한다(한계 절).
- live(B): 위 셋에 `scene_damaged` 를 더한다.
- **B0 에 위반이 있으면:** 그 장면·seed 는 "기준선 위반"으로 총괄에 올린다. 지연과 별개인 결함이다. 그 장면·seed 의 지연 팔 위반도 절대 기준으로 판정한다. 다만 물체·단계가 B0 와 같고 최소 거리가 B0 보다 1 cm 넘게 나빠지지 않은 사건에는 "B0 재현" 표시를 단다. 표시가 달려도 위반은 위반이다.

### 4.2 정지·종료의 구분

- **안전 정지 확인:** 실행이 끝나는 시각까지 이어진 **마지막** 구간이 0.5 s(60 제어 틱) 이상이고, 그 구간 내내 요청 속도 0, 참 차속 < 0.05 m/s, 제어 틱 기록이 끊기지 않았으며, 4.1 위반이 없는 경우. 그 앞의 정지 구간은 쓰지 않는다. 다시 움직이면 확인이 처음부터 다시 시작한다(3판 Codex P1-2). 임무 실패 사유로 끝나도 같다.
- **관측 종료(정지 안전성 미확인):** 위 조건을 채우지 못한 채 `require` 실패나 예외로 실행이 끝난 경우. 끝난 순간의 차속이 0.05 m/s 아래여도, 제동·정착이 0.5 s 관찰되지 않았으면 여기에 든다(2판 Codex P2-5). 배치에서 신선도 실패(`localization_stale`)가 그렇다(`run_transport.py` 6553–6563 → `RuntimeError`). 끝난 순간의 참 차속을 함께 적는다.
- B 는 live 라 `SessionFailure` 뒤 바퀴를 세우는 경로가 있다. 그래도 같은 두 종류로 나눠 적는다.

### 4.3 임무 결과와 운영 지표(A, 같은 장면·seed 의 B0 대비)

| 지표 | 출처(분석기 규칙) | 허용 폭 |
|---|---|---|
| 임무 결과 | `success`·`failure_reason` | 완료 |
| 임무 시뮬 시간 | `transitions` 의 첫 시각 → 마지막 시각(완료 실행만) | B0 × 1.15 와 B0 + 30 s 중 큰 쪽 이하 |
| 하역 오차 | `delivery_error_m`(m → cm) | B0 + 1.0 cm 이하 |
| 도킹 라운드 | 하역 도킹 라운드 수 | B0 + 1 이하 |

- 보고만(판정 밖): 감속 틱(`obstacle_layer.slowed_ticks` 의 단계별 값과 합), 장애물 재계획(`len(obstacle_layer.replans)`), 임무 재계획(`len(mission_replans)`, 따로 센다), 신선도·증거 나이 정지 횟수.
  - 감속과 정지가 늘어나는 것은 안전을 지키는 동작일 수 있다. 그래서 성능 실패로 세지 않는다(1판 Codex P2 반영).
- 허용 폭은 측정값이 아니다. "100 ms 이하의 지연이 임무를 눈에 띄게 늘리지 않아야 한다"는 운영 기대를 숫자로 적었다. 이 폭은 총괄이 계획 PR 에서 승인한다.
- B0 가 임무에 실패한 장면·seed 는 운영 지표를 비교하지 않는다. 그 지연 팔은 안전과 임무 결과로만 판정하고, 총괄에 올린다.

### 4.4 칸 분류와 결론(A)

- 분류는 위에서부터 처음 맞는 것 하나다(2판 Codex P1-2: 노출 부족이 실패·위험을 덮지 않는다).
  1. **위험:** 안전 위반 1 이상.
  2. **관측 종료:** 실행이 4.2 의 관측 종료로 끝남.
  3. **안전 실패:** 임무 실패, 안전 정지 확인.
  4. **노출 부족:** 임무 완료, 4.5 미충족. 허용으로 세지 않는다.
  5. **운영 저하:** 임무 완료, 운영 지표가 허용 폭 밖.
  6. **허용:** 임무 완료, 운영 지표 허용 폭 안, 노출 조건 충족.
- 노출 수치는 모든 칸에 함께 적는다. 실패 칸에서는 판정을 바꾸지 않고 참고로만 쓴다.
- 결론 규칙:
  - "위험"은 P1 결함이다. 기전을 진단해 고친다.
  - "관측 종료"는 P1 다음 우선순위의 결함이다. 정지 안전성을 알 수 없어서다.
  - S3·S6·U3·U6·C6 에서 "허용" 말고 다른 칸이 나오면 결함으로 진단한다(총괄 지시: 실패는 SW 결함). 운영 저하는 결함 목록에 넣되 진단 순서는 실패 뒤다.
  - S12·U12·D12·J 의 안전 실패·관측 종료도 결함이다. 우선순위는 50 ms 이하 칸 다음이다.
  - D12 와 U12 는 짝으로 읽는다. "지연을 알면 견디고, 모르면 선다"는 D12 허용이고 U12 가 **안전 실패(안전 정지 확인)**일 때만 쓴다. U12 가 관측 종료면 "정지 안전성 미확인", 위험이면 "안전 위반"으로 적는다(2판 Codex P2-5). 고칠 방향의 예는 실제 설치 지연을 재서 사용 나이를 맞추는 것(측정 기반 알림)이다.
- 결정 모드라 같은 장면·seed 는 같은 결과를 낸다. 한 칸 한 실행이 그 seed 의 결과다. seed 셋은 일반화가 아니라 표본이다.

### 4.5 노출 조건(주입이 실제로 작동했는가)

- 노출 조건은 팔마다 본다. 미충족이면 "노출 부족"이다.
- **SLAM 팔:** 반영 시점에 차속 > 0.05 m/s 이고 추적기가 holding 밖인 지연 답(직접 자세 영향)이 200 개 이상. holding 안의 지연 답 수(신선도 영향)는 따로 보고한다.
- **층 팔:**
  - 제출 시점에 차속 > 0.05 m/s 인 작업이 200 개 이상(holding 안팎을 모두 센다. holding 은 층의 설치·허가 갱신을 멈추지 않는다).
  - 그 가운데 예정 틱에 설치된 비율(장벽 설치 아님)이 0.8 이상.
  - 실제 설치 지연의 분포(최소·중앙·최대 틱)와 holding 안팎별 수치·예정 설치 비율을 보고한다.
- **B:** 임무를 마친 판정 세션마다 지연을 받은 답이 3 개 이상이고, `prepare` 와 `dock` 가 그 안에 있어야 한다. 임무 실패·위험 세션은 노출과 관계없이 그 판정을 따른다(4.4 와 같은 순서).
- B0 의 노출 표를 함께 낸다. 장면에서 근접 캡처·후진·복귀·장애물 재계획이 몇 번 일어났는지 보여 주는 표다.
- 200·0.8 은 정한 값이다. 한 실행에 이동 중 스캔이 수백 개 이상이라는 기대(10 Hz × 이동 시간)에 맞춘 하한이다.

### 4.6 B 판정

- d = 0·25·50·100 의 12 세션 모두 안전 위반 0, 기대한 임무(임무 ID 와 개수)가 모두 완료, 노출 조건 충족이면 "B 통과"다. 임무 완료는 세션의 최상위 `success` 가 아니라 임무 결과 목록으로 본다(live 세션은 실패 임무가 있어도 `success=True` 로 끝날 수 있다).
- 안전 위반은 P1 결함이다. 임무 실패와 관측 종료는 결함으로 진단한다.
- 보고만: 팔마다 계획 대기 합(선 시간), 사이트·사유별 버림, 다시 요청 수, 임무 시뮬 시간, AUTO 배율, 실제 주입 지연(도착 → 전달)의 분포. 비결정이라 팔 사이 수치를 비교해 판정하지 않는다.
- 500 ms 는 보고만 한다. 실패는 결함 목록에 넣고 우선순위는 가장 낮다.

## 7. 한계

- **결정 배치의 틱 지연은 live 의 벽시계 지연과 같은 것이 아니다(대용 관계).**
  - 배치에서는 지연 동안 시뮬이 정확히 n 틱 돌고, 다른 계산은 시간이 들지 않는다.
  - live 에서는 지연이 벽시계로 생기고, 배율·다른 스레드·다른 채널의 지연과 섞인다. live 에는 이미 자연 지연이 있다(SLAM 답 중앙 31 ms).
  - 그래서 A 의 결과는 "이 시뮬 시간 지연에 이 제어 논리가 어떻게 반응하는가"이다. 실차·live 의 내성 값으로 옮기지 않는다.
- 배치에는 계획 지연 경로가 없다. 계획 채널은 B(비결정, 한 장면·한 seed, 팔마다 3 세션)로만 본다. B 는 빈도를 추정하지 못한다.
- 결정 모드의 설정 차이: 학습 제안기 대신 oracle 마스크, 픽셀 지연 0, 계획 예산 상한(결정 모드 계획 D1b·D6). 이 차이가 지연 반응을 바꿀 수 있다.
- 두 장면·세 seed 는 작은 표본이다. "허용"은 이 칸들에서 실패를 못 봤다는 뜻이고, 내성의 보장이 아니다.
- 고정 지연과 균등 흔들림만 본다. 긴 꼬리(가끔 수백 ms)나 채널 사이 상관은 J 와 B 500 ms 로만 조금 본다.
- 층 지연은 장벽 설치로 짧아질 수 있다. 실제 지연 분포와 노출 조건으로만 다룬다.
- 배치의 `require` 실패는 실행을 그 자리에서 끝낸다. 그래서 그 뒤 "안전하게 서는가"는 A 에서 보이지 않는다(4.2 의 관측 종료).
- 낮은 물체의 정지 호는 0.1 s 표본에서만, 무적재 후진은 빼고 평가한다. 이 범위의 허용은 "평가한 범위에서"다.
- 장애물은 장면에 고정된 정적 물체다. 움직이는 장애물은 없다.
- SLAM 지연은 holding 단계(접근·삽입·들기·빼기·내리기·물러나기)의 제어 자세 보정에 바로 닿지 않는다(2.1). 이 구간은 신선도와 해제 점프·재계획으로만 본다.
- A 는 결정 모드 온라인 매핑이라 SLAM 정적 층이 계획에 들어가지 않는다. SLAM 지연이 정적 지도 갱신·`unsent_scans` 거부를 거쳐 계획을 바꾸는 경로는 시험하지 않는다.
- 층의 delay 모드는 계산을 주 스레드에서 끝낸다. 스레드 작업자의 GIL 경합과 주 스레드 감속(1e 단계 1 에서 관찰)은 들어 있지 않다. 설치 때 허가 갱신이 스캔 시각의 자세·경로를 쓰는 것은 지연의 일부로 보고 그대로 둔다.
- 장면 대표성: line_2·random_1 은 좁은 통로(aisle_rack)·트레일러 출구(trailer)를 포함하지 않는다. 출구 면제(`exit_stamp_back_s`)처럼 그 장면에서 주로 쓰이는 지연 보정 경로는 이 시험에서 거의 쓰이지 않는다. 운용 기본인 조사 지도 위치 추정도 A 에는 없다(B 만 쓴다).
- 검정력: 한 팔이 6/6(A, 장면·seed 합)이나 3/3(B) 통과해도, 단측 95 % Clopper-Pearson 상한으로 실패율 39.3 %·63.2 % 를 배제하지 못한다. "허용"은 실패율이 낮다는 증거가 아니다.
- B 는 한 장면(1 임무)이라 `observe_failed`·`scene_replan` 경로가 거의 불리지 않는다.
