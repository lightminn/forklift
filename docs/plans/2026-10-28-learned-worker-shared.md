- `docs/plans/2026-10-24-ws1-isaac-bundle.md`(7 절 노드 단독 측정)

총괄 지시는 "우선순위 낮음, 계획만"이다. 이 문서는 착수 조건과 단계를 고정해 두는 계획이고, 착수는 총괄 결정으로 한다.

## 0. 왜

live 세션은 GPU 당 3 개다. 넷째가 들어가지 못하는 이유는 VRAM 이다.
- 세션 정점은 Isaac 과 그 세션의 learned 작업자를 합쳐 3,890–4,047 MiB 다. 그 밖에 세션당 약 50 MiB 의 차이가 있다.
- GPU 에서 쓸 수 있는 몫은 15,839 MiB 다.
- 작업자 하나는 514 MiB 이고(따로 잰 값), 그 절반은 CUDA 컨텍스트와 ORT 기본 몫이다.
- CPU 제공자(A2)는 지연 때문에 불채택됐다.

A3 는 한 GPU 의 세션들이 CUDA 작업자 하나를 같이 쓰게 하는 안이다.

## 1. 계산과 그 한계

**VRAM.** 지금 3 세션이면 3 × (4,047 + 50) = 12,291 MiB 다. 공유 4 세션이면 다음과 같다.
- 4 × (4,047 − 514 + 50) + 514 + Δ = 14,846 + Δ ≤ 15,839 이므로 Δ ≤ 993 MiB 다. 여유 300 MiB 를 두면 Δ ≤ 693 MiB 다.
- 이것은 조건부 예산이다.
  - 4,047 정점에서 작업자 몫이 실제로 514 였는지는 원표본으로 확인하지 않았다(따로 잰 514 를 뺀 추정이다).
  - 50 MiB 는 관측된 프로세스 합 밖의 차이일 뿐, 프로세스마다 고정으로 붙는 값이 아니다.
  - Δ 에는 동시 요청의 활성 메모리, 공유 서버의 드라이버 차이, 스레드별 자원, ORT 아레나의 잔류 증가(BFCArena 는 확장분을 돌려주지 않는다)가 다 들어간다.
- 네 세션의 정점이 겹치는 경우도 이 식에 들어 있다(세션마다 정점을 쓴다). 정점이 4,047 을 넘는 세션이 나오면 식이 깨진다. 그래서 P1 에서 세션별 정점을 다시 잰다.

**지연.** 평균 이용률로는 판단하지 않는다.
- 세션 전체 평균 호출률은 약 0.28 회/s 다(line_m CUDA 1,349 회 ÷ 4 세션 ÷ 약 20 분).
- 실제 공급은 관측 구간 안에서만 시뮬 시간 5 Hz 로 들어온다. 배속 0.35–0.4 면 세션당 벽시계 약 1.75–2 회/s 다. 네 세션이 겹치면 7–8 회/s 다.
- 작업자 시간은 p50 43, p95 119 ms(line_m)와 p50 78, p95 159 ms(random_m)다. 겹침 동안의 부하는 line_m 30–35 %, random_m 54–62 %(중앙값 기준)로 낮지 않다.
- M/D/1 평균이나 "최대 +130 ms" 같은 상한은 근거로 쓰지 않는다. 판정은 P0·P1 의 실측으로 한다.
- §6 의 0.5 s 는 촬영 시각(시뮬) 간격이고, 서버 대기(queue_ms)는 벽시계다. 두 값을 직접 비교하지 않는다. 판정은 FarWorker 의 큐·버림과 LiveFar 반영까지 통과한 결과(반영 프레임 간격)로 한다.
- 요청마다 RGB 640×480(약 900 KB)을 직렬화한다. 소켓 IPC 비용은 지금 파이프와 같은 크기로 보지만, P0 에서 따로 잰다.

**CPU.** live 묶음의 CPU 예약은 슬롯 × 2 + 2(브리지)다. 공유 서버의 추가 예약을 C 라 하면 다음과 같다.

| 구성(GPU 두 장) | CPU 예약 | 동시 세션 |
|---|---|---|
| 지금 3 + 3 | 16 | 6 |
| 공유 4 + 지금 3 | 18 + C | 7 |
| 공유 4 + 공유 4 | 20 + 2C | 8 |

- C = 2 면 4 + 3 은 노드 CPU 20 에 들어가지만 4 + 4 는 들어가지 않는다.
- 세션당 2 코어에는 지금 작업자의 부하도 들어 있으므로, 서버 비용이 전부 순증인지 재야 한다.
- 채택 기준은 배속이 아니라 **노드 완료 실행/h** 다.

**호스트 RAM.** KINDS live 의 session_gib 5.5 × 4 + 공유 캐시와 여유 2 = 24 GiB 에 서버 RSS(R, 미측정)를 더한다.
- 노드 Slurm 몫은 56.6 GiB 이고, 4 + 3 이면 24 + R + (5.5 × 3 + 2 = 18.5)다.
- R 은 P0 에서 잰다.

## 2. 설계

- **서버.** `forklift_learned.worker --serve-socket PATH` 를 더한다.
  - 연결마다 스레드 하나가 지금 틀로 요청을 받는다.
  - 추론은 공유 InferenceSession 으로 하고, 동시 Run 과 잠금 직렬화 중 무엇으로 할지는 P0 로 정한다. 잠금이면 잠그는 범위(Run 만인지, propose 전체인지)를 적는다.
  - CUDA Graph 는 쓰지 않는다(같은 세션 다중 스레드 Run 을 지원하지 않는다).
  - 응답에는 대기·전처리·Run·후처리 시간을 나눠 넣는다.
- **핸드셰이크.** 연결 때 다음 항목이 다르면 서버가 연결을 거부한다.
  - 프로토콜 버전, 모델 sha256, 입력 규격
  - 후처리 설정(conf·IoU·max_det)
  - 실제 provider 와 device
  - 준비 완료 신호는 모델 적재·워밍업·provider 확인 뒤에 낸다. 세션은 그 신호를 받은 뒤에 미션 관측을 시작한다.
- **실패 정책(공유 모드).** 자기 작업자로 돌아가지 않는다.
  - 서버가 죽거나 연결이 끊겨 네 세션이 각자 작업자를 띄우면 4 × (4,047 + 50) = 16,388 MiB 로 예산을 549 MiB 넘는다. 서버가 살아 있는데 연결만 끊긴 경우도 16,902 + Δ 다.
  - 묶음의 VRAM 문은 다음 시작만 막고, 이미 도는 세션의 작업자 생성은 막지 못한다.
  - 그래서 공유 모드에서 서버를 잃은 세션은 **실패로 끝난다**.
    - 러너는 전용 실패 사유 `learned_server_lost:` 로 끝나고, 실패 분류표와 콘솔 사유에 이것을 넣는다.
    - 묶음의 infra 판정 패턴(`infra_signs`)에도 이 사유를 넣는다.
    - 묶음 실행기는 서버가 다시 준비 완료를 낼 때까지 그 GPU 에서 재시도와 새 시작을 하지 않는다.
  - `LearnedSource.run` 은 지금 모델 예외를 받아 geometric_fallback 으로 바꾼다. 공유 모드에서는 엄격 정책을 전달해 기하 대체 대신 실패로 끝나게 한다. 결정 모드의 기존 중단과 같은 경로다.
  - 서버 기동 실패나 준비 지연에도 같은 정책을 쓴다.
- **소유와 VRAM 회계.** 서버는 묶음 실행기(runner)가 소유한다(자손 프로세스).
  - 그래야 `sample_vram` 의 잡 합계에 들어간다.
  - 시작 허용식에 서버의 예약 상한과 아직 늘 워밍업 메모리를 넣는다.
  - 서버의 RSS·VRAM 은 vram 표본에 따로 남긴다.
- **소켓 경로.** 소켓은 짧은 경로(`/tmp/forklift_lw_<job>_<gpu>.sock`)에 두고, 107 바이트 검사를 한다.
- **크기.** KINDS live 에 공유용 항목을 둔다(세션 vram 3,600 과 서버 vram·CPU·RSS 따로). 공유를 켠 묶음만 4 슬롯을 쓴다. 기본값은 판정 뒤에 바꾼다.
- **기록.**
  - 실행 결과에 `learned_worker: {mode, socket, handshake, failures}` 를 남긴다.
  - 러너 인자는 기본(없음)일 때 기록하지 않는다. 근접 계약과 s4 비교에서는 RUN_SPECIFIC·by-design 으로 둔다.
- **결정 모드.** 공유 모드는 결정 모드와 함께 쓰지 않는다(러너가 거부한다). 다른 세션의 요청 시각이 응답 시각을 흔들어 재현성을 깬다.

## 3. 단계와 판정(사전 등록 초안)

**P0 탐침(GPU 한 장, Isaac 없음, 노드 단독 측정 절차를 따른다).** 운영 구성을 고정한다. ORT·CUDA·cuDNN, provider 옵션, 4 스레드, CPU affinity, 실제 저장 RGB 다.
- 동시성·메모리
  - 1·2·4 클라이언트로 잰다.
  - 직렬과 동시 Run 을 비교한다.
  - handler 별 첫 호출을 따로 본다.
  - 반복 연결과 장시간 요청 뒤 남는 VRAM·RSS 를 잰다.
  - 지속 4 중 관측 겹침(세션당 벽시계 약 2 회/s)과 동기화된 반복 요청도 넣는다.
- 정확성·격리: 서로 다른 프레임을 동시에 보내 직렬 기준과 mask·score·ID 가 같은지, 응답이 섞이지 않는지 본다.
- 시간·공정성
  - 대기·전처리·Run·후처리·송수신을 나눠 잰다.
  - 클라이언트별 꼬리와 최장 대기·기아를 본다.
- 장애
  - 서버 종료·정지, 연결 단절, 느린 수신자, 타임아웃, 클라이언트 종료를 주입한다.
  - 한 클라이언트의 close·타임아웃이 서버와 다른 클라이언트를 끝내지 않아야 한다.
- 중단 조건
  - Δ > 693 MiB 면 멈춘다.
  - 같은 P0 환경·입력·집계로 1 클라이언트 왕복 기준선을 먼저 잰다. 4 클라이언트 지속 겹침의 왕복 p95 가 그 기준선 p95 의 2 배를 넘으면 멈춘다(같은 지표끼리 비교한다).
  - 정확성이 깨지면 멈춘다.
  - 서버 CPU 와 RSS 로 1 절 표를 다시 계산해, 4 + 3 이 CPU 20 과 RAM 56.6 에 안 들어가면 멈춘다.

**P0 실행 조건(2026-10-28 사전 등록, 총괄 승인, 결과 전).**
- P0 는 Isaac 렌더 경합이 없는 **선별 시험**이다. 실제 운용 조건의 지연은 P1 에서 판정한다.
- 노드 단독 대신 한 Slurm 잡(shard 1, Isaac 없음)에서 잰다.
  - 1 클라이언트 단계(A)와 4 클라이언트 단계(B)를 번갈아(ABAB…) 잰다. 단계는 90 s, 쌍은 4 개다.
  - 이것을 잠금 방식(serial, concurrent)마다 한다.
  - 클라이언트는 공통 시계에 맞춰 같은 순간에 요청한다(세션당 2 회/s = 시뮬 5 Hz × 배속 0.4, 동기화된 최악). 4 중 관측이 끝까지 겹치는 경우다.
- 입력: ws1 `test_runs/live/ct2_07ca86aa_auto_random_m_s4` 의 원거리 인식 프레임 RGB(480×640)다.
- 제외 규칙: 측정 내내 같은 GPU 의 다른 프로세스 SM 사용률(nvidia-smi pmon)을 1 s 마다 기록한다.
  - 어느 단계의 평균이 모든 단계 평균의 **중앙값**에서 30 % 넘게(그리고 5 %p 넘게) 벗어나면, 그 단계가 든 쌍을 쌍째로 뺀다.
  - 중앙값으로 한 이유: 처음 문구("모든 단계 평균")대로 평균을 기준으로 하면, 튀는 단계 몇 개가 기준을 끌어올려 정상 단계까지 모두 빠진다. 단위 시험이 이것을 보였다(10 % 단계 6 개와 60 % 단계 2 개면 평균은 22.5 이고, 모든 쌍이 빠진다). 결과 전에 고쳤다.
  - 남은 쌍이 3 개 미만이면 지연 판정은 미판정이다.
- 판정(잠금 방식마다, 모두 참이어야 통과)
  - **Δ** = 공유 서버의 VRAM 최대 − 같은 잡에서 잰 자기 작업자(파이프, 지금 방식)의 VRAM 최대. 693 MiB 이하.
  - **지연**: 남은 쌍마다 B 의 왕복 p95 ÷ A 의 왕복 p95 가 2 이하.
  - **정확성**: 모든 응답이 직렬 기준(자기 작업자로 같은 프레임)과 같다. id 순서가 같고, 점수 차 ≤ 1e-3, 마스크 IoU ≥ 0.99 다. 오류도 0 이어야 한다.
  - **CPU·RAM**: B 단계 동안 서버의 평균 코어 C 와 RSS 최대 R 로, 4 + 3 구성이 CPU 18 + ⌈C⌉ ≤ 20 과 RAM 24 + R + 18.5 ≤ 56.6 GiB 에 들어간다.
  - **장애**: 반쪽 프레임을 보내고 사라지는 클라이언트와 응답을 읽지 않는 클라이언트 옆에서, 정상 클라이언트의 20 호출이 모두 맞다.
- 두 잠금 방식 중 하나라도 통과하면 P0 통과이고, 통과한 방식이 P1 의 방식이다. 둘 다 통과하면 B 왕복 p95 가 낮은 쪽을 쓴다.
- 도구: `tools/learned_share_probe.py`(learned venv 에서 실행)다. 출력은 summary.json, calls_*.jsonl, samples.jsonl 이다.

**P0 → P1 단계 조건.**
- P1 은 P0 결과로 아래 노출량 하한을 숫자로 정하고, 그 하한을 P1 사전 등록 문서에 적어 Codex 검토를 받은 뒤에만 낸다. P1 결과를 본 뒤에는 하한을 바꾸지 않는다.
- 하한의 시작값(P0 가 더 엄하게 할 수는 있지만 느슨하게 할 수는 없다)은 다음과 같다.
  - 구성 B 의 공유 묶음에서, 넷이 동시에 원거리 관측 중인 벽시계 시간이 실행 묶음 합계 120 s 이상이다.
  - 그 동안의 learned 호출이 200 회 이상이다.
  - 관측 다리마다 반영 프레임 간격 표본이 10 개 이상이다. 미달인 다리는 미판정이고, 미판정 다리가 전체의 20 % 를 넘으면 P1 전체가 미판정이다.

**P1 live 시범**
- 장면: line_m·random_m(random_m 은 P-4:D-1,P-5:D-2,P-3:D-3) × seed 0–3.
- 구성 둘을 같은 스냅숏·같은 실행 목록으로 **따로** 돌린다(각각 노드 단독, 같은 seed).
  - A = 지금 3 + 지금 3(기준선)
  - B = 공유 4 + 지금 3
- 처리량 = 유효 완료 실행 수 ÷ 측정 구간이다.
  - 측정 구간은 그 구성의 첫 실행 시작부터 마지막 실행 끝까지다.
  - 기동, 꼬리, 실패와 재시도 시간을 모두 넣는다.
- 유효 조건
  - 모든 세션이 미션 3/3 이다.
  - learned 100 %, 기하 대체 0, 공유 모드 실패 0 이다.
  - 동시 관측 노출이 사전 고정량 이상이다. 4 중 겹침 시간·호출 수, 다리별 유효 간격 표본 수를 본다. 표본이 부족하면 미판정이다(`far_frame_gaps.py` 는 표본 0·1 개에서 primary_ok=true 를 내므로 표본 수를 따로 본다).
- 판정
  1. 공유 팔에서 넷째가 매번 시작하고, GPU free 최소가 300 MiB 이상이다.
  2. §6 주 조건을 두 팔 모두 통과하고, 경보(연속 버림, 0.4 s 초과, 정지 미반영)가 공유 팔에서 더 많지 않다.
  3. B 의 처리량(완료 실행/h)이 A 보다 높다.

- 집계는 적용된 결과의 요약뿐 아니라 live.jobs, 폐기된 완료 호출, late_calls 를 포함한다.
