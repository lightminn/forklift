# riib 영상 인코딩 비용 측정 M1 — 사전 등록 (2026-10-28)

관련: 총괄 결정(2026-10-27, 2026-10-28), PR "video preset"(`--video-preset`, riib `VIEWS`). 이 문서는 배치를 내기 전에 쓴다. 판정 규칙은 결과를 본 뒤 바꾸지 않는다.

## 1. 묻는 것

1. 기본 preset 을 veryfast 와 ultrafast 중 무엇으로 둘까(세션 CPU 와 mp4 크기).
2. riib 묶음의 CPU 예약(지금 3 슬롯 CPU 8 = 세션당 2 + 브리지 2)을 줄일 수 있나.

## 2. 실행

- 스냅숏: 영상 PR 머지 커밋의 main(`snapshots/m1v_<sha>`).
- 팔 4 개. 나머지 env 는 T2(t2d_1b60df21) 목록과 같다.
  - V0: `EXTRA_ARGS=--video-preset medium`. 옛 인코더, 두 보기.
  - V1: 기본(veryfast). 두 보기.
  - V2: `EXTRA_ARGS=--video-preset ultrafast`. 두 보기.
  - V3: `VIEWS=none`. veryfast, 전체 영상 하나.
- 장면은 `SCENE=aisle_rack`, `SCENE=line_2`(MARKERS 기본 on → line_2_m)이고 seed 0–2 다. 팔당 6 실행, 모두 24 실행이다. MODE·NEAR 등은 런처 기본이다.
- 묶음: riib 묶음 두 잡(GPU 하나에 하나, 3 슬롯, sizes riib)이 claim-dir 하나를 나눠 쓴다.
  - 목록 순서는 (장면, seed) 마다 V0–V3 를 차례로 둔다. 그래서 같은 시점에 네 팔이 섞여 돈다.
  - 다른 GPU 잡이 없을 때 낸다(대기 조건 없이 FIFO).
- 사전 검사: `isaac_bundle.py check` 로 증명을 만들고 낸다.

## 3. 재는 것(실행 단위)

- `cpu_s`: 묶음 기록이다. 실행의 자식 rusage 라 ffmpeg 를 포함한다.
- `wall_s`, 세션 평균 코어 = cpu_s / wall_s.
- 배속: 배치 실행은 live 배속 기록이 없으므로 result.json 의 `samples[-1].time_s` ÷ `wall_time_s` 로 셈한다. frames.jsonl 은 보기 영상이 있을 때만 생겨서 V3 에 없으므로 쓰지 않는다.
- mp4 합계 바이트: 실행 폴더의 *.mp4.
- maxrss, vram_max.
- 미션 결과(성공 여부, 실패 이유)는 기록만 한다.

## 4. 판정(사전 등록)

- **preset**(V1 대 V2, 두 보기 팔끼리만; V3 는 mp4 비교에서 뺀다)
  - ultrafast 를 기본으로 하려면 두 조건을 모두 만족해야 한다.
    - 세션 평균 코어 중앙값이 veryfast 보다 10 % 이상 낮다.
    - mp4 합계 중앙값이 veryfast 의 2.5 배 이하다.
  - 아니면 veryfast 를 유지한다.
- **CPU 예약**
  - 고른 기본값 팔(V1 또는 V2)의 세션 평균 코어 p90 을 c 라 한다.
  - 필요 CPU = ⌈3 × c⌉ + 2(브리지)다.
  - 이 값이 8 보다 작고, 그 팔의 배속 중앙값이 V0 의 배속 중앙값 이상이면 sizes 의 riib 코어 수를 낮추는 PR 을 낸다. 아니면 그대로 둔다.
  - V3 은 CPU·배속만 보고한다(비교 배치용 참고, 기본 변경 없음).
- **결과 확인**: 팔 사이 미션 결과 차이는 판정에 쓰지 않는다. preset 은 결과에 영향이 없어야 하므로, 다르면 따로 보고한다.

## 5. 크기·시간

- 실행당 약 40 분이다(T2 기록).
- 24 실행 ÷ 6 슬롯 = 4 파동, 약 2.7–3 시간이다.
- sizes riib --runs 24 --jobs 2 --run-min 45 의 값을 그대로 쓴다.

## 6. 결과 (2026-10-28, 판정은 4 절 그대로)

스냅숏 `m1v_28e6fbcd`, 목록 `test_runs/riibotics/m1v/RUNS.jsonl`(check 증명 verified), 잡 11895·11896, 24 실행 모두 끝났다(infra 실패 0). 집계는 `m1v/m1_analyze.py` 다.

**측정 조건의 어긋남.** 노드를 혼자 쓰지 못했다.
- M1 은 홀 조사(11888)와 trf1(11898)을 afterany 로 기다렸다.
- trf1 이 먼저 끝난 04:16 에, 의존 없는 다른 잡(dk9_b1, 이어서 nrm_b1)이 빈 GPU 를 가져갔다. 의존이 남은 잡은 FIFO 자리를 잡지 못하기 때문이다.
- 그래서 bundle1 은 04:50–06:41 에 nrm_b1 과 노드를 같이 썼고, bundle2 는 06:41 에 시작했다. bundle1 은 16 실행, bundle2 는 8 실행을 돌렸다.
- 팔은 (장면, seed)마다 섞여 있어 팔 사이 비교에는 같은 부하가 대체로 고르게 걸렸지만, 절대값(배속·코어)에는 경합이 섞였다.
- 다음 측정은 의존이 아니라 나머지 GPU 잡이 다 빠진 뒤에 제출해야 한다.

| 팔 | 세션 코어 중앙값 / p90 | 배속 중앙값 | mp4 합계 중앙값 | 성공 |

**판정.**
- preset: ultrafast 의 코어 중앙값이 veryfast 와 같다(1.80 대 1.80, 0.3 %). mp4 는 5.3 배다. 그래서 **veryfast 를 유지**한다. veryfast 는 medium 보다 세션당 약 0.3 코어(15 %) 덜 쓰고, 파일은 0.6 배다.
- CPU 예약: V1 의 코어 p90 은 1.98 이다. ⌈3 × 1.98⌉ + 2 = 8 로 지금과 같으므로 **8 을 유지**한다. 3 × 1.98 = 5.94 로 6 바로 아래라 줄일 여지가 없다.
- V3(참고): 추가 보기 둘을 끄면 코어는 1.57 로 줄고 배속은 0.203 으로 오른다(V1 대비 약 +37 %). 추가 카메라 두 대의 렌더 비용이다. 영상이 필요 없는 비교 배치에 `VIEWS=none` 을 두 팔 같게 쓰면 시간을 꽤 줄일 수 있다. 기본값은 바꾸지 않는다.
- 미션 결과(판정 밖, 기록): aisle_rack 12 실행 중 6 건이 `Tracking timeout in transport` 로 끝났다(V0 2, V1 1, V2 1, V3 2). line_2 는 12/12 성공이다. 팔 사이 차이는 preset 과 무관해 보인다. aisle_rack 의 운반 추적 시간 초과 자체는 이 측정의 범위 밖이다.
