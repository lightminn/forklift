# cusp 정체 래치가 반대 제동 `braking` 에 닫히는 결함 (3판)

브랜치 `fix/cusp-latch-braking`(origin/main `1b9de67`). 사용자 결정(2026-10-22, 총괄 세션 경유): 고친다 — 원인 확정 → 반례 시험 먼저 → 수정 → Codex 수렴 → Isaac 확인. 다리 끝 크리프와 정지 문턱(약 2.3σ)은 관절각 오도메트리 전환 뒤 다시 재고 범위를 정한다(이번에 고치지 않는다).

## 1. 사실 (원자료에서 다시 계산)

원자료: ws1 `test_runs/riibotics/n2_random_1_s0/run`(스냅숏 `nrc_be901a0`, `docs/validation/2026-10-22-near-recapture-scenes.md`). 근접 다리 cusp 에서 0.070 m·0.062 rad 모자라 서서 관측 시간 초과로 끝났다.

- `cusp_stalls`: 래치 19 번, 그중 18 번이 `closed: status:braking`, `stop_confirmed` 17 번, `observe_rule` 1 번(46.783 s, 46.817 s 에 다시 `braking` 으로 닫힘). 5 s 판단 대기를 채운 판단은 그 한 번뿐이었다.
- 정지 검출기 입력 재현: `slam_log.npz` 의 바퀴 각속도에 실행의 잡음 seed(`OdometryNoise`, 바퀴 각속도 다음 조향 순서)를 다시 적용하고, 러너처럼 뒤 두 바퀴 평균 × 반지름 0.125 m 로 오도메트리 속도를 만든 뒤 12 tick(0.1 s) 평균을 냈다(`stop_probe.py`).
  - 차가 서 있던 30–53 s(2,760 tick): 창 평균 −0.0159 … +0.0187 m/s, 원시 σ 0.0179 m/s, 창 평균 σ 0.0051(문턱 0.012 ≈ 2.4σ). |창 평균| > 0.012 는 66 tick(2.39 %) — 다리 진행 반대(< −0.012) 50 tick(1.81 %), 같은 방향 16 tick(0.58 %).
  - 문턱을 처음 넘은 tick 32.900 s = 첫 래치 종료 32.900 s. 이후 종료(38.875, 38.933, 39.292 …)도 반대 방향 초과 구간과 겹친다.
  - Codex 재계산: 이 오도메트리를 적분하고 기록된 SLAM 보정을 적용한 제어 자세가 저장 표본과 최대 1.8×10⁻¹⁵ 로 일치했다. 종료 18 회 모두 창 평균이 음의 문턱을 넘었고, 추종기를 다시 돌리면 그 tick 들은 `at_endpoint=False`·`cusp_pending=False`·`status="braking"` — 끝점·보류 분기나 cusp 방향 보류(수정 A)는 원인이 아니다. 18 회 중 한 번은 `observe_rule`(46.783 s) 뒤에 닫혔다.
- 기전:
  - `StopDetector.tracker_speed(0.012)` 는 창 평균이 문턱을 넘으면 그 평균을 그대로 추종기 속도로 준다(`slam_pose.py`).
  - 추종기는 `target_speed * signed_speed < 0 and |signed_speed| > stop_speed` 이면 목표를 0 으로 두고 상태를 `braking` 으로 낸다 — 움직임 반대 제동(`path_tracking.py` 489–495행).
  - `CuspStallMonitor.tick` 은 래치 중 원래 상태가 `tracking` 이 아니면 래치를 닫는다(`cusp_stall.py` 438–446행; 설계 `docs/plans/2026-10-04-lidar-obstacle-map.md` K2: "원래 상태가 `tracking` 이 아니게 되면 풀린다 — 실패를 덮지 않는다").
  - 그래서 서 있는 차의 오도메트리 잡음이 진행 반대쪽으로 문턱을 넘을 때마다 래치가 닫히고, 120 tick 진행 조건으로 다시 걸리기를 되풀이해 5 s 판단에 거의 닿지 못한다.
- 관절각 오도메트리(`--encoder-model team_spec_quantized`, 브랜치 `feat/joint-angle-odometry` 9b1ff43, T11 세션 측정)에서는 정지 감지기 입력이 두 뒤 바퀴 계수 증분 평균 × r / dt 라 정지 중 값이 0 또는 1 계수 0.0115 m/s·2 계수 0.023 m/s 의 이산 값이다. 시험 실행 jao_smoke_tq_off_s0 정지 틱 1,496 에서 0.1 s 평균 σ 0.0006, 최대 0.0019, 문턱 초과 0 %(reported 모델 bs_off_s0/s1 은 3.6 %/5.0 %). 즉 이 계기는 지금 기본(reported) 모델의 잡음에서 생기고 관절각 모델에서는 거의 사라진다. 그래도 래치가 잡음성 반대 제동에 닫히는 것은 모델과 무관한 계약 결함이라 고친다(총괄 지시).
- 기존 시험 `tests/unit/control/test_cusp_stall.py::test_one_forced_replan_per_key_across_a_new_latch` 는 `status="braking"` 으로 바꾼 원래 결과가 래치를 닫는 것을 고정하고 있다(554행). 그 시험의 목적은 "같은 키로 다시 걸려도 강제 재계획은 한 번"이다.

## 2. 범위

- 래치 중 원래 상태가 `braking` 이어도, 그 `braking` 이 움직임 반대 제동이면 래치를 닫지 않는다. 판별:
  - `raw.failure is None`, `not raw.cusp_pending`(cusp 방향 보류는 다른 규칙 — 수정 A — 의 몫), `raw.at_cusp`, 같은 키(지금처럼 `key_changed` 가 먼저).
  - 추종기에 "지난 `update()` 의 `braking` 은 움직임 반대 제동"이라는 읽기 전용 속성 `braking_against_motion` 을 둔다 — `update()` 시작에 False, 반대 제동 분기에서만 True. 끝점·도착·보류의 `braking` 과 구별하려면 상태 문자열만으로는 부족하다. `TrackingCommand` 필드로 두면 `asdict(tracking)`(표본·SAMPLE 출력)과 `MissionState.last_tracking` 의 리플레이 최종 비교가 바뀌어 옛 기록 재생이 깨지므로 속성으로 둔다(Codex 1차 P2 — 필드 추가로 최종 상태 불일치를 재현함). 모니터는 원래 결과를 만든 그 추종기에서 곧바로 읽는다(지금 호출 순서: 원래 update 직후 모니터).
  - 예외는 래치의 모든 단계(`brake`·`judge`·`observe_rule`·`handed`)에서 같다. 각 단계의 다른 규칙(정지 재인정, 인계 중 `hold=False`·소유권 반환·키당 강제 재계획 1 회)은 그대로다.
- 실패(`failed`), 도착(`arrived`), 끝점·보류의 `braking`, 키 변경, 제외는 지금처럼 닫는다.
- 래치가 이미 내는 것은 그대로: 래치 중 명령은 0(제동·판단) 또는 장애물 인계, 정지를 잃으면 `stop_lost` → 제동 → 재인정(5 s 는 첫 정지 인정부터).
- 설계 K2 의 "원래 상태가 `tracking` 이 아니게 되면 풀린다"를 "실패·도착·끝점/보류 제동이면 풀린다 — 위 판별을 만족하는 움직임 반대 제동은 래치의 어느 단계(`brake`·`judge`·`observe_rule`·`handed`)에서도 풀지 않는다"로 좁힌다(인계 단계에서는 모니터가 0 을 덮어쓰지 않고 장애물 처리가 명령을 맡는다). 이 문장을 설계 문서에 덧붙인다.
- 러너 인자·기록 형식 변경 없음(추종기 결과 dataclass 는 그대로). 래치 기록의 `closed` 값과 그 뒤 사건 순서는 결함을 밟는 실행에서 달라진다 — 의도한 제어 동작 차이다.
- 하지 않는 것: "명령이 이미 0 이면 반대 제동을 생략"(실제로 반대로 움직이는 차에 새 진행 명령이 나간다 — 이 실행의 원래 목표 속도도 0 이 아니라 +0.000818 m/s, Codex), 래치가 내보내는 상태를 `tracking` 으로 바꾸기(agy ③ 지적 — 아래 검토 기록).
- 범위 밖: 정지 문턱·창 길이, 다리 끝 크리프(작은 비영 명령의 정지 누적 초기화), cusp 위치 정체 종료(자세 범위 밖) — 관절각 오도메트리 전환 뒤.

## 3. 작업

- 시험 먼저:
  - 추종기: 끝점 전 cusp 다리에서 측정 속도가 진행 반대로 문턱을 넘으면 `braking` + `braking_against_motion=True`; 끝점·도착·보류의 `braking` 은 False; 정상 추종은 False.
  - 래치: 래치 뒤 원래 결과가 움직임 반대 제동 `braking` 으로 몇 tick 바뀌어도 래치가 유지되고, 5 s 뒤 판단(`observe_rule`/종료/해제)에 닿는다 — `brake`·`judge`·`observe_rule`·`handed` 각 단계에서. 끝점·보류 `braking`, `failed`, `arrived`, 키 변경, 제외(D7·held realign·legacy 프로파일·`retry_stand`) 는 같은 반대 제동 tick 에서도 지금처럼 닫는다.
  - 정지 인정 경계: 반대 제동과 함께 `stopped=False` 가 계속되면 0 명령을 유지하다 `brake` 단계 5 s 뒤 `cusp_position_stall_unconfirmed`, 다시 서면 첫 `stopped_s` 를 보존해 판단한다. 해제(`release_cusp`)는 정지 인정 뒤에만, 성공한 tick 에 다음 다리 명령을 다시 받는 순서 그대로.
  - 재현(고정 시간열): 정해진 tick 열의 진행 반대 오도메트리 평균 초과(이 실행의 초과 구간 길이·간격을 닮은 짧은 묶음 반복)를 `StopDetector` → 추종기(`tracker_speed`) → 모니터에 그대로 연결한다. 수정 전에는 래치가 매 묶음에 닫혀 5 s 판단에 못 닿고, 수정 뒤에는 닿는다. 관절각 기반 속도(0 / ±0.0115 / ±0.023 m/s 이산 값)는 고정 열로 넣되, 12-tick 평균이 문턱을 넘지 않는 열(대조: 수정 전에도 안 닫힘)과 넘는 열(−0.023 이 7 tick 연속이면 평균 −0.0134 — 이산 모델에서도 계기가 생길 수 있음)을 둘 다 둔다.
  - 기존 `test_one_forced_replan_per_key_across_a_new_latch` 는 `replace(..., status="braking")` 이 새 속성 기본 False 라 그대로 종료 분기를 검증한다 — 바꾸지 않는다.
- 구현: `path_tracking.py`(읽기 전용 속성 `braking_against_motion` 과 그 설정), `cusp_stall.py`(종료 조건), 설계 문서 문장.
- 관측 정체 규칙의 120 tick 카운터(`core.py` 2087행: `status == "tracking"`·`stop_now`·`not holds_observe()`)는 바꾸지 않는다. 반대 제동 tick 에는 `stop_now` 도 False 라(같은 0.012 문턱) 상태만 바꿔도 도달 시각이 같다(Codex 2차 — 기록 입력에서 반대 제동 50 tick 중 `stop_now` True 0). 시험에서 잡음 묶음 뒤 연속 정지 구간이 충분하면 120 tick 에 닿고, 정지가 계속 끊기면 카운터가 초기화되는 것을 함께 본다 — 이 변경이 모든 잡음열에서 관측 재계획을 보장하지는 않는다.
- 검증: ws1 pytest 전체, M-a1 리플레이 게이트 29 건(스키마는 그대로 — 갈리는 기록이 있으면 결함을 밟은 의도한 동작 차이인지 가른다), Isaac random_1 s0 여러 seed(재현이 비결정적이라 CPU 재현 시험을 주 증거로 쓴다).

## 4. 위험

- 움직임 반대 제동은 실제로 차가 반대로 움직일 때도 난다. `brake`·`judge` 단계에서는 명령이 0 이고 정지 인정이 안 되면 제동 단계에 머물므로(5 s 뒤 `cusp_position_stall_unconfirmed` 종료) 실제 움직임을 덮지 않는다. `observe_rule`·`handed` 에서는 각 인계 대상의 규칙(관측 정체 규칙의 정지 120 tick, 장애물 처리)을 따른다.
- 리플레이: 속성으로 두어 스키마는 그대로지만, 결함을 밟는 옛 기록이 있으면 래치 사건·이후 호출 순서가 달라져 그 기록의 재생이 갈린다 — 29 건 게이트에서 스키마 차이와 의도한 동작 차이를 구분해 적는다.

## 5. 자체 검토 — 직접 재계산

- 래치·종료 집계와 시각: `result.json` `cusp_stalls`(19·18·17·1, 32.900 s 첫 종료, 46.783/46.817 s).
- 창 평균 재현: `stop_probe.py` 출력(구간 30–53 s 2,760 tick, 범위 −0.0159…0.0187, 2.4 %, 원시 σ 0.0179, 문턱 첫 초과 32.900 s).
- 코드 위치: 추종기 반대 제동 조건, `tracker_speed`, 래치 종료 조건을 소스에서 직접 읽었다.

## 6. 검토 기록

### 2판 → 3판

- **② Codex 재검토(2차): 새 P1/P2 없음(수렴), P3 2 — 반영.** 작업 절의 1판 필드 문장 정리, K2 문장을 모든 래치 단계로 통일. Codex 는 속성 방식으로 기록 입력 비교를 다시 돌려 같은 결과(래치 1, 반대 제동 종료 0, `observe_rule` 36.075 s, 120 tick 37.067 s)를 얻었고, 출력 상태를 바꾸지 않는 결정에 동의했다(반대 제동 tick 에는 `stop_now` 도 False).

### 1판 → 2판

- **② Codex 적대적 검토(1차, 새 스레드): P1 없음, P2 1, P3 2 — 모두 받아들였다.**
  - P2: `TrackingCommand` 필드는 기록 형식을 바꾼다 → 추종기 읽기 전용 속성.
  - P3: 초과율(반대 방향 1.81 %)·종료 시각·"18 회 모두 판단 전" 정정; 재현은 비율이 아니라 고정 시간열로, 관절각 이산 값도 넘는 열을 따로.
  - Codex 확인(반박 없음): 원인 재구성(제어 자세 1.8×10⁻¹⁵ 일치, 종료 18 회 모두 반대 제동), 기록 입력에 제안 조건만 적용하면 래치 19 → 1, 반대 제동 종료 18 → 0, `observe_rule` 46.783 → 36.075 s, 관측 재계획 120 tick 조건 미도달 → 37.067 s 도달(기록 입력의 CPU 비교 — 그 뒤 물리 궤적은 증명하지 않음). K1–K3 의 다른 파손 없음, "명령 0 이면 반대 제동 생략" 대안은 권하지 않음.
- **③ 독립 검토(agy, Gemini 3.8 Flash Medium — Argon 은 일할 한도 보류).** ②의 결론을 보이지 않고 1판만 주었다. 8 개 중:
  - 받아들임: 래치 단계 전체에 같은 예외(②와 같은 결론), 정지 재인정 경계 시험, 래치가 `observe_rule` 로 넘긴 뒤 관측 정체 규칙도 `status == "tracking"`·`stop_now` 를 매 tick 요구해 같은 반대 제동이 그 120 tick 카운터를 0 으로 만든다는 지적 — 그러나 ②의 기록 입력 비교에서 수정 뒤 37.067 s 에 120 tick 조건에 닿았으므로 이번에는 래치 출력 상태를 바꾸지 않고, 재현 시험에서 120 tick 도달 여부를 함께 본다.
  - 받아들이지 않음: 끝점 근처 목표 0 에서 반대 제동이 안 난다(그때는 `braking` 도 없어 래치가 닫히지 않는다), 정지 중 잡음 속도가 소유권 호를 늘린다(정지 중 |속도| ≤ 0.019 m/s 로 호가 짧다), 추적 시간 한도(래치 대기는 5 s, 이 실행의 정지는 23 s 동안이었다), 래치 중 추종기 slew 누적(래치 진입·인계 반환·해제 경로가 모두 `restart_speed_slew(0)` 또는 해제 직후 새 다리로 시작 — 설계 7판 그대로).
