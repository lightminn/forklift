# live 세션 VRAM 줄이기 — learned 작업자 시범 계획 (2026-10-27)

ws1 에서 live 세션(Isaac + learned 작업자)은 정점이 3,890–4,047 MiB 다. GPU 한 장에서 쓸 수 있는 VRAM 은 15,839 MiB(16,303 − 드라이버 예약 464)다. 그래서 커진 뒤에는 GPU 당 세 세션만 들어가고, live 는 3 슬롯 shard 4 묶음으로 낸다(총괄 결정, `docs/plans/2026-10-26-ws1-isaac-array.md` 5.4). 넷째가 들어가려면 세션이 약 3,910 MiB 이하여야 하므로, 최악의 세션에서 약 140 MiB 를 줄여야 한다.

이 계획은 **시뮬레이션 자원 문제만** 다룬다. 실차(Jetson Orin) 추론 구성(공급자·정밀도·TensorRT 여부)은 별개이고, 여기서 정하지 않는다.

## 1. 측정한 것

**learned 작업자 VRAM.** 잡 11646 에서 쟀다. 모델 `yolo11s-seg_p15/best.onnx`, 입력 1×3×480×640, onnxruntime-gpu 1.31.0 이다.
- 옵션마다 새 프로세스를 띄웠다. 같은 무작위 입력을 50 번 돌렸다.
- 같은 GPU 에 다른 잡이 3,944 MiB 를 쓰고 있었다. VRAM 은 이 프로세스의 것만 셌다(`nvidia-smi --query-compute-apps`).
- CUDA 쪽은 스레드 수를 지정하지 않았다. 실제 작업자는 4 스레드로 고정한다. 그래서 지연은 운영 조건과 다르고, 아래 표의 지연은 참고값이다.

| 옵션 | 최소 세션(Identity) | 세션 생성 | 워밍업 뒤 | 지연 p50 / p95 / 최대 |
|---|---|---|---|---|
| 기본 | 258 MiB | 304 | **514** | 13 / 22 / 27 ms |
| `arena_extend_strategy=kSameAsRequested` | — | 284 | 480 | 13 / 32 / 33 ms |
| + `cudnn_conv_algo_search=HEURISTIC` | — | 286 | 482 | 22 / 45 / 50 ms |
| + `cudnn_conv_use_max_workspace=0` | — | 284 | 480 | 22 / 48 / 54 ms |
| + `gpu_mem_limit=256 MiB`(EP arena 한도, 프로세스 전체가 아님) | — | 286 | 482 | 16 / 33 / 46 ms |
| `CUDA_MODULE_LOADING=EAGER` | — | 828 | 1,336 | 15 / 41 / 46 ms |
| CPU 4 스레드 | 0 | 0 | 0 | 86 / 87 / 87 ms |

- Identity 모델 하나만 올린 세션도 258 MiB 다. 514 MiB 의 절반은 CUDA 컨텍스트와 ORT 기본 몫이라 공급자 옵션으로는 줄지 않는다. 시험한 옵션 중 가장 많이 줄인 것이 34 MiB 였다. 넷째에 필요한 최대 140 MiB 에 못 미친다. 이것은 시험한 옵션의 결과이고, 모든 CUDA 구성의 한계라는 뜻은 아니다.
- lazy 모듈 로딩은 이미 기본으로 켜져 있다.
- CPU 로 돌리면 작업자가 GPU 를 쓰지 않아 514 MiB 가 통째로 빠진다. 세션은 3,376–3,533 MiB(같은 실행이 아닌 따로 잰 514 를 뺀 추정)가 되고, 4 × (3,533 + 50) = 14,332 < 15,839 MiB 다.

**미션 안 지연(지금 CUDA, S3 2 차).** 2026-10-27 05:10 에 `s3conf2_3a37e216/s3b_*/live/epoch_*/run/missions/*/records.json` 136 개에서 `model_ms` 를 읽었다.
- 136 미션에서 20,318 호출이다. 미션당 약 150 호출이다.
- 미션별 p50 은 32.0–82.3 ms, p95 는 83.8–165.0 ms 다.
- 실행별 최대는 199.2–240.7 ms 다. 여덟 실행 중 일곱이 설계 §6 의 200 ms 를 넘었다.
- `model_ms` 는 작업자 왕복(파이프·직렬화 포함)을 **적용된 결과만** 요약한 값(n·p50·p95·max·first)이다. 폐기된 호출(세대·구간이 바뀐 뒤 도착한 결과)이 빠지고, 200 ms 초과율은 이 요약으로 복원할 수 없다.

10-19 의 CPU 4 스레드 미션 안 측정은 p50 115–129, p95 138–171, 최대 232 ms 였다(Isaac 과 같은 잡, 6 CPU). 그때 GPU 로 옮긴 이유가 최대 232 ms > 200 ms 였다(`docs/validation/2026-10-19-recognition-stage3-learned-proposals.md`).

설계 §6 계약은 갱신 5 Hz 이상, 지연 200 ms 이하, 후보 만료 0.5 s 다. 작업자 요청 타임아웃 10 s(`--recognition-timeout-s`)와 미션 제한 2,400 s 는 다른 값이다. 그래서 이 두 값의 여유는 200 ms 기준을 완화할 근거가 아니다.

## 2. 안

- **A1 CUDA 옵션(kSameAsRequested):** −34 MiB 다. 최악의 세션(4,047 → 4,013)이 문턱 3,910 을 여전히 넘는다. 이번 시범에서 뺀다.
- **A2 CPU 공급자:** −514 MiB 다. 넷째가 들어간다. 대가는 지연과 CPU 경합이다. 이번 시범의 대상이다.
- **A3 묶음 안 작업자 공유(나중 후보, agy 제안):** 한 묶음의 세션들이 작업자 하나를 함께 쓴다. 4 슬롯이면 세션당 약 385 MiB 가 줄고 GPU 지연은 유지된다. 대신 작업자 서버와 세션 간 요청 경로를 새로 짜야 한다. A2 가 지연 기준에서 떨어질 때 다음 후보로 둔다.
- **A4 Isaac 쪽(나중 후보):** PhysX GPU 힙 축소처럼 화면을 바꾸지 않는 설정이다. RTX 반사·GI 같은 렌더 품질은 learned 입력 영상을 바꾸므로 대상이 아니다. Isaac 프로세스 안에 작업자를 넣는 안은 Isaac 이 번들한 CUDA 와 충돌할 위험이 커서 대상이 아니다.

## 3. 시범(A2)

### 3.1 먼저 고칠 계측

지금 기록으로는 지연 기준을 계산할 수 없다. 그래서 시범 전에 작업자 호출마다 한 줄을 남기는 기록을 넣는다.
- 남길 항목: 요청 시각, 왕복 ms, 성공·오류, 적용·폐기 여부, 사유.
- 이 기록은 `sim/isaac/far_recognition_runtime.py` 의 learned 경로를 바꾼다. 그 경로를 맡은 콘솔 세션과 합의하고 따로 PR 로 낸다. 결정 모드의 재생 게이트도 통과해야 한다.
- CUDA 기준 팔도 이 계측으로 다시 잰다. 기존 S3 요약은 비교에 쓰지 않는다.
- 계측은 PR #163 으로 들어갔다. 미션 records 의 `live.jobs` 에 `model_ms`(왕복)·`infer_wall_s`(작업자 안 시간)·`model_source`·`request_mono` 가 남는다. 미션이 끝난 뒤 완료된 호출은 `live.late_calls` 나 실행 결과의 `far_late_calls` 에 남는다.
- 집계 규칙(콘솔 리뷰):
  - 짝 없는 in_flight(`late_calls`·`far_late_calls` 에도 없는 것)는 결과가 오지 않은 호출이다. 세션 close 의 join 1 s 안에 끝나지 않은 경우다. 이런 호출은 "최소 (끝 시각 − `request_mono`) 걸린 검열값"으로 200 ms 초과 비율의 분모와 분자에 넣고, 그 수를 따로 보고한다. 빼면 가장 느린 호출이 빠진다.
  - 세션 첫 호출의 `model_ms` 에는 모델 적재 대기(첫 마감 120 s)가 들어간다. 그래서 두 팔 비교에서 첫 호출은 빼고 따로 보인다(`timing()` 의 first·max_after_first 와 같은 처리). `infer_wall_s` 에는 적재가 들어가지 않는다.

### 3.2 구성

- **시점:** 진행 중인 비교 배치(S3 2 차 11590·11596·11639, 다른 세션의 대기 배치)가 끝난 뒤에 낸다. 제출 직전에 `squeue` 로 확인한다.
- **두 팔은 노드로 늘릴 수 있는 구성끼리 비교한다.** 노드는 CPU 20·shard 8 이다. 한 GPU 의 결과를 노드 두 장으로 늘렸을 때 들어가는 구성이어야 한다.

  | 팔 | 묶음 하나 | 노드 전체 |
  |---|---|---|
  | CUDA 팔(기준) | 3 슬롯 shard 4, CPU 6·19G(지금 기본) | 2 묶음 = 6 세션, CPU 12 |
  | CPU 팔 | 4 슬롯 shard 4, CPU 10·24G | 2 묶음 = 8 세션, CPU 20 |

  - CPU 10 이면 runner `--bridge-cpus auto` 가 브리지 넷에게 한 코어(CPU 2)를 함께 주고(10 ≥ 2 × 4 + 2), 세션 넷이 CPU 8 을 나눈다.
  - CPU 팔은 실행 목록 env 에 `MORE="--recognition-providers CPUExecutionProvider"` 를 넣는다. `ct1_queue.sbatch` 는 `MORE` 를 FAR 뒤에 붙이고 argparse 는 뒤 값을 쓰므로 런처를 바꾸지 않는다.
  - runner 에는 `--kind live --slots 4 --session-vram-mib 3600` 을 준다. 4 × 3,600 = 14,400 이라 1,439 MiB 가 남는다. 정점 상한으로 입증된 값은 아니다.
- **목록:** live 짧은 실행(ct1 연속 이송 seed, 실행당 약 25–30 분) 8 개를 두 팔이 같은 seed 로 돈다. 순서는 CUDA 팔 → CPU 팔이고, 한 팔이 끝난 뒤 다음 팔을 낸다(동시에 내면 서로의 경합이 섞인다).
- 이 비교는 운영 구성끼리의 비교다. 공급자·동시 세션 수·CPU·브리지 배치가 함께 바뀌므로 공급자 효과만 떼어 보는 시험이 아니다.

### 3.3 잴 것

- 작업자 호출 기록(3.1): 호출 단위 왕복 분포, 200 ms 초과 비율(분모는 성공한 모든 호출, 폐기 포함), 오류·폐기 건수
- 실제 활성 공급자(`active_providers`)
- 배속: 실행별 sim/wall 창 중앙. 기동 540 s 는 뺀다. 동시 세션 수별로 나눠 본다. tick 공백 p99 도 본다.
- SLAM 브리지 처리 시간 p50·p99, `slam_link_failed`(원인과 무관하게 모두 셈)
- GPU: runner 의 `vram.jsonl`(1 s 간격, 잡 VRAM·free)로 세션 정점과 free 최소를 본다. 기동·워밍업 구간도 포함한다. 5 분 감시(`array_watch3.sh`)는 프로세스 소유자 확인에만 쓴다.
- 잡 cgroup: CPU 사용률, memory.peak, memory.events, memory.pressure
- 노드 처리량: 실행당 벽시계와 노드 전체 동시 세션 수로 시간당 완료 실행 수를 추정한다(CUDA 6 세션 대 CPU 8 세션).
  - 이것은 GPU 한 장의 결과를 노드 두 장으로 늘린 외삽이다. 8 세션 동시 실측이 아니다. 채택 뒤 첫 실제 배치에서 노드 전체 동시 실행으로 다시 확인한다.

### 3.4 판정(결과 전에 고정)

**유효 조건.** 하나라도 어기면 결과를 판정에 쓰지 않고 원인부터 본다.
- 두 팔 모두 8/8 정상 완료
- CPU 팔의 활성 공급자가 CPU
- 작업자 오류 0 건, 기하 대체(geometric fallback) 0 건(작업자가 죽어도 기하 경로로 미션이 끝나 다른 기준을 통과할 수 있기 때문이다)

**통과 기준.**
1. CPU 팔에서 넷째 세션이 매번 시작하고, GPU free 최소(1 s 표본)가 300 MiB 이상이다.
2. 노드 처리량 추정이 CUDA 팔 이상이다.
3. `slam_link_failed` 가 CUDA 팔보다 많지 않다.
4. 지연: 200 ms 초과 비율을 두 팔 나란히 보고한다. CUDA 팔도 넘으므로 0 을 요구하지 않는다. CPU 팔이 더 나쁘면 숫자를 붙여 §6 기준(최대인가 p95 인가)을 어떻게 볼지 총괄 결정으로 올린다. 이 계획 안에서는 기준을 바꾸지 않는다.

배속 차이는 실행별 대응 비교(같은 seed)로 보고, 8 쌍이 분산을 말하기에 충분한지도 같이 적는다. 창이나 호출 수를 독립 표본으로 세지 않는다.

### 3.5 채택 시 바꿀 것

진행 중인 비교 배치 중간에는 바꾸지 않고, 기본값 변경으로 문서화한다.
- `ct1_queue.sbatch` 의 FAR 공급자, 저장된 `MORE`·`EXTRA_ARGS` 에 남은 CUDA 지정
- `KINDS["live"]` 의 VRAM·슬롯·코어
- `ARRAY["live"]` 의 크기

CUDA 지정이 남은 채 VRAM 예산만 낮추면 A1 에서 뺀 구성이 다시 생긴다. 그래서 위 세 곳을 함께 바꾼다.
