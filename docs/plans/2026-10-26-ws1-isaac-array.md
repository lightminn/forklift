# ws1 Isaac 실행 하나 = 잡 하나 (job array) 계획 (2026-10-26)

사용자 지적(총괄 경유, 2026-10-26): "자원이 많이 남는데 왜 못 들어가냐". 묶음 잡은 마지막 실행이 끝날 때까지 shard·CPU·메모리를 다 쥐고, 실행 중인 잡의 예약은 줄일 수 없다. 그래서 제출 구조를 바꾼다. 관리자 측 공유 설정(ws1 gres.conf 등)은 건드리지 않는다.

## 2. 제안: 실행 하나 = array task 하나

`sbatch $(python3 tools/isaac_bundle.py sizes KIND --array --runs N --run-min M) deploy/slurm/isaac_array.sbatch RUNS OUT KIND` 로 낸다(`BUNDLE_ARGS="--run-est-min M"`). sizes 가 `--array=0-(N-1)%K` 와 task 하나의 크기·한도를 찍는다.
- 각 task 는 RUNS 의 `SLURM_ARRAY_TASK_ID` 번째 줄 하나를 기존 묶음 runner(`--slots 1`)로 돌린다.
- 끝나면 그 task 의 shard·CPU·메모리가 바로 풀린다. 꼬리가 구조적으로 없다.
- 전부 작은 단위(live shard 1)라 같은 크기끼리는 조각나지 않는다.
- `%K` 는 그 배치가 동시에 쥘 수 있는 task 수다. 기본은 live 7, riib 4 이다. live 는 메모리 예산(아래)과 다른 사용자를 위한 shard 1 개 여유로 정했다.
- **실행 길이 M 은 배치마다 준다(필수).** 같은 live 라도 실행 길이가 시간 단위로 다르다(S3 21–209 분). M 은 그 배치에서 정상인 가장 긴 실행이다. 한도는 (M + 재시도 여유 10 분 + 5 분) × 1.15 를 5 분 단위로 올린 값이다. GPU 할당 실패는 실행의 처음 몇 분에 나므로, 재시도 여유 10 분 안에서 runner 의 재시도 1 회가 같은 task 안에 들어간다.

| 종류 | task 하나 | 근거 |
|---|---|---|
| live | shard 1·CPU 2·7G | VRAM 3,886–3,920 MiB < shard 4,076 MiB. 오래 도는 S3 세션의 anon 이 5.998 GiB 까지 갔다(learned worker 0.82·probe 0.49 GiB 포함, Codex 실측). 단독 live 잡 MaxRSS(캐시 포함)는 5.98–6.51 GiB 였다. 세션당 평균 약 1.05 코어로, CPU 2 는 물리 코어 하나다 |
| riib | shard 2·CPU 2·7.5G | 세션 4.47 GB 라 shard 1 을 넘는다. 그래서 GPU 당 2 세션이다(묶음은 3). anon 5.93, 단독 MaxRSS ≤ 7.41 GB(8G 한도) |
| bd | shard 1·CPU 2·6.5G | cgroup peak ≤ 5.82 GiB |

메모리 예산(live 7 task): 예약 7 × 7 = 49 GiB 로 Slurm 몫 56.6 GiB 안이다. 여기에 브리지(cgroup 밖) 최대 7 × 0.74 = 5.2 GiB 를 더하면 54.2 GiB 다. 다른 잡에 남는 Slurm 예약 7.6 GiB 까지 다 쓰면 61.8 GiB 로 물리 61.4 GiB 를 조금 넘는다. 그래서 runner 의 노드 RAM 장부(시작마다 MemAvailable 확인, `--slots 1` 에서도 기본으로 켜짐)를 유지한다.

runner 를 그대로 쓰므로 다음은 남는다.
- SESSION_ID·포트·브리지 이름과 정리
- 기반 실패(GPU 할당 실패) 재시도 1 회
- 멈춤 감시·진단(live 10 분), 남은 시간 판정
- 결과 기록(`OUT/task_<i>/results.jsonl`·`summary.json`)

## 3. 묶음이 주던 것 중 잃는 것

| 묶음의 이점 | array 에서 | 판단 |
|---|---|---|
| 꼬리 없이 자원 반환 | **얻는다**(task 마다 끝나면 풀림) | 위 표의 꼬리 2–42 % 가 사라진다 |
| 시작 시차(60 s)·VRAM 관문 | 잃는다. task 들이 같은 GPU 에 동시에 시작할 수 있다 | shard 로 GPU 당 live 4 세션이 상한이고, 4 × 3,920 = 15.7 GB < 16.3 GB 다. 기동 중 순간치는 정상 상태를 넘지 않았다(31–40 s 에 정상 상태, 넘는 순간치 없음) |
| 배속 물러남·되돌림 | 잃는다. task 하나에는 낮출 상한이 없다 | 지금까지의 물러남은 대부분 오작동이었다(#134·#139·#150). 실제 하락은 SLAM 그래프 크기(lfv4)였고, 세션 수와 무관했다. 노드 과부하는 shard·CPU 예약이 막는다 |
| 공유 파일 캐시를 한 번만 셈(메모리) | 잃는다. task 마다 7G 다(묶음은 세션당 6.0) | 같은 메모리로 동시에 도는 live 세션이 묶음의 8 에서 7 로 준다. 이것이 array 의 대가다. **첫 array 배치에서 OOM 0 건(memory.events)을 확인**한다 |
| 노드 RAM 장부(브리지 메모리, cgroup 밖) | **유지한다**(runner 가 `--slots 1` 에서도 UID 공용 장부를 쓴다) | 위 예산처럼 예약만으로는 물리 메모리를 넘을 수 있어 장부가 필요하다 |
| claim-dir 공유·time_left | 필요 없다. task 하나에 실행 하나다 | 결과는 `isaac_bundle.py collect OUT --expect N` 이 task 마다 마지막 상태와 그 task summary 의 exit_code 를 내고, 기록이 없는 task(미시작·취소)를 따로 적는다. 실행이 rc 0 으로 끝나도 브리지 정리가 실패하면 summary 가 1 이라 실패로 센다. 판정 도구는 glob 합산 대신 이것을 쓴다. task 번호는 빈 줄을 빼고 센 목록 줄 번호다(`load_runs` 와 같은 셈) |
| 기반 실패 재시도 | task 안에서 유지한다(한도에 재시도 여유 10 분) | 처음 10 분 뒤의 실패는 재시도할 시간이 없어 `time_left_retry` 로 남는다. 그 task 는 `bundle/` 을 옮긴 뒤 다시 낸다 |
| riib 밀도(GPU 당 3) | 잃는다(GPU 당 2) | riib 는 실행 길이가 고르면(lcg 97 %) 3 슬롯 묶음을 유지한다. 길이가 섞이면 array 로 낸다 |

## 4. 권고(2 슬롯 시범·조각남 결론과 합침)

1. **live 의 기본은 array 다.** 2 슬롯 묶음은 꼬리를 줄였지만(osbb 87 %) 조각남을 새로 만들었다. 서로 떨어져 시작하는 잡 사이에서는 실행을 못 받는 일도 생겼다. array 는 같은 크기(live shard 1)끼리는 둘 다 없앤다. 대가는 동시 live 세션 8 → 7 이다.
2. **riib 는 실행 길이가 고른 배치만 3 슬롯 묶음으로 낸다.** 실패로 일찍 끝날 수 있는 실행이나 장면 길이가 다른 실행을 섞는 배치는 array(shard 2)로 낸다.
3. **크기가 다른 단위를 같은 시간대에 섞지 않는다.** shard 4 묶음은 GPU 한 장이 통째로 빌 때까지 기다린다. riib array(shard 2)도 live task 가 두 GPU 에 3 개씩 남으면(빈 shard 1+1) 들어가지 못한다. FIFO·backfill 예약이 늦어지게 할 뿐 굶기지는 않지만, 큰 단위 배치는 live array 가 끝난 뒤에 이어서 내는 편이 낫다.
5. **공정성.** 우선순위 가중치가 0 이라 순서는 제출 순서다. array task 는 array 를 낸 시각을 따르므로, 120 실행 array 는 뒤에 낸 다른 사용자의 잡보다 계속 먼저 선다. `%K`(live 7)가 shard 하나를 남기지만 그것만으로 기회를 보장하지는 않는다. 아주 큰 배치는 나눠 내거나, 다른 사용자의 잡이 기다리면 `scontrol update ArrayTaskThrottle` 로 K 를 줄인다.
4. 묶음 runner·sizes·check 는 그대로 둔다. riib 묶음과 기존 배치의 재현에 쓴다.

## 5. 시범과 다시 볼 조건

- 다음 live 배치(실행 8 개 이상)를 array 로 낸다. 확인할 것:
  - OOM 0 건(task cgroup 의 memory.events)
  - 실행별 배속(Δsim/Δwall 창 중앙)이 같은 종류 단독·묶음 기록(0.355–0.365)에서 2 % 넘게 떨어지지 않음
  - 기반 실패 0 건. 같은 GPU 에 4 세션이 동시에 기동하는 경우와 learned worker 워밍업 GPU OOM 전례(isaac_live.sbatch 머리말)를 포함한다
  - 동시 세션 7, SLAM 응답 상위 지연, 상태 기록 공백, learned fallback
  - `collect` 가 N 개를 모두 셈
- 하나라도 어긋나면 task 메모리를 7G 로 올리거나 CPU 4 로 바꾼다. 배속 하락이 세션 수와 함께 움직이면 동시 task 상한(`%K`)을 줄인다.
