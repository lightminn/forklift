# ws1 Isaac 실행 하나 = 잡 하나 (job array) 계획 (2026-10-26)

사용자 지적(총괄 경유, 2026-10-26): "자원이 많이 남는데 왜 못 들어가냐". 묶음 잡은 마지막 실행이 끝날 때까지 shard·CPU·메모리를 다 쥐고, 실행 중인 잡의 예약은 줄일 수 없다. 그래서 제출 구조를 바꾼다. 관리자 측 공유 설정(ws1 gres.conf 등)은 건드리지 않는다.

## 2. 제안: 실행 하나 = array task 하나

`sbatch $(python3 tools/isaac_bundle.py sizes KIND --array --runs N --run-min M) deploy/slurm/isaac_array.sbatch RUNS OUT KIND` 로 낸다(`BUNDLE_ARGS="--run-est-min M"`). sizes 가 `--array=0-(N-1)%K` 와 task 하나의 크기·한도를 찍는다.
- 각 task 는 RUNS 의 `SLURM_ARRAY_TASK_ID` 번째 줄 하나를 기존 묶음 runner(`--slots 1`)로 돌린다.
- 끝나면 그 task 의 shard·CPU·메모리가 바로 풀린다. 꼬리가 구조적으로 없다.
- 전부 작은 단위(live shard 1)라 같은 크기끼리는 조각나지 않는다.
- `%K` 는 그 배치가 동시에 쥘 수 있는 task 수다. 기본은 live 5, riib 3, bd 3 이다. CPU 20 개를 task 크기로 나눈 값이다(5 절 시범 뒤 고침).
- **실행 길이 M 은 배치마다 준다(필수).** 같은 live 라도 실행 길이가 시간 단위로 다르다(S3 21–209 분). M 은 그 배치에서 정상인 가장 긴 실행이다. 한도는 (M + 재시도 여유 10 분 + 5 분) × 1.15 를 5 분 단위로 올린 값이다. GPU 할당 실패는 실행의 처음 몇 분에 나므로, 재시도 여유 10 분 안에서 runner 의 재시도 1 회가 같은 task 안에 들어간다.

| 종류 | task 하나 | 근거 |
|---|---|---|
task 하나는 묶음의 세션 몫이 아니라 단독 잡처럼 잡는다. task 는 옆 세션의 빈 CPU 를 빌릴 수 없고, 파일 캐시도 자기 cgroup 에 따로 청구된다(물리적으로는 공유될 수 있어도 각 task 의 상한에 잡힌다). 처음 정한 CPU 2·7G 는 5 절 시범에서 실패했다.

| 종류 | task 하나 | 근거 |
|---|---|---|
| live | shard 1·CPU 4·8G | VRAM 3,886–3,920 MiB < shard 4,076 MiB. CPU 4 는 물리 코어 둘이다. runner 의 `--bridge-cpus auto` 가 한 코어를 SLAM 브리지에, 한 코어를 세션(Isaac·learned 작업자·probe)에 준다. 단독 isaac_live 잡은 세션이 네 CPU 를 다 쓰고 브리지가 그중 하나를 같이 쓰므로, 같은 구성이 아니다. 8G 는 단독 live 잡과 같다. 실패한 7G task 의 MaxRSS 5.60·7.00·6.99 GiB 중 둘은 상한에 눌린 값이라 필요량의 근거가 되지 못한다 |
| riib | shard 2·CPU 6·8G | 세션 4.47 GB 라 shard 1 을 넘는다. 단독 riib 세션이 CPU 4 개 중 3.1 개를 썼으므로, 세션에 두 코어, 브리지에 한 코어를 준다. 8G 는 단독 riib 잡과 같다(MaxRSS ≤ 7.41 GB) |
| bd | shard 1·CPU 6·7G | 단독 bd 잡과 같다 |

메모리 예산(live 5 task): 5 × 8 = 40 GiB, 브리지(cgroup 밖) 최대 5 × 0.74 = 3.7 GiB. 다른 잡 몫 16.6 GiB 를 더해도 물리 61.4 GiB 안이다. runner 의 노드 RAM 장부(`--slots 1` 에서도 기본으로 켜짐)는 그대로 둔다.

runner 를 그대로 쓰므로 다음은 남는다.
- SESSION_ID·포트·브리지 이름과 정리
- 기반 실패(GPU 할당 실패) 재시도 1 회
- 멈춤 감시·진단(live 10 분), 남은 시간 판정
- 결과 기록(`OUT/task_<i>/results.jsonl`·`summary.json`)

## 3. 묶음이 주던 것 중 잃는 것

| 묶음의 이점 | array 에서 | 판단 |
|---|---|---|
| 꼬리 없이 자원 반환 | **얻는다**(task 마다 끝나면 풀림) | 위 표의 꼬리 2–42 % 가 사라진다 |
| 시작 시차(60 s)·VRAM 관문 | 잃는다. task 들이 같은 GPU 에 동시에 시작할 수 있다 | shard 로 GPU 당 live 4 세션이 상한이고, 4 × 3,920 = 15.7 GB < 16.3 GB 다. 기동 중 순간치는 정상 상태를 넘지 않았다(31–40 s 에 정상 상태, 넘는 순간치 없음) |
| 배속 물러남·되돌림 | 잃는다. task 하나에는 낮출 상한이 없다 | 지금까지의 물러남은 대부분 오작동이었다(#134·#139·#150). 실제 하락은 SLAM 그래프 크기(lfv4)였고, 세션 수와 무관했다. 노드 과부하는 shard·CPU 예약이 막는다 |
| 공유 파일 캐시·CPU 를 함께 씀 | 잃는다. task 마다 CPU 4·8G 다(묶음은 세션당 CPU 2·6.0 GiB) | 노드에서 동시에 도는 live 세션이 묶음의 8 에서 array 5 로 준다(CPU 가 묶는다). 이것이 array 의 대가다 |
| 노드 RAM 장부(브리지 메모리, cgroup 밖) | **유지한다**(runner 가 `--slots 1` 에서도 UID 공용 장부를 쓴다) | 위 예산처럼 예약만으로는 물리 메모리를 넘을 수 있어 장부가 필요하다 |
| claim-dir 공유·time_left | 필요 없다. task 하나에 실행 하나다 | 결과는 `isaac_bundle.py collect OUT --expect N` 이 task 마다 마지막 상태와 그 task summary 의 exit_code 를 내고, 기록이 없는 task(미시작·취소)를 따로 적는다. 실행이 rc 0 으로 끝나도 브리지 정리가 실패하면 summary 가 1 이라 실패로 센다. 판정 도구는 glob 합산 대신 이것을 쓴다. task 번호는 빈 줄을 빼고 센 목록 줄 번호다(`load_runs` 와 같은 셈) |
| 기반 실패 재시도 | task 안에서 유지한다(한도에 재시도 여유 10 분) | 처음 10 분 뒤의 실패는 재시도할 시간이 없어 `time_left_retry` 로 남는다. 그 task 는 `bundle/` 을 옮긴 뒤 다시 낸다 |
| riib 밀도(GPU 당 3) | 잃는다(GPU 당 2) | riib 는 실행 길이가 고르면(lcg 97 %) 3 슬롯 묶음을 유지한다. 길이가 섞이면 array 로 낸다 |

## 4. 권고(2 슬롯 시범·조각남 결론과 합침)

1. **live 의 기본은 array 다.** 2 슬롯 묶음은 꼬리를 줄였지만(osbb 87 %) 조각남을 새로 만들었다. 서로 떨어져 시작하는 잡 사이에서는 실행을 못 받는 일도 생겼다. array 는 같은 크기(live shard 1)끼리는 둘 다 없앤다. 대가는 동시 live 세션 8 → 5 다. 그래서 실행 길이가 고른 live 목록은 묶음이 더 빽빽하다. 길이가 섞이거나 실패로 일찍 끝날 수 있는 목록에 array 를 쓴다.
2. **riib 는 실행 길이가 고른 배치만 3 슬롯 묶음으로 낸다.** 실패로 일찍 끝날 수 있는 실행이나 장면 길이가 다른 실행을 섞는 배치는 array(shard 2)로 낸다.
3. **크기가 다른 단위를 같은 시간대에 섞지 않는다.** shard 4 묶음은 GPU 한 장이 통째로 빌 때까지 기다린다. riib array(shard 2)도 live task 가 두 GPU 에 3 개씩 남으면(빈 shard 1+1) 들어가지 못한다. FIFO·backfill 예약이 늦어지게 할 뿐 굶기지는 않지만, 큰 단위 배치는 live array 가 끝난 뒤에 이어서 내는 편이 낫다.
5. **공정성.** 우선순위 가중치가 0 이라 순서는 제출 순서다. array task 는 array 를 낸 시각을 따르므로, 120 실행 array 는 뒤에 낸 다른 사용자의 잡보다 계속 먼저 선다. live K 5 는 CPU 20 개를 모두 예약하므로 다른 사용자 몫을 남기지 않는다. 다른 사용자의 잡이 기다리면 K 를 4 이하로 줄인다. 아주 큰 배치는 나눠 내거나, 다른 사용자의 잡이 기다리면 `scontrol update ArrayTaskThrottle` 로 K 를 줄인다.
4. 묶음 runner·sizes·check 는 그대로 둔다. riib 묶음과 기존 배치의 재현에 쓴다.

## 5. 시범과 다시 볼 조건

- 다음 live 배치(실행 8 개 이상)를 array 로 낸다. 확인할 것:
  - OOM 0 건(task cgroup 의 memory.events)
  - 실행별 배속(Δsim/Δwall 창 중앙)이 같은 종류 단독·묶음 기록(0.355–0.365)에서 2 % 넘게 떨어지지 않음
  - 기반 실패 0 건. 같은 GPU 에 4 세션이 동시에 기동하는 경우와 learned worker 워밍업 GPU OOM 전례(isaac_live.sbatch 머리말)를 포함한다
  - 동시 세션 7, SLAM 응답 상위 지연, 상태 기록 공백, learned fallback
  - `collect` 가 N 개를 모두 셈
- 하나라도 어긋나면 task 크기를 올린다. 배속 하락이 세션 수와 함께 움직이면 동시 task 상한(`%K`)을 줄인다.

### 5.1 첫 시범: 11590(S3 2 차 확인, live 8 실행, CPU 2·7G)

- task 0–2 가 모두 `slam_link_failed`(브리지 1 s 무응답)로 끝났다. task 0 은 7 분째, task 1 은 111 분째, task 2 는 129 분째였다. 같은 장면을 4 슬롯 묶음(11506·11507, CPU 8)으로 돌린 1 차 S3 는 8/8 성공했다.
- 브리지 처리(processed scan wall_s) p50 은 array 0.174–0.178 s, 묶음 0.132–0.136 s 였다. R(매핑)은 p99 0.661·최대 1.13 s 로 묶음 R 의 0.451·0.647 보다 크다. L 두 실행은 실패한 스캔이 브리지 기록에 남지 않았다. 브리지는 응답을 보낸 뒤에 기록하므로, 처리 지연뿐 아니라 수신 지연·pose 미수신·처리 중 종료도 같은 누락을 만든다. R 의 처리 시간은 그래프가 커지며 스캔 구간별 중앙값 0.047 → 0.247 s 로 늘었고, 비교 묶음 R 은 스캔 18,808 에서 끝나 실패 스캔(22,076) 구간의 대조군이 없다.
- task 하나의 CPU 2 개는 한 물리 코어의 두 하이퍼스레드(예: 7·19)였다. 세션, learned 작업자, 거기 묶인 브리지 컨테이너가 이 코어를 같이 썼다.
- 메모리: task 1·2 의 cgroup 이 7G 상한에 590·707 번 닿았다(memory.max, OOM kill 0). task 0 은 0 번이었다. 그래서 메모리만으로는 task 0 의 실패를 설명할 수 없다.
- 세션당 CPU 2 개인 V5 2 슬롯 묶음(CPU 4)에서도 같은 실패가 두 번 났다(18:38, 21:55; 끝난 실행 약 86 개 중). 하나는 11590 task 0 과 2 분 안팎으로 가까웠다(같은 순간이라는 근거는 없다). 묶음에서도 세션당 한 코어면 드물게 생기고, 이웃 세션이 없는 array task 에서 훨씬 자주 생겼다.
- 판단: 세션·브리지가 한 코어를 같이 쓴 CPU 경합이 가장 유력하지만 확정은 아니다. 노드 전체의 기동 몰림·reclaim·I/O 압박은 그때 PSI·디스크 지연 기록이 없어 배제하지 못한다.
- 조치: 대기 중이던 task 3–7 을 CPU 4·8G 로 올렸다(runner 기본 `--bridge-cpus auto` 로 브리지가 따로 한 코어를 갖는다). 실패한 task 0–2 는 인프라 실패로 따로 적고 같은 크기로 다시 낸다. array 기본값을 위 표처럼 고쳤다. 새 task 들은 cgroup peak·anon/file·memory PSI·memory.max 증가분을 정상 종료까지 기록한다.
- 남은 질문: CPU 4 에서 브리지를 따로 두는 것(auto)과 네 CPU 를 함께 쓰는 것(`--bridge-cpus 0`) 중 무엇이 나은지는 자료가 없다. 같은 스냅숏·seed·8G 로 두 방식을 비교해야 정할 수 있다. R 은 스캔 22,076 이후까지 보고, K 5 부하에서 SLAM 실패와 배속을 함께 본다.

### 5.3 세션당 CPU 와 SLAM 링크 실패, 결과 전에 고정한 판정 규칙(2026-10-27)

ws1 에 남은 묶음 기록을 구성별로 세었다(`slam_link_failed` / 실행 시간).

| 구성 | 세션이 쓸 수 있는 CPU | 실패 / 실행 시간 |
|---|---|---|
| array CPU 2(11590 task 0–2) | 물리 코어 하나, 혼자 씀 | 3 / 4.1 h |
| 2 슬롯 묶음 CPU 4(V5·kob) | 물리 코어 둘을 두 세션이 함께 씀 | 6 / 62 h(10 h 에 약 1) |
| 4 슬롯 묶음 CPU 8(S3 1 차) | 물리 코어 넷을 네 세션이 함께 씀 | 0 / 약 15 h |
| riib 3 슬롯 CPU 6 | — | 0 / 1.3 h |

세션당 물리 코어 하나는 2 슬롯 묶음에서도 실패를 만든다. 함께 쓰는 코어가 많을수록 실패가 줄어든다.

**판정 규칙(결과를 보기 전에 고정).** 대상은 CPU 4·8G·브리지 전용 코어로 도는 11590 task 3–7 과 11596 task 0–2 이다(S3 8 실행, 약 25 실행 시간).
- `slam_link_failed` 0 건: "브리지에 코어를 따로 둔다"를 잠정 채택하고, 묶음 sizes 에도 브리지 코어를 더하는 안을 올린다.
- 1 건 이상: 같은 스냅숏·seed·8G 로 공유(`--bridge-cpus 0`)와 분리(auto)를 비교하는 계획으로 간다.
- 한계: 2 슬롯 묶음의 비율(10 h 에 약 1)이면 25 실행 시간에 2.5 건을 기대한다. 효과가 없어도 0 건이 나올 확률이 e^−2.5 ≈ 0.08 이므로, 0 건은 약한 근거다. 그래서 "잠정" 채택이고, 채택 뒤에도 실패율을 계속 센다. 장면(S3 L·R)과 실행 길이도 비교 묶음과 같지 않다.

**묶음에 브리지 코어를 더할 때의 CPU 비용.** 노드는 CPU 20, Slurm 메모리 56.6 GiB, shard 8 이다. runner 의 `--bridge-cpus auto` 는 CPU 가 2 × 슬롯 + 2 이상이면 한 코어(CPU 2)를 그 잡의 모든 브리지에 준다.

| 단위 | 지금 shard·CPU·메모리 | 노드에 동시에(병목) | 브리지 코어를 더하면 | 노드에 동시에(병목) |
|---|---|---|---|---|
| live 2 슬롯 | 2·4·13G | 4 잡 = 8 세션(shard) | 2·6·13G | 3 잡 = 6 세션(CPU) |
| live 4 슬롯 | 4·8·24G | 2 잡 = 8 세션(shard) | 4·10·24G | 2 잡 = 8 세션(shard·CPU 둘 다 꽉 참) |
| riib 3 슬롯 | 4·6·20G | 2 잡 = 6 세션(shard) | 4·8·20G | 2 잡 = 6 세션(shard) |
| live array task | 1·4·8G | 5 task = 5 세션(CPU) | 이미 포함 | 같음 |

- 브리지 코어는 2 슬롯 묶음에서만 세션을 줄인다(8 → 6). 4 슬롯과 riib 3 슬롯은 shard 가 먼저 묶으므로 CPU 를 더해도 세션 수가 그대로다. 다만 live 4 슬롯 두 잡이 CPU 20 을 다 쓴다.
- 그래서 브리지 코어를 채택하면, 길이가 고른 live 목록은 2 슬롯이 아니라 4 슬롯 묶음이 맞다(같은 8 세션, CPU 여유는 없음).
- 주의: 4 슬롯이면 브리지 넷이 한 코어를 나눈다. 이것이 충분한지는 따로 확인해야 한다(R 매핑 브리지의 처리 시간은 그래프가 커지며 늘었다).

**원인 쪽 대안.**
- 우선순위: 브리지 컨테이너의 `docker run --cpu-shares` 를 올리거나, Isaac 쪽을 `nice` 로 낮추는 방법이 있다. 둘 다 우리 런처 안에서 바꿀 수 있고 관리자 설정은 아니다. 다만 같은 물리 코어에 있으면 우선순위가 높아도 하이퍼스레드 경합은 남는다. 그래서 코어 분리보다 약한 수단으로 본다.
- 응답 한도: `SLAM_LIVE_REPLY_DEADLINE_S = 1.0`(실시간 계획 D9a, 10 Hz 스캔 20 개 대기열)은 SLAM 쪽 계약이다. 한도를 늘리면 실패가 줄지만, 늦은 pose 가 제어에 들어가는 것을 허용하게 된다. 바꿀지는 콘솔 세션과 함께 판단한다. 이 계획에서는 바꾸지 않는다.

### 5.2 조각남 12 시간 관측(10:16–22:16, 1 분 간격 623 샘플)

shard 가 빈 시간은 5,758 shard·분 중 약 660(11.5 %)이었다. 샘플 사이 공백이 최대 39 분 50 초였고 직전 상태를 다음 샘플까지 이어 셌으므로 추정값이다. 빈 이유는 다음과 같다.

| 이유 | 빈 shard·분 | 예 |
|---|---|---|
| 한 GPU 에 들어갈 shard 는 있는데 다른 자원(메모리·CPU)으로 기다림 | 353 | 13:46–18:38 V5 11474(shard 2·13G)가 GPU 1 의 빈 shard 2 앞에서 대기 |
| 조각남(합계로는 들어가는데 어느 GPU 에도 안 들어감) | 179 | 19:10–20:26 V5 shard 2 잡이 빈 shard [1, 1] 앞에서 대기. live array task(shard 1)·팀원 shard 1 잡과 shard 2 묶음이 섞인 때다 |
| 기다리는 잡이 남은 shard 합계보다 큼 | 125 | shard 4 묶음이 GPU 한 장이 빌 때까지 대기 |

처음 230 분만 보고 조각남이 0 건이라고 총괄에 보고했는데, 이것은 틀렸다. 12 시간 전체로는 조각남이 빈 시간의 약 27 % 였고, 모두 크기가 다른 단위가 섞인 때였다(4 절 규칙 3). 가장 큰 몫은 메모리·CPU 예약이었다.
