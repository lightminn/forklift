# 장애물 층 지연 예산: 알리지 않은 층 지연에 견디게 하기 (2026-11-11, 3판)

- 지시: 총괄(2026-11-11). 진단 `docs/validation/2026-11-11-latency-layer-diagnosis.md` 뒤의 수정 계획과 실차 허용 지연 권고. 값은 총괄이 정한다.
- 출발 사실(진단):
  - 허가는 FREE 칸의 스캔 시각부터 제어 틱까지의 나이를 사용 나이 L(지금 0.2 s)과 비교한다(`drive_permission.py` 870).
  - 한 스캔 걸러 갱신되는 칸은 제자리 갱신에서도 23 틱(0.1917 s)까지 쓰인다. 모형상 여유가 1 틱이다.
  - 그래서 알리지 않은 층 지연 25 ms 부터 매 주기 초과 틱이 생긴다. 기록에서는 감속이 스캔 주기에 묶였고, 이동 속도가 기준선의 30–60 % 로 떨어져 단계 시간 한도로 끝났다.
  - 지연을 알린 D12 는 line_2 3/3 허용, 감속 0 이었다.

## 1. 무엇을 바꾸나: 층 지연 예산 B

- 장애물 층 설정에 **지연 예산 `latency_budget_s` = B** 를 둔다.
- **정의(Codex P2-2):** 스캔마다 세 시각을 같은 시계(시뮬은 시뮬 시각, 실차는 단조 시계)로 적는다. t_scan(스캔 시각, FREE 칸의 시각과 같은 값), t_install, t_use(그 결과를 처음 읽은 제어 틱).
  - 그 스캔의 지연은 **D = t_use − t_scan** 이다(Codex 2 회차 P1-1). 시뮬의 스캔 시각은 물리 스텝 뒤 시각이고, 다음 제어 틱의 시각과 같다. 그래서 제자리 갱신은 D = 0 이다.
  - live 작업자의 정시 설치 k 는 D = (k − 1)/120 이다(#417 과 같은 값). 지연 내성 시험의 배치 주입 k 는 D = k/120 이다.
  - 실차는 그 루프의 단조 시계로 같은 식을 쓴다. 제자리에서도 계산·대기만큼 D > 0 이다.
  - B 는 D 의 상한이다. 계산·설치·스레드 대기·장벽 대기를 모두 포함한다.
- B 는 #417 의 닫힘 규칙을 그대로 쓴다. 다른 점은 '작업자 k 로부터 계산한 값' 대신 '설정한 상한'이라는 것뿐이다.

| 곳 | 지금(B 없음) | B 를 두면 |
|---|---|---|
| 정지 모델 지연 `permission.latency_s` | 0.15 s | 0.15 + B |
| 사용 나이 L(`grid.free_use_age_s`): 허가 나이 비교, 격자 FREE 축소, 텔레옵·후보 허가, cusp 판정, 그림자 기억 지평, 알려진 팔레트 투영 지평 | `free_max_age_s` = 0.2 s | 0.2 + B |
| 출구 접두 변환 칸의 시각 | 검증 시각 | 검증 시각 − B(만료 시각 유지, #417 과 같음) |
| 받아들이는 나이(스캔 선택, 계획 기억, 출구 검증 수용) | 0.2 s | 그대로. 이 판정은 그 스캔의 시각으로 계산 안에서 한다(`refresh_prepare` 의 `now_s` = 스캔 시각). 그래서 설치 지연이 바꾸지 않는다(agy ③-7) |
| 센서 침묵 한도 `sensor_timeout_s` | 0.25 s | 그대로. 층의 `last_scan_s`(스캔이 들어온 시각, `add_scans`)로 판정해 설치 지연과 무관하다. 정상 실행에서 오탐을 피하도록 설정 검사로 `sensor_timeout_s` ≥ 스캔 주기 + B 를 요구한다(B = 0.10 에서 0.20 ≤ 0.25, agy ③-2). 이 검사는 하한일 뿐, 전달 지연의 안전 회계는 아니다(아래 보장 범위) |

- **live 층 작업자와의 관계:** live 의 `--layer-worker` 는 지금 (k − 1)/120 을 더한다(`worker_config`). B 가 있으면 B 를 쓴다. 작업자의 정시 설치 지연이 B 를 넘는 설정, 즉 (k − 1)/120 > B 이면 시작 전에 거부한다.
- **B 를 넘는 실제 지연은 감시로 막는다(Codex 1 회차 P1, 2 회차 P1-2).** D > B 라고 증거 나이가 L 을 넘는 것은 아니다. 예를 들어 B = 0.10, D = 0.15 인 새 스캔의 증거 나이는 0.15 s 로 L = 0.30 안이다. 그러면 정지 모델이 덮지 못한 반응 지연으로 계속 움직일 수 있다. 그래서 층 지연 감시(`layer_overdue`)를 넣는다. 감시는 매 제어 틱 허가 계산 안에서 판단하고, 둘 중 하나면 속도 0 이다.
  - **(i) 기한 넘김:** 접수된 스캔마다 마감 t_scan + B 가 고정된다. 지금 쓰고 있는 층에 '마감이 지난 스캔 가운데 가장 새것'(t_scan ≤ now − B 인 가장 새 스캔 ID)이 들어 있지 않으면 정지한다.
    - 새 스캔이 와도 앞선 스캔의 마감은 밀리지 않는다.
    - 한 번에 하나만 대기하는 지금 구조에서 앞 작업이 다음 스캔에 밀려 장벽 설치되는 경우도 같은 규칙으로 본다. 설치된 층의 스캔 ID 로 판단한다.
  - **(ii) 늦게 쓰인 층:** 지금 쓰고 있는 층이 처음 쓰일 때 D > B + ε 였으면 정지한다. 그 뒤 D ≤ B 로 처음 쓰인 층이 들어올 때까지 이어진다. 허가 계산 직전에 늦게 설치된 결과(live 는 허가보다 먼저 설치한다)도 이 조건에 걸린다.
  - ε = 1e−6 s 는 실제 틱 간격(1/120 보다 조금 김)으로 경계가 뒤집히지 않게 하는 허용이다.
  - 그래서 차가 움직이는 틱의 층은 '처음 쓰일 때 D ≤ B'이고, '마감 지난 스캔을 다 반영한 층'이다. 정지 모델의 +B 는 이 조건 위에서 반응 지연을 덮는다.
  - **보장 범위(Codex 3 회차 P2): 접수 이후의 층 처리 지연만이다.** 감시는 접수된 스캔의 마감만 본다.
    - 스캔이 접수되기 전 전달 중에 밀리는 지연은 이 감시가 막지 않는다. 그때는 센서 침묵 한도와 증거 나이 검사가 대신 멈춘다. 그 정지 지연이 0.15 + B 안에 든다는 보장은 없다.
    - 시뮬은 스캔이 그 스텝 안에서 바로 접수되므로 전달 지연이 없다(이 PR 의 범위).
    - 실차에서 전달 지연까지 덮으려면 예상 도착 기한 감시와 스캔 미도착 시험을 실차 PR 의 별도 조건으로 둔다.
  - 시뮬 제자리 갱신은 D = 0 이고 매 스캔 바로 반영되므로 감시가 걸리지 않는다. 기본 경로의 동작은 같다(게이트·시험으로 확인).
- **전제: 제어 루프가 층을 기다리며 막히지 않는다(Codex 2 회차 P1-3).**
  - 지금 장벽 설치는 제어 스레드에서 작업 완료를 기다린다(`layer_worker.py` 180, 최대 `timeout_s`). 그동안 허가 계산이 돌지 않는다.
  - 시뮬은 시계가 함께 멈춰 D 에 드러나지 않는다. 실차는 이전 명령이 이어진다(실차 계획 2.2 의 같은 지적).
  - 그래서 실차 적용의 전제로 다음 둘을 둔다(이 PR 은 시뮬 범위이고, 실차 구동 PR 에서 맞춘다).
    - (가) 실차 런타임의 층 설치는 제어 틱을 막지 않는다. 결과가 준비되지 않으면 이전 층을 쓰고 감시가 정지를 낸다.
    - (나) MCU 의 명령 기한(실차 계획의 deadline·stop_grace)이 제어 루프가 막힌 경우를 독립적으로 멈춘다. 그 최악 지연(감시 표본화 주기 + 명령 적용·만료)은 정지 모델의 기본 지연 0.15 s 안에 있어야 한다. 실차 계획의 측정으로 확인한다.
- **기록 계약(Codex 2 회차 P2):**
  - 스캔마다 scan ID, t_scan, t_install, t_use, D.
  - 감시가 걸린 제어 틱마다 틱 시각, 필요한 스캔 ID, 설치된 스캔 ID, 그 층의 최초 사용 D, 사유((i)·(ii)), 허가 결과 속도.
  - 온라인 불변조건 검사: 감시가 걸린 틱의 허가 결과가 0 이 아니면 위반으로 센다(있어서는 안 된다).
  - 결과에는 감시 횟수·최대 초과·총 시간·위반 수가 남는다. 임무를 끝내는 규칙은 넣지 않는다(4 절 b).
- **안전 평가기의 정지 모델(Codex P2-6):** 러너의 참값 평가는 지금 층 작업자가 있을 때만 추가 지연을 뺀다(`run_transport.py` 10573 부근). B 를 두면 모든 경로에서 B 를 빼서, 예산 없는 공통 정지 모델로 평가한다. 지연 내성 A 의 4.1 과 같고, 낮은 물체 보고서도 같은 값을 쓴다. 예산 포함 모델 기준 결과는 보고만 한다.
- **부동소수 주의(① 재계산에서 찾음):** 오차표 조회는 `age_s <= 행 나이` 다(`obstacle_grid.py` `AgeErrorTable.at`). 그런데 0.2 + 0.1 = 0.30000000000000004 라 0.3 s 행이 아니라 0.5 s 행으로 넘어간다. 그래서 L 은 `round(free_max_age_s + B, 9)` 로 만들고, 시험으로 B = 0.10 이 0.3 s 행을 쓰는지 확인한다.
- **기본값:** 코드 기본은 B = 0(지금과 같음)이다. 운영 설정 파일(`config/obstacle_layer_single_team_spec.yaml` 등 riib·콘솔이 쓰는 것)에 권고값을 넣는다. 그래서 기록된 실행을 재생할 때(게이트의 recorded setup)는 옛 설정이 쓰여 동작이 같다.

## 2. 실차 목표 허용 지연(권고, 결정은 총괄)

- **권고: B = 0.10 s**(제어기 최초 사용까지 100 ms). 근거는 다음과 같다.
  1. **raw 격자 축소 비용은 B = 0.05 와 같다.** 오차표(`config/obstacle_odometry_age_team_spec.json`)가 계단식이다(0.2 s 행 0.0236 m·0.01372 rad, 0.3 s 행 0.0257 m·0.01424 rad). L 이 0.2 를 넘으면 0.25 든 0.30 이든 0.3 s 행을 쓴다. 축소 반경 증가는 ρ = 4 m 에서 약 4.2 mm 로 같다.
     - 다만 그림자 기억과 알려진 팔레트는 '현재 나이 + L' 로 조회한다(Codex P2-4). 예를 들어 현재 나이 0.04 s 면 0.29 s(0.3 행)와 0.34 s(0.5 행)로 갈린다. 그래서 운영 비용이 정지 거리만 다른 것은 아니다. 두 값의 비용은 검증 배치에서 함께 잰다(3 절).
  2. **정지 거리 비용만 B 에 비례한다.** d(v) 가 v·B 만큼 는다.

| B | 0.30 m/s 에서 정지 거리 증가 | 0.60 m/s 에서 |
|---|---|---|
| 0.05 s | 1.5 cm | 3.0 cm |
| 0.10 s | 3.0 cm | 6.0 cm |

  3. **시험 근거:** 알린 100 ms(D12)는 line_2 에서 3/3 허용이었다. random_1 에서는 운영 저하 2 와 관측 종료 1(`near_capture_misaligned`)이 있었다. 하역 오차가 같은 seed 의 B0 대비 s0 +2.85 cm, s2 +1.54 cm 늘었고, 허용 폭(+1 cm)을 넘었다.
     - 그 저하가 지연 자체 때문인지 늘어난 정지 거리 때문인지는 분리되지 않았다.
     - 그래서 0.10 은 '안전·완주 쪽으로 넉넉한 값'이고, 운영 정밀도의 비용은 검증 배치에서 B0 대비로 잰다(3 절).
  4. **실차 지연은 아직 모른다.** ws1 live 의 층 계산은 스캔당 수–십수 ms 였다(1e 단계 1 기록). Jetson 실측은 없다. 0.10 은 그 몇 배와 LiDAR 주기 흔들림을 덮는 값으로 고른 설계 가정이다. 실차 첫 측정에서 실제 지연 분포를 재서 다시 정한다.
- **대안:** B = 0.05 s. 정지 거리 비용이 절반이다. 실차 지연이 그보다 작다는 근거가 생기면 고른다.
- **SLAM 쪽(참고, 이 계획 밖):** A 에서 SLAM 답 지연은 25 ms 까지 두 장면 모두 허용이었고, 50·100 ms 에서 random_1 이 흔들렸다. 실차의 SLAM 답 지연 목표는 25 ms 이하로 두는 것을 권고한다. 그 이상이면 따로 계획한다.

## 4. 총괄에게 묻는 것

- (a) B 값: 권고 0.10 s, 대안 0.05 s.
- (b) 예산을 넘는 실제 지연의 처리:
  - 지금 안: 감시(`layer_overdue`)가 그 틱부터 속도 0 을 내고, 설치되면 다시 간다. 기록·경보는 남긴다. 임무는 끝내지 않는다. 예산 넘는 일이 잦으면 진단에서 본 것처럼 진행이 느려져 시간 한도로 끝날 수 있다.
  - 대안: 감시가 정해진 시간(예: 1 s) 넘게 이어지면 이름 있는 사유(`layer_latency_over_budget`)로 임무를 깨끗이 끝낸다. 시간 초과 대신 원인이 드러나지만, 계산이 잠깐 밀린 것으로 임무를 잃을 수 있다.
- (c) 운영 설정에 넣는 범위: riib 장면·콘솔 런처가 쓰는 장애물층 설정 파일 전부. 결정 모드 배치의 지난 결과와는 섞지 않는다.

## 5. 다른 세션과의 순서

- 바뀌는 파일: `sim/isaac/obstacle_layer.py`(설정 적용·지연 기록), `src/forklift_core/control/drive_permission.py`(감시 사유), `run_transport.py` 의 층 설정 읽는 곳과 참값 평가의 정지 모델 두 군데, `config/obstacle_layer_*.yaml`, 분석기, 시험.
- 재생 게이트는 `run()` 초기화를 거치지 않으므로 새 B 설정 적용 자체는 게이트로 검증되지 않는다(Codex). 단위 시험과 검증 배치로 본다.
- 콘솔 세션의 P0-4(`drive()` 분할)가 `run_transport.py` 를 옮기는 중이다. 구현 전에 콘솔 세션에 바뀌는 줄을 알리고 순서를 맞춘다. main 을 자주 병합한다.

## 7. 한계

- B 는 상한이다. 실제 지연이 늘 B 에 가깝다면 이 설정은 견딘다. 다만 B 의 크기가 실차 실측에 기대지 않은 설계 가정이다.
- 오차표가 계단식이라 비용 계산(4.2 mm)은 0.3 s 행에 기댄다. B 가 0.10 을 넘으면 0.5 s 행으로 넘어가 축소 비용이 커진다.
- 검증 배치는 결정 배치의 틱 지연(대용)이다. live·실차 지연과 같지 않다(지연 내성 A 의 한계와 같음).
- SLAM 지연과 겹치는 경우(agy ③-8): 실차에서는 LiDAR 하나를 SLAM 과 층이 함께 쓰고 같은 계산 자원을 나눈다. 층 지연이 클 때 SLAM 답도 늦을 수 있다. 이 계획은 층만 다룬다. A 에서 SLAM 답 50 ms 부터 random_1 이 흔들렸으므로, 두 지연이 겹친 경우는 실차 측정 뒤 따로 본다.
- 회전 LiDAR 의 t_scan(agy ③-8): A2M12 는 한 바퀴에 약 0.1 s 가 걸린다. t_scan 을 스캔의 시작으로 볼지 끝으로 볼지(드라이버 관례)에 따라 FREE 시각과 D 가 함께 달라진다. 시뮬은 한 시각의 스캔이다. 실차 적용 때 그 정의를 정하고 B 에 반영한다(실차 계획의 시계 규칙).
